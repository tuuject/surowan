# 管理记忆与辞典

塑料碗有四处「记住的东西」，它们解决的问题各不相同：

- **连续上下文（Context）**记住这场对话本身。
- **Memo Pad（记忆）**保存模型主动写下的资料。
- **群聊记忆**记录这个群以前发生过什么。
- **辞典**解释某个词在这里是什么意思。

四者都以 Chat 为边界。同一个群的所有 Forum Topic 共用一份 Memo Pad、群聊记忆和辞典，私聊各自一份，不同 Chat 互相读不到。只有连续上下文按 Conversation（每个 Topic 一个）单独保存。相关边界见[为不同群和话题设置边界](chats.md)。

## 四层知识一览

| 层 | 谁写 | 什么时候回到对话 | 面板位置 |
| --- | --- | --- | --- |
| 连续上下文 | 每个批次的真实消息，加上运行时注入的状态块 | 每次运行自动带上 | **上下文（Contexts）**，只读 |
| Memo Pad | 模型通过 `execute` 调用 `add_memo` / `update_memo` / `delete_memo`；管理员也能在面板维护 | 短期条目自动注入；长期条目要模型自己 `search_memory` | **记忆（Memories）** |
| 群聊记忆 | 后台 sleeping 整理，使用 Tool Model | 模型按需调用 `search_group_memory`，再用 `read_group_messages` 读原文 | **群聊记忆（Group memory）** |
| 辞典 | 管理员，或群里的模型写**本群**词条 | 按注入模式自动注入，也可用 `lookup_dictionary` 主动查 | **辞典（Dictionary）** |

## 连续上下文：不需要手工维护

一个 Conversation 在整个生命周期里只有一份连续历史。它不做摘要，只按 checkpoint 丢弃最旧的部分，具体阈值属于 `agent.context`，见[Agent 配置](../configuration/agent.md)与 [`agent` 字段参考](../configuration/fields-agent.md)。

由此有两条实用结论：

- 你不需要为「让模型记得刚才说了什么」做任何事，那本来就是上下文的工作。
- 换模型、改人格 Prompt、改工具集合都会让上下文在**下一次**运行时重建，但不会删除 Memo Pad、群聊记忆或辞典。只有删除 Chat 才会连带删除这些数据。

## Memo Pad：模型主动写下的资料

每个条目由两段内容组成：

- **摘要（summary）**：最多 150 字符。列表、搜索结果与自动注入看到的就是它，所以它应该描述「这条记录存了什么」，而不是「为什么存」。
- **详情（detail）**：最多 32768 字符的 Markdown，只有真正读取条目时才返回。图片以 `pwblob://` 引用。

### 短期与长期

期限由写入者决定，也决定条目怎么回到对话：

| | 期限 | 行为 |
| --- | --- | --- |
| 短期条目 | 设了期限 | 未过期时自动出现在上下文里，到期后不再注入，并在保留清理时删除 |
| 长期条目 | 不设期限 | 永不自动注入，模型需要时用 `search_memory` 找、`read_memory` 读 |

自动注入的细节值得知道，因为它解释了「为什么刚才记的事模型没提」：

- 短期未过期条目按创建顺序进入 `<memo_list>`，预算约为上下文窗口的 10%。超出时隐藏最早的条目，并注明隐藏了多少条，模型可以搜索补回。
- 完整列表只在首批、上下文重建，或上次渲染列表所在批次已被淘汰时重新发送，其他变化以 `<memo_updates>` 增量出现在消息之后。没有变化时不发任何内容。

### 模型怎么读写

- `search_memory` 与 `read_memory` 是原语，直接可用。搜索同时匹配摘要与详情文本（不区分大小写），关键词多于一个时至少命中一半，可以按创建时间过滤。
- `add_memo`、`update_memo`、`delete_memo`、`save_memo_image` 属于内部能力，经 `execute` 调用。
- 修改前必须先 `read_memory` 当前版本。读到之后有人（包括面板）改过它，写入会被拒绝并要求重读，删除不需要先读。
- 条目归属按 Chat 校验，写入前还会复查 Chat 仍在配置里。Chat 被移除后，正在执行的写入会被拒绝。

### 图片附件

`save_memo_image` 把对话里可见的一张图片复制成这个 Chat 自己的 Blob，返回 `pwblob://` 地址，模型再把它写进 detail。要点：

- 单张最大 10 MiB，同一 Chat 内按内容去重，同一张图只存一份。
- Blob 属于 Chat，不属于某条条目，只有没有任何 detail 再引用它时才连同文件清理。刚保存 10 分钟内的 Blob 不会被清理，给「先保存图片、再写 detail」这个两步流程留出窗口。
- 原始图片引用会随上下文淘汰失效，Blob 不会。
- 面板通过受控的字节端点读取这些图片，需要已认证访问，detail 里的 HTML 不会被执行。

### 在面板维护

打开 **记忆（Memories）**：

![记忆页的备忘录编辑对话框](__DOCS_BASE__/screenshots/knowledge/memo-editor.zh-CN.light.png)

1. 按会话与**状态**筛选：**生效中**、**已过期**、**短期**、**长期**。列表只显示摘要，点「查看」看详情全文。
2. **新建备忘录**：选择会话、填写摘要与详情（支持 Markdown）、填写**有效期（天）**。
3. 有效期留空表示永久保留，否则填 1–1825 天。修改从下一次运行起生效。
4. 删除需要确认，只被这条备忘录引用的图片会一并删除。

### 什么时候该用 Memo Pad

- 群友托付的长期资料、偏好、约定、材料清单。
- 需要跨 Topic 生效的事实（同一个群的话题共用）。
- 不要用它存 Token、API key 或其他凭据。
- 需要所有人都遵守的稳定规则，写进人格 Prompt 或每群的附加指令文件，而不是只放进 Memo Pad。

## 群聊记忆：这个群以前发生过什么

群聊记忆默认关闭，按 Chat 开启。开启方式有两种，效果相同：

- 在 **会话（Chats）** 页打开该群行的群聊记忆对话框，勾选「为这个会话开启群聊记忆」。
- 在 `config.jsonc` 的 `telegram.chats[]` 条目里写 `group_memory`：

```jsonc
{
  "telegram": {
    "chats": [
      {
        "id": -1001234567890,
        "group_memory": { "enabled": true, "idle_minutes": 30 }
      }
    ]
  }
}
```

开启或关闭会中止这个 Chat 正在进行的运行，并重建它的上下文，因为回忆工具本身是工具集合的一部分。

### 整理是怎么发生的

一个 Chat 停止说话一段时间后，后台把一个本地日期里还没整理的消息交给 Tool Model，生成若干条带 Telegram message-id 区间的事件摘要，例如：

```text
- gmem_… [2026-10-01; messages 4005-4114]: Natu 和 tcdw 讨论了 eSIM 的价格。
```

触发条件：

- 已经结束的本地日期直接整理，不等待。
- 当天（也就是还在进行的日期）要等群里安静 `idle_minutes` 分钟（默认 30，范围 1–1440）。
- 只整理**开启之后**收到的消息。开启前的历史、关闭期间的消息都不会补整理。
- 每批只处理一个本地日期，最多 120 条消息、约 40000 字符，最多 50 个事件，摘要上限 200 字符（提示词要求 150 以内）。

以下情况这一轮会跳过，之后照常继续：

- 同一个 Chat 有排队或正在运行的发话、或正在收集新消息的批次（实时通道不抢运行中的对话）。
- 群里执行了 `/pause`，`/resume` 后继续，暂停期间积压的消息会补整理。
- 全局处于 `zzz` 睡眠时段，后台整理也是付费模型调用，睡眠期间不发起。
- Tool Model 无法解析（未配置且没有可继承的全局模型）。

### 两条通道与失败处理

- **实时通道**跟随新消息。它落后超过一天（服务停机、模型连续失败）时，昨天之前的积压会交给**回填通道**，昨天和今天的消息不必等它清完，两边互不重复、互不遗漏。
- 模型输出不合格时，会带着具体原因再请求一次，仍不合格则这一批 30 分钟后重试，不影响其他批次，也不影响同一个群的另一条通道。
- 整理使用系统级 **Tool Model**，未配置时继承全局 Agent 模型。它不计入每日 Agent Token 预算。

### 模型怎么回忆

回忆分两层，由模型自己判断要不要用：

1. `search_group_memory`：按 Chat 本地日期、关键词或条数上限查询事件摘要，只返回摘要与消息区间。摘要不会自动注入，因此不占普通上下文。
2. `read_group_messages`：用摘要里的 `first_message_id` / `last_message_id` 读取原始消息。区间是闭区间，范围过宽会被拒绝，超出条数或字符预算的部分会提示「缩小范围」。

群聊记忆按 Chat 共享，Topic 共用，不同 Chat 的摘要与原文互不可见。

### 在面板查看整理进度

打开 **群聊记忆（Group memory）**，顶部是「整理进度」：

![群聊记忆页顶部的整理进度](__DOCS_BASE__/screenshots/knowledge/group-memory-progress.zh-CN.light.png)

每个开启群聊记忆的群一行，显示：

- **状态**：整理中 / 正常 / 连续失败 N 次，并给出下次重试时间。
- **已整理到**：已经整理到哪个消息 ID 与时间。
- **待整理**与**回填**：还有多少条待整理，以及回填通道的进度与截止时间。
- **最近成功**与**最近 24 小时**：成功与失败的批次数量。

点「查看批次」列出该群最近的整理批次：开始时间、通道（实时 / 回填）、这一批的日期与条数、结果（生成了几个事件，或失败）、模型调用次数与失败原因。排查某个群为什么没有记忆时，先看这里。

### 30 小时制

深夜群聊常常跨过零点，按自然日查「昨晚聊了什么」会被切成两半。可以给**按日期搜索**开启 30 小时制（默认关闭）。它沿用日本放送业的习惯，一个「放送日」到次日早上 6:00 才结束。

在 **会话（Chats）** 页的群聊记忆对话框里设置，或写配置：

```jsonc
{
  "telegram": {
    "chats": [
      { "id": -1001234567890, "group_memory": { "enabled": true, "thirty_hour_clock": "non_overlapping" } }
    ]
  }
}
```

![群聊记忆对话框里的 30 小时制设置](__DOCS_BASE__/screenshots/knowledge/thirty-hour-clock.zh-CN.light.png)

| 取值 | 搜索某个日期时返回 |
| --- | --- |
| `off`（默认） | 当日 0:00–24:00 |
| `non_overlapping` | 当日 6:00 至次日 6:00；相邻两天互不重叠 |
| `overlapping` | 当日 0:00 至次日 6:00；当日 0:00–6:00 也会出现在前一天的结果里 |

时间按 Chat 的本地时区计算，夏令时的日子也按当地 6:00 切分。每个事件按第一条消息的时间归属，结果里仍显示它按自然日归档的日期，并在开头注明这次搜索覆盖的时段。这个设置只影响带日期的搜索，不带日期的搜索、后台整理和归档都仍按自然日。

### 事件条目与删除

事件列表可以按会话、日期与摘要筛选。每条可以：

- **查看原文**：读取对应区间的原始消息（展示内容会截断）。
- **修改群聊记忆**：只能改摘要（1–200 字符）。日期与消息区间是整理结果，不能改。
- **删除**：这个事件不再出现在模型的回忆结果里，**该区间也不会被重新整理**。

群聊记忆随 Chat 删除。它不随 `retention.online_days` 清理，所以磁盘占用会随聊天量增长，需要彻底清理时删除 Chat 或定期归档事件。

## 辞典：这个词在这里是什么意思

辞典解释昵称、缩写、黑话和内部梗。它和 Memo Pad 分开维护。词条描述一个表达的含义，Memo Pad 保存事实、材料或偏好。**辞典解释属于数据，不能授予工具权限，也不能替代人格 Prompt。**

### 全局与群组

- **全局辞典**对所有会话可读，包括私聊。
- **群组辞典**属于一个 Chat，同群各 Topic 共用，其他群的词条不会进入当前群的查询或注入结果。
- 私聊只能读全局词条。

群里的模型可以查询全局与本群的启用词条，并**新增、修改本群**词条，但不能写全局词条、不能改其他群的词条，也不能把群词条提升为全局。管理员在面板可以维护两种作用域。

### 匹配规则

- 区分大小写，按字面字符串匹配，不做语义搜索、拼写纠错或分词扩展。
- 唯一放宽的是汉字与英文字母/数字之间的水平空白（盘古之白）：`AB钙` 与 `AB 钙` 匹配同一条词条。英文单词之间的空格与换行不忽略，保存的词条与别名保留原文。
- 主词和别名都能在较长消息里命中，例如别名「碗」会匹配「今天碗怎么不说话了？」。
- 多个词条同时命中时保留所有解释，全局词条不会覆盖群组词条。

### 自动注入

可以设置全局注入策略，并按 Chat 覆盖：

| 模式 | 面板文案 | 行为 |
| --- | --- | --- |
| `off` | 关闭 | 不自动注入；模型仍可以主动查询 |
| `on_demand`（默认） | 按需 | 命中本批次消息里的主词或别名时注入 |
| `aggressive` | 预加载 | 预加载全局与本群的有效词条 |

在 **辞典（Dictionary）** 页的「自动注入」区域设置（宽屏时在右栏）：先在作用域面板选好作用域，再改**全局模式**或该会话的**覆盖**，然后点「应用模式」。

注入的细节：

- 注入块被裁剪到消息选完之后剩余的上下文预算，所以新消息永远优先于预加载。
- 同一条词条（按 id 与版本）仍在保留的上下文里时不会重复注入，上下文被淘汰或词条被改过（版本变化）才会重新注入。
- 辞典没有独立的 Token 预算，仍受模型上下文窗口限制。
- 停用词条后，后续查询与注入不再使用它，已经写进历史上下文的旧解释不会因此被抹去。

### 冲突与 AI 融合

两个不同词条的主词或别名在匹配规范化后相同时，面板会提示潜在冲突，例如 `AB钙` 与 `AB 钙`。检查覆盖主词与主词、主词与别名、别名与别名，以及全局与所选群的交叉。冲突**不会**阻止保存、查询或注入，可以保留多种含义。

需要整理时，选中两个或更多词条，点「融合所选」：

1. 点「生成建议」，工具模型会把来源合并成一条建议。
2. 直接修改建议里的主词、解释或别名。
3. 选择**保存到**全局还是指定群组。
4. 决定是否「删除来源词条」（关闭则保留每一条来源，融合结果作为新词条并存）。
5. 确认保存。

生成建议会调用 **Tool Model**（在 **模型（Models）** 页配置，未配置则继承全局 Agent 模型），**可能产生模型费用**。建议本身不会修改数据库。来源在审阅期间被修改过时，面板会提示并在保存前要求重新生成。

### 批量导入与导出

在辞典页顶部使用「导入」与「导出」，支持 CSV 和 JSONL。导入时选择目标作用域、读取文件或粘贴内容、查看解析预览与潜在冲突，确认后才写入。导入**只创建新词条**，不会因为同名而覆盖或更新已有词条。

![辞典导入预览：解析出的词条、别名与冲突检查](__DOCS_BASE__/screenshots/knowledge/dictionary-import.zh-CN.light.png)

CSV 的列是 `term`、`definition`、`aliases`、`enabled`。多个别名在一个单元格里用 `|` 分隔，别名中的竖线写 `\|`，反斜杠写 `\\`。包含逗号、引号或换行的单元格按 RFC 4180 加引号，其中的引号写两次：

```csv
term,definition,aliases,enabled
塑料碗,群内对 Bot 的昵称,碗|塑料,true
```

JSONL 每行一个 JSON 对象，别名直接写数组：

```jsonl
{"term":"塑料碗","definition":"群内对 Bot 的昵称","aliases":["碗","塑料"],"enabled":true}
```

导出所选作用域后可以用相同格式重新导入，但重新导入会创建新词条，所以导入自己的导出文件也可能产生重复项，先看预览。导出文件可能包含群内术语，分享前核对内容。

## 该用哪个

- 「他刚才说的事你怎么不记得？」→ 先看上下文是否被重建。
- 「这份资料以后还要用」→ Memo Pad，短期条目让模型随时看到，长期条目让它按需搜。
- 「上周群里讨论过什么？」→ 群聊记忆。
- 「这个缩写是什么意思？」→ 辞典。

## 常见误区

- Memo Pad 不是全局知识库，它按 Chat 隔离，Topic 共用，跨群读不到。
- 摘要写得太含糊，模型就搜不到，它是检索索引，不是正文。
- 长期条目不等于「更重要」，只是不自动注入。需要模型随时知道的事，设成短期条目。
- 群聊记忆不会补整理开启之前的历史，也不会因为删除一个事件而重新整理那段区间。
- 辞典没有语义搜索，写词条时把常见写法都列进别名。
- 删除消息或切换模型都不会清空 Memo Pad。
