# 按表现和费用调优

调优不是把参数挨个调一遍。先确定「是哪一批消息、为什么这么处理、花了多少」，只改一个开关，然后再收集一遍证据对照。本页按症状组织，说明每个症状该动哪一处开关、之后去哪里看结果。字段的完整定义、默认值和生效方式在[Agent 配置](../configuration/agent.md)与 [Telegram 配置](../configuration/telegram.md)，本页不重抄字段表。逐字段的类型与默认值见 [`agent` 字段参考](../configuration/fields-agent.md) 与 [`telegram` 字段参考](../configuration/fields-telegram.md)。

先记住一件事：**Bot 不回话经常是正常结果**。是否发言由模型自己决定，运行记录里「发送」为 0 多半只代表它读完之后选择了沉默（被拦下的发送会留在工具调用里）。真正要查的是「它有没有机会读」，不是「它有没有说话」。

## 先拿到证据

调优前先固定看三个地方，每次改动前后各看一遍：

- **运行记录**（Tool sessions，`/invocations`）。列表能按会话、状态、模型、时间筛选。详情页的「概要」给出状态、完成原因、错误码、Token 与费用，标签页分别列出「工具调用」「模型调用」「Telegram 发送」「对话记录」与「冻结上下文」。判断「它看到了什么」看冻结上下文，判断「它做了什么」看工具调用与发送。
- **警告**（Warnings）。它只列此刻成立的条件，例如模型没配全、Telegram 连不上、MCP 服务器降级、配置里还留着废弃字段。清掉之后警告会自己消失，没有历史记录。
- **概览**（Overview）的每日用量。可以切 7 天与 30 天，看模型 Token、运行次数、工具调用与运行状态分布。Bot 睡眠时这里也显示状态与唤醒按钮。

入场闸门是唯一没有面板列表的审计，它的判断记录要用客户端 CLI 或 HTTP 读（见下文「入场闸门」）。

## 症状对照表

| 症状 | 先动的开关 | 之后看什么 |
| --- | --- | --- |
| 太吵：群友没叫它也要插话 | 主动回复概率、入场闸门、活跃时段或「仅 /ask」 | 运行记录的运行次数与发送数；入场闸门的判断记录 |
| 太慢：叫了它却要等很久 | 消息批次时间 | 运行记录的创建时间，以及当时用的批次时间 |
| 太贵：Token 与费用涨得快 | 每日预算、入场闸门、上下文与历史条数、限流 | 概览的每日用量，以及每次运行的模型调用明细 |
| 不接话：群里说话它完全不动 | 白名单、活跃时段、仅 `/ask`、暂停、睡眠、入场闸门 | 消息是否入库；运行记录里有没有运行 |
| 说话怪：语气不对、重复、发空消息 | 人格提示词与本群提示词、模型与思考强度、发送保护 | 被拦下的工具调用与它的错误码 |

## 太吵：它太爱接话

按代价从低到高，有三层开关可以叠：

1. **入场闸门**（见下文）是最对症的一层。它在一批消息交给主模型之前，先问一个小的决策模型「要不要回」。开成 `enforce` 之后被拒绝的批次不会启动运行，也就不会产生回复。
2. **主动回复概率**（见下文）只作用于没有被直接叫到的普通群消息，被 @、被回复、命中关键词、`/ask` 都不受它影响。
3. **活跃时段与「仅 /ask 唤起」**改写「什么消息才有资格开批次」，粒度最粗但最省事，时段外、或开启「仅 /ask」之后，普通消息根本不会开批次。这两项的配置方式见[为不同群和话题设置边界](chats.md)。

再往上一层是人格提示词本身，如果提示词鼓励它「看到有趣的话题就接」，前三个开关只能压制频率，改不了倾向。人格怎么改见[你的第一个人设](first-persona.md)。

## 太慢：叫了它却要等

等待由两段构成，都可以在运行记录里看出来：

1. **批次还在收集**。第一条消息到达后，Bot 先攒一小段时间再交给模型，这段时间就是消息批次时间（见下文）。
2. **它在排队或在跑**。`agent.max_concurrency` 限制同时运行的次数，同一次运行的运行期间还有 `agent.context.max_wall_clock_seconds` 作为最长时间上限。

先把消息批次时间的「最短等待」调小（例如 5 秒），再决定要不要缩短「最长等待」。缩短之后对话会被切得更碎，模型看到的上下文批次更小，短句可能各自成批。

## 太贵：Token 与费用涨得快

- **每日 Token 预算** `agent.daily_budget.max_tokens`。它同时计量回复和聊天里看图消耗的 Token，按「作用域」汇总：所有 Telegram 会话共用一份，虚拟群聊另有一份。它不是美元账单上限，供应商侧的额度仍要自己设。
- **预算快用完时会睡眠**。当日剩余比例低于 5% 时模型可能看到 `zzz` 工具，调用它就进入睡眠，至少 8 小时，或者到下一次 UTC 日预算重置，取更晚的那个。睡眠期间新批次直接以 `sleeping` 结束，不会补发。**概览**上的「立即唤醒」能解除睡眠，但不会补跑睡眠期间跳过的批次。
- **入场闸门不在日预算里**。决策请求有自己的 Token 与费用记录（判断记录里的 `input_tokens`、`cost`），不写进每日用量，所以开闸门是纯粹多花一点、而不是挤占 Bot 的预算。
- **上下文与历史**：`agent.history_messages` 决定每次运行带多少历史消息，`agent.context` 一组参数决定什么时候清理、引用多久过期、多少上下文留在内存。把它们调小是最直接的降本手段，代价是模型记性变差。
- **限流不等于省钱**：`agent.rate_limits` 限制发送频率与每批消息的轮次上限，能拦住「一直说」，但不减少已经发生的模型调用。

有两类回执故意不占预算。Alarm 与循环闹钟的完成回执带着预算与睡眠豁免投递，这是设计上的例外，不是漏计。

## 不接话：群里说话它完全不动

按顺序排查，前一步成立就不用看后面：

1. **这个会话在允许范围里吗**。不在 `telegram.chats` 里的会话不会被处理，触发词也不能。
2. **它有没有资格开批次**。活跃时段外只有 `/ask`、直接 @、回复 Bot 自己发过的消息、命中触发关键词能开，开了「仅 /ask」之后就只剩 `/ask`。
3. **会话被暂停了吗**。管理员 `/pause` 之后消息照常入库，但不启动运行。
4. **Bot 在睡眠吗**。概览会显示睡眠与唤醒时间。
5. **入场闸门拦下了吗**。`enforce` 下被拒绝的批次以 `skipped_budget` 结束，错误码 `decision_gate_dropped`。
6. **到底有没有运行**。运行记录里有没有这一批的运行，比群里「没看到回复」可靠得多。

六步都通过之后，还剩一种解释：运行发生了，模型选择沉默。这时先用下一节的批改工具把它该不该说、说得对不对记下来，再决定改哪里。

## 说话怪：语气不对、重复、发空消息

- **人格与群规则**。全局人格写在 **提示词**（Prompts）的全局范围，单个会话的附加指令写在同一个页面的「会话 <id>」范围。改了提示词从下一次运行起生效。
- **模型与思考强度**。换模型会改变表达倾向；**模型**（Models）页负责角色分配与思考强度。
- **发送保护**。这些是「说不出口」的规则，在 **运行参数**（Harness tuning）页的「发送行为」组里：最大文本长度、禁止空行、无文本发送策略、重复发送保护、允许对同一消息多次回复。被拦下的发送会留在工具调用里并带错误码，看那里比猜更快。
- **辞典与记忆**。专有词解释和过去的记忆会影响它说什么，分别见[管理记忆与辞典](knowledge.md)。

## 消息批次：等多久再交给模型

从这一批的第一条消息到达，到这一批交给模型之间的时间，由三个字段决定，单位都是秒，取值 0–300：

| 字段 | 面板标签 | 作用 |
| --- | --- | --- |
| `telegram.bucket_window_seconds` | 最短等待 | 一批至少收集这么久；一轮运行结束时，还在收集的批次从这里重新起算。 |
| `telegram.bucket_bump_seconds` | 每条消息延长 | 每来一条能触发它的消息，把结算时刻推到「这条消息到达后」这么久；`0` 表示不延长。 |
| `telegram.bucket_max_seconds` | 最长等待 | 从这一批的第一条消息算起，延长不会超过这个时间；不写时等于最短等待。 |

```jsonc
{
  "telegram": {
    "bucket_window_seconds": 5,
    "bucket_bump_seconds": 8,
    "bucket_max_seconds": 30
  }
}
```

上例的效果：孤零零一条消息 5 秒后交给模型，有人连着说话时，每句话都让它多等到这句之后 8 秒，但从第一句算起最多等 30 秒，之后的消息进下一批。

![Telegram 设置页的「消息批次」一组，三个时间字段与保存按钮](__DOCS_BASE__/screenshots/tuning/bucket-timing.zh-CN.light.png)

三条跨字段规则由服务端校验：

- `bucket_max_seconds` 不能小于 `bucket_window_seconds`。
- `agent.context.idle_grace_seconds` 要么是 0（关闭长驻运行），要么不小于 `bucket_max_seconds`。所以想在 Telegram 页把最长等待调到 60 秒，就得先把空闲等待调到 0 或至少 60 秒。
- `agent.context.max_wall_clock_seconds` 必须大于 `idle_grace_seconds`。

生效时机：三个字段都是热更新。在 **Telegram** 设置页的「消息批次」里保存后立即生效，不用重启，手改配置文件之后到 **设置**（Settings）点「应用配置文件」也一样。新的时间只影响之后开始收集的批次，正在收集的那一批仍按它开始时的时间结算。

只有能触发 Bot 的消息会延长等待。其他 Bot 的消息、入群退群这类服务消息、未开启贴纸触发时的单独 Sticker 会被收进这一批，但不会推迟它。

## 入场闸门（Decisions）

入场闸门在批次到期、准备创建或接入运行之前，先让一个小的决策模型读一遍这批消息，判断 Bot 会不会想接话。它不代替人格。真正说什么仍由主模型决定，闸门只负责不把明显不需要回应的批次交给它。

它默认关闭，关闭时行为与没配置完全一样。开起来之后有两种模式：`shadow`（面板写作「只记录」）只记录判断、不影响调度；`enforce`（「拦截」）才会把被拒绝的批次关掉。

![入场闸门页面的「行为」与「连接」两块设置](__DOCS_BASE__/screenshots/tuning/entry-gate.zh-CN.light.png)

### 它问什么

默认提问是一道是非题：把这批新消息和之前的若干条历史一起交给决策模型，问它作为普通群成员读完之后会不会发言。回答是一个「是」的概率 P，判定规则固定为 `P ≥ threshold` 才送入主模型。

请求里只带一个问题，`state` 里放消息：`pending` 是这一批新消息，`history` 是更早的若干条。自定义提问里可以写 `{{ bot.name }}` 与 `{{ bot.username }}` 两个占位符。自定义提问必须仍然是一道是非题，并且「是」必须仍然表示「应该交给主模型」。换掉提问文本或决策模型之后，0.57 这个默认阈值就没有依据了，先用 `shadow` 重新观察一段时间再定新的阈值。

### 先观察，再拦截

建议的上线顺序：

1. 在全局 `telegram.decision_gate` 写好 `api_key`，`enabled` 先开着、`mode` 保持 `shadow`。
2. 跑大约一周，让它积累真实消息上的判断记录。`shadow` 不会让 Bot 少说话。
3. 用 `surowan-utils decision-gate decisions --chat <会话 ID> --limit 50` 导出判断记录，对照同期运行记录核对：被判为「不送入」的批次里，有多少其实该回。
4. 再把 `mode` 改成 `enforce`。可以只先改一个群，确认效果后再改全局。

```jsonc
{
  "telegram": {
    "decision_gate": {
      "enabled": true,
      "mode": "shadow",
      "threshold": 0.57,
      "api_key": { "jar": "openrouter" }
    },
    "chats": [
      {
        "id": -1001234567890,
        "decision_gate": { "mode": "enforce" }
      }
    ]
  }
}
```

### 拦截之后发生什么

- 被拒绝的批次以 `skipped_budget` 结束，错误码是 `decision_gate_dropped`。消息、修订和批次成员全部保留，之后仍会作为历史进入模型上下文。
- 这个会话**不再做主动回复抽样**。主动回复按保底计数发放机会，抽中了又被闸门丢掉会白白清空保底，所以处于 `enforce` 的会话跳过抽样，`shadow` 不改变抽样。
- 决策请求自己产生的 Token 与费用记在判断记录里，不占每日预算。
- 判断结果落成一行记录：模式、模型、阈值、历史与批内条数、`state`、`outcome`、`applied`、概率、Token、费用、耗时与错误码。`state` 为 `stale` 表示结论已经作废（批内又进了新消息），不是故障。

### 哪些批次不经过闸门

以下情况根本不发决策请求，也不写判断记录：

- 批内有 `/ask`、直接 @、回复 Bot 自己发过的消息，或命中触发关键词。只要有一条，整批直接送入。
- 私聊。私聊没有「一批群消息」，配置整个 `decision_gate` 对象会被 `check-config` 拒绝。
- 启动追赶批次（`startup_catch_up`）。
- 不经过「批次到期」这条路径的工作：长程任务完成回执、管理员定义的循环闹钟、从面板续跑的运行、虚拟群聊的放行与重试。它们直接创建运行，闸门没有机会被问。
- 被暂停、已离开配置、模型配置不完整或处于睡眠的会话，这些既有闸门先生效。
- 开启「仅 /ask」的会话只有一个入口，它的批次全部是直接触发，闸门不会发出请求。

### 失败一律放行

闸门是为了省钱，不是为了拦消息，所以它的错误方向全部是「送入主模型」：

- 请求超时、网络错误、非 2xx、响应形状不合法、模型拒绝回答，都按送入处理并且不再重试。
- 解析密钥失败时记为 `secret_unresolved`，同样送入。
- 同时在途的决策请求最多 4 个，超过上限的批次直接送入并记 `concurrency_limit`，不排队。
- 一批消息在等答案的时候又进了新消息，结论作废并重新问一次，最多重问两次，两次用完就送入，不会有消息被悄悄扣下。

### 密钥与连通性

`api_key` 只写在全局段，是普通的密钥引用（`{ "jar": "<条目名>" }`、`env` 或 `command`），每次决策前重新解析，所以在**密钥**（Keychain）页轮换条目后，下一次决策就用新值。

`enabled: true`（无论是全局还是某个会话覆盖）都要求全局段写了 `api_key`，`check-config` 只检查字段在不在，不解析引用。引用坏掉不会让加载失败，只会让闸门静默地一直放行，所以开启之后务必运行一次 `doctor`。闸门开着时它会解析密钥并发一次最小请求，失败直接报错，输出里不会出现密钥的值。

所有字段（含 `api_key`、`base_url`、`model`）都是热更新，保存后下一次决策就生效。按会话覆盖、私聊不能配置、以及面板里那个「为会话单独设置…」开关的用法见[为不同群和话题设置边界](chats.md)。

## Harness 运行参数：预算与发送保护

**运行参数**（Harness tuning，`/harness`）页集中编辑 `config.jsonc` 的 `agent` 段，分五组：

- **预算与并发**：每日 Token 预算、最多同时运行、历史消息条数、上下文收尾比例。
- **发送行为**：最大文本长度、禁止空行、发送提醒、等待新消息、允许对同一消息多次回复、重复发送保护、无文本发送策略与兜底文本。
- **限流**：窗口内发送上限、窗口长度、每批消息的轮次上限。
- **上下文**：保留发送目标与上限、强制清理比例、引用有效期、空闲等待、最长运行时间、内存缓存数。
- **主动回复**：全局默认（见下文）。

![运行参数页的「预算与并发」与「发送行为」分组](__DOCS_BASE__/screenshots/tuning/harness-budget.zh-CN.light.png)

一次可以改多项，点「保存并应用」写回配置文件并应用，点「放弃修改」恢复成文件里的值。只有真正改过的字段会写入文件，注释与格式保持不变。超出范围的值当场标红，需要跨字段判断的规则（例如保留发送目标必须小于保留发送上限、空闲等待必须覆盖消息批次最长等待）由服务端校验，失败时文件不动并给出原因。

生效方式：每日预算从下一次模型调用起按新值计量，所以调低之后正在跑的那次运行也会立刻受约束。其余字段都是热保存、不需要重启，数值在运行读取它的那一刻取当时生效的值，新的历史条数作用于之后创建的运行，新的限流作用于之后的发送。

## 主动回复概率

主动回复给普通群消息加一道按会话的概率闸门：只有被抽中的批次才创建运行，同时用连续未命中计数保证它不会一直轮不到。

默认关闭。打开之后，第 n 次连续尝试的机会是：

```text
n >= hard_pity ? 100% : min(100%, base_probability + (n - 1) × increment)
```

按默认参数（`base_probability` 0.2、`increment` 0.1、`hard_pity` 8）依次是 20%、30%、40%……第 8 次必定命中。

- **哪些消息不受影响**：直接 @、回复 Bot 自己发过的消息、命中触发关键词、Telegram 命令、`/ask`。任何一条直接唤起都整批放行，而且不增加也不清零保底计数。
- **计数按会话隔离**，同一群的 Forum Topic 共享一个计数，存在数据库里，重启不清零。
- **改参数会重置计数**：`base_probability`、`increment`、`hard_pity` 三者任一变化，下一次抽样就把该会话的计数清零，避免旧进度让新参数立刻触发保底，只关掉再打开、或者只重启，都不会清零。
- **未命中的批次**照常保存消息，只是以 `proactive_reply_skipped` 结束，不创建运行。

面板有两个入口：全局默认在 **运行参数** 页的「主动回复」组（概率按 0–1 填写），单个会话的覆盖在 **会话**（Chats）页的「更多操作」→「编辑主动回复概率」（按百分比填写）。会话那一层可以选「沿用全局设置」「关闭主动回复」或「自定义本群参数」。

## 批改（Reviews）：把不满写下来

运行详情页和 **批改**（Reviews，`/reviews`）页提供一套批注工具，让你在审计记录上直接写下「这句太长」「这里不该接话」，最后导出一份带完整提示词的 Markdown，交给本地 Coding Agent 去查和改。

- **只存在浏览器里**。草稿保存在当前浏览器的 `localStorage`（键名 `surowan-admin-review`），不会上传服务器，也不写数据库。浏览器禁止本地存储或空间不够时，内容只保留在当前标签页直到关闭。
- **可以批的地方**。运行详情页「概览」时间线上，除了入队、开始、结束三个生命周期节点，每张事件卡片（新到或历史消息、模型调用、工具调用含 `send`、助手私有文本与工具结果）都能加一条意见，摘要卡片下方还有一个整体评价。每条意见最多 4,000 字符，保存时自动截取最多 280 字符的事件摘录。
- **跨标签页同步**。同时开着多个详情页和批改页时，任一标签页的保存、修改或删除都会同步到其它标签页。
- **导出用途二选一**：「调优此机器人」写给管理这套 Bot 的人，导出的提示词要求外部 Agent 对照审计定位到人格提示词、本群提示词、运行参数、模型或辞典记忆，并在你逐项确认后修改；「开发者反馈」写给塑料碗开发者，要求它不改运行中的配置，只定位内置系统提示词、工具定义或运行时行为的缺陷并按影响排序输出报告。
- **改进目标**（选填）会一起写进提示词。「预览 Markdown」可以在导出前看完整内容，展开预览不会清空草稿。
- **导出即清空**。点「下载 Markdown」（文件名形如 `surowan-review-20260101-120000.md`）或「复制 Markdown」都会先确认，确认后清空草稿。面板不支持把导出的文件重新导入，请自己保存好。
- **末尾的 JSON 尾块**。文档最后有 `## Review data (JSON)` 一段，`format` 为 `surowan.invocation-review`、`version` 1，是上面全部意见的机器可读副本，外部 Agent 可以用它做结构化输入。

![批改页的导出用途选择与导出确认弹窗](__DOCS_BASE__/screenshots/tuning/review-export.zh-CN.light.png)

导出的 Markdown 怎么交给本地 Agent、以及 Agent 会先做哪些只读检查，见[与 Agent 配合使用](agent-assisted.md)。

## 续跑失败的运行（Resume）

运行以 `failed`、`aborted` 或 `outcome_unknown` 结束时，详情页会出现「续跑」按钮，它用**当前**配置真实地再跑一次这个会话，Bot 可能因此发消息并产生费用。

能续跑的前提（不满足时接口返回 `resume_*` 错误码，按钮也不会出现）：

- 它是这个会话**最新**的一次运行。续跑接续的是会话的连续上下文，只有最新那次才等价于「把这一批再跑一遍」。
- 这个会话当前没有排队或运行中的运行。
- 会话仍然在配置里、没被暂停、话题仍然允许、模型配置完整。
- Bot 不在睡眠，Telegram 已连接。
- 虚拟群聊不走这条路，房间有自己的放行与重试。

续跑之后，失败的那一批如果已经写进上下文，新运行会以空批次开场（否则消息会被注入两遍），提示词里会说明这一点；如果那一批根本没进去，则复制当时冻结的快照。

续跑是**真的花钱、真的可能发消息**的操作，所以对 API key 调用方它属于 `write+paid`，只有 `all` 模式的 key 能调。重放（replay）是另一件事，它不产生 Telegram 副作用，见[Invocation 预检与重放](../developer/replay.md)。

## 用证据比较改动的结果

每次改动之后，拿同一类证据对比，而不是看「保存成功了」：

- **运行记录**：同类批次的运行次数、发送数、Token、费用前后对比。列表能按会话与模型筛，所以一次只改一个开关时最容易看出差别。
- **入场闸门判断记录**：`surowan-utils decision-gate decisions` 给出的 `outcome`、`probability`、`threshold` 与错误码，说明是「被拦下」还是「问都没问」。
- **概览的每日用量**：Token 与运行次数的趋势，看 7 天或 30 天。预算调低后要确认 Bot 没有因为睡眠而长时间静默。
- **批改草稿**：把「这次哪里不对」写下来，比事后回忆可靠，交给 Agent 时它也能拿到同一份事实。

配置改动的生效方式是另一类证据：**设置**（Settings）页的「配置版本」一组显示生效哈希、文件哈希，以及「与文件一致」还是「文件有改动」。如果文件已写入但应用失败，「最近错误」会写原因。哪些字段热应用、哪些要重启，见[配置生命周期](../configuration/lifecycle.md)。
