# 功能名称

警告管理

## 为什么要做？

系统会出现一些异常的事件，或者是存在着一些不应该常态开启的配置，但是我可能会忘记，因此需要一个警告系统来告诉用户哪里不对劲，并且提醒用户做出相应的改变。

## 希望实现什么？

- Admin Panel 看板有专门的栏目，展示收到的警告。
- 点进去可以查收历史收到的警告，并且可以标为已读。
- 侧边栏增加警告列表页面的入口。
- 看板和列表页面都能展示常态警告。

## 打算怎么做？

塑料碗系统的任何一个模块都可以往这里发送警告。

警告记录到 SQLite 中，已读的警告会在超过 30 天（数值可配置）被清理。

另外，看板和列表页面都需要能够展示常态警告，例如当用户开启了「记录原始请求报文」，则一直显示这个警告在最上面。这种常态警告不能被标记已读，必须等用户关闭相关设置才可以消失。

警告内容需要能够在 Web Admin 按照类别使用不同模板渲染，以便展示动态更新详情（变量）的警告，如登录失败次数、最近触发时间。

变量本身使用 JSON 字符串存储在 SQLite 中，方便渲染丰富的卡片内容和 Action Item。

### Phase 1 警告来源

常态警告：

- 开发者选项中开启了记录请求原始报文。
- 未配置 agent 模型。
- 未配置 vision 模型。

事件警告：

- Invocation 运行失败率超过 50%（取样最近 100 次）。
- 连续 5 次发生登录鉴权失败（用户名/密码错误）。

### 警告查询与重复控制

需要允许增加警告前查询是否当前有未读的同类型警告。

Invocation 运行失败率超过上述阈值、登录鉴权失败时增加一条警告；当前已有未读的同类型警告时，不再重复增加，或者是允许修改警告内容，例如将登录失败次数修改为 5 次、10 次、15 次……

### 审阅意见

本轮按要求核对了现有源码。以下选项是审阅建议，尚未成为已确认的设计。

3. **保留期限的起点与清理触发必须一起写明**：「已读的警告会在超过 30 天被清理」还未区分从收到还是从标已读起算。现有在线数据清理由 `backupDatabase()` 在备份前触发（`src/adapters/local-monolith/database.ts:351-363`），并非服务定时清理；直接接入该流程会依赖外部备份调度。建议从标已读起算 N 天，未读不自动删除，以免未查收就丢失；代价是未读积压会持续占用空间。
   - 选项：A，采用上述保留规则，由运行中的服务自动清理，到期后允许最多 24 小时延迟，停机期间到期的在下次启动清理（需要新增服务内清理触发）；B，采用上述保留规则，随现有备份清理（复用现有入口，但没有备份就不会清理）；C，仅对已读记录按收到时间算 N 天，并由服务自动清理（历史总年龄较短，但一条超过 N 天才被查收的警告可能刚标已读就被清理）。
   - 需要决定：采用哪套保留与清理规则？

4. **常态警告解除后是否留下历史，需要独立于「已读」定义**：正文已经确定「不能被标记已读，必须等用户关闭相关设置才可以消失」，但尚未明确消失是否包括历史页。若保留解除历史，不能套用已读时间清理，因为这类警告没有已读动作。
   - 选项：A，常态警告只表示当前状态，条件解除后从看板和列表消失，不保留开启/解除历史（简单，但不能回看曾经开启的时段）；B，解除后退出置顶区域，历史保留为「已解除」，从解除时间起按 N 天清理，再次开启产生新记录（可追溯，但增加一种状态和生命周期）。
   - 需要决定：常态警告采用只展示当前状态，还是保留已解除历史？

5. **看板上的普通警告是待处理摘要，还是近期事件记录**：现有看板只有运行状态和统计，没有警告栏目（`src/ingress/admin/audit/overview.ts:53-77`）。常态警告置顶已确定；普通警告标已读之后是否仍出现在看板，会影响栏目用途。
   - 选项：A，常态警告下方显示未读总数与最近 5 条未读普通警告，标已读即退出看板，历史列表仍可查询（突出待关注事项，但查看已读记录要进入列表）；B，常态警告下方显示最近 5 条普通警告并区分已读/未读（近期事件连续，但已读条目会占用摘要位置，更早的未读可能不在摘要中）。
   - 需要决定：看板采用未读摘要，还是最近事件摘要？

6. **页面停留期间是否自动更新，决定警告能否及时提醒**：现有 `overviewQuery` 没有定时刷新；全局 `staleTime: 5_000` 只是缓存陈旧时间，且关闭了窗口聚焦刷新（`apps/admin-next/src/lib/queries.ts:35-38`、`apps/admin-next/src/lib/query-client.ts:48-53`）。沿用现状时，其他模块新发警告或另一页面关闭相关设置，不会保证正在停留的页面及时更新。
   - 选项：A，看板和警告列表在前台可见时自动更新，正常联网且服务可用时最多 10 秒反映新增、已读或解除（多一些查询；浏览器后台暂停期间不保证时效，返回前台立即刷新）；B，只在重新进入页面、手动刷新或本页操作成功后更新（查询更少，但停留时可能长期显示旧状态）。
   - 需要决定：采用自动更新，还是沿用重新进入或手动刷新的方式？
