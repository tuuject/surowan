# 功能名称

警告管理

## 为什么要做？

系统会出现一些异常的事件，或者是存在着一些不应该常态开启的配置，但是我可能会忘记，因此需要一个警告系统来告诉用户哪里不对劲，并且提醒用户做出相应的改变。

## 希望实现什么？

- Admin Panel 看板有专门的栏目，展示收到的警告。
- 点进去可以查收历史收到的警告，并且可以标为已读。
- 用户可以手动清空历史警告。
- 侧边栏增加警告列表页面的入口。
- 看板和列表页面都能展示常态警告。

## 打算怎么做？

塑料碗系统的任何一个模块都可以往这里发送警告。

警告记录到 SQLite 中。已读警告从标为已读时起算，超过 30 天（数值可配置）后清理。

由运行中的服务自动清理，到期后允许最多 24 小时延迟。停机期间到期的警告在下次启动时清理。

另外，看板和列表页面都需要能够展示常态警告，例如当用户开启了「记录原始请求报文」，则一直显示这个警告在最上面。这种常态警告不能被标记已读，必须等用户关闭相关设置才可以消失。

常态警告只表示当前状态。触发条件解除后从看板和列表消失，不保留开启或解除历史。

警告内容需要能够在 Web Admin 按照类别使用不同模板渲染，以便展示动态更新详情（变量）的警告，如登录失败次数、最近触发时间。

变量本身使用 JSON 字符串存储在 SQLite 中，方便渲染丰富的卡片内容和 Action Item。变量里面的内容不能放置可以直接执行的代码。

### 看板展示与刷新

看板将常态警告置顶，下方显示未读事件警告总数与最近 5 条未读事件警告。事件警告标为已读后退出看板，仍可在历史列表查询。

看板和警告列表页面在前台时每 10 秒刷新一次，从后台恢复到前台后再刷新一次。

### Phase 1 警告来源

常态警告：

- 开发者选项中开启了记录请求原始报文。
- 未配置 agent 模型。
- 未配置 vision 模型。

事件警告：

- Invocation 运行失败率超过 50%（取样最近 40 次，至少 20 次才判断）。
- 连续 5 次发生登录鉴权失败（用户名/密码错误）。

### 警告查询与重复控制

需要允许增加警告前查询是否当前有未读的同类型警告。

Invocation 运行失败率超过上述阈值、登录鉴权失败时增加一条警告；当前已有未读的同类型警告时，不再重复增加，或者是允许修改警告内容，例如将登录失败次数修改为 5 次、10 次、15 次……

Invocation 失败率使用浮标标记应该从哪里开始判断成功率：只取样浮标之后的 Invocation。失败率警告变为已读以后更新浮标，确保不会马上再来一个警告。

取样最近 40 次而不是 100 次：窗口太大时，前 50 次成功、后 50 次失败才会报警，反应太慢。
