# telegram 配置可选

## 为什么要做？

塑料碗目前必须配置 Telegram Provider 才能运行。只想在虚拟群聊（Playground 房间）里试用的用户，也得先申请 Telegram bot 并填好凭据，才能把塑料碗跑起来。

## 希望实现什么？

用户可以完全不配置 Telegram Provider，只通过虚拟群聊试用塑料碗。

## 打算怎么做？

- 配置文件里的 `telegram` 字段从必填改为可选。
- 不配置 `telegram` 字段、token 置空或 token 无效，都是合法状态：此时塑料碗不发起任何 invocation，虚拟群聊除外，也不运行 grammy 实例。
- `telegram` 节存在时 chats 不能为空，仍按配置错误报错。
- `--playground-only` 启动形态完全砍掉：只跑虚拟群聊改为由上述状态触发，不再有单独的启动形态。
- `admin` 配置从可选改为必填，配了即开启面板（`enabled` 开关一并取消）：管理面板是塑料碗的重要部分，也是虚拟群聊的唯一入口。
- Telegram 的连接状态分四种：
  - 停用：没有 `telegram` 字段，或 Bot Token 为空。配置文件里没有 `telegram` 字段时，服务启动后默认就处于停用状态。
  - 正常：token 有效，实例在运行。
  - 网络异常：连不上 Telegram 服务器，警告写「未能成功连接 Telegram 服务器」。
  - 配置异常：Telegram 返回 401（token 被拒）或 409（同一个 token 正在别处收消息）。
- 连接状态的 flag 要为后续接入 Discord、WhatsApp、Slack 等其他 IM 留好位置：每个 IM 各自一份状态，用 namespace 之类的方案区分，互不影响。Telegram 的状态变化不影响其他 IM，反之亦然。
- `telegram` 配置以管理面板为主入口；面板应用配置时，按连接状态迁移 grammy 实例：
  - 正常（token a）→ 正常（token b）：立刻重启实例（先停止当前正在运行的 Telegram 聊天 invocation），改用 token b；重启包含一次停止，已经排队、还没运行的 invocation 一并作废，不交给新 bot 处理；
  - 正常 → 停用或配置异常：立刻停止实例，立刻停止当前正在运行的 Telegram 聊天 invocation；
  - 停用或配置异常 → 正常：立刻启动实例，改用 token b。
- token 是否被拒以 Telegram 认证结果为准；应用配置时连不上 Telegram 会先重试 3 次，仍无法确认则按「正常 → 停用或配置异常」的同一条路径停止实例（实例停止、正在运行的 invocation 停止），之后通过再次应用配置恢复。
- 实例运行中：单纯的网络错误无限重试，实例保持运行；Telegram 返回 401 或 409 时进入配置异常，按「正常 → 配置异常」的路径处理，并在警告系统发布警告。服务不再因此退出。
- 进程冷启动时处于停用或配置异常：与运行态一致，服务照常启动、不运行 grammy 实例，同时向用户发出面板可见的警告。
- 实例从停用或配置异常进入正常，或 a → b 切换后用 token b 启动时，都补拉积压消息，与进程冷启动的补偿拉取一致，但控制数量：每个群组最多收录 100 条（暂定值，可以再调）。补拉是为了让塑料碗有充足的上下文，知道群里最近一小段时间讨论了什么。
- 启动与重启都指 grammy 实例，不是塑料碗服务：塑料碗服务全程保持运行，任何状态迁移都不要求用户手动重启塑料碗。
- 实例停止时全部作废：已经批准、还没送到 Telegram 的消息不再投递，已经排队、还没运行的 invocation 一并作废。

## 还有什么没想清楚？

### 审阅意见

3. **网络异常这个状态什么时候进、什么时候出**：现在有了独立的「网络异常」状态，但正文里两处网络错误的行为对不上它：
   - 运行中：网络错误无限重试、实例保持运行。重试期间连接状态是显示「网络异常」，还是仍算「正常」？网络恢复后是否自动回到「正常」？
   - 冷启动和应用配置时：重试 3 次后停止实例，只能靠手动再应用一次配置恢复。比如容器网络还没就绪时冷启动，bot 会一直离线，直到用户发现警告。这时状态算「网络异常」吗？
   - 选项：A. 三处统一为无限重试，连不上就显示「网络异常」，连上后自动回到「正常」（规则统一，不需要人工干预，代价是网络长期不通时实例一直在后台重试）；B. 运行中无限重试，冷启动与应用配置时保持重试 3 次后停止（行为可预期，代价是同一个「网络异常」状态有两种表现：有的会自己恢复，有的要手动恢复）。
   - 需要决定：网络异常是否一律无限重试并自动恢复？重试期间状态是否显示「网络异常」？

4. **实例停止期间到期的定时任务怎么处理**：「不发起任何 invocation」和「实例停止时全部作废」只说到了消息触发的 invocation。Telegram 对话里由模型设定的 Alarm 这类长期任务，到期时会唤起 invocation 并往 Telegram 投递回执。实例停着的时候，它们到期了怎么办没写。
   - 选项：A. 到期即作废（与「全部作废」一致，代价是用户设的提醒会悄无声息地丢掉）；B. 先挂起，实例恢复后补投（提醒不丢，代价是可能恢复好几天后才突然冒出一条过时的提醒）；C. 按原计划在后台完成，只是不投递（状态一致，代价是用户收不到回执）。
   - 需要决定：实例停止期间，Telegram 对话的定时任务到期后作废、挂起还是静默完成？

5. **面板首次加入 Telegram 时的先后顺序**：面板是主入口，但「`telegram` 节存在时 chats 不能为空」意味着用户必须同时填好 token 和至少一个 Chat 才能保存；而 Chat ID 通常要等 bot 跑起来、拉进群之后才知道。（删掉整个 `telegram` 节已明确属于停用状态，剩下的是面板是否允许这个操作。）
   - 选项：A. 保持 chats 非空，在面板上引导用户先拿到 Chat ID 再保存（规则不变，代价是首次配置要绕到别处查 ID）；B. 放宽为「token 有效时 chats 才必填」，或允许 chats 为空、此时不处理任何 Chat（首次配置顺畅，代价是推翻了正文里已有的一条约束）。
   - 需要决定：首次配置时 chats 为空能否保存？面板是否允许删掉整个 `telegram` 节？

6. **对现有部署的升级影响没写**：`admin.enabled` 取消、`admin` 改为必填、`--playground-only` 删除之后，现有配置里写着 `enabled`、没写 `admin` 的，以及启动命令里带 `--playground-only` 的部署，升级后会直接启动失败。另外，面板变成必开之后，没有建好管理员账号时，第一个访问面板的人就能创建管理员；`admin.host` 绑在非回环地址的部署，这个窗口会暴露在网络上。
   - 选项：A. 直接报错，在升级说明里写清怎么改（与仓库「清理式切换」一致，代价是用户升级时必须手动改配置）；B. 旧字段和旧参数先忽略并发警告，过渡一个版本后再删（升级平滑，代价是要暂时保留兼容路径）。
   - 需要决定：旧配置和旧启动参数是直接报错还是过渡处理？「面板必开带来的建号暴露窗口」是否算运维责任、不在本 PRD 处理？

7. **停用状态要不要发警告，其余状态用哪种警告**：「停用」已经和「配置异常」分开了，但正文冷启动那一条仍写着停用时也发面板警告。如果停用也发警告，只用虚拟群聊试用的用户会一直看到它；将来接入 Discord、WhatsApp、Slack 后，只用其中一个 IM 的用户，还会看到其余几个 IM 的停用警告。另外，按警告管理 PRD 的分法，常态警告只反映当前状态、不能标为已读，解除后自动消失；事件警告可以标为已读，但会留在历史里。
   - 选项：A. 停用不发警告，网络异常与配置异常用常态警告（停用是用户主动的选择，没必要提醒；代价是忘了配 token 的用户只能从连接状态上看出来）；B. 停用也用常态警告（不会漏掉，代价是上面说的长期置顶和多 IM 噪音）；C. 网络异常与配置异常用常态警告，进入时再额外发一条事件警告留作历史（当前状态和发生记录都有，代价是同一件事出现两条警告）。
   - 需要决定：停用发不发警告？网络异常与配置异常用常态警告还是事件警告？

8. **原来那条警告文案拆开之后各写什么，token 取不到归哪个状态**：「你的 Telegram Token 没有配置或已被吊销」原本同时覆盖置空和被拒，现在两者分属停用和配置异常。另外，之前定的「token 来源取不到（环境变量没设、命令执行失败）属于异常」，在四种状态下归到停用还是配置异常，也要重新定。
   - 选项（文案）：配置异常按原因分两句，401 写「你的 Telegram Token 已被吊销或无效」，409 写「这个 Telegram Token 正在被其他程序使用」（准确，代价是多一条文案）；或者合成一句「Telegram Token 配置有误」（简单，代价是用户要自己去查是哪种原因）。
   - 选项（token 取不到）：归停用（和「为空」一样，代价是写错环境变量名会被当成用户主动停用，不容易发现）；归配置异常（能提醒部署出错了，代价是「配置异常」的范围不再只是 401 和 409）。
   - 需要决定：配置异常的警告文案怎么写？token 来源取不到归停用还是配置异常？
