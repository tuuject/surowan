# 功能名称

非核心功能内部插件化。

## 为什么要做？

塑料碗正在推进将「非核心功能」插件化。

## 希望实现什么？

继续推进以下四项功能的内部插件化：

1. 文档／手册查询。
2. 短期记忆。
3. Sticker 内容服务。
4. 按需视觉分析。

## 打算怎么做？

这里的插件化并不是给用户暴露插件能力，而是内部架构设计。

## 还有什么没想清楚？

以下迁移计划尚未确定，具体边界和执行顺序待讨论。

1. **迁移顺序**：是否先迁移文档／手册查询和短期记忆，再处理 Sticker 内容服务与按需视觉分析？后两项共享图片处理能力，是否一起划分边界？

2. **文档／手册查询**：是否将文档目录查询、页面读取和使用说明一起归入插件？文档空间的装配、受限文件读取和产品自知内容分别由谁负责？

3. **短期记忆**：是否将记忆增删、有效期规则、每批记忆注入和使用说明一起归入插件？需要明确 Chat、Topic 与 Playground 房间的隔离，以及删除、过期和人工审核的处理边界。记忆作为持久化数据进入上下文时，如何表达它与运行时指令的区别？

4. **Sticker 内容服务**：是否将贴纸包同步、后台视觉索引、搜索、目录注入和使用说明一起归入插件？连接建立、替换和断开时，由谁启停相关工作？贴纸引用的签发与发送授权由谁负责？目录恢复为旧内容时，是否仍按最近一次目录的变化重新注入？

5. **按需视觉分析**：是否将图片分析、分析缓存和使用说明归入插件，并供 Sticker 索引复用？媒体下载、格式转换、直接向模型附图、图片生成输入和 Replay 图片读取如何共享？会话引用授权、模型并发限制和分析预算由谁执行？

6. **已有插件的迁移范围与共同边界**：以下事项是否纳入本次迁移，仍需决定。
   - 是否把图片生成的完成回执补充信息归回图片功能，同时保留统一的任务完成与投递机制？
   - 是否让各功能分别提供 Replay 中的合成行为，同时由 Replay 统一隔离生产副作用？
   - 是否让各功能拥有对应的管理操作和查询，同时保留统一认证、来源校验和写入权限边界？
   - 插件继续随应用发布、由宿主统一装配是否足够？是否需要统一的启动与停止约定？
   - 调度、连续上下文、历史裁剪、引用授权、发送、通用任务、预算和运行控制，以及通信宿主与进程基础设施，各自应保留哪些职责？
