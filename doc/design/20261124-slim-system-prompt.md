# 精简系统提示词（Slim）

## 为什么要做？

- 现在的系统提示词除了原则和工具用法，还写了怎么实施这些原则。对 SOTA 的大语言模型（比如 GPT Sol／Astra、Claude Opus／Fable），这部分可能是多余的。
- 模型可以利用自己的理智去决定什么时候实施这些原则，这样可能会更好地改进这些模型的表现。
- 这些高端模型很贵，但也要预留空间，给它们充足的想象空间，让它们能够更加自由地发挥。
- 现在的提示词渲染只实现了 mustache 的子集语法。要更好地实现这个目标，需要一套真正的模板渲染引擎。

## 希望实现什么？

- 塑料碗有一个「启用精简提示词」的开关，默认关。
- 开启以后，提示词只包含原则和工具用法等，不包含做事方法。
- 提示词渲染换成真正的 mustache。

### 这一期不做

- 精简不管 System Skills。
- 精简不管管理员自己写的全局人格提示词和 Chat 指令。

## 打算怎么做？

### 用户的想法

- 精简版的系统提示词只介绍原则和工具的使用方法，不会介绍怎么实施这些原则。
- 计划拆成两个 Phase。
- Phase 1：更换模板引擎为 mustache。因为 mustache 绝对不会拿来渲染非管理员提供的 prompt 等内容，所以不需要过度防御。
- Phase 2：增加一个「启用精简提示词」的开关，默认关。开启以后提示词只包含原则和工具用法等，不包含做事方法。
- 精简只管两处：runtime prefix 和工具描述。

### 现状（agent 核对源码）

- 稳定的系统提示词由两部分拼成：runtime 自带的一段（runtime prefix：核心协议、产品知识索引、能力说明、人格段的边界声明），以及管理员写的全局人格提示词和 Chat 指令。
- runtime prefix 约 18KB：产品知识索引约 9KB，核心协议约 6.4KB，能力说明约 2.5KB。
- 模板渲染现在只作用于管理员写的那两层，只做变量替换，一共六个变量。runtime prefix 和工具描述都是固定文本，不经过模板。
- 现有模板的写法都是合法的 mustache 写法。
- 现在遇到未知变量或写坏的表达式，配置会被拒绝加载。
- mustache 的标准行为有两处和现在不同：变量默认按 HTML 转义，`&`、`<`、`>` 和引号会被改写；未知变量不报错，静默渲染为空。
- Decisions 入场闸门的提问文本有自己的两个变量，由另一套独立的替换处理，不走上面这套渲染。
- 模型可以按 Chat 覆盖，也可以在运行中切换。同一个实例里，不同 Chat 可能用着不同档位的模型。
- 稳定的系统提示词内容一变，对应会话保留的上下文会整份重建，之前保留的历史被丢弃。切换精简开关会改变提示词内容，所以会触发一次重建。

## 还有什么没想清楚？

### 审阅意见

1. **变量名写错还报不报错**：现在管理员把变量名写错，配置会被拒绝加载。mustache 的标准行为是静默渲染为空，写错了没有任何提示。「不需要过度防御」是否也包括去掉这条拼写检查，文中没有说。
   - 阻塞点：Phase 1 换引擎后，配置加载遇到未知变量时该拒绝还是放行，无法确定。
   - 必须裁决的原因：这是管理员看得见的行为变化，两种做法都说得通，实施时只能替你选一个。
   - 选项：A 保留现在的行为，写错变量名就拒绝加载（代价：渲染前要多做一遍检查，段、注释等新语法也要一并定规则）；B 按 mustache 标准行为，不检查（代价：变量名写错只会让提示词里少一段字，管理员不容易发现）。
   - 需要决定：换成 mustache 之后，变量名写错还要不要拒绝加载配置？

2. **开关管多大范围**：精简版是为 SOTA 模型准备的，但同一个实例里不同 Chat 可以用不同的模型，也可以在运行中切换。
   - 阻塞点：Phase 2 的开关放在哪一层，决定了混用模型的实例里谁会拿到精简版。
   - 必须裁决的原因：按「一个开关」的字面做成整个实例一个，用便宜模型的 Chat 也会失去做法指引；这是产品行为，不是实施细节。
   - 选项：A 整个实例一个开关（代价：混用模型时，弱模型也拿到精简版）；B 实例级开关之外允许按 Chat 覆盖（代价：多一层配置和面板入口）；C 跟着模型走，在模型上标记（代价：管理员要逐个模型设置，切换模型时提示词跟着变，会话上下文随之重建）。
   - 需要决定：「启用精简提示词」是整个实例一个开关，还是要能按 Chat 或按模型区分？
