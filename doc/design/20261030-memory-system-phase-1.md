# 记忆系统

## 为什么要做？

塑料碗目前缺少一套能够跨 Invocation 持续保存、维护和读取信息的记忆机制。

这限制了塑料碗处理长程任务的能力。例如，群友与塑料碗持续讨论五个小时，逐步明确了一项任务的需求和约束，最后希望塑料碗通过 ACP 协议将任务委派给外部 Agent。塑料碗需要能够在讨论过程中积累资料，而不是完全依赖当前 Context 保留全部信息。

此外，塑料碗还遇到过这样的场景：群友上传一张香烟价格表图片，要求塑料碗记住其中的信息，以便日后随机提问。这要求记忆系统不仅能保存总结，还能持久化多媒体资料，并允许模型在后续 Invocation 中重新读取。

计划中的记忆需求可以分为三类：

- **群友档案记忆**：保存与特定群友有关的信息。
- **群聊记忆**：保存群聊的历史背景和有价值的信息。
- **Memo Pad**：保存资料、讨论成果以及长程任务所需的工作信息。

三者需要有机结合，但不必强行使用完全相同的上层数据结构。

## 希望实现什么？

### 1. 三种记忆能力

记忆系统包含群友档案记忆、群聊记忆和 Memo Pad。

群聊记忆通过定期对一段时间内的群内聊天记录进行 Dreaming 实现：总结这些聊天记录，形成 summary，并标明对应消息的 message id 区间，用来记住群里发生了什么。

群聊记忆需要用到较早的聊天记录；聊天记录的保留和清除规则，等做群聊记忆时再规划。

其中，群友档案记忆和 Memo Pad 的每条记录具有 `summary` 和 `detail` 两部分，支持增删改查。

Memo Pad 严格按 Chat 隔离，每个 Chat 相互独立，同一个 Chat 的各 Topic 共用；Phase 1 完全不考虑 Memo Pad 全局记忆。

群友档案默认是局部档案，同样按 Chat 隔离。群友印象可能需要跨群聊共享：经管理员确认后手动提升，即创建全局群友档案，再删除局部群友档案。同一个群友的全局档案和局部档案在设计上可以并存。群友档案会复用 Blob 的数据结构。

群友档案记忆和 Memo Pad 的列表会呈现 `summary`。`detail` 只有在查询单条记录详情时才会呈现。

塑料碗能够在聊天过程中使用 Memo Pad 保存资料，并在后续 Invocation 中重新读取和修改。

现有的短期记忆迁移到 Memo Pad，不再单独保留；迁移的旧记录 summary 与 detail 暂定完全一致，并保留原到期时间；同一个 Chat 各 Topic 原有的短期记忆合并到该 Chat 的 Memo Pad。Memo Pad 的记录可以设置期限，默认永久保存；Admin Panel 不再警告期限过长的记忆。设了期限的记录算短期记忆，永久保存的记录算长期记忆。

Invocation Context 只自动注入短期记忆的 summary。长期记忆的 summary 不再自动注入，也不再按模型 Context Window 15% 的预算注入最近的条目；长期记忆不依靠常驻 Context 的 summary 让模型发现，而是通过记忆查询机制获取。

短期记忆的注入总量上限为模型 Context Window 的 10%；Token 数暂时按每字 1 Token 估算。超出上限时，隐藏最早创建的短期记忆，直到注入总量符合 10% 的上限，并在列表末尾提示还有 X 条较早的短期记忆未展示，需要查询才能看到。

短期记忆列表放在 Context 的前面，只在前缀本来就要变动、缓存本来就会失效时刷新，例如 Context GC 丢弃旧历史、Context 重建。其余时候短期记忆发生的新增、删除等变化，随下一批注入追加在 Context 末尾单独提示，不改动前面的列表；这些变化会跨 Invocation 累积，直到下一次刷新。同一个 Chat 其他 Topic 产生的变化，同样追加到本 Topic 下一批注入的末尾。Chat 被删除后又重新加入时，重新加入后的第一次运行强制刷新这个列表。

summary 的字数限制与现有短期记忆一致（150 字）。summary 必须准确描述这条记忆存储了什么内容，而不是侧重保存时间、保存过程等与内容检索无关的信息，也不解释 detail 的内容；它应当提供足够的内容线索，使模型能够根据查询结果识别相关记忆。detail 不自动注入，由模型在需要时主动查阅。

只有读取记忆（查询，以及查看单条记录的 detail）的 Tool 做成原语 Tool，直接暴露给模型，不经 `execute` 调用：它的调用频率会比图片生成之类的花边功能高得多。新增、修改、删除记忆不做成原语，经 `execute` 调用，用法由内部 Skill 说明。查询支持单个和多个关键词查询、日期区间查询，关键词匹配 summary 和 detail 的文字；单个关键词必须命中，多个关键词时命中的关键词不少于 50% 才算命中。未来可能还要考虑 RAG 查询。

模型在本轮 Invocation 中没有读取过某条记忆，或者对这条记忆进行修改、删除操作之后没有再次读取时，不能直接修改这条记忆。只有查看过这条记忆的 detail 才算读取过，在查询结果或短期记忆列表里看到 summary 不算。删除记忆不需要先读取。模型读取之后，如果这条记忆在 Admin Panel 被修改，本轮的「已读」作废，模型要重新读取才能修改。

模型应当能够从用户提出的抽象或间接问题，联想到可能需要查询的历史记忆，并推导出合适的检索关键词。例如，用户询问「澳门的雪茄多少钱」，模型需要能够联想到查询「香烟 价格」相关的记忆。模型何时需要查询长期记忆，由稳定系统提示中的查询规则引导。

记忆系统应当为未来的 ACP 任务委派提供持久化上下文的技术可能。

### 2. 统一的 Markdown 内容表达

记忆内容使用 Markdown 表达。

Markdown 可以引用由记忆系统管理的 Blob，例如：

```markdown
# 香烟价格表

![香烟价格表](pwblob://5464363543523...)
```

Blob URI 是内部资源引用，不是实际文件系统路径或公开 HTTP 地址。

### 3. 多媒体文件支持

记忆系统能够保存并引用多媒体文件，而不仅限于纯文本。

例如，群友要求塑料碗保存一张图片时，记忆可以保留图片的 Blob 引用，供后续 Invocation 读取。

塑料碗可以通过 `read_image` 一类的 Tool，读取 Markdown 引用的图片。

Phase 1 只支持当前 Context 里能看到的图片：保存时当场把图片复制到 Blob，不只记录 Context 中的图片引用，因为这些引用会随 Context GC 和引用有效期失效。

### 4. Admin Panel 展示

Admin Panel 能够识别 Markdown 中的 `pwblob://` 引用，并将其转换为可访问的资源地址。

例如：

```text
pwblob://5464363543523...
```

在前端展示时，可以转换为：

```text
https://example.com/api/blob/5464363543523...
```

资源访问仍须经过权限检查。

Admin Panel 可以增删改 Memo Pad。

### 5. Blob 的存储和生命周期

采用 **SQLite + 外部 Blob 存储** 的设计：

- SQLite 管理记忆数据及 Blob 的元数据、引用关系。
- 多媒体 Blob 存放于 SQLite 数据库之外。
- Markdown 中的 Blob 引用与 Blob 生命周期关联。
- 删除或修改记忆时，需要考虑 Blob 是否仍被其他记忆引用，避免错误删除仍在使用的文件。
- 不再被任何有效记忆引用的 Blob，应有相应的清理机制。
- 在 Admin Panel 删除 Chat 时，该 Chat 的 Memo Pad 和 Blob 一起删除，删除前要弹出警告。
- 在 Admin Panel 删除 Chat 改为立刻生效（热更新），不再等待重启：该 Chat 进行中的 Invocation 和长程任务必须立刻停止，Memo Pad 和 Blob 随之立刻删除。
- 写入记忆时检查 Chat 是否还在配置里，不在就拒绝写入，避免中止过程中仍在执行的写入在删除之后留下记录。
- 手改配置文件删除 Chat（之后点「Apply config file」或重启）时，只停止该 Chat 的运行，不删除 Memo Pad 和 Blob，数据留到管理员在 Admin Panel 手动删除。

### 6. 记忆隔离与权限

记忆 Blob 严格归属一个 Chat，同一个 Chat 的各 Topic 共用。

- 一个 Chat 不能访问其他 Chat 的 Blob。
- 同一个文件被多个 Chat 保存时，各自保存一份。
- Blob URI 本身不代表访问授权。
- Phase 1 不提供将 Blob 提升为全局资源的能力。
- 无论是 Admin Panel 还是 Agent Tool，访问 Blob 时都需要执行权限检查。

### 7. 与外部文件机制交换文件

记忆系统的 Blob 存储与[《文件系统》PRD](./20261023-file-system.md) 中的文件机制保持独立。

两套机制职责不同：

**外部文件机制**负责塑料碗与外部系统之间的文件交互，包括 IM 文件接收、MCP 文件访问、ACP 参考资料传递和 Artifact 交付。

**Memory Blob** 负责记忆系统内部文件的持久化、引用和读取。

两套机制平行存在，不共享文件生命周期，但需要保留相互交换文件的能力。

文件交换采用显式复制，而不是让两套机制直接共享同一份受管理的文件。

例如：

1. 群友向塑料碗发送图片，进入外部文件机制。
2. 塑料碗决定将其保存为记忆时，将文件复制到 Memory Blob。
3. Memo Pad 通过 Blob URI 引用该文件。
4. 未来需要将记忆中的文件交给外部 Agent 时，再将其复制到外部文件机制。

## Phase 1 边界

- **不做 Dreaming**：不实现独立的后台记忆整理、提炼或巩固流程。
- 不将记忆系统与 10 月 23 日设计的外部文件机制合并。
- 不做与外部文件机制之间的文件交换，只考虑内部 Blob 管理；多媒体只支持当前 Context 里能看到的图片。
- 不为了记忆系统引入完整的 Virtual FS。
- 不预先要求实现 `patch_file` 等通用文件编辑工具。
- 不将 Embedding 模型或 RAG 作为已经确定的必需依赖。
- 不做 Memo Pad 全局记忆，也不做 Blob 全局提升。
- 不做群友档案。
- 不做群聊记忆，也不改变现有的数据清除规则。
- 不做孤儿数据的管理和删除功能；未来会新增功能，帮助管理员管理和删除孤儿数据。

## 尚未确定的问题

以下问题在本次讨论中尚未形成明确决定：

- 群友档案记忆、群聊记忆与 Memo Pad 的具体数据结构，以及三者如何关联。
- 三种记忆各自的写入、更新和读取策略。
- 群聊记忆是否需要进一步按照 Topic 隔离。
- Memo Pad 的 Summary / Detail 如何参与检索和 Context 构建。
- 是否采用全文检索、Embedding 或 RAG，以及何时引入。
- 记忆中的原始资料与模型提取结果如何关联。
- Blob 的具体存储目录结构、容量限制及清理策略。
- Agent 读取不同媒体类型所需的 Tool 接口。
- 长程任务与 ACP 委派如何具体使用记忆系统。
- 做群聊记忆时，是否取消丢弃 30 天前的聊天记录、只丢弃 30 天前的 Invocation 记录；哪些数据算聊天记录、哪些算 Invocation 记录；聊天记录按什么粒度删除。
- 群友档案的呈现方式与写入权限；同一个群友的全局档案和局部档案并存时，模型看到哪份、冲突时以谁为准；Blob 严格归属一个 Chat，全局档案如何引用图片。
