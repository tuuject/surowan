# 记忆系统

## 为什么要做？

塑料碗目前缺少一套能够跨 Invocation 持续保存、维护和读取信息的记忆机制。

这限制了塑料碗处理长程任务的能力。例如，群友与塑料碗持续讨论五个小时，逐步明确了一项任务的需求和约束，最后希望塑料碗通过 ACP 协议将任务委派给外部 Agent。塑料碗需要能够在讨论过程中积累资料，而不是完全依赖当前 Context 保留全部信息。

此外，塑料碗还遇到过这样的场景：群友上传一张香烟价格表图片，要求塑料碗记住其中的信息，以便日后随机提问。这要求记忆系统不仅能保存总结，还能持久化多媒体资料，并允许模型在后续 Invocation 中重新读取。

计划中的记忆需求可以分为三类：

- **群友档案记忆**：保存与特定群友有关的信息。
- **群聊记忆**：保存群聊的历史背景和有价值的信息。
- **Memo Pad**：保存资料、讨论成果以及长程任务所需的工作信息。

三者需要有机结合，但不必强行使用完全相同的上层数据结构。

## 希望实现什么？

### 1. 三种记忆能力

记忆系统包含群友档案记忆、群聊记忆和 Memo Pad。

其中，Memo Pad 的每条记录具有 `summary` 和 `detail` 两部分，支持增删改查，并按照聊天隔离。

塑料碗能够在聊天过程中使用 Memo Pad 保存资料，并在后续 Invocation 中重新读取和修改。

记忆系统应当为未来的 ACP 任务委派提供持久化上下文的技术可能。

### 2. 统一的 Markdown 内容表达

记忆内容使用 Markdown 表达。

Markdown 可以引用由记忆系统管理的 Blob，例如：

```markdown
# 香烟价格表

![香烟价格表](plasticwanblob://5464363543523...)
```

Blob URI 是内部资源引用，不是实际文件系统路径或公开 HTTP 地址。

### 3. 多媒体文件支持

记忆系统能够保存并引用多媒体文件，而不仅限于纯文本。

例如，群友要求塑料碗保存一张图片时，记忆可以保留图片的 Blob 引用，供后续 Invocation 读取。

塑料碗可以通过 `read_image` 一类的 Tool，读取 Markdown 引用的图片。

### 4. Admin Panel 展示

Admin Panel 能够识别 Markdown 中的 `plasticwanblob://` 引用，并将其转换为可访问的资源地址。

例如：

```text
plasticwanblob://5464363543523...
```

在前端展示时，可以转换为：

```text
https://example.com/api/blob/5464363543523...
```

资源访问仍须经过权限检查。

### 5. Blob 的存储和生命周期

采用 **SQLite + 外部 Blob 存储** 的设计：

- SQLite 管理记忆数据及 Blob 的元数据、引用关系。
- 多媒体 Blob 存放于 SQLite 数据库之外。
- Markdown 中的 Blob 引用与 Blob 生命周期关联。
- 删除或修改记忆时，需要考虑 Blob 是否仍被其他记忆引用，避免错误删除仍在使用的文件。
- 不再被任何有效记忆引用的 Blob，应有相应的清理机制。

### 6. 记忆隔离与权限

记忆 Blob 默认按照群聊隔离。

- 一个群聊不能访问其他群聊的 Blob。
- Blob URI 本身不代表访问授权。
- 管理员可以将 Blob 提升为全局资源，使其允许跨群聊访问。
- 无论是 Admin Panel 还是 Agent Tool，访问 Blob 时都需要执行权限检查。

### 7. 与外部文件机制交换文件

记忆系统的 Blob 存储与[《文件系统》PRD](./20261023-file-system.md) 中的文件机制保持独立。

两套机制职责不同：

**外部文件机制**负责塑料碗与外部系统之间的文件交互，包括 IM 文件接收、MCP 文件访问、ACP 参考资料传递和 Artifact 交付。

**Memory Blob** 负责记忆系统内部文件的持久化、引用和读取。

两套机制平行存在，不共享文件生命周期，但需要保留相互交换文件的能力。

文件交换采用显式复制，而不是让两套机制直接共享同一份受管理的文件。

例如：

1. 群友向塑料碗发送图片，进入外部文件机制。
2. 塑料碗决定将其保存为记忆时，将文件复制到 Memory Blob。
3. Memo Pad 通过 Blob URI 引用该文件。
4. 未来需要将记忆中的文件交给外部 Agent 时，再将其复制到外部文件机制。

## Phase 1 边界

- **不做 Dreaming**：不实现独立的后台记忆整理、提炼或巩固流程。
- 不将记忆系统与 10 月 23 日设计的外部文件机制合并。
- 不为了记忆系统引入完整的 Virtual FS。
- 不预先要求实现 `patch_file` 等通用文件编辑工具。
- 不将 Embedding 模型或 RAG 作为已经确定的必需依赖。

## 尚未确定的问题

以下问题在本次讨论中尚未形成明确决定：

- 群友档案记忆、群聊记忆与 Memo Pad 的具体数据结构，以及三者如何关联。
- 三种记忆各自的写入、更新和读取策略。
- 群聊记忆与 Memo Pad 是否需要进一步按照 Topic 隔离。
- Memo Pad 的 Summary / Detail 如何参与检索和 Context 构建。
- 是否采用全文检索、Embedding 或 RAG，以及何时引入。
- 记忆中的原始资料与模型提取结果如何关联。
- Blob 提升为全局资源后的权限管理、撤销和生命周期规则。
- Blob 的具体存储目录结构、容量限制及清理策略。
- Agent 读取不同媒体类型所需的 Tool 接口。
- 长程任务与 ACP 委派如何具体使用记忆系统。
