# SuroScript Phase 1：Agent Code Mode

## 为什么要做？

- 多步工具编排，以及确定性的筛选、汇总、并发，适合交给一段代码去做，而不是让模型一步一步调用工具。
- SuroScript 是塑料碗企划里的远期设想，打算渐进开发。Code Mode 是它的第一期。

## 希望实现什么？

- 模型可以生成一段 JavaScript，交给塑料碗执行。
- 代码里通过受控 API 编排 MCP 和其它工具，并对结果做过滤和计算。
- 执行结果通过 stdout／结构化数据回传给模型，必要时可以回传图片。
- 模型知道什么时候该用 Code Mode：多步工具编排、确定性的筛选／汇总／并发适用；简单的单工具调用、语义判断、闲聊不应滥用。
- Code Mode 是速度敏感的服务，执行一段代码不应该有明显的启动等待。

### 这一期不做

- 管理员上传自定义脚本。
- 用 Cron／Webhook 触发脚本。
- 完整的 WinterTC Web API，以及 Node 兼容。
- 模型临时写的代码不能直接使用 fetch。
- 把 Runner 放到另一台服务器运行。

长期底线：SuroScript 不提供宿主 Shell Access，任何一期都不提供。

## 打算怎么做？

### 用户的想法

- 这玩意说白了就是 codemode 的超集。第一期只做 codemode 这一部分。
- 立场还是不给模型提供 Bash 或者 Shell Access。
- Code Mode 是一个在受限的空间执行脚本解决问题的方案：它不能访问文件系统，也不能访问系统的 Shell 等各种资源，而且还有墙钟等各种限制。
- 这实际上是给「不向模型暴露任意代码执行」这条限制稍微做了一点松。项目目标里对应的那一条，实施时按这个立场改写。
- 我作为开发者会对用户的安全负责，但是这个安全负责不是无限度的。
- 脚本可以调用塑料碗的各种 tool，唯独不能调用执行脚本的那个 tool，这样可以防止死循环。
- 这个功能是必选的：JavaScript 运行时捆绑在塑料碗的发行版里面。用户可以选择开启或关闭。
- 不直接使用 Node／Bun 执行不可信代码。直接 eval 只可能用于小范围、完全可信的概念验证，不能视为安全沙箱。
- 执行要限制 CPU 时间、墙钟时间与内存，防死循环，并且隔离主进程。
- JS 部分由一个单独的 Runner 进程运行，Runner 用 Go 写，由塑料碗主服务拉起。
- Runner 不是每执行一次 JS 就拉起一次。塑料碗主服务端启动了，它也一直运行。
- 主服务往 Runner 的 stdin 传入一组 JSON 参数，里面包含可以使用的、由塑料碗主服务端负责处理的函数列表等。
- 不使用命令行参数传输，因为进程列表会把参数暴露给其它进程。
- 主服务和 Runner 之间希望不走 HTTP。通信方式之前设想过 JSON-RPC 之类的做法。
- Runner 和主服务一股脑打包到同一个 Docker 镜像里。

### 现状（agent 核对源码）

- 模型现在没有任何执行代码的途径。项目目标里写着「不向模型暴露 Bash、任意代码执行或不受限文件系统能力」。
- 模型一次调用一个工具，每次调用的结果在大小上限内完整回到模型手里，由模型自己决定下一步。
- 塑料碗内部的能力通过「搜索 → 看说明 → 调用」三步使用。MCP 工具按 Server 的设置，要么直接摆在模型面前，要么收进一个统一入口按需查找。
- 每次工具调用都要经过许可名单、只读策略、大小限制和超时，计入这次 Invocation 的预算，并留下审计记录。
- 发消息只能通过 send。模型的普通文本不会发出去。
- 图片只能引用当前对话里已授权且没过期的。
- 主服务已经会拉起并管理子进程：stdio 形态的 MCP Server 就是这样运行的，只执行配置里写死的命令。
- 现在发布的 Docker 镜像里只有 Node 运行时和媒体处理依赖，没有 Go 程序。
- 塑料碗不只跑在 Docker 里，也可以从源码直接运行、交给 systemd 托管，另有 Electron 版。

## 还有什么没想清楚？

1. **怎么引导模型知道何时使用 Code Mode**：这是关键的产品问题，具体做法待定。

2. **JS 引擎选型**：重点评估 [moejs](https://github.com/MoeForge/moejs)，也讨论过 QuickJS、workerd、deno_core，还没有定。

3. **通信用 key 是否还需要**：最初的想法是 stdin 传入的参数里包含一把通信用 key。如果主服务和 Runner 全程只通过 stdin／stdout 对话，目前倾向不需要 key，等 Runner 要跑到另一台服务器时再引入。还没有最终确认。

### 审阅意见

1. **开关的默认值没有定**：功能必选、运行时随发行版捆绑，用户可以开启或关闭，但没有说默认是哪一边。默认开启的话，现有部署升级后，模型能用的工具会在管理员没有操作的情况下改变。
   - 选项：A 默认开启（代价：升级即改变模型行为）；B 默认关闭（代价：功能虽然必选，但管理员不知道就不会用上）。
   - 需要决定：Code Mode 的开关默认开启还是关闭？
