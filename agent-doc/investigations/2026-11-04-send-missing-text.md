# 生产环境 `send` / `send_reply` 缺少 `text` 参数调查报告

- 调查时间：2026-11-04（Asia/Singapore）
- 方式：`surowan-utils` 只读 Admin API（`doctor` 连通校验通过，凭据为 API key）
- 范围：生产 endpoint，`invocation list` 完整枚举 `2026-10-28T00:00:00+08:00` 至 `2026-11-04T00:33:42+08:00`
- 约束：未修改代码、配置或生产状态；未执行重放、未调用模型；未导出对话正文；报告只含聚合统计与脱敏案例

## 1. 结论摘要

1. **异常真实存在，但“缺 `text`”必须精确表述为“进入 `send` 实现时没有正文”**。它可能是模型省略了 `text`，也可能是模型给出 `text: null` 后被运行时归一化删除；现有审计无法区分这两种 wire 层形态。
2. **调用级缺参率 37.7% 不能直接当作“模型错误率”**。少数 Invocation 单次响应就产出数百到上千个 `send`，把调用级分母严重拉偏：两个 Invocation（8183、7912）贡献了全部 2,031 个缺失调用中的 **70.7%**。请求级为 26.5%，首次发送级为 22.2%。
3. **上下文长度与缺参率之间没有可靠的单调关系**。调用级曲线呈“中间高、两端低”，请求级、首次发送级曲线同样非单调；分层配对比较结果方向互相矛盾。当前数据不支持“上下文越长，参数可靠性越低”这一简单假设。
4. **更强的相关因素是“单次模型响应内 `send` 调用数量”**：单发请求缺参率 21.4%，一旦同响应出现 ≥2 个 `send`，缺参率跃升至 91%–100%，且在全部上下文区间都成立。这更像**批量工具调用参数生成退化**，而不是纯上下文长度效应。
5. **无法证明与“输出截断”有直接因果**：18 次模型调用输出恰为 131,072（该模型 `max_tokens`），但生产审计不记录 `stopReason`，且这些调用中大部分 `send` 都带有正文。截断只能列为待验证假设。
6. **本次样本窗口内没有观察到 `send_empty_text_fallback` 的成功补全痕迹**（`agent_messages.tool_result` 中无补全尾注），因此“兜底掩盖了缺参”在本窗口内**不构成**主要观测偏差；但这不代表更早历史。

| 每个 Invocation 首个文本发送 | 567 个，126 个缺参（22.2%） |

### 2.2 关键数据限制

- **原始模型参数不可得**。`tool_calls.arguments_json` 是运行时归一化后的快照：成功路径为补全并窄化后的参数，拒绝路径为补全后、窄化前的参数。`model_calls.response_json` 只保存 HTTP 状态，不含模型输出；本窗口 `request_json` / `response_json` 全部为空（`developer.record_model_payloads = false`）。
- **`text: null` 与“省略 `text`”不可区分**。当前依赖的 Pi 会在校验前删除可选且不接受 `null` 的字段。
- **调用与模型请求没有外键**。本文的“请求级”关联按 `created_at` 时间序推断（全部 5,388 条均可唯一归属），**不是直接关联**；模型调用状态非 success 或时间缺失时不做因果解读。
- **“缺正文”计数是下界**。兜底补全后若被 `send_barrier`、去重、限流或 Telegram 错误拒绝，`arguments_json` 已含补全文本、工具结果又无补全尾注，原始缺参不可恢复。本文无 `fallback_candidate_unmarked` 候选命中，但当前兜底文本配置不等于历史配置，不能反推。
- **token 是 Provider 报告值**，不是本地 tokenizer 实测；`input` 采用 `input_tokens + cache_read_tokens + cache_write_tokens`，缓存命中同样占用上下文。上下文窗口按**采集时的 active 配置**反查，若历史模型或窗口变过，窗口占用率口径不可靠；因此本文主要按**绝对输入 token 区间**分组，占用率仅作辅助。
- **`context_messages` 是冻结的公开消息快照**，不是 canonical transcript，无法用于恢复模型当时看到的完整工具历史。
- **`send_barrier` 不代表 Telegram 故障**，是发送闸门；同批剩余调用会被机械放大，不能当作独立模型决策。
- **样本完整性**：583 条详情全部有 `finished_at` 且早于截止时间、无重复；未纳入的 3 条为 7827、7695（`network_error`，未重试）与 8250（采集时仍在 running）。

## 3. 异常识别口径

本次把“缺正文”限定为：文本类发送（`kind` 省略或为 `text`，且未携带 sticker/image/file 引用）中，至少一个 `text` 部件缺失。

- 排除 `kind` 为 `sticker` / `image` / `file` 的发送（本次 6 条 `image` 发送全部排除）。
- `kind` 缺省但携带 `image_ref` 等引用的 6 条记为“ambiguous”，不计入缺正文。
- `send_reply` 按根调用计数，`<parent>:N` 派生发送不重复计入。
- 全部 2,031 个缺失调用均伴随 `error_code = send_input_invalid`，参数形状以 `{reply_to_message_id}` 为主（2,030 条），另有 1 条空对象。

## 4. 分组统计

### 4.1 按模型 / Provider

| Provider / 模型 | 调用数 | 缺参 | 缺参率 |
| --- | --- | --- | --- |
| openrouter / `deepseek/deepseek-v4-flash-0731` | 5,376 | 2,031 | 37.8% |
| deepseek / `deepseek-flash` | 12 | 0 | 0% |

对照极弱：直接 DeepSeek Provider 样本过少（6 个 Invocation，输入均 < 20k），不能据此判断 Provider 优劣。窗口内几乎所有生产流量走同一模型，模型维度不具备区分力。

### 4.2 按上下文长度（调用级）

| 输入 token 区间 | 调用数 | 缺参 | 缺参率 |
| --- | --- | --- | --- |
| < 16k | 126 | 5 | 4.0% |
| 16–32k | 456 | 151 | 33.1% |
| 32–64k | 756 | 336 | 44.4% |
| 64–128k | 1,721 | 1,466 | 85.2% |
| 128–256k | 91 | 35 | 38.5% |
| ≥ 256k | 2,238 | 38 | 1.7% |

曲线**非单调**：最高点在 64–128k，两端反而最低。但两端样本被少数超大批量 Invocation 主导——≥256k 的 2,238 条调用中有 1,447 条来自 Inv 8198 单次响应，因此该曲线不能解释为上下文效应。

### 4.3 按请求级与首次发送（降低批量偏斜）

| 口径 | 样本数 | 缺参 | 缺参率 |
| --- | --- | --- | --- |
| 调用级（根 `send`） | 5,388 | 2,031 | 37.7% |
| 请求级（任一调用缺参） | 1,201 | 318 | 26.5% |
| 每 Invocation 首个文本发送 | 567 | 126 | 22.2% |
| Invocation 级（任一调用缺参） | 567 | 143 | 25.2% |

请求级按上下文：<16k 4.0%、16–32k 24.4%、32–64k 35.6%、64–128k 28.1%、128–256k 8.2%、≥256k 33.0%——依然非单调。

三种口径不可互相替代：调用级会被单个响应内的重复发送放大；请求级把“任一调用缺参”压成一次；首次发送与 Invocation 级各占一个单位。**下文结论以请求级与首次发送级为准，调用级只作分布描述。**

### 4.4 按单响应内发送数（最强相关项）

| 单请求内 `send` 数 | 请求数 | 含缺参 | 比率 |
| --- | --- | --- | --- |
| 1 | 1,117 | 239 | 21.4% |
| 2 | 35 | 32 | 91.4% |
| 3–4 | 21 | 20 | 95.2% |
| 5–8 | 10 | 10 | 100% |
| 9–32 | 10 | 10 | 100% |
| 33+ | 8 | 7 | 87.5% |

该效应在全部上下文区间都成立：单发请求各区间为 4%–29%，而 ≥2 发的 28 个请求中 27 个含缺参（96.4%）。

### 4.5 按 Invocation 内调用序号

调用级：第 1 次 21.9%、第 2 次 27.6%、第 3–4 次 32.1%、第 5–8 次 42.9%、第 9+ 次 40.0%。请求级：第 1 次 21.9%、第 2 次 23.5%、第 3–4 次 25.7%、第 5–8 次 34.8%、第 9+ 次 37.1%。序号效应存在但明显小于“单响应批量”效应，且与批量大小高度共线。

### 4.6 其他分组

- **是否出现过 harness_nudge**：出现过 48.6%（2,305 条），未出现 29.6%（3,083 条）。但 nudge 是“模型输出普通文本未发送”后的提醒，与缺参同为输出质量问题，不构成独立解释。
- **调用前已有 ≥2 次工具错误**：缺参率 91.9%（1,012 条），这是批量退化后的自我延续现象，不能倒推为原因。
- **配置 hash**：22 个配置分组间差异很大（0%–71%），但每个分组的调用量被少数批量 Invocation 主导，不能作为配置差异的证据。
- **日期**：10-29 为 0%，11-01 为 66.1%，11-03 为 37.5%，波动主要来自当天是否发生批量退化 Invocation。

## 6. 机制核对（本地源码）

- `text` 在 `send` / `send_reply` 的 Schema 中均为可选（`src/capabilities/send/index.ts:24-38`、`53-62`）。
- `fillEmptyText` 只处理 `text === undefined` 且推断为文本的输入（`src/capabilities/send/support.ts:75-82`），随后审计记录的是**补全后**的参数。
- 成功补全会在工具结果里追加 “The call had no text, so the configured fallback text …” 尾注（`src/capabilities/send/index.ts:108-114`）；本次 2,031 条缺失调用中**无一条**出现该尾注，说明它们都在补全后被校验拒绝，或补全未生效。
- 运行时**没有每 Invocation 工具调用次数上限**（`src/orchestration/agent-runtime/run-hooks.ts:118-127`），单次响应内的工具调用会被顺序全部执行，普通工具错误不会中断该批。
- `send_barrier` 会在同批剩余调用中继续触发，因此批量 Invocation 的错误分布被机械放大。
- 当前依赖 Pi 1.1.0 对 `stopReason=length` 的工具调用会在执行前拒绝；但这只适用于当前依赖版本，不能证明生产当时行为。

## 7. 可能原因与证据强度

| 假设 | 证据 | 强度 | 说明 |
| --- | --- | --- | --- |
| A. 上下文过长导致参数可靠性下降 | 调用级/请求级曲线均非单调；按同模型、同配置、同 Chat、同日的 <64k / ≥64k 分层比较方向不一致 | **弱 / 不支持** | 分层本身仍混杂时间、轮次与失败后重复，只能算描述性比较，不能因果推断 |
| B. 单次响应内批量 `send` 导致参数生成退化 | 单发 21.4% vs ≥2 发 91%–100%，跨所有上下文区间成立 | **强相关** | 因果关系仍待受控验证 |
| C. 输出截断导致参数不完整 | 18 次调用输出恰为 131,072；但多数发送仍带正文 | **弱** | 审计无 `stopReason`，无法确认 |
| D. Schema 或工具描述问题 | 窗口内 Schema 版本无法还原；`send` 描述较长 | **未知** | 需按 `request_json` 或部署版本核对 |
| E. 上游 Provider 参数序列化/修复异常 | 部分调用为残缺参数形态 | **待验证** | 无原始响应体 |
| F. 兜底掩盖了缺参 | 本窗口无兜底尾注，也无补全候选文本 | **已排除（本窗口）** | 拒绝路径的原始缺参仍是不可恢复的下界 |

## 8. 后续值得验证的假设

1. **受控复现“单响应多发送”**：在相同上下文下，让模型分别产出 1 个与 3 个 `send`，比较缺参率；这是区分 B 与 A 的关键实验。
2. **临时开启 `record_model_payloads`**（需用户授权与运维确认）以获取原始模型输出与 `finish_reason`，确认是否存在 `length` 截断与残缺 JSON。
3. **按 Schema 版本分组**：结合部署版本与 `tool_registry_hash`，检查 `text` 是否曾被标为必填或 `minLength` 变化。
4. **观察 `send_barrier` 与批量大小的关系**：确认批量 Invocation 是模型行为还是上下文注入节奏造成的。
5. **扩大直接 DeepSeek Provider 的样本**，在相近上下文下与 OpenRouter 对照。
