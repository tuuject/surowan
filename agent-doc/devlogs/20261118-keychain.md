# Surowan - 20261118 key jar 升级为 keychain：稳定条目名、原地轮换与密钥管理页

## 背景

密钥原本存在配置旁边的 `key.json`（key jar）里，配置只写 `{ "jar": "<name>" }` 引用。但每把密钥没有稳定的身份：

- 面板和 `configure` 录入的条目名是 16 位随机 hex，人认不出来。
- 热应用只看引用变没变，不看值变没变，所以换密钥只能新建条目、换一个新名字。
- 同一把密钥没法被多处共用，图片配置只好在自己的段里另起一层「凭据名」。
- 每次写配置都会自动删除不再被引用的条目。`image` 段结构不合法时会被校验整段丢掉，此时任何一次配置写入（包括成员的 `/ignoreme`）都会把图片凭据当成「不再引用」删掉。PRD 写作时这一条只是读代码推断的。
- 没有地方能看到现在存了哪些密钥、各自被谁使用。

PRD 是 `doc/design/20261116-keychain.md`，实施计划是 `agent-doc/design/20261116 Keychain 实施计划.md`（D1–D15）。按用户要求整体实现计划；其中 D5 在实现过程中由用户改为「轮换后自动重连 MCP」，见第 3 节。

本次改动由 Pi（`magpie/auto/glm-5.3-flash`，thinking `max`，T3 子线程「Implement Keychain (upgrade key jar to keychain)」）实现，共一轮首次实现加两轮修正。主会话负责 review、复验、两处小修与交付。

## 主要变更

### 1. 存储：新文件格式与一次性迁移

`src/platform/key-jar.ts` 改名为 `src/platform/keychain.ts`，全部调用方迁移，不留别名。文件名 `key.json`、配置键 `jar`、`SecretRefSchema` 不变。新格式：

```json
{ "version": 1, "entries": { "openrouter": { "value": "…", "created_at": "2026-11-18T…Z" } } }
```

- `migrateKeychain`（`src/platform/keychain.ts:170`）把旧的扁平格式原地转成新格式，条目名不变。它沿用临时文件加 rename 的写法，权限 `0600`，拒绝符号链接，不留备份副本。`serve`、`configure`、`doctor` 启动时各调用一次。
- 其余读路径只认 `version === 1`。遇到旧格式时报一个可操作的错误（提示启动 `serve` 或运行 `configure`），错误信息不回显文件内容。这是单向升级，旧版本程序读不了新文件。
- `updateKeychain`（`:193`）新增 `replace` 操作：条目必须已存在，并保留 `created_at`。文件不存在时视为空 keychain，`add` 会创建文件。
- `nextEntryName`（`:66`）给推导出来的名字加 `-2`、`-3` 后缀，截断时先为后缀留出位置。
- `collectSecretReferences`（`:308`）结构化遍历配置，返回「条目名 → 引用路径」，同时收集 `env` / `command` 引用（`command` 不带 argv）。

### 2. 取消全部自动回收

- `src/adapters/local-monolith/config/file.ts` 不再在写入后删除不被引用的条目。rename 失败时撤销本次新建的条目，这属于事务回滚，保留。
- `src/tui/configure.ts` 删除 `pruneKeyJar`，退出时不再清理。
- 孤儿条目只由密钥管理页显式清理。
- 回归测试 `test/keychain/reclaim.test.ts`：`image` 段不合法时走一次成员 `/ignoreme` 写入，`image.credentials` 引用的条目必须还在。子 agent 报告这条测试在旧代码上失败（条目被删），复现了 PRD 里那条推断出来的误删。

### 3. 热应用与轮换

- **Provider**：`buildModelRegistry` 为每个 Provider 计算一个连接摘要（`src/platform/providers.ts:242`），由它引用的 jar 条目值的 SHA-256 组成。`env` / `command` 引用固定摘要为空串，所以检测时不会执行命令。旧连接只有在「连接字段相同且摘要相同」时才复用（`:222`）。摘要只存在内存里。`serve` 启动时用启动那次构建的摘要做种子。
- **MCP（用户决定，替换计划的 D5）**：计划原本写的是「MCP 是重启字段，轮换后提示重启」。但最近的 MCP 改动已经让 `mcp.*` 可以热更新，用户于是决定轮换后自动重连。`applyFile` 计算 `env` / `headers` 里 jar 引用的摘要发生变化的 server alias，把这组 alias 经 `onPublished → mcp-cutover → McpManager.reconcile` 一路传下去：
  - `reconcile` 对这些 alias 强制替换，即使 `sameMcpServerConfig` 认为配置相同（`src/capabilities/mcp/reconcile.ts:45`）。
  - `affectedMcpChatIds` 把能访问这些 alias 的 Chat 算作受影响（`src/capabilities/mcp/bindings.ts:135`），走现有的 fence、Context 重建与续跑流程。
  - 发布钩子失败时，这组 alias 留在 `pendingMcpRotations`（`src/adapters/local-monolith/config/reload-apply.ts:45`）里，下次 apply 重试时一并带上。
- 图片凭据与 Telegram token 原本就在每次 apply 时重新解析，没有改。联网搜索每次请求都解析，也没有改。

### 4. 写端点：`SecretInput`、命名规则与调用方区分

Provider、Telegram、联网搜索、图片四类写端点里的密钥字段统一接受 `SecretInput = string | { value, name? } | { entry }`（`src/ingress/admin/secret-input.ts`）。一个请求内所有密钥字段共用一个 `SecretAllocator`（`:63`），已分配的名字在请求内保留：显式重名返回 409，自动名在已有条目和本请求已分配的名字之上取下一个空号。填新密钥时的规则（D7）：

```ts
  const currentName = slot.current !== undefined && 'jar' in slot.current ? slot.current.jar : undefined;
  if (currentName !== undefined && allocator.has(currentName)) {
    if (allocator.usedOnlyHere(currentName, slot.path)) {
      // The entry exists for this use alone: rotate its value in place. The
      // file keeps pointing at the same name, so this is not a change.
      return { kind: 'rotate', ref: { jar: currentName }, name: currentName, plaintext: value };
    }
  } else if (currentName !== undefined) {
    // The file names an entry the keychain lacks: the submitted value repairs it.
    return { kind: 'repair', ref: { jar: currentName }, name: currentName, plaintext: value };
  }
  const name = allocator.next(slot.suggestedName);
```

- 调用方类别 `'session' | 'programmatic'` 由 `AdminServer` 显式传给各写处理器，不解析 actor 字符串。
- 外部凭据（API key、已配对客户端）提交 `{ entry }` 一律 403。改 Provider `base_url` 时仍须在同一请求里重交密钥。对联网搜索，「保留密钥」和「改 `endpoint`」同时出现会被拒绝（`src/ingress/admin/search.ts:338`）。子 agent 核实了旧代码确实可以用 `keep_api_key` 加任意 `endpoint`，把已存的 DeepSeek 密钥发到任意地址，这一处现在已经关上。
- 面板会话可以选用任意已有条目，改 `base_url` 也不再要求重交密钥。
- 搜索的 `key_source` 与图片的 `credential_sources` 两条专用复用路径删除，改用通用的 `{ entry }`（D8）。
- 设置页的读接口只对面板会话返回各密钥字段的来源（条目名 / 环境变量名 / `command`），外部凭据仍只看到布尔值（D13）。

### 5. 密钥管理 API 与事务写入

- `src/ingress/admin/routes/keychain.ts` 提供 `GET/POST /api/keychain`、`PUT/DELETE /api/keychain/<name>`、`POST /api/keychain/purge`。这组端点不在 `packages/admin-surface` 登记，所以外部凭据得到 403，也不会生成 CLI 命令或 MCP 工具（D11）。
- 判断使用处时看两边：磁盘上配置文件的原始 JSONC（被忽略的段里的引用也算），以及运行中的 active 配置。配置文件无法解析时拒绝 purge 和 DELETE。`purge` 只删除提交的名单里此刻仍是孤儿的条目（D12）。
- 设置页的「原地轮换 / 修复 / 新建 + 改配置」统一走 `ConfigController.writeSecretsAndApply`（`src/adapters/local-monolith/config/reload-keychain.ts:76`），整个过程在一次 reloader 锁内完成：
  1. 校验 revision。
  2. 从原始文件复查待替换的条目是否仍只被发起请求的那个路径引用。
  3. 写 keychain。
  4. 写配置并 apply。
  5. 配置没落盘就失败时，恢复旧值。
- 涉及条目名的查找一律用 `Object.hasOwn` 或无原型的对象，所以名为 `constructor`、`__proto__` 的条目也能正常增删和清理。

### 6. 前端

- 新增 `/keychain` 页（`apps/admin-next/src/pages/keychain.tsx`、`keychain-dialogs.tsx`），导航在「系统」分组，中文标题「密钥」，四个 locale 都已补齐。
- 页面有条目表（新建、轮换、删除未使用的条目、清理孤儿）和只读的外部引用列表。
- 轮换和新建的弹窗每次打开都重新挂载，所有关闭路径都会清空输入。mutation 结束后立即 `reset()`，不在缓存里留明文。
- 清理确认在弹窗打开时冻结名单，请求只提交这份名单。
- 共享的密钥输入组件 `components/secret-input/secret-field.tsx` 用在 Provider、Telegram、联网搜索、图片四处。它有三种状态：填新密钥（条目名可改）、选用已有条目、外部引用只读。
- 草稿里没被手动改过的条目名保持为空，由服务端按当时的使用处推导，避免 header 默认取到 Provider 别名、导致和 API key 撞名。

### 7. TUI

`promptSecretRef` 改为「填新密钥 / 选用已有条目」两种来源，`env` / `command` 两项照旧保留。新密钥的默认条目名按使用处推导：API key 用 Provider 别名，header 用 `<别名>-<header>`，可以改，重名会被拒绝。输入后仍立即写入条目（「获取模型列表」依赖它），放弃保存时也不再清理。

### 8. 文档与其他

- 同步了 `agent-doc/{configuration,admin-panel,architecture,operations,verification}.md`、`AGENTS.md` 和用户手册（新增 `apps/docs/content/docs/configure/admin-keychain.md`）。另外更新了 `packages/cli/README.md`、`skills/surowan-utils`、`skills/surowan-mcp`，以及 `packages/admin-surface` 的接口 summary。
- 实施计划的 D5 行改为记录用户的决定。
- `vitest.config.ts` 把 mock 了 `@inquirer/prompts` 的 `test/tui-secret-ref.test.ts` 放进 `isolated` project，这是主会话的小修。

## review 过程

首轮实现后跑了一次 ocr（105 个文件，45 条意见），主会话逐条回到代码核实，同时自己通读了 diff。成立的问题合并成 16 条，打回同一子线程。主要几条：

| 问题 | 判定与处理 |
| --- | --- |
| `key.json` 不存在时 `updateKeychain` 直接返回，全新部署的第一把密钥被静默丢掉，配置却引用了它 | 成立，主会话用脚本复现。改为空 keychain 起步并补测试 |
| `nextEntryName` 先拼后缀再截断到 64 字符，长名字撞名时同步死循环，会卡死 `serve` | 成立。截断时先为后缀留位 |
| 前端把推导出的默认名存进草稿：新建 header 默认取 Provider 别名，新建 Provider 时 header 值会覆盖 API key | 成立。未手改的名字保持为空 |
| 同一请求里多个字段显式重名，`Object.assign` 合并后只剩最后一个值 | 成立。引入请求级 `SecretAllocator` |
| D7 只对名字等于推导名的条目原地替换，迁移来的随机名条目每次都会新建 | 成立。改为看字段当前指向的条目是否只在这里使用 |
| 原地轮换与配置写入分两次加锁，也不校验 revision | 成立。改为 `writeSecretsAndApply` 单锁事务 |
| 轮换弹窗会把上一次的明文带进下一个条目；清理名单不是固定快照；`constructor` / `__proto__` 条目删不掉 | 成立，均已修 |
| MCP 重启标记永远不会清除（diff 只产出 `mcp.servers` 这个整体路径） | 成立。随后用户改为自动重连，整套标记机制删除 |
| e2e 里的孤儿条目名含花括号，测试走不到清理流程 | 误报。实际名字是合法的 `e2e-keychain-orphan` |
| `configure` 与运行中的 `serve` 之间没有跨进程锁 | 旧 key jar 就有这个问题，不在本期范围，不改 |

第一轮修正期间，子 agent 误判一批文件是无关改动，整体 `git restore` 后又手动补回，但 TUI provider 向导的三个文件没补全。主会话复核时发现，加上另外三处问题（配置写入返回失败结果时没有执行回滚、代码里残留「key jar」字样、发布钩子失败后丢失待重连的 MCP alias）一起打回第二轮。修正轮按约定不再跑 ocr。

主会话自己做的两处小修：上面那条 vitest 隔离配置，以及 `test/keychain/migrate.test.ts` 里一条不稳定的断言。原断言要求错误信息「不包含 `b`」，但 `mkdtemp` 随机生成的目录名里可能带 `b`，改为检查一个不可能出现在路径里的密钥值。
