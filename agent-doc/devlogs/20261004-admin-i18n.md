# Surowan - 20261004 Admin Panel 正式 i18n（英文 + 简体中文）

## 背景

Admin Panel 的 UI 文案此前是历史分层混排：主体页面（Invocations、Messages、Models、Settings 等）为英文，后加的图片生成全套为中文，侧边栏甚至同一数组内混用 `Bot sticker sets` 与 `图片生成`。没有语言机制，文案分散在 62 个文件的 JSX 字面量里，改动只能全局搜索。

目标是一次性建立正式 i18n：英文与简体中文两种界面语言、顶栏切换、持久化、跟随浏览器默认语言，并借机统一两种语言的文案基线。选型 react-i18next：与 React 19、Rsbuild、TanStack Router 均无耦合，无 SSR，无需框架集成。

两条基线决策先于实施确定：

- **en 为源语言目录**。现网大部分文案已是英文；英文文案逐字保留意味着既有 Playwright 断言零扰动，key 语义也比中文短句稳定。中文图片模块的既有文案原样进入 zh 目录，其余中文由英文新译。
- **技术名词在中文界面保留英文**（Invocation、Context、Prompt、Token、Bucket 等），与项目现有中文文档的行文一致。后端返回的错误消息始终按服务端原文显示（`code: message`），不在前端翻译范围。

## 主要变更

### 1. i18n 基础设施与类型安全

`apps/admin-next/src/lib/i18n.ts` 初始化 i18next 单例：内联资源包、`fallbackLng: 'en'`、`returnNull: false`。语言解析链为「localStorage `admin-language` → 浏览器语言（`zh*` 前缀解析为 `zh-CN`）→ `en`」，与 ThemeProvider 的持久化模式同构；切换时同步 `document.documentElement.lang`。

`apps/admin-next/src/i18next.d.ts` 通过 `CustomTypeOptions` 把 key 类型绑定到 en 目录编译期结构：任何 `t('...')` 的 key 拼写错误都是 `tsc` 错误。这个约束在本次开发中真实生效——抓到了一处 `pages.stickers.setTitle`（目录中是 `setsTitle`）的拼写漂移。

语言包按区域拆为 6 组文件（`common`/`layout`/`invocations`/`models`/`pages`/`image`，合计约 926 个 key），en 与 zh-CN 成对。zh 文件以 `export const x: typeof xEn = {...}` 镜像 en 文件，key 结构漂移同样编译期失败；`src/locales/resources.ts` 按区域嵌套组合两个目录。

字符串抽取覆盖 62 个文件约 500+ 处可见文案：标题、CardTitle/Description、Label、按钮、placeholder、aria-label、sr-only、toast、ConfirmDialog props、表格列标题、emptyText、option 等。共享动作复用 `common.*`；模块作用域的列定义/导航数组移入组件 render 作用域，保证切换语言即时重渲染。中文文案中的模板语法示例（`{{prompt:…}}`）必须作为插值变量传入——i18next 不会二次扫描插值值，字面量安全输出；孤立的 `{{`（不完整对）原样通过。中文无复数形式，计数场景全部使用单 key 加 `{{count}}`，不引入 `_one/_other`。

### 2. 语言切换入口与配套

`apps/admin-next/src/components/themes/language-toggle.tsx` 复用 ThemeModeToggle 的图标按钮 + Tooltip 形态，置于顶栏主题切换左侧。`formatNumber` 改为跟随当前语言的 `toLocaleString`；日期保持固定 `sv-SE` 格式（locale 中立）。`errors.ts` 的兜底文案经 `i18n.t` 输出。

Playwright 配置增加 `locale: 'en-US'`，浏览器语言检测在整套 E2E 中确定性地解析为 en；`vitest.config.ts` 在 worker fork 前 pin `LANG/LC_ALL=en_US.UTF-8`（原因见下文第 4 节）。

### 3. 面包屑跟随界面语言

面包屑标题此前由 URL slug 直接 title-case 生成，完全不经过 i18n（空路径的 `Overview` 除外），中文界面下会得到英文面包屑。`breadcrumbs.tsx` 增加 `SEGMENT_TO_NAV` 映射：14 个一级路由段解析到侧边栏 nav key，面包屑与侧边栏对同一目的地共用同一名称；详情页的 ID 段不是可翻译文本，保持 slug 原样。

这带来一处英文行为变化：`/invocations` 的面包屑从 `Invocations` 变为 `Tool sessions`（与侧边栏一致）。已核实全部 E2E 无面包屑文本断言。

### 4. 集成期发现并修复的三个坑

- **资源组合误用 spread**。首版 `resources.ts` 用 `{...common, ...layout, ...}` 组合，区域对象的内部键被平铺到 catalog 根部，`t('common.requestFailed')` 运行时查找 `translation.common.requestFailed` 全部 miss。同时 `i18next.d.ts` 引用的 `en` 并未导出，而 `skipLibCheck: true` 跳过了 d.ts 的类型检查，typed keys 静默退化为任意 string——`tsc` 全绿但运行时全部返回 key。修复为按区域嵌套组合并显式导出 `en`。教训：类型增强的实际效果需要至少一次「错误 key 应当编译失败」的负向验证。
- **vitest 不解析 `@/` 别名**。Rsbuild 与 tsc（bundler resolution + paths）都认识别名，但根 vitest 没有 resolve.alias；此前 lib 目录全部相对导入正是这个约束的既有体现。i18n 链路（`lib/i18n.ts` 及引用它的 5 个 lib 模块）改回相对导入，组件层保留 `@/`。
- **Node 的 `navigator.language` 跟随环境 locale**。开发机为中文 locale 时，单测进程内 i18n 默认语言解析为 `zh-CN`，断言英文的既有测试失败。Node 24 中 `LANG=en_US.UTF-8` 决定 `navigator.language`，在 vitest 配置文件（先于 worker fork 执行）设置即可全环境确定性。另核实 i18next v26 已移除 `initImmediate` 选项且内联资源默认同步初始化，无需兼容代码。

### 5. E2E 与文档

中文文案集中在图片模块，其断言分布在 `10-developer`、`11-image-settings`、`12-image-generations` 三个 spec，全部更新为新的英文字符串（套件固定 en 运行）；`01-routes` 经排查无侧边栏/面包屑断言，唯一的 developer 页断言在 `01-routes.e2e.ts:139`（首轮流水中遗漏），随后修复。用户指南 `apps/docs/content/docs/configure/admin.md` 新增「界面语言」节，说明切换、持久化、技术名词保留与后端错误消息原文策略。
