## 本单元范围

按 §7 的 U2：

- §4.2 进程内连接状态登记处；
- §4.4 身份、Telegram host、媒体下载、Sticker、MCP 与 host 集合的解耦；
- §4.5 只做 Scheduler 动态放行，不含停止/作废流程（U3）；
- §4.6 定时任务与图片生成在实例未就绪时挂起。

本单元仍然在启动时一次性连接 Telegram：token 存在时构造 Bot、`getMe()`、注册命令、`deleteWebhook`、补拉，然后进入长轮询；不做运行中启停、重连或配置迁移，也不删除 `--playground-only`。

## 主要变更

### 连接状态（§4.2）

新增 `src/platform/im-connection.ts`：

- `ImNamespace = Exclude<HostKind, 'playground'>`，键面向以后的 Discord/WhatsApp/Slack，不写 Telegram 专用类型。
- `ImConnectionState` 用可辨识联合表达 `disabled | connected | network_error | config_error`；`reason` 只允许出现在 `config_error`（`unauthorized`、`conflict`、`token_unreadable`），`since` 为进入当前状态的 ISO 时间，`bot` 为 `{ id: string; username: string | null }`（id 保持字符串，不做 number 转换）。
- `ImConnectionRegistry` 只在内存保存状态：未登记的 namespace 视为 `disabled`；`isReady()` 要求已有身份且状态为 `connected` 或 `network_error`。

### 身份与 transport 间接层（§4.4）

新增 `src/adapters/local-monolith/telegram-instance.ts`：

- `TelegramInstanceHolder` 持有当前实例（api / bot / token / me）以及该实例的 grammY transport；设置 `undefined` 立即停止转发。
- `forwardingTelegramTransport()` 每次调用读取当前实例；没有实例时抛 `TelegramUnavailableError`。
- `ForwardingTelegramMedia` 下载时读取当前实例；没有实例时按现有 Playground-only 文案拒绝：`this process has no Telegram media transport`。
- `TelegramConnectionIdentity` 用 getter 暴露 `id` / `displayName` / `username`，没有实例时回退到 `0n` / `PLAYGROUND_BOT_DISPLAY_NAME` / `null`。

`createTelegramHost` 现在每个进程只构造一次，transport 转发到当前实例。`telegram-host.ts` 的失败分类拆到 `telegram-host-failures.ts`（同时满足 5,000 token 限制），并新增：

```text
telegram_unavailable / permanent / outcomeUnknown: false
```

`runtime-host-serve.ts`：

- `openServeEnvironment` 创建唯一 registry（初始全部 `disabled`）。
- `startServeServices` 固定 `servedHosts = ['telegram', 'playground']`，并用 `isHostReady` 回答「现在能不能执行该 host 的工作」。
- 成功拿到 `getMe()` 后写入 `connected` 与 bot id/username；没有 token 或 Playground-only 时保持 `disabled`。
- `TelegramMediaClient` 换成转发器，MCP 总是构造，StickerService 仍只在实例存在时构造、`sync()` 并 `start()`。

`runtime-host-serve-run.ts`：

- `createCoreRuntime` 的 `hosts` 固定包含两个 host，`bot` 传入身份持有者。
- `createTelegramHost` 总是构造；`runServeLoop` 在没有实例时进入新的 `telegram-disabled` idle 分支，不再尝试 `bot.start()`。
- 面板的 `mediaDownloader` 总是注入（无实例时由转发器拒绝）；`mcpManager` 不再可选。

### Scheduler 放行（§4.5）

新增 `src/orchestration/host-scope.ts`，把「进程静态 host 范围」与「实时就绪」合成为每次查询都重新求值的 SQL 谓词：

- `activeHosts()`：`hosts` 缺省表示全部 host，再按 `isHostReady` 过滤；
- `conversationsOfHosts()`：返回 conversations 子查询，全部 ready 时为 `1 = 1`，一个都没有时为 `1 = 0`。

`InvocationQueueService`、`scheduler-loop.ts` 的 `servedConversations`、`nextDelayMilliseconds`、`launchQueued` 都改走这个谓词。效果：

- Telegram 未就绪时，due bucket 不转 invocation、queued invocation 不启动、recovery 不碰它的 running/queued 行、sleep 跳过与 receipt 失效检查也不触碰它；
- Playground 不受影响；
- 没有每轮重建 Scheduler，也没有把 host 从集合里拿掉。

### 定时任务与图片挂起（§4.6）

- `BucketScheduler` / `InvocationQueueService` 增加可选 `isHostReady`（缺省 `everyHostReady`），生产装配传入 registry 判定。
- `LongTaskService.processDue` 仍按固定 host 集合完成计时；receipt 是否 claim 由 `processReceiptsDue` 的 served 谓词决定，所以 Telegram 未就绪时 timer 正常 `completed`，receipt 留 `pending`，不排 invocation。
- `generationEligibilityForHosts(store, hosts, isHostReady)` 改为每次查询实际 host 与就绪状态；没有实例时 Telegram 会话的图片生成不执行、留在队列。Admin actor 仍恒可执行。

## 关键决策与和交接文档的出入

1. **身份用「持有者 + getter」而不是 getter 函数。** `AgentRuntimeOptions.bot` 的形状保持 `{ id, displayName, username }`，但生产装配传的是 `TelegramConnectionIdentity` 实例，每次属性访问读当前实例。这样 `AgentRuntime`、`ProactiveReplyGate`、send 记录、参与判定都自然拿到当前值，也不需要改动大量测试构造点。符合 §4.4「getter/持有者」的要求。
2. **Playground 显示名只在装配时求值一次。** 有 Telegram 身份时沿用 `first_name + last_name`，否则用 `PLAYGROUND_BOT_DISPLAY_NAME`。身份在运行中变化后，已构造的房间 host 名称不会追改；交接文档明确「按现有逻辑走，不额外处理」，U2 也没有身份迁移。
3. **Sticker 的「没有时 stop()」在本单元表现为不构造。** U2 没有运行中启停，因此不存在「曾经启动、随后没有实例」的窗口；没有实例时 `state.stickers` 为空、搜索能力不注册。实例存在时仍 `sync()` + `start()`。实例切换时调用 `stop()` 的路径由 U3 的连接管理器迁移接入。
4. **`servedHosts` 固定带来一个可观察变化：Playground-only 进程的 Telegram 定时器现在会到点完成。** 这是 §4.6 的明确要求（计时照常，receipt 留 pending）。因此同步更新了 `test/playground-only.test.ts` 的两条最终落盘断言（`long_tasks = completed`、receipt 数量 1 且 `pending`）；其余「不 recovery、不 expire、不启动、不跳过」断言保持不变。U3 会按计划把该套件改写成「Telegram 停用时的 serve」。
5. **`runServeLoop` 增加 `telegram-disabled` 模式。** U1 之后「无 token」已是合法配置，但旧 `serve` 在非 Playground-only 且无 Bot 时会解引用 `undefined`。U2 在没有实例时等待 `idle`，日志 `mode: 'telegram-disabled'`；`--playground-only` 仍保留原日志值，直到 U3 删除该参数。
6. **面板媒体下载器在 Playground-only 下也注入。** 以前该模式省略下载器；现在统一注入转发器，无实例时按要求返回 `this process has no Telegram media transport`。
7. **`telegram_unavailable` 的语义**：`permanent` + `outcomeUnknown: false`，明确表示什么都没有发出去，避免调用方把它当成可能已送达。
8. **未产生 `token_unreadable`。** registry 支持该原因码，但本单元仍是旧的一次性启动：token 解析失败会让启动失败（U3 的连接管理器负责把它变成 `config_error`）。`unauthorized`、`conflict`、`network_error` 同样只有类型与判定，运行时生产者留给 U3。
9. **没有新增表、迁移或配置字段。** 连接状态按 §4.2 的推断只存在内存。

## 测试

新增 `test/telegram-connection-readiness.test.ts`（6 个用例）：

- Telegram 未就绪时 queued invocation 不启动、bucket/invocation 落盘仍是 `queued`；写入 `connected` 后唤醒并启动到 `completed`；
- 到期 Telegram timer 照常 `completed`，receipt 留 `pending`、不创建 invocation；就绪后 claim、启动、receipt 到 `handled`；
- Telegram 未就绪时 Playground room Release 仍正常启动；
- 图片资格：未就绪的 Telegram 会话不可执行，Playground 与 admin actor 可执行；就绪后 Telegram 变为可执行；
- registry 的默认 `disabled`、`config_error` 不就绪、`network_error` 有身份时就绪、回到 `disabled` 不就绪；
- 无实例时转发 host 返回 `permanent / telegram_unavailable`、媒体下载返回指定文案；设置实例后发送成功、身份 getter 读到新值；再次清空后重新拒绝。
