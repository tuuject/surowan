## 警告文案

`warning-card.tsx` 加了 `telegram_network_error`、`telegram_config_error` 的标题、正文与动作。`telegram_config_error` 按 `variables.reason` 选模板；未知 reason 回退到通用「Telegram 配置异常」。

| 情况 | 中文 | 英文 |
| --- | --- | --- |
| 网络异常 | 未能成功连接 Telegram 服务器 | Could not connect to the Telegram server |
| 配置异常 / `unauthorized` | 你的 Telegram Token 已被吊销或无效 | Your Telegram token has been revoked or is invalid |
| 配置异常 / `conflict` | 这个 Telegram Token 正在被其他程序使用 | This Telegram token is already in use by another program |
| 配置异常 / `token_unreadable` | 无法读取 Telegram Token | The Telegram token could not be read |
| 配置异常 / 未知 reason | Telegram 配置异常 | Telegram configuration error |

正文（提示下一步操作）：

- 网络异常：Bot 会持续重试；Telegram 恢复可达后会自动重连。
- `unauthorized`：请到 Telegram 页换一个 @BotFather 提供的有效 Bot Token。
- `conflict`：另一个进程正在用这个 Token 收消息。请停掉它，或换一个 Token。
- `token_unreadable`：配置的 Token 来源无法解析。请检查 key.json、环境变量或命令。

四句中文由 `apps/admin-next/src/lib/i18n.test.ts` 直接断言，防止后续改动走样。severity 沿用 U5：网络异常 `warning`，配置异常 `critical`。

## 必须报告的失败（不在 U6 范围）

完整 e2e 唯一的失败：

- 用例：`apps/admin-next/e2e/04-writes.e2e.ts` › `configuration file` › `applies the config file from the settings page`
- 断言：`after.restart_required` 应包含 `admin.port`，实际为 `[]`。
- 单独运行 `pnpm run admin:test:e2e 04-writes` 同样失败（9 通过、1 失败），不是并行或本单元新增页面造成的。

原因追溯：

- e2e fixture 把 `admin.port` 写在文件里（`1`），加载后再把运行态改写成 `0`，用来制造「文件端口与运行进程不同、需要重启」的场景。
- U1 的 `c0eb7a9 Make telegram config optional and admin required` 把 `assembleRawConfig` 的 `admin` 从共享引用改成了 `{ ...fileConfig.admin, enabled: ... }`。于是 `e2e/server-config.ts` 里的 `adminConfig.port = 0` 不再同时改写 `loaded.fileConfig.admin.port`；`ConfigReloader` 的 `activeFile` 克隆自 `fileConfig`，仍是 `1`，与磁盘文件没有差异，`restart_required` 自然为空。
- 这属于 U1 引起的 e2e fixture 语义漂移，不涉及 U6 的前端或 Telegram 端点。按 §9「e2e 失败原因不在本单元范围」未擅自修改。

建议单独修：在 `apps/admin-next/e2e/server-config.ts` 的 `loadConfig` 之后同时把 `loaded.fileConfig.admin.port` 设为 `0`，让「运行态覆盖」同时反映在 reloader 的 active file 上；或改由测试显式构造 active file。两种做法都需要另立单元确认，不属于 U6。

## 与文档的出入

1. §4.9 只要求「看板或侧边栏」二选一；本单元选了概览页「Bot 状态」卡片，没有在侧边栏重复状态查询。
2. e2e server 原本没有连接登记处。为了让页面与警告能呈现非 `disabled` 状态，新增了 test-only 的 `POST /__e2e/telegram-connection`；生产代码与端点未变。
3. 交接没有规定轮询周期；`telegramQuery` 采用与警告摘要一致的 10 秒。
4. 英文文案为自拟；中文四句原样实现。通用 `telegram_config_error` 标题/正文用于未知 reason，交接未规定。
5. 页面只编辑 Token，没有把 `telegram.process_bot_messages`、`bucket_window_seconds`、`participation` 等字段塞进本页，与 U5 端点契约一致。

## 剩余不确定项

- 完整 e2e 的 `04-writes` 既有失败留给后续单元；U6 指定与新页面相关套件全部通过。
- 未做真实 Telegram 人工验收：写入有效/无效 Token 后页面的状态轮询、清空后警告消失、401/409 的端到端表现仍需要真实凭据。
- 中文界面文案只由 i18n 单测断言精确字符串，e2e 在英文 locale 下运行；这是现有 e2e 的固定语言策略。
