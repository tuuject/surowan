## 本单元范围

按 §7 的 U3：

- §4.3 Telegram 连接管理器（token 三态、`getMe` 重试、运行时启停、迁移表、运行时 401/409、`getUpdates` 网络异常观察）；
- §4.5 停止流程（Scheduler 停止放行、停止长轮询与 activity、事务性作废、中断运行中 invocation、宽限等待、停 Sticker、清空身份/transport、更新连接状态）；
- §4.5 receipt：排队 invocation 的 claim 退回 `pending`，运行中 invocation 的 claim 最终也回 `pending`；
- §4.10 删除 `--playground-only`、`runServeLoop` 统一等 `idle`、`serve_started` 改用连接状态、useless 规则；
- §4.5 配置发布通知：`ConfigReloader` 在发布时把 token 源交给管理器。

运行时限量补拉（§4.7）仍属于 U4；本单元只保留调用点（见下文第 2 点）。

## 主要变更

### 连接管理器（§4.3）

新增 6 个模块，按职责拆分（同时满足单文件 5,000 token 的上限）：

| 文件 | 职责 |
| --- | --- |
| `telegram-connection-token.ts` | `telegram.token` 的三种解析结果（停用 / 取不到 / 明文）、`isTelegramDisabled`、发布用的 token 身份摘要 |
| `telegram-connection.ts` | 管理器：请求串行化、迁移表、重试循环、stop 流程的调度、连接状态发布、shutdown |
| `telegram-connection-connect.ts` | 一次完整的连接尝试：`getMe`、命令注册、`deleteWebhook`、ingestion/holder、Sticker、补拉钩子、长轮询启动 |
| `telegram-connection-polling.ts` | 单个实例的长轮询观察（`getUpdates` transformer）与之后的流重启 |
| `telegram-connection-stop.ts` | 停止时的事务性作废、运行中 invocation 的等待、receipt 回退 |
| `telegram-connection-support.ts` | 就绪闸门、共享类型、时间/状态小工具 |

行为要点：

- **输入三态**：没有 `telegram.token` 是停用；`SecretStore.resolve` 抛 `SecretResolutionError`（环境变量没设、jar 无此项、命令失败、解析为空串）是 `config_error / token_unreadable`；其余是明文 token。
- **启动流程**：新建 grammY `Bot` → 循环 `getMe`；401 进入 `config_error / unauthorized`，409 进入 `conflict`，网络错误、5xx、429 进入 `network_error` 并按指数退避重试（1s 起，最长 60s；429 优先用 `retry_after`，同样封顶 60s）。成功后设置 `bot.botInfo`（避免 grammY 自己再走一次可能无限重试的 `getMe`）、注册命令、`deleteWebhook`（冷启动首连才 `drop_pending_updates`）、用新身份构造 `TelegramIngestion`、写入 `TelegramInstanceHolder`、启动 Sticker、执行补拉钩子、发布 `connected`、后台启动长轮询。
- **不再阻塞 serve**：`bot.start()` 的 promise 由 poller 持有；serve 只等 `idle`。
- **运行时错误**：`bot.start()` 因 401/409 reject 时，通过管理器的请求队列走 `config_error` + 停止流程，异常不会冒到 serve，进程不退出。其它无法归因的 reject 标记网络异常并重启轮询。
- **网络异常感知**：`bot.api.config.use(transformer)` 观察 `getUpdates`；非 401/409 失败标记 `network_error`（保留身份，Scheduler 照常放行），下一次成功回到 `connected`。grammY 自己的重试循环没有被替换。
- **迁移表**（全部有测试）：

| 当前 | 新 token | 动作 |
| --- | --- | --- |
| 运行中 | 相同明文 | 不动（不新建 Bot、不停止轮询） |
| 运行中 | 另一个明文 | 走 stop 流程 → 用新 token 启动 |
| 运行中 | 空 | stop → `disabled` |
| 运行中 | 取不到 | stop → `config_error / token_unreadable` |
| 停用 / 配置异常 | 明文 | 启动流程 |
| 停用 / 配置异常 | 空 / 取不到 | 只更新状态（相同状态不重置 `since`） |

- **一次一个迁移**：请求按队列串行；新请求先 abort 当前请求的 controller（中断 `getMe` 退避与补拉），再按最新 token 执行。token 相同按解析后的明文比较。
- **发布立即返回**：`applyToken` 返回 `void`，配置 HTTP 请求只完成文件写入与发布。
- **日志脱敏**：管理器把每个 token 注册进 `SecretStore`，所有错误消息经 `redact`；有测试断言日志中不出现明文。
- **冷启动**：连不上不阻止 serve；Scheduler 不等 `getMe`；首次尝试失败后 `start()` 立即返回，补拉推迟到后续重试连上时按运行时处理。`app_state.telegram_initialized` 在有任意一次成功连接时写入，但只有冷启动首次尝试成功时才丢弃积压。
- **就绪闸门**：`TelegramReadiness` 在 `ImConnectionRegistry` 之外增加「迁移进行中」状态。a → b 的停止与启动之间，Scheduler 与图片资格都不能放行 Telegram 工作；网络异常但有实例时仍然就绪。

### 停止流程（§4.5）

`TelegramConnectionManager.#stopInstance` 顺序固定：

1. 请求入队时即进入迁移状态，`TelegramReadiness.isReady()` 为 false；
2. `poller.stop()`：`bot.stop()`（吞掉 offset 确认请求的 rejection，最多等 5s）并等待轮询 promise；`stopActivity()` 停掉全部 typing；
3. `abandonTelegramWork()` 在**一个 immediate 事务**里，只针对 `host_kind = 'telegram'`：
   - `collecting`、`queued` 的 Bucket 和「已 attach 到 running invocation、未注入」的 Bucket → `expired`，`error_code = 'telegram_stopped'`；
   - 排队 invocation claim 着的 receipt → `pending`（清 `invocation_id`、`bucket_id`、`claimed_at`、`handled_at`、outcome/completion 字段、cancellation 字段）；
   - 排队 invocation → `aborted`，`completion_reason = 'telegram_stopped'`；
4. 查询所有 running 的 Telegram invocation，`scheduler.abortInvocations(ids, 'telegram_stopped')`；
5. 宽限等待（默认 10s，可注入）这些 invocation 落到终态；超时只记 `telegram_invocation_stop_timeout`。等待可被新 token 的 abort 提前结束；
6. `restoreAbandonedReceipts()`：这些 invocation 的 receipt（`claimed` / `handled` / `suppressed`）全部回到 `pending` 并清空链接字段；它们打开或附着的 Bucket 若已终态且没有原因码，补写 `telegram_stopped`；
7. 停 Sticker、清空 `TelegramInstanceHolder`；状态由调用方在此之前发布。

`shutdown()` 只停长轮询、Sticker、activity 与持有者，**不**作废数据库工作：进程重启由既有 recovery 负责，若在这里作废会让重启丢掉本可恢复的队列。

### receipt 状态机（交付报告要求说明）

现状：`executeInvocation` 在运行结束时把该 invocation 的 claimed receipt 写成 `handled`（`invocation_outcome` 为 abort 原因）；`releaseUninjectedBuckets` 对已被作废的附着 Bucket 把 receipt 写成 `suppressed`。停止流程先作废附着 Bucket，使 release 变成 no-op 并把 receipt 留在 `claimed`，再在运行结束后统一把 `claimed` / `handled` / `suppressed` 三种状态改回 `pending`。

因此：

- 没有新增 receipt 状态，也没有新表/迁移；
- 排队 invocation 的 receipt 在同一个事务里直接回 `pending`，不会像面板「Cancel ongoing」那样变成 `suppressed`；
- 运行中 invocation 的 receipt 在 abort 落盘之后（或宽限超时之后）回 `pending`。若 run 在宽限内没有落盘，receipt 仍然先回 `pending`；之后 `executeInvocation` 的写回条件已经是 `claimed`，不会覆盖它。

### 配置发布（§4.5）

- `ConfigReloaderOptions` 新增可选 `telegramConfig` prepare/publish 网关；`applyFile` 在发布配置的同一同步段里调用 `publish(source)`。
- `prepare` 只解析 token，**不会**让取不到 token 的 apply 失败（这与 image gateway 不同，也是交接要求的语义）。
- 发布身份用 `telegramTokenIdentity`（disabled / unreadable / token 的 SHA-256 前缀）参与「是否有变化」的判断，所以只改 key jar、不改配置文件也会重新发布。明文不落日志。

### 修正：`telegram.token` 的 SecretRef 原本不是原子热字段

交接 §4.1 声明 token 是热字段，但 `config-diff` 会把 `SecretRef` 当普通对象逐字段合并：`{jar:'a'}` → `{jar:'b'}` 被报成 `telegram.token.jar` 的 restart 变更，候选配置保留旧 token。这会让 a → b 迁移根本收不到新 token。

处理：`mergeTelegram` 把 `token` 当原子值：出现/删除/替换整个引用都记为 `telegram.token` 的 hot 变更，候选配置取文件里的完整 SecretRef。新增 `test/config-telegram-optional.test.ts` 的旋转用例与 `test/config-reload-telegram-token.test.ts` 覆盖。**这是对 U1 范围代码的修正**，review 时请重点看。

### serve、CLI 与 useless 规则（§4.10）

- 删除 `--playground-only`：`cli-options.ts`、`cli.ts`、`ServeOptions`、`ServeContext`、`runtime-host*.ts`、`src/image/bridge.ts` 注释中的分支与用法字符串全部移除，无兼容别名。
- `runServeLoop` 统一 `await idle`；`serve_started` 的 `mode` 改为初始连接状态（`disabled` / `connected` / `network_error` / `config_error`），`config_error` 时附 `reason`，`bot_id` 取自当前实例。
- useless 规则在 `serve()` 打开 store/lock 之前判断：`isTelegramDisabled(config) && admin.enabled === false` 抛 `Surowan is useless if neither admin panel is enabled nor telegram is configured`，CLI 以 1 退出。配置异常/网络异常不触发；`check-config` 未改动。
- `openServeEnvironment` 不再解析 token；token 解析失败不再阻止 takeover/启动。
- Playground 房间的显示名改为读取实时 `TelegramConnectionIdentity`（连接可能在房间宿主构造之后建立）。此前 U2 在装配时冻结名称；因为连接现在异步，冻结会让混合部署永远显示 `Playground Bot`。身份变化后的既有房间行为按 §4.4 的「按现有逻辑走」处理。
- `HostToolingOptions.stickers` 改为 getter：实例停止时不提供 `search_stickers`（与旧 Playground-only 一致），实例恢复后无需重建工具装配即可提供。
- `test/playground-only.test.ts`、`test/playground-only-serve.test.ts` 改写为「Telegram 停用时的 serve」，文件名保留。serve 套件改用 stop-request 文件收尾，不再依赖 Windows 上不稳定的 SIGTERM；新增 useless 规则与「token 取不到不触发 useless」用例。

## 关键决策与和交接文档的出入

1. **拆成 6 个模块**：管理器、连接尝试、轮询、停止事务、支撑类型、token 各自成文件，均在 20KB 以内；没有为拆文件引入新的抽象层。
2. **运行时补拉只留调用点**：`TelegramConnectionHooks.runtimeCatchUp` 已定义并由连接流程调用，但生产组合根在本单元不传它，所以 a → b 与「停用/配置异常 → 正常」暂时没有补拉。U4 填充即可，不需要改管理器。冷启动补拉仍由组合根提供，且在 `scheduler.start()` 之前完成（与旧行为一致）。
3. **宽限超时不强制终结 invocation**：超时只记日志并按上文回退 receipt；若某个 run 连 abort 都不响应，它的 invocation 行会保持 `running`（与现有 `/pause`、面板 Cancel 的语义一致），不会被本单元强行改写。若 U4 认为需要强制终结，应单独决定。
4. **`telegram_initialized` 的语义**：任何一次成功连接都会写入，只有冷启动的首次尝试才丢弃积压。若首次冷启动一直失败、后来以运行时方式连上，下一次进程启动不会再丢积压。
5. **非 401/409 的 4xx 归为 `unauthorized`**：Telegram 明确拒绝了这次调用（不是网络、不是限流），重试无意义；连接状态的 reason 词汇里只有 `unauthorized` 能表达「token/配置不被接受」。
6. **取不到 token 的判定**：任何 `SecretResolutionError`（包括 SecretRef 解析出空串）都是 `token_unreadable`；「空 token = 停用」只表示配置里没有 `token` 字段，与 §4.1 一致。
7. **`bot.stop()` 的 offset 确认有 5s 上限**：dead network 下它默认可能挂 500s。极端情况下确认请求没完成就开始新连接，可能触发 409 → 连接管理器会如实报 `conflict`。
8. **停止流程使用独立的原因码 `telegram_stopped`**，不修改 `invocations` / `buckets` 的既有状态集合。
9. **Playground 显示名走实时身份**（见上），与 U2 的「装配时冻结」不同；这是异步连接带来的必要调整，交接 §4.4 允许按现有逻辑处理。
10. **没有新增表、迁移或配置字段**；连接状态仍然只在内存。

## 未执行的检查

真实 Telegram 验收（需要人工）：

- 面板/配置换 token：旧实例停止、新 token 实例启动、旧队列不投递给新 bot；
- 吊销 token：运行中进入 `config_error / unauthorized`，进程不退出，面板显示原因；
- 同一个 token 开两个进程制造 409：第二个进程进入 `config_error / conflict`，不退出；
- 断网后恢复：进入 `network_error`、Scheduler 继续放行、恢复后自动回到 `connected`；
- 冷启动时断网：serve 正常启动、面板可用、连上后按运行时语义继续。

## 剩余不确定项

- U4 需要决定运行时补拉的收尾是否复用 `finishStartupCatchUp`；本单元只留了钩子，没有改变冷启动补拉语义。
- 宽限超时后仍 `running` 的 invocation 会阻塞该 Conversation 的下一个 invocation，直到它落盘或进程重启。当前与既有 abort 路径一致，未在本单元加入强制终结。
- 若 `bot.stop()` 的 offset 确认在 5s 内没有完成，紧接着的新连接可能拿到 409 并被报成 `conflict`。真实网络验收时应关注这一极端路径。
