## 端点契约

### `GET /api/telegram`

仅面板 Session（程序化 API key 落到既有 403 规则）。读**磁盘上的** `config.jsonc`：

```json
{
  "revision": "<config.jsonc 原始字节的 SHA-256>",
  "status": {
    "status": "connected",
    "since": "2026-10-25T00:00:00.000Z",
    "bot": { "id": "42", "username": "surowan_bot" }
  },
  "telegram_section_present": true,
  "token_configured": true
}
```

- `status` 直接来自 `ImConnectionRegistry`：`disabled` / `connected` / `network_error` / `config_error`；只有 `config_error` 带 `reason`（`unauthorized` / `conflict` / `token_unreadable`），连接过时带 `bot`。
- `telegram_section_present` 与 `token_configured` 读的是文件层；`token_configured` 永远是布尔值，不说明 SecretRef 是 jar、env 还是 command，也不回显任何值。
- `ConfigReloader` 未接线时返回 503 `config_reload_unavailable`。

### `PUT /api/telegram`

body 只接受 `{ "token": string | null }`：

- 字符串：写 key jar，`config.jsonc` 只保留 `{ jar }`；明文在写文件前 `SecretStore.remember`，供后续错误与日志脱敏。
- `null`：删除 `telegram.token`；`writeConfigEdits` 回收新文件不再引用的 jar 条目。token 本来就缺失时幂等返回 200，不重写文件。
- `telegram` 段缺失：由 `config-file.ts` 的通用建段逻辑按 `TELEGRAM_DEFAULTS` 创建（`process_bot_messages: false`、`bucket_window_seconds: 15`、`chats: []`），再写入 token。
- 只改 token；不碰 Chats、`admins`、`participation` 等其它 `telegram.*` 字段，也不提供删除整段的写法。
- `If-Match` 规则与其它配置写端点一致：缺失 400 `revision_required`，过期 409 `config_conflict`；body 不合法 400 `invalid_body`。
- 成功响应：

```json
{
  "revision": "<写入后的 revision>",
  "status": { "status": "disabled", "since": "..." },
  "telegram_section_present": true,
  "token_configured": true,
  "apply": { "applied": ["telegram.token"], "restart_required": [], "outside_serve": [] }
}
```

- 失败响应 `{ error, message }`，状态码沿用 `CONFIG_WRITE_STATUS`（未知码回退 409）。message 经 `SecretStore.redact`；revision 冲突、`config_invalid` 与 reload 日志都不出现明文。
- 写入经 `ConfigReloader` 原子应用；`telegramConfig.publish` 只把新 token 源交给连接管理器，HTTP 响应不等 `getMe`（与 §4.3 一致）。

### 警告

- `telegram_network_error`：`category: runtime`、`severity: warning`、`variables: {}`；连接状态为 `network_error` 时存在。
- `telegram_config_error`：`category: runtime`、`severity: critical`、`variables: { reason }`；连接状态为 `config_error` 时存在。
- `disabled`、`connected` 都不产生 Telegram 警告；警告没有 `id`，不能标为已读，状态解除后下一次读取自然消失。
- 中文/英文模板与 locale 属于 U6；本单元只保证 `code` 与 `reason` 足以区分四种情况。

## 决策与和交接文档的出入

1. **`severity` 分配**：交接只规定 category 用 `runtime`。这里把网络异常定为 `warning`（实例仍在重试，面板可继续工作），配置异常定为 `critical`（token 不可用，必须人工处理）。前端模板会按 severity 选择图标/色调。
2. **`GET /telegram` 的 token 与 revision 来自文件，状态来自内存**：面板编辑的是文件，所以手改但未 apply 的 token 会先反映在 `token_configured`，`status` 仍是当前进程的连接状态。没有把两者混成一个「实际生效」字段。
3. **PUT 只接受 token**：交接把「其它 `telegram.*` 字段是否一起编辑」交给现有页面覆盖情况决定。目前面板没有 Telegram 页面，也没有任何现有端点编辑 `telegram.process_bot_messages` / `bucket_window_seconds` / `participation` / `sticker_*`，因此本端点严格只收 `{ token }`，多带字段返回 400 `invalid_body`，避免静默忽略。U6 若需要这些字段，应另立端点。
4. **`null` 清空是幂等的**：token 已缺失时返回 200 与空 `apply.applied`，而不是让 `jsonc-parser` 以「edit changed nothing」失败。
5. **token 输入校验**（推断）：拒绝空串、超过 4096 字符、含空白或控制字符的 token；Bot Token 不含这些字符，提前拒绝好过写进一个 Telegram 永远拒绝的合法配置。
6. **`connections` 在 `AdminServerOptions` 里可选**：大量既有测试与独立面板不构造连接管理器；缺省时 `createAdminRoutes` 建一个全 `disabled` 的登记处，语义与「没有连接」一致，不影响既有测试。
7. **`standingWarnings` 接收 `Pick<ImConnectionRegistry, 'get'>`**：交接示例是 `standingWarnings(config, connections, now)`；用窄接口而不是整个 registry，测试可以直接传快照对象。实际调用方仍传进程内唯一登记处。
8. **`warnings-admin` 与 Telegram 路由共享同一个登记处**：`admin-routes.ts` 解析一次 `options.connections ?? new ImConnectionRegistry()`，两条读路径不会出现一份快照、一份旧状态。

## 剩余不确定项

- `GET /telegram` 没有返回 `restart_required`；U6 若需要展示待重启字段，可复用 `GET /config/status`，或由 U6 决定是否在本响应补充（会改变端点契约）。
- 连接状态快照与文件 revision 来自不同来源。面板在「文件已改、尚未 apply」的窗口里看到「有 token」但状态仍是旧的；这是刻意区分，不是竞态。
- 端点只编辑 token。若产品后来希望面板编辑 `process_bot_messages`、`bucket_window_seconds` 或全局 `participation`，需要新增写端点并同步 `agent-doc/admin-panel.md` 白名单。
