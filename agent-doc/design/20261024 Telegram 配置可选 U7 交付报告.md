## 本单元范围

按 §4.11 与 §7 的 U7：

- 新命令 `admin-account` 取代 `admin-reset`，旧命令与用法字符串一并删除，不做兼容；
- `--username <name>` 必填，`--password-stdin` 沿用旧命令的读取方式，新增 `--revoke-passkeys`；
- `admin_users` 为空时建号（等同面板 setup，但不创建会话）；已有唯一管理员时改用户名与密码；多于一行直接报错；
- 每次执行注销该账号全部登录会话；只有显式传 `--revoke-passkeys` 才删除全部 passkey；
- 不触碰 `admin_api_keys`；
- 复用 `ServeLock.acquire` 拒绝在服务运行时执行；
- 在 `AdminAuth` 新增承载逻辑的方法，删除 `recoverCredentials`；
- 改写 `test/admin-recovery.test.ts`，同步 `test/admin-passkeys-service.test.ts` 里对已删除方法的调用。

没有新增依赖、没有新增表或迁移，也没有修改 PRD 与实施交接文档。

## 命令契约

```bash
node src/cli.ts admin-account --config <path> --username <name> [--password-stdin] [--revoke-passkeys]
```

| 项目 | 契约 |
| --- | --- |
| 命令 | `admin-account`；`admin-reset` 不再是合法命令，`parseCli` 直接报用法错误 |
| `--config <path>` | 必填 |
| `--username <name>` | 必填。3–32 位字母、数字、点、下划线或连字符（沿用 `AdminAuth` 的既有校验） |
| 密码 | 只从 TTY 隐藏提示（两次输入）或 `--password-stdin` 读取；不进入 argv，不写入日志，错误输出不带密码。stdin 上限 800 字节、10 秒超时，沿用旧命令的实现 |
| `--revoke-passkeys` | 可选。仅在 `admin-account` 上合法；重复出现会被拒绝 |
| 其他 flag | `--password-stdin`、`--revoke-passkeys`、`--username` 在其它命令上仍被拒绝，行为与旧命令的边界测试一致 |
| 成功输出 | stdout 单行 JSON：`{"status":"ok","username":"<新用户名>","created":true|false}` |
| 失败输出 | 沿用 `cli.ts` 的 `{"status":"error","error":"<message>"}`，进程退出码 1 |

stderr 在执行前打印一行摘要：会创建或改名账号、注销全部会话，并说明 passkey 将保留还是删除。摘要使用静态文案，插入的用户名不是秘密，密码永不出现在其中。

## 行为

`AdminAuth.createOrResetAccount(credentials, { revokePasskeys }, now)`（`src/ingress/admin/auth.ts`）：

1. `assertCredentials` 校验用户名与密码长度，与面板登录/建号同一套规则。
2. 读取 `admin_users`：多于一行时抛 `AdminAuthError(409, 'multiple_accounts', ...)`，不猜改哪一个；该检查在 Argon2 哈希之前做一次，在事务内再做一次。
3. 表为空：插入该用户，返回 `{ userId, created: true }`。不写 `admin_sessions`，因此面板 setup 不会重新开放；`last_login_at` 为 `NULL`（CLI 没有登录，见「与文档/推断的出入」）。
4. 表里恰好一行：把该行改成新的用户名与新的 Argon2id 密码，保留 `id`、`webauthn_user_id`、`created_at` 与 `last_login_at`，返回 `{ userId, created: false }`。
5. 改完（或建完）后删除该 `user_id` 的全部 `admin_sessions`。
6. 只有 `revokePasskeys === true` 时才删除该 `user_id` 的全部 `admin_passkeys`；默认保留，旧命令「每次清光 passkey」的语义已移除。
7. 不读写 `admin_api_keys`。
8. 事务使用 `behavior: 'immediate'`，与现有凭据写入保持一致。

CLI 层（`src/ingress/admin/admin-account.ts`，由 `src/ingress/admin/recover.ts` 重命名而来）保持旧命令的离线边界：

- `loadConfig` + `assertConfigPermissions`；
- 非 TTY 且没有 `--password-stdin` 时立即失败；
- `ServeLock.acquire(data_dir)` 先于读密码与打开数据库；锁被占用时报 `Another serve process holds ...` 并退出，不接管、不写入；
- 读密码 → `SqliteStore.open` → `new AdminAuth(store.orm, admin.session_ttl_hours ?? 168)` → `createOrResetAccount`；
- `finally` 中先关 store 再释放锁；密码读取失败或校验失败也会释放锁。

## 与文档 / 推断的出入

1. **命令名与多账号行为**：按 §6 推断 9 实现为 `admin-account`，多于一个管理员时退出码 1、错误码 `multiple_accounts`。交接没有规定错误码与 JSON 输出字段，属于本单元的补充。
2. **成功输出多了 `created`**：新字段用于区分「建号」与「重置」，不影响旧脚本读取 `status`/`username`。旧命令的 stdout 只有 `status` 与 `username`。
3. **建号不写 `last_login_at`**：面板 `POST /auth/setup` 建号时会同时创建会话，因此写 `last_login_at`；CLI 按要求不创建会话，所以写 `NULL`。其余字段（`created_at`/`updated_at`/随机 `webauthn_user_id`）与 setup 一致。
4. **文件与方法改名**：`src/ingress/admin/recover.ts` → `admin-account.ts`，`recoverCredentials` → `createOrResetAccount`。这是清理式切换的落点；旧路径没有保留转发文件。
5. **测试文件名保留** `test/admin-recovery.test.ts`：§7 的验证列写了「改写后的 `admin-recovery` 测试」，因此沿用文件名，只改内容。
6. **stderr 摘要**：旧命令固定声称会删 passkey；新命令按是否传 `--revoke-passkeys` 分别写「deleted」或「kept」。摘要里出现用户名，但不出现密码。

## 剩余不确定项

- 真实 TTY 的双次密码提示没有自动化测试（旧命令同样只测了 stdin 路径）；本次验证覆盖了非 TTY、超时、超长与正常 stdin。
- 没有在真实部署上验证「服务运行时拒绝执行」——测试用 `ServeLock.acquire` 模拟占锁进程，与 `serve` 实际持锁是同一个互斥文件。
- 多管理员场景按 PRD 直接失败，没有自动合并或删除多余账号的恢复路径；`admin_users` 的 `username` 唯一约束已在 schema 中，无需迁移。
- 完整测试的 2 个 Windows 基线失败（`doc-spaces` symlink `EPERM`、`playground-scheduler` 的 `afterAll` 清理超时）不在本单元范围，未修复。
