## 本单元范围

按 §7 的 U4：

- §4.7 运行时限量补拉：停用/配置异常 → 正常，以及 a → b 切换到 b 时触发；
- 整条 bot-wide `getUpdates` 流分页取完，按 Chat 只保留最新 100 条 message；
- `/pause`、`/resume` 按原 update 顺序执行；
- 与 Scheduler 并发时不重复排 invocation；
- 补拉可被 U3 的 AbortSignal 中断；
- 冷启动补拉与 Scheduler 启动顺序保持不变。

### 运行时补拉流程

1. `startedAt = now()`；以 `limit: 100, timeout: 0` 分页调用 `getUpdates`（第一页带 `allowed_updates`，与冷启动一致），直到空页；每一页前后、以及每条 ingest 前后检查 AbortSignal。
2. 全部 update 先留在内存。按 `chat.id` 分组 `message` update，每组只保留最新 100 条；随后按原 update 顺序逐条调用 `ingestion.ingestCatchUp`。
3. 命令和冷启动完全同路：`ingestCatchUp` 返回的 `/pause`、`/resume` 立即按顺序 `commands.run`；其它命令只审计、不执行。
4. 收尾在**一个事务**里把本次补拉窗口（`received_at >= startedAt`）内、尚未进入任何 Bucket 的 Telegram 消息变成每 Conversation 一个 `startup_catch_up` Bucket，并走与冷启动相同的门槛（chat 被删、agent 未配齐、`/pause`、sleeping、participation、proactive reply）。最多取每 Conversation `agent.history_messages` 条，与冷启动一致。
5. `scheduler.finishRuntimeCatchUp(...)` 之后 `wake()`；连接流程继续 `publish connected`、安装 handler、启动长轮询。
6. 完成/中断分别记录 `runtime_catch_up_completed`（updates / retained / dropped / stored_messages / invocations）与 `runtime_catch_up_aborted`（updates / stored_messages）。

### Update 类型处理策略（§4.7 留给实现决定的部分）

| 类型 | 处理 |
| --- | --- |
| `message`（普通消息） | 以 `chat.id` 为单位只保留最新 100 条；更早的在 ingest 之前丢弃 |
| `message`（Bot 命令） | **不计入 100 条上限，总是保留**。命令是状态变更而不是上下文，不能被繁忙群聊挤出窗口；仍按原 update 顺序执行 |
| `edited_message` | 仅当被编辑的原消息也在这 100 条窗口内才保留；否则丢弃。否则会给一条从未保留的消息凭空建 revision |
| `my_chat_member` 及其它 update | 不设上限，全部交给 ingestion。`my_chat_member` 是迁移授权所必需；其它类型量小且 ingestion 已有拒绝/审计路径 |

被丢弃的 update **不会写入 `telegram_updates`**：如果写入，ingestion 的 update_id 去重会让 Telegram 之后合法重发的同一条 update 永远被当成重复。丢弃量只出现在 `runtime_catch_up_completed.dropped` 审计字段里。

### 与 Scheduler 并发

- 补拉发生在 U3 迁移的 `beginTransition` 期间，`TelegramReadiness` 不放行 Telegram 工作；收尾事务提交后，Scheduler 也只会看到 `queued` 的 invocation，不会为同一个 Bucket 再排一次。
- 冷启动的 `finishStartupCatchUpQueue` 仍然只看自己的 marker，运行时不写也不删 `telegram_startup_catch_up`。
- 运行时的选择额外要求「消息不在任何 Bucket 中」，防止同一 backlog 被重发时重复物化。
- 新增 `onSettled`：迁移结束、就绪闸门打开时唤醒 Scheduler。否则补拉在闸门内提交的 invocation 要等 Scheduler 最长的 60 秒轮询；这也是 U3 的一次小修正（见「和交接文档的出入」）。

### 中断与失败

- AbortSignal 来自 U3 的迁移请求 controller：新 token、进程关停都会 interrupt。分页之间和每条 ingest 之前检查；不额外中断已经在飞的 `getUpdates`（冷启动同样如此；运行时页面用 `timeout: 0`，一次请求很快返回）。
- 中断时**不执行收尾**：已经 ingest 的消息留在库里作为会话历史，不产生 Bucket / invocation；不写任何 marker。下一次连接会重新拉到同一批 update（offset 未确认），ingestion 去重，不会重复执行命令。
- 非 abort 的失败（网络、DB）沿用 U3 的连接器语义：记 `telegram_catch_up_failed`，连接继续进入长轮询；长轮询自己的 401/409/网络感知仍由连接管理器接管。不会让 serve 退出。

## 和交接文档的出入 / 需要 review 的决定

1. **收尾复用而非完全新写**：§4.7 说「不能复用就新写一个只处理本次补拉 Bucket 的收尾函数」。`finishStartupCatchUpQueue` 的选择依赖冷启动 marker 与 Scheduler 启动前的时序，不能直接调用；但门槛逻辑（chat/agent/pause/sleep/participation/proactive）没有必要复制。做法是把「选中消息 → 建 Bucket」抽到 `catch-up.ts`，冷启动保留 marker 校验与清理、运行时走无 marker 的 `finishRuntimeCatchUpQueue`。冷启动的测试全部保持通过，语义未变。
2. **选择窗口用 `received_at >= startedAt`，不用消息 ID 列表或第二份 marker**：与冷启动一致，避免第二份进程状态；配合「不在任何 Bucket」保证重发幂等。代价见下文不确定项。
3. **命令不受 100 条限制**：§4.7 说限量只针对 message、命令处理方式自定。这里把命令当作「状态变更」，即使早于第 100 条也会执行。
4. **编辑必须依附被保留的原消息**：交接没有规定；不保留会凭空生成一条从未存在的消息。
5. **新增 `onSettled` 回调（改了 U3 的 `telegram-connection.ts`）**：运行时补拉在就绪闸门内提交工作，闸门打开后没有别的东西唤醒 Scheduler，最坏要等 60 秒。`#finish` 释放 `TelegramReadiness` 后回调组合根的 `state.scheduler?.wake()`。这是 U4 工作能被及时执行的必要接线，不是新的调度约定。
6. **hook 增加第 4 个参数 `me`**：运行时补拉需要 Bot username 才能正确识别 `/pause@ThisBot`。冷启动 hook 忽略该参数即可。
7. **冷启动连不上、后来才连上时走运行时路径**（§6 推断 2）：`#retryUntilConnected` 一直用 `coldStart: false`，因此延迟成功的冷启动连接会走 100 条限量补拉；`telegram_initialized` 的语义不变。

## 真实环境未执行的检查

- 停用 → 正常、a → b 切换后，Telegram 群里积压的最新 100 条是否进入下一次 catch-up invocation；
- 100 条上限在真实 backlog 上的内存占用与耗时（尤其跨多个群、每页 100 条）；
- 补拉过程中再次换 token、进程关停的中断是否及时（真实网络下 `getUpdates` 的在飞请求不会被主动取消）；
- 限流（429）恰好落在补拉阶段的恢复行为。

## 剩余不确定项

- **abort 后已 ingest 的消息不进入 catch-up Bucket**：它们作为消息留在库里，但本次补拉不建 Bucket；下一次补拉的选择窗口从新的 `startedAt` 起算，不会把它们补进 Bucket。U3 的中断冷启动补拉有同样性质（重发被 update_id 去重），本单元没有改变这一边界。若要求「中断也要保留已拉到的上下文」，需要把部分 drain 的结果也物化，和「取消迁移不产生旧 bot 工作」冲突，建议单独决定。
- **命令不受上限**带来的取舍：一个群里很旧的 `/pause` 仍会执行。交接把命令策略留给实现；如果 review 希望命令也受窗口约束，删除 `retainUpdates` 里的 `commandKeys` 分支即可。
- **100 条是「本次补拉存下的消息」上限**，不是「每个群历史上只有 100 条」。多次迁移会各自补拉一次，旧消息仍留在库里。
- `onSettled` 是对 U3 模块的小改动，review 时请确认「迁移一结束就唤醒 Scheduler」没有和 U3 的停止流程竞态：`#finish` 只在没有更新请求接管时调用，被接管时由新请求结束时调用。
