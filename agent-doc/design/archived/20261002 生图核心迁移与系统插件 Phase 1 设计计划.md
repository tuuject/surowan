# 生图核心迁移与系统插件 Phase 1 设计计划

记录日期：2026-10-02。阶段：需求范围已确认，实施尚未开始。

## 1. 最终范围与决策层级

目标：从现有独立图片生成项目提取核心，在 Plastic Wan 中提供内置 Image Generation 插件，以及同一 Admin Panel 内的工作台、生图审计、资产管理。用户使用生图能力不需要另装独立生图 Server 或应用。

### 用户已确认的要求

- Phase 1 只保留 Plastic Wan 一个宿主；废弃独立生图项目的主后端、管理员认证、Admin Panel 等产品壳，不承担两个产品并行维护。
- 生图功能作为 Plastic Wan 内置插件存在，复用现有宿主基础设施。
- Admin 侧栏提供 Image Generation 入口，下设「工作台」「生图审计」「资产管理」三个子页面。
- 三页的页面逻辑、区域布局和交互参考原生图 Admin；组件库、主题、导航、表单、弹窗、通知和请求状态管理以 Plastic Wan Admin 为准。
- 原有 Prompt 资产、图片参考、多图输出、解析预览、重试与复用等业务能力随三页承接；不能按此前的单图纯文生图裁剪方案实施。
- 生图供应商配置必须热加载，无需重启。沿用宿主应用配置流程；候选配置整体验证后生效，失败继续使用旧有效配置。
- 已提交任务保留模型与输入快照；执行中的轮次不切换凭据，后续轮次读取更新后的凭据。同名凭据的值轮换也必须生效。

### 本计划采用的实现建议

以下是基于源码评估形成的默认实施方向，不是用户逐项指定的 API 或目录命名：

- 核心放入 private workspace package；Phase 1 不对外发布 npm，但保持无 Plastic Wan import 的依赖边界。
- 共用 Plastic Wan 主数据库、连接生命周期和 migration 入口；核心直接使用 Drizzle，不新增通用 repository 框架。
- 原有 OpenRouter 图片适配器作为首个实现，不扩展多供应商通用框架，不把图片输出协议硬塞入 Pi 聊天模型注册表。
- 插件服务由进程组合根创建一次；复用长期任务和唯一 Scheduler，补齐图片 capability 引用与 `send` 图片分支。
- Admin 页面直接进入现有前端，不建立 `image-ui` package。

### 已被本次范围覆盖的早期提议

不再采用「Phase 1 不做生图后台」「暂缓资产管理和参考图」「只生成单张图片」「供应商配置重启生效」的裁剪。也不再要求每个迁移步骤都保持独立生图产品可运行。初次双宿主评估中的分库优先、跨仓库发布和旧 Host 兼容不是本期默认方案。

## 3. 必须带入实施的代码事实

- 原 HTTP 与 MCP 已直接调用同一组业务服务；核心生成链路没有接收 Fastify request/reply。拆分主要是收窄依赖和资源所有权，不需要重写生成算法。
- 原 `createCore()` 同时创建 Auth、Worker 并关闭配置 watcher 和数据库。原 `createImageService()` 仅指图片素材 CRUD，不是目标中的整个核心入口。
- 原模型 schema 的 provider 只有 OpenRouter；生产 endpoint 固定，客户端每次调用接收 model 和 credential。改模型或密钥不需要重建当前这种客户端。
- 原素材 DTO 含固定 HTTP `contentUrl`，Actor 为 `admin/apiKey`，来源为 `admin/http/mcp`；这些独立产品假设必须拆掉。
- 原配置依赖文件与全局 redactor，快照只是浅冻结，版本 hash 不反映同名密钥值变化；原 Worker 每个输出临执行才读取密钥，不是整轮固定。
- 原 Worker 的 generation 队列顺序执行，同一 generation 的输出项受并发限制。启动恢复会处理库中全部 running 任务；同一图片数据集合只允许一个 Worker 执行者。
- 原 Worker 关闭超时后仍可能有异步工作未结束，随后 core 直接关库；迁入宿主前必须处理晚到结果和释放后写入。
- 宿主 SQLite 开启 `defaultSafeIntegers(true)`。本次内存验证中，普通 Drizzle integer 列返回 bigint，原 `round + 1` 和直接 JSON 序列化会失败。
- 宿主插件当前只贡献 skills/capabilities；没有完整生命周期、动态 UI 注册或通用 service 容器。Alarm 是长期任务与 Admin 静态接入参考。
- 宿主 `send` 只发送文字/贴纸；`execute` 只输出有界文本和受限 refs，不能搬用原 MCP 的图片二进制响应。
- 当前仓库是 Node.js Telegram Bot + Admin Web，尚无已实现的 Desktop/Electron 宿主；本期不能把同进程运行等同于完成 Desktop 发布。

## 4. 目标边界与落点

```text
Plastic Wan Admin API ───────────────┐
Agent → execute → image plugin ─────┼→ image-service → OpenRouter / 原图文件
                  │                 │       │
                  └→ LongTaskService┘       └→ 图片领域表（同一个宿主 SQLite）
                         │
                    唯一 Scheduler → 完成回执 → 受限图片引用 → send
```

建议新增 `packages/image-service/`，包含领域 contracts、配置快照、素材、解析、generations、Worker、OpenRouter adapter、本地图片存储和 schema。建议插件位于 `src/plugins/image-generation/`，包含工具、任务桥接、权限映射、Admin handler 和只读 skills；前端位于 `apps/admin-next/src/pages/image-generation/` 并接入现有 routes。

依赖只能是宿主/插件 → 核心。核心不 import Plastic Wan、Telegram、Admin、HTTP/MCP Server，不自行读取宿主配置、env 或进程信号；可以保留 Node 文件操作、Sharp、SQLite 和上游 HTTP。HTTP 错误码、图片 URL、宿主身份映射由 adapter 提供，领域层保留明确的业务错误与不透明 owner 信息。

公共能力至少覆盖模型元数据、输入解析、生成创建/查询/列表/重试、Prompt 与图片资产管理、读取图片内容，以及 `start()` / `stop()` / `updateConfig()`。命名在实施时确定；不要把现有 core 的全部内部对象和原始连接直接公开。公共输入边界仍须校验，不能因为不再经过原 routes 就信任 TypeScript 类型。

保留本地图片存储实现，注入明确目录即可；不提前做 S3 adapter、repository 框架、配置事件总线或通用 DI 容器。按宿主 TypeBox 边界校验外部输入；核心已有校验可逐步收敛，但参数与引用规则只维护一份。

## 5. 数据库、所有权与数据安全

核心拥有图片领域的表定义与查询：Prompt 资产、图片资产、generation、attempt、幂等记录。宿主拥有数据库打开/关闭、升级 SQL、migration 调度、备份，以及 Conversation/Invocation/长期任务的关联。新表使用图片域命名；宿主 schema 聚合需要的核心定义，避免复制两份表定义。原管理员、Session、API Key 表不迁入。

- 使用现有主库和 Drizzle 同步查询，不启动第二个 migration runner，也不在 service 构造时自动开库或迁移。
- 新 migration 加入宿主 `src/store/migrations/`，依当前最新版本编号，不在本计划提前固定编号。借入的连接只能由宿主关闭。
- 图片资产的 UUID 可保留；宿主关联 ID 按 bigint 规则处理。宽高、字节数、round、itemIndex 等业务 number 在数据边界作安全范围校验与转换；不能全局关闭 safe integers 或对 Telegram ID 粗暴转 number。
- 提交 Agent 请求时，应能把长期任务、关联记录、generation 与幂等记录纳入同一明确事务。共用数据库不代表分散调用自动原子；需设计可组合的事务入口，网络调用与文件处理不放在长事务中，入队/唤醒在提交后发生。
- generation 与素材保存宿主可核验的来源/所有权关联；核心不理解 Telegram 角色，不允许让插件伪装成原来的 `admin` 来绕过检查。
- 原图库是全局库，不能原样授权给所有 Conversation。读取、列表、引用展开、重试和发送均检查范围；公开共享资产的策略未确认前，对 Agent 默认只开放明确授权资产。
- Admin 手动生成独立记录管理员身份；不伪造 Invocation 或 Conversation，不强制创建聊天长期任务。Agent 生成则关联真实调用和长期任务，两者在同一生图审计中可区分。
- 原图存入宿主 data directory 下专属目录，不混入临时媒体缓存。归档不删历史引用所需字节，不改写已经保存的快照。
- 文件落盘与 SQLite 提交不是原子操作，需处理失败留下的孤儿文件。备份覆盖数据库和原图，采用可核验的文件清单并验证恢复；原有仅主库备份流程不能直接算作完整交付。
- 旧独立项目数据导入尚未确认。保留旧数据，不为本期默认实现双向同步或旧库在线兼容；若要求导入，再设计一次性映射、快照和文件校验流程。

## 6. 供应商配置热加载

### 来源和最小实现

配置由 Plastic Wan 现有配置系统持有，可增加明确的图片配置段；Secret 使用现有 SecretRef/SecretStore，禁止另设 `models.json` / `key.json` 格式、watcher 或第二套通用 Provider 注册系统。图片输出模型的参数与能力保留为图片领域结构；聊天模型 `input: image` 只表示能理解图片，不等于可生成图片。

Phase 1 热加载至少覆盖凭据值与引用、可用模型、上游模型标识、Provider 路由标签、模型参数及能力限制。沿用现有「应用配置」入口，无需重启。当前适配器只有固定 OpenRouter 协议，不因热加载要求擅自扩展任意供应商 API。数据库/目录、执行器并发及服务启停可先保持重启生效；不以这些字段为由把供应商配置退回重启生效。

Host 解析候选值并准备完整配置对象，service 通过 `updateConfig(nextConfig)` 切换内存快照。配置内部复制并保持不可变，不公开可变 Map 或凭据；校验失败不得部分替换。供应商配置编辑器不是旧 Admin 已有能力，本期不默认增加第四个管理页面，但三页应展示可用模型、配置错误和应用结果。

### 发布顺序和密钥轮换

1. 复用宿主 reload 串行化流程，读取、验证图片候选配置并解析 SecretRef。
2. 在发布前完成所有可能失败的异步准备和交叉引用检查，准备可同步切换的 service 配置。
3. 在同一同步发布区间切换宿主配置状态和图片配置；其间不能 `await`，不能在已发布后的 `onPublished` 中才执行可能失败的准备。
4. 成功后唤醒排队工作、刷新前端模型数据和状态；失败保留旧运行态，同时报告候选配置应用失败。
5. 即使配置文件/SecretRef 名称未变化，也要重新解析并应用轮换后的图片凭据。处理当前 reload 的 hash 相同短路、Provider 连接复用和秘密读取缓存，不能只比较 key 名称。

现有 `onPublished` 不是预发布钩子；需要最小范围调整现有准备/发布流程，不建立平行配置系统。增加对应 hot 白名单并验证既有聊天模型热切换不回归。运行版本使用不暴露秘密的标识；同名 key 换值可推进图片运行版本，不能公开密钥或可用于猜测密钥的派生值。最近应用失败和当前仍有可用配置须分别表达。

### 生效时刻

| 对象 | 规则 |
| --- | --- |
| 新 generation | 接受时冻结当时的模型定义、解析后 Prompt、参考素材、参数及配置版本 |
| 已提交/排队 generation | 语义快照不随配置更新；模型从新列表移除不改写已接受输入 |
| 开始执行的 round | 一次性取得该快照所引用凭据的当前值；该轮所有输出共用，不在每个 item 中重新读取 |
| 执行中的 round | 不被 reload 中断或中途换密钥；旧秘密持续受到脱敏保护，直到相关调用结束 |
| retry | 保留原生成语义，创建新 round，并使用执行时可用的凭据；引用已被撤销时明确失败，不偷偷换模型或其它凭据 |
| 复用到工作台 | 恢复用户输入供编辑，重新提交时按当前配置与素材重新解析 |

秘密仅存在内存，不进入 generation snapshot、数据库 JSON、Admin 响应或日志。外层 Agent Invocation 的配置快照与图片 generation 接受/round 执行边界不同，不能默认把前者当成图片配置快照。

## 7. 插件、长期任务与图片交付

Alarm 提供能力、任务作用域、审计和 Admin 接入范例；Worker 生命周期可参照现有长期服务在组合根中的管理方式。先增加最小类型化依赖或插件工厂，不要求为本功能完成通用插件平台。

- `application.ts` 创建一个图片 runtime，再把窄服务依赖交给插件和 Admin。capability 工厂不创建数据库、Worker、watcher 或 HTTP Server。技能发现、registry 预览和 doctor 的静态装配不得触发生成。
- Agent 创建工具为有副作用能力，经 `execute` 审计；使用稳定请求身份和幂等键防止重复付费。继续使用宿主的只读 System Skills，避免与现有 `read_image` 能力撞名。
- 接受时读取 live InvocationContext，固定该任务的调用者、Conversation 和 Invocation 关联；不能在异步完成后再从可变 context 推断创建者。
- Agent 任务接受后由 service 自己的生命周期管理执行，不把它永久绑定到已经返回的工具调用/Invocation AbortSignal。取消请求在持久接受前检查；接受后的取消政策须明确区分执行取消和通知取消。
- 复用 `LongTaskService` 承载完成回执；图片 Worker 只负责图片 Provider 工作，宿主唯一 Scheduler 负责 Conversation 唤醒与回执投递。
- 现有任务 create 没有请求幂等键，需要扩展最小幂等/关联能力。完成状态与回执转换应可重放；启动时对账，覆盖提交后未入队、生成完成未发回执、重启及部分成功。不能只依赖内存回调。
- 结果传小型 ID/元数据，遵守 task 和 execute 的现有大小限制；base64 与完整输入快照不放入完成回执或工具文本。
- Telegram 输入图先经当前 Context capability 验证，再读取受限字节并保存为生成所需素材。裸资产 UUID、路径、file ID 不能成为模型侧绕过授权的入口，Prompt 内嵌图片引用也要检查。
- 结果在接收完成回执或查询任务的有效 Context 中获得新授权引用；不要在旧 Invocation 中提前铸造一个完成时可能已失效的 token。沿用 Conversation 隔离、TTL、head_seq 与 canonical history 规则。
- 图片发送扩展现有 `send`，保留工具侧授权、发送限流、deadline/abort、send barrier、未知结果处理、审计及发送后消息落盘；插件不能直接调用 Telegram API 发图。

保留原生图的快照、参数限制和有界输出数。幂等命中先于重复解析；retry 追加一轮并重新生成整轮输出，不只补失败项，也不覆盖旧输出。上游结果未知时记录 interrupted，不自动重发可能已付费的请求。

停止顺序必须阻止新提交、停止 Worker 并处理在途结果，再释放图片资源，最后由宿主关库；`stop()` 返回后不得再有回调写已释放资源。保持同一图片数据集合单 Worker。插件重启禁用时保留历史与文件，重新启用再按恢复规则处理；Phase 1 不要求热卸载和自动删数据。

## 8. Admin 三页与 API

| 子页面 | 必须承接的布局与操作 |
| --- | --- |
| 工作台 | 桌面端主区为 Prompt 编辑和当前引用，侧区为模型/参数、输出数量、提交、解析预览和草稿摘要；窄屏按同一操作顺序重排。插入 Prompt/图片资产、定位与移除引用、重置参数、新建/清空、预览过期提示、提交后保留草稿并跳转详情 |
| 生图审计 | 原历史页的状态/搜索/刷新区、任务列表、缩略图、操作者/来源、分页；详情展示 authored/resolved/final Prompt、模型/参数快照、round/attempt、输出与错误。保留重试确认和复用到工作台，区分 Admin 与 Agent，Agent 记录可关联宿主审计 |
| 资产管理 | 图片与 Prompt 两个页内分类；图片上传、列表、预览、下载、编辑名称/分类/描述、归档；Prompt 创建、正文编辑、列表、详情和归档；二者均可插入工作台草稿，生成输出进入图片资产库 |

共用 Plastic Wan 的组件、主题、图标、表单、弹窗、通知、空态/错误态、TanStack Query、登录与路由框架；复用原业务纯函数和交互逻辑，不复制原全局 CSS、SessionProvider、API singleton 或导航壳。不要因为宿主已有表格组件就把原版的逻辑布局全部改成另一种信息结构。

Admin API 在现有认证和 Origin 检查之后调用同一 service，覆盖模型、解析、生成、审计、资产及受鉴权图片内容；不新增 Fastify Server、监听端口、MCP Server 或浏览器直连 Provider。新增管理写端点同步宿主 [API 白名单](../admin-panel.md#api)，适配既有方法和错误响应约定，不机械沿用原 PATCH/CSRF 方案。

上传使用端点专属请求体与解码后图片上限，保留真实文件类型、尺寸和透明度等检查；不全局放宽管理 API 上限。图片 URL 由 Admin adapter 生成，核心不保存固定 `/api/v1` 地址。前端模型查询在配置应用后失效并刷新；旧草稿遇到模型删除/参数变化时明确提示，不自动替用户切模型或提交。

原历史页筛选/搜索仅针对已加载页，这是代码事实，不是应固化的产品要求。本期可先保持但必须明确标注范围；若改为全库筛选，需一起调整后端查询、分页和测试。原页面中的独立 `models.json` / 设置页文案替换为宿主配置入口，不暗示不存在的供应商编辑器。

## 9. Salvage 与构建边界

| 来源模块 | 去向与处理 |
| --- | --- |
| resolve、参数/引用规则、OpenRouter adapter、image-store | 核心，优先保留业务行为，收窄类型与依赖 |
| assets、generations | 核心，适配主库整数、所有权、URL 与事务；保留快照、幂等、归档和重试语义 |
| worker | 核心，替换配置依赖、整轮凭据快照、可靠关闭和完成协调 |
| schema、领域 contracts | 核心声明 + 宿主 migration；移除 auth/MCP/SystemConfig DTO，避免重复类型 |
| core 装配、config registry、全局 redactor | 按核心/宿主职责重组；文件读取、秘密来源、发布和资源关闭交宿主 |
| 原 generate/history/assets 页面 | Plastic Wan Admin 业务页面，重接宿主组件和请求体系 |
| 原 auth、login throttle、HTTP/MCP、Server、独立 layout/login/access/settings | 不迁入；原仓库保留作历史参考，不建立兼容入口 |
| 原领域测试 | 随核心迁移；独立 HTTP/MCP 测试只作行为参考，不作为新产品壳的维护承诺 |

workspace 配置和根 package 的 workspace 声明纳入新包；包产出明确的 JS 和声明文件，浏览器 contracts 导出不能导入 Node/SQLite/Sharp。依赖版本以仓库 manifests/lockfile 为准，统一验证 native 模块，不直接照搬来源的驱动版本或 TS 编译约定。

宿主运行时仍遵守原生 `.ts`、可擦除语法和严格检查约定；作为依赖的包验证真实构建产物，不能假设 Node 会处理 node_modules 内的 TS。调整 check/test/build 顺序及 Docker 的安装缓存、workspace 链接目标与最终产物复制。本期无跨仓库 npm 发布、image-ui、第二 Host、独立 Electron 打包或其它 IM Adapter。

### 必测行为

- 核心：参数组合、引用顺序/去重/归档、解析不付费、多输出部分成功、幂等重放/冲突、retry 全轮与旧输出保留、未知上游结果不自动重试。
- 数据/恢复：真实 safe-integer 主连接、BigInt JSON 边界、事务部分失败、入队前崩溃、完成回执前崩溃、启动对账、关闭超时与晚到结果、原图与备份恢复一致性。
- 配置：有效/无效候选、模型删除/改参数、相同 SecretRef 换值且文件 hash 不变、配置准备失败、并发 apply 串行化、排队/在途/重试各边界、旧秘密脱敏、候选失败后 UI 仍可使用旧有效配置；无 image 段与结构残缺 image 段（剥离+警告）都正常启动且图片功能处于禁用态，禁用→启用→再禁用零重启，删除 image 段后未引用的 jar 条目被回收。
- 安全/工具：当前调用者固定、幂等额度限制、管理员与 Conversation 所有权、UUID/Prompt 内嵌引用绕过、跨会话和过期引用、execute 输出限长、send barrier/未知结果/发送后落盘失败。
- UI/API：三页主流程、草稿保留、引用插入、解析预览、多图、重试与复用、资产编辑/归档、模型刷新、筛选分页范围、登录/Origin/错误格式和上传边界；按桌面/窄屏及宿主主题进行浏览器验收。

实施验证遵循 [verification.md](../verification.md)：相关测试与 `pnpm run check`；跨模块交付运行完整 `pnpm test`、`pnpm run lint`、`pnpm run admin:build`，新增浏览器流程按现有 E2E 方式验证，并检查包/Docker 实际产物。真实上游和 Telegram 验收与模拟测试分开记录，不把 mocked Provider 测试写成真实生成成功。实现后更新主题文档、管理写入清单、配置示例和对应用户指南。
