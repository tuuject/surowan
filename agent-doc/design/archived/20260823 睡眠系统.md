请为「塑料碗」实现一个基于每日 token budget 的睡眠系统。

目标行为如下：

* 系统存在一个所有 Chat 共享的全局“每日 token budget”，并且可以获取当前剩余比例或已使用比例；各 Chat 只保留用量归属统计，不设独立 token 上限。
* 当且仅当**当日剩余 budget 低于 5%** 时，Agent 才能看到一个名为 `zzz` 的 tool。
* 在剩余 budget >= 5% 时，`zzz` 不应出现在当前 Agent session 的 tool registry / available tools 中，而不是仅靠 prompt 告诉模型“不要调用”。
* `zzz` 的语义是：Agent 判断当前语境已经适合结束活动时，可以主动“睡觉”。
* `zzz` 的 tool description 应该采用面向 Agent 的自然语义，不要暴露 token、budget、quota 等实现细节。类似：“你现在已经很困了。如果当前对话适合结束，可以使用这个工具去睡觉。”
* Agent 调用 `zzz` 后：

  1. 将 bot 标记为 sleeping；
  2. 当前 Agent session 应尽快正常结束；
  3. 不应再继续调用 `send` 或执行新的实际工作；
  4. sleeping 状态期间不得创建新的 Agent session；
  5. 收到的新 Telegram 消息仍可按现有逻辑保存/记录，但不要触发 Agent session。
* 不需要为了说晚安而额外创建一个 Agent session。只有已经存在的活跃 session 恰好看到 `zzz` 时，Agent 才有机会自然地说晚安并调用它。
* 如果 budget 已经低于 5%，但当前没有活跃 Agent session，不要专门唤醒 Agent；直接阻止后续新 session 即可。
* 睡眠的主要目的，是避免在当日 budget 即将耗尽时继续产生新的昂贵 session。

唤醒逻辑：

* 每日 token budget 会在下一周期重置。
* 调用 zzz 时计算 sleepUntil = max(now + 8 hours, nextBudgetResetAt)。
* sleeping 状态持续到 sleepUntil。即使 budget 在此之前已经重置，也不要提前唤醒；反过来，如果 8 小时结束时 budget 尚未重置，也继续睡到 reset。
* 如果现有代码中已经有可靠的 budget period ID、reset timestamp、日期 key 或类似机制，请复用，不要另外制造一套脆弱的定时器。
* sleeping 状态必须能够跨进程重启保持。如果项目现有状态适合持久化到 SQLite，请复用现有数据库/状态存储机制，而不是只放在内存里。

实现要求：

* 先阅读项目现有的 Agent session 创建流程、tool 注册方式、token budget 统计方式、Telegram 消息 debounce/queue 流程以及 SQLite 状态管理方式。
* 尽量沿用现有架构，做最小而清晰的改动。
* 不要创建与现有抽象重复的 manager/service。
* 把“是否允许创建新 session”和“当前 session 是否暴露 zzz tool”作为两个明确的判断点。
* 注意并发：多个接近同时运行的 session 不应该重复触发睡眠状态，`zzz` 应具有幂等性。
* 如果已经进入 sleeping，重复调用 `zzz` 应安全返回，不产生额外副作用。
* 考虑 session 在开始时 budget 尚 >=5%，运行过程中跌到 <5% 的情况。请根据现有 Agent framework 的 tool lifecycle 判断是否能够动态更新 tools；如果不能，不要强行设计复杂的动态注入机制，优先在下一次合理的 tool/session 边界生效，并在代码注释中说明。
* 不要把预算阈值散落成 magic number；为 5% 提供语义清晰的常量或配置。
* 添加必要的日志，使我能看出：

  * 什么时候进入低 budget 状态；
  * `zzz` 什么时候被暴露；
  * Agent 什么时候调用了 `zzz`；
  * 什么时候因为 sleeping 跳过了 session 创建；
  * 什么时候因为 budget reset 被唤醒。
* 不要打印敏感内容或完整消息正文。

测试至少覆盖：

1. 剩余 5% 以上时没有 `zzz`。
2. 剩余低于 5% 时有 `zzz`。
3. 调用 `zzz` 后进入 sleeping。
4. sleeping 状态下不会产生新的 Agent session。
5. sleeping 状态跨重启仍然有效。
6. budget reset 后会自动恢复 awake。
7. 并发/重复调用 `zzz` 不会造成重复副作用。
8. 临界值 5% 的行为明确且与定义一致：只有 `< 5%` 才出现。
