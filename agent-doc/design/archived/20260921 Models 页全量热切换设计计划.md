## 目标

Models 页上的任何保存都不再需要重启 `serve`：

1. Provider 的新增、删除。
2. 连接字段：`base_url`、`api`、`api_key`、`headers`（builtin 只有 `api_key`）。
3. 正在使用的 agent 模型或 vision 模型的定义（上下文、输出上限、价格、compat、thinking 级别……）。
4. 切换 vision 模型（`PUT /vision`）。
5. 把 agent 切到一个刚刚新增的 Provider 上的模型。

保存后界面只显示 “Applied”，Models 页自己的操作不再产生任何 `restart_required` 路径。

## 用户已确认的约束

### C1. Models 页上的操作全部热切换

范围是上面「目标」的 1–5。**不在**范围内的 restart 字段保持不变，见「不在本计划范围」。`POST /restart` 端点、`supervised` 标记与重启横幅都保留，它们还服务于那些字段。

### C2. 每个 Invocation 把模型与 Provider 参数钉死

一个 Invocation 从 `queued → running` 那一刻起，到它结束为止，用的都是**同一份**模型定义与 Provider 连接（地址、key、headers、API 适配器）。运行期间发布的新配置不影响它，只影响之后开始的 Invocation。

这和配置快照现有的语义一致：`RuntimeConfigurationStore.beginInvocation()` 已经把配置钉死在 Invocation 上，本计划把模型注册表也放进同一份快照。

已知代价（已接受）：开了 `agent.context.idle_grace_seconds` 的长活 Invocation 可能持续到 `agent.context.max_wall_clock_seconds`。如果换 key 是因为旧 key 被吊销，这个 Invocation 会一直失败到结束。

## 已核实的事实（2026-09-21）

### 现在为什么要重启

| 操作 | 代码里的原因 |
| --- | --- |
| 新增、删除、改 kind 的 Provider | `config-diff.ts` 的 `mergeProviders` 记为 `providers.<alias>` restart，candidate 保留 active 的 Provider |
| 连接字段 | 同一函数里除 `models` 以外的字段走 `mergeField`，不在 `HOT_PATHS` 里，因此是 restart |
| 在用模型的定义 | `mergeModels` 里 `isInUse` 为真就记 restart，candidate 保留旧定义 |
| agent 切到新 Provider | `mergeAgent` 的 `providerIsNew` 分支把 `agent.provider` / `agent.model` 记为 restart |
| vision | `vision.*` 不在 `HOT_PATHS` 里；`MediaService` 构造时把 `registry.visionModel` 存进 `#model`，并据此算出 `#analysisVersion` |

### 模型注册表是全进程共享、可修改的一个对象

- `application.ts` 在启动时调用一次 `createModelRegistry`，得到 `{ models, visionModel }`，把同一个 `registry.models`（`MutableModels`）交给 `AgentModelSwitcher`、`MediaService`、`AgentRuntime`、`ConfigReloader` 与 `AdminServer`。
- reload 时 `ConfigReloader.#rebuildProviders` 只重建 `models` 变了、连接没变的 Provider，并在发布配置之前同步地 `this.#models.setProvider(...)` **原地替换**。`rebuildCustomProvider` / `rebuildBuiltinProvider` 复用注册表里旧 Provider 的 `baseUrl`、`headers`、`auth`，从不重新解析 SecretRef（`command` 引用会执行进程）。
- Pi 的 `Models.streamSimple` 每次调用都会按 `model.provider` 在注册表里查 Provider，再走 `applyAuth` 解析 key 与 headers（`node_modules/@earendil-works/pi-ai/dist/models.js` 的 `requireProvider` / `applyAuth`）。
- `AgentRuntime.#runInvocation` 在开始时用快照里的配置查一次模型（`this.#models.getModel(config.agent.provider, config.agent.model)`），但之后每一轮都调 `this.#models.streamSimple(...)`。所以**模型对象已经钉死，Provider 没有**：原地替换 Provider 会影响运行中 Invocation 的下一轮；如果改了 `api`，旧模型对象会被送进新的适配器。
- `MutableModels` 支持 `setProvider`、`deleteProvider`、`clearProviders`，新建一个注册表用 `createModels()`。

### vision 与缓存

- `MediaService` 的分析缓存按 `analysis_version = <provider>/<model>/prompt-<prompt_version>` 命中（`#analyzeDeduplicated` 与 `media_analyses` 查询）。换 vision 模型后，聊天图片的分析会按新版本重新做。
- **后台 Sticker 索引不会因为换 vision 模型而重跑**：`stickers.ts` 的 `runOne` 只挑 `index_state` 为 `pending` / `error` 的 Sticker，`#applyStickerSet` 的 upsert 冲突分支也不重置 `index_state`。已索引的 Sticker 保留旧模型写的描述。本计划不改变这一点。
- `vision.max_concurrency`（`#visionSemaphore`）与 `vision.prompt_version` 在构造时读取，它们不在 Models 页上，保持 restart。

### Admin 里依赖「运行中的注册表」的地方

- `POST /providers/discover` 的 saved 模式（`providers-admin.ts` 的 `discoveryRequest`）从运行中的注册表取 key 与 `baseUrl`，并在该 Provider 有待重启路径时返回 409 `restart_pending`：key 绝不能发往只存在于文件里的地址（上一份计划的 C5）。
- `AdminServer.#providerContext` 把 `this.#models` 放进 `ProviderWriteContext.models`。

## 本计划的实现选择

### S1. 注册表进入配置快照

`RuntimeConfiguration` 增加两个字段：

```ts
export interface RuntimeConfiguration {
  readonly generation: number;
  readonly hash: string;
  readonly config: RawConfig;
  /** 这一代配置的模型注册表。发布后不再修改，reload 发布一个新的。 */
  readonly models: Models;
  /** `config.vision` 指向的模型，构建注册表时已校验存在且支持 image。 */
  readonly visionModel: Model<Api>;
}
```

- 类型用只读的 `Models`，不是 `MutableModels`：发布出去的注册表不能再被任何人修改。构建过程中用 `MutableModels`，发布时收窄类型。
- `ModelRegistry` 接口与 `registry` 这个组合根变量删除；所有调用方改成读快照（清单见「调用方迁移」）。
- 旧快照不需要回收逻辑：最后一个持有它的 Invocation 结束后，它自然被 GC。

### S2. 每次 reload 构建一个新注册表

新增一个函数（放在 `providers.ts`，替换 `rebuildCustomProvider` / `rebuildBuiltinProvider`，二者删除）：

```ts
buildModelRegistry(
  config: RawConfig,
  previous: { readonly file: FileConfig; readonly models: Models } | null,
  secrets: SecretStore,
): Promise<{ models: Models; visionModel: Model<Api> }>
```

- `previous` 为 `null` 时（启动）等价于现在的 `createModelRegistry`，后者删除。
- 对每个 Provider：如果 `previous` 里同 alias、同 kind，且**连接字段完全相同**（除 `models` 以外的所有字段 `deepEqual`），就复用旧 Provider 对象上的 `baseUrl`、`headers`、`auth`，只用新的 `models[]` 重新 `createProvider` / `aliasBuiltinProvider`（与现在 rebuild 的做法相同，不解析 SecretRef）。否则按启动时的路径完整构建，解析它的 SecretRef。
- 只有新增或连接变了的 Provider 会解析 SecretRef，这是 `command` 引用在 reload 时唯一会执行的情况（见 S5）。
- 所有 Provider 都成功以后才返回；任何一个失败，整个函数抛错，reload 失败，active 配置不变。
- `visionModel` 的校验（存在、支持 image、`vision.max_output_tokens ≤ maxTokens`）从 `createModelRegistry` 原样搬过来。

`ConfigReloader.#applyFile` 在锁内调用它（异步），拿到新注册表之后，再在同一个同步块里发布 `{ config, hash, models, visionModel }`。现在「setProvider 与 publish 之间不能有 await」的注释与约束随原地替换一起消失：新注册表在发布前没有任何人能看到。

`#resolveAgentModel` 与 `validateAgentModel` 改为在新注册表上检查 candidate 的 agent 模型。

### S3. 把 providers、agent、vision 从 restart 里拿掉

`config-diff.ts`：

- `mergeProviders`：新增、删除、改 kind 都记为 `hot`，candidate 直接取文件里的 Provider；连接字段走 hot。
- `mergeModels`：删除 `isInUse` 分支与 `InUseModels`，模型的新增、修改、删除都是 `hot`。
- `mergeAgent`：删除 `providerIsNew` 分支，`agent.provider` / `agent.model` 永远是 `hot`。
- `vision.provider`、`vision.model` 加入 `HOT_PATHS`。`vision.max_output_tokens` 也加入（它每次调用都现读，且会在构建注册表时与新模型的上限一起校验）；`vision` 的其余字段保持 restart。
- 更新 `HOT_PATHS` 上方关于「provider 的模型列表是 hot」的注释。

删除 Provider 的在用保护（`provider_in_use` / `model_in_use`，基于**文件**里的 agent / vision 指向）保留：它防的是配置里出现悬空引用，与重启无关。

### S4. Invocation 与 vision 分析各自钉住一份快照

- `AgentRuntime.#runInvocation` 用 `snapshot.models` 查模型，每一轮用 `snapshot.models.streamSimple(...)`。runtime 里 `#models` 目前只有这两处用法，字段删除。
- attach 进运行中 Invocation 的新批次继续用这个 Invocation 的快照（现状如此，不需要改）。
- `MediaService` 删除 `#models`、`#model`、`#analysisVersion` 字段。每次分析（`read_image` 的聊天分析与 `analyzeStickerForIndex`）开始时取一次 `configStore.current()`，从里面拿 `models`、`visionModel`，并算出这次分析的 `analysis_version`；同一次分析的缓存查询、in-flight 去重键、`media_analyses` 与 `model_calls` 行都用这一份。
  - 取「当前」而不是「所在 Invocation 的」快照，是因为 vision 分析也发生在 Invocation 之外（后台 Sticker 索引走 `analyzeStickerForIndex`，没有 Invocation 快照可用）；统一按「分析开始时的当前快照」处理，两条路径规则一致。交付报告里说明这一点即可。
- `AgentModelSwitcher` 改为每次从 `configStore.current()` 取 `models`，不再在构造时接收注册表。
- `validateAdditionalTools` 的调用点（`application.ts`）通过 `modelSwitcher.model()` 读当前快照，不用改。

### S5. reload 可以执行 `command` SecretRef

新增或连接字段变了的 Provider，其 SecretRef 会在 reload 时解析，`command` 引用因此会执行。这是可以接受的：reload 只由管理员的显式操作触发（面板保存、「Apply config file」、`/model`），效果与重启相同；连接没变的 Provider 不会重新解析。

解析出的值照常进入 `SecretStore`（`resolve` 已经这样做），保证之后的错误输出被脱敏。解析失败时 reload 以新错误码 `secret_unresolved` 失败，`message` 经过 `redact`；把它加进 `ConfigErrorCode` 与 `CONFIG_WRITE_STATUS`（422）/ `MODEL_ERROR_STATUS`。

面板本身只写明文 key（上一份计划的 C4），面板写入的 Provider 解析时不会执行任何命令。但任何一次 reload 都会应用整份文件：如果有人手改文件、新增或修改了一个带 `command` 引用的 Provider，那么下一次无论由谁触发的 reload（包括面板上一次无关的保存）都会执行它。这与「手改文件后需要一次应用才生效」的现有语义一致，文档里写明即可。

### S6. saved 模式的 discover 改为比对「文件」与「active」

`restart_pending` 这个理由消失了，但它保护的不变式还在：写入成功而应用失败时（`fileWritten: true`），文件里的连接与运行中的不同，这时仍然不能把 active 的 key 发往文件里的新地址。

- `discoveryRequest` 删除 `restart_pending` 分支，改为：文件里该 Provider 的连接字段与 **active 配置**里的不一致时，返回 409 `connection_not_applied`（message 提示先「Apply config file」或用临时模式）。
- active 的连接从 `configStore.current()` 读，key 与 `baseUrl` 从 `configStore.current().models` 读。`ProviderWriteContext.models` 删除，改为传 `configStore`（或直接传当前快照）。
- `provider_not_registered` 分支保留（文件里有、active 里没有的 Provider）。

### S7. 前端

Models 页不再产生 restart 路径，删除所有为「待重启」服务的 Models 专属逻辑（清理式切换）：

- `lib/model-manager.ts`：删除 `providerPendingRestart`、`modelPendingRestart` 及其测试。`applyFeedback` 保留（其它字段仍可能待重启）。
- `pages/models.tsx`：删除 Provider 列表与模型表格里的 “Restart pending” 徽章。`RestartBanner` 保留在页面顶部，它显示的是全局的 `restart_required`。
- `provider-connection-card.tsx`：删除 “Connection fields take effect after a restart.”。
- `model-picker-dialog.tsx`：删除 `restartPending` 属性与「enter the API key once more」提示；`connection_not_applied` 由通用错误显示处理。
- `provider-wizard.tsx`：删除 “Saved, restart required” 结束页与其中的 “Restart now”，新建成功后和其它写入一样提示 “Applied”，关闭向导并选中新 Provider。向导里「新 Provider 还没进注册表，所以用临时模式拉列表」的说明仍然成立（保存之前它确实不存在），保留但去掉 “until a restart” 的措辞。
- `In use` 面板不变。

## 测试

后端（vitest）至少覆盖：

- **钉住**：用 faux Provider 启动一个 Invocation，让它停在两轮之间；此时改连接字段（例如 `base_url`，faux 记录每次请求看到的 baseUrl / key）并 reload；断言这个 Invocation 的后续轮次仍用旧连接，之后开始的 Invocation 用新连接。再覆盖一次改 `api` 的情况。
- **复用**：只改某 Provider 的 `models[]` 时，`CountingSecrets.resolutions`（`config-reload.test.ts` 已有）不增加；改它的 `api_key` 时只增加这一个 Provider 的次数。
- **失败原子性**：两个 Provider 同时改连接、其中一个的 SecretRef 解析失败时，reload 失败，`configStore.current()` 的 generation 与注册表都不变，错误码 `secret_unresolved`，message 已脱敏。

- **discover**：写入成功但应用失败的状态下（例如制造一个 `candidate_invalid`），saved 模式返回 409 `connection_not_applied`，且没有向任何地址发请求。
- 删除依赖旧行为的用例（例如 `setAgentModel` 或 reload 期待 `restartRequired` 含 `providers.*` 的断言），不要为了让它们通过而保留旧路径。
