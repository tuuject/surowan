# 辞典插件化设计计划

状态：待评审，未落地。本文基于 2026-10-14 `develop`（`facf88f`）源码核对，未参考 `20260918 内置能力插件化计划与结论.md`；若需与其结论对齐，评审时另行指明。

## 背景

辞典已有独立的 store、工具、导入导出、融合与 Admin 页面，却散落在核心目录，并在 ContextBuilder / AgentRuntime 里留有专用分支。当前插件接口（`src/plugins/plugin.ts`）只支持 `skills` 与经 `execute` 调用的 `capabilities`，没有「按批注入 Context」的扩展点，这是辞典无法插件化的根本原因。

辞典用到的扩展点最全（能力、Skill、按批注入、带去重的保留段状态、Admin、配置、表），适合作为第一个验证插件接口的「非纯能力型」插件。

## 目标

1. 辞典代码集中到 `src/plugins/dictionary/`，`src/context/`、`src/orchestration/` 不再出现辞典专用代码。
2. 为插件接口新增一个通用的**按批 Context 注入钩子**，辞典只是它的第一个使用者。
3. 对模型、Admin API、配置与数据库的外部可见行为不变（审计字段除外，见下文）。

## 非目标

- 插件自带表定义与迁移：`dictionary_entries` 继续留在 `src/store/schema.ts` 与 `034_dictionary.sql`。插件独立迁移牵涉迁移排序、备份与保留，单独设计。
- 插件自带配置 Schema：`dictionary` 段与 `chats[].dictionary_injection_mode` 继续由 `src/platform/config.ts` 定义，热更新白名单（`config-diff.ts`）不动。
- 通用 Admin 路由钩子：沿用 alarm 先例，`server.ts` 直接 import 插件的 admin 模块。
- Admin 前端（`apps/admin-next`）、API 路径与 locale 文案不改。
- Sticker catalog、记忆注入的插件化（新钩子应能承载它们，但不在本次范围）。

## 插件接口扩展

### 1. `InvocationScope` 增加 `orm`

辞典工具需要数据库，现有 scope 只给了 `tasks`。`loadPlugins().capabilities` 已经拿到 `store`，直接透传即可：

```ts
export interface InvocationScope {
  // …现有字段
  readonly orm: Orm;
}
```

插件内用 `scope.context.chatId`、`scope.context.invocationId` 构造 `DictionaryToolScope`，`privateChat` 沿用 `chatId > 0n` 的判断，和 `application.ts:219` 现有逻辑一致。

### 2. 新增 `contextInjectors`

```ts
export interface ContextInjector {
  /** 注入器名，同时作为审计键；匹配 PLUGIN_ID_PATTERN，跨插件唯一。 */
  readonly name: string;
  /**
   * 从保留段的一条 user 消息文本里，取出这个注入器写过的去重签名。
   * GC、缓存重建后由 runtime 对全部保留消息重新调用。
   */
  collect(text: string): Iterable<string>;
  /** 渲染本批注入块；不注入时返回空 text。 */
  render(input: ContextInjectionInput): ContextInjectionResult;
}

export interface ContextInjectionInput {
  readonly config: RawConfig;
  readonly orm: Orm;
  readonly chatId: bigint;
  readonly chatType: ContextIdentity['chatType'];
  /** 本批被选中消息的 text 与 caption（history + new），供按需匹配。 */
  readonly messageTexts: readonly string[];
  /** 选完消息、扣掉前序注入器之后剩余的字符预算。 */
  readonly remainingCharacters: number;
  /** 保留段里仍存在的签名。 */
  readonly carried: ReadonlySet<string>;
}

export interface ContextInjectionResult {
  readonly text: string;
  /** 本批新写入的签名。 */
  readonly signatures: readonly string[];
  /** 审计用的注入条目数。 */
  readonly count: number;
}

export interface AgentPlugin {
  // …现有字段
  readonly contextInjectors?: readonly ContextInjector[];
}
```

设计取舍：

- **签名用不透明字符串集合**，不用泛型状态。辞典签名是 `dic_<id> r<revision>`，「同 id 同 revision 才算已注入」与现在的 `Map<id, revision>` 精确比较等价；runtime 不需要理解签名的含义。
- **增量维护语义不变**：runtime 为每个注入器保存一个 `Set<string>`。`rebuildVisibleState` 时清空并对保留消息逐条 `collect`，注入成功后把 `signatures` 并入集合。这和现在 `carriedDictionary` 的「GC 时重建、注入后累加」完全一致。不改成每批全量重扫，避免 steer 队列里尚未进入 `agent.state.messages` 的批次被漏算而重复注入。
- **预算**：注入器按插件加载顺序串行执行，在消息选择之后运行，`remainingCharacters` 逐个递减。「新消息优先于预加载」的不变量由调用时机保证，注入器只负责不超出给它的预算。
- **块位置**：所有注入器的输出按顺序放在现在辞典块的位置，也就是 sticker catalog 之后、`<untrusted_telegram_history>` 之前。辞典单独存在时，渲染出的文本和现在逐字节一致。
- **信任边界**：注入块必须是 `<untrusted_…>` 包裹的不可信数据，且每一行都不缩进；Telegram 消息行缩进两格，因此无法伪造块或签名（现有 `dictionary-injection.ts` 的防伪约束）。这条写进接口注释，并由 `loadPlugins` 校验注入器名唯一。text 的格式不做运行时校验，靠各插件的测试保证。

`LoadedPlugins` 新增 `readonly contextInjectors: readonly ContextInjector[]`；`application.ts` 把它交给 `AgentRuntime` options，再由 `AgentRuntime` 传给 `new ContextBuilder(store, refs, skills, injectors)`。replay 和 participation 测试里的 `ContextBuilder` 不传，默认 `[]`。

### 3. 审计字段

`context_injected.dictionary_count` 换成通用的 `injections: { [name]: count }`，每个已注册注入器都写一项（含 0），让字段形状稳定。按清理式切换原则，不保留旧字段。目前只有 `test/dictionary-runtime.test.ts` 和 `agent-doc/dictionary.md` 读这个字段，Admin 前端与 `scripts/audit.ts` 都没有用到。

## Tool Model 归属

`resolveToolModel` 目前放在 `dictionary-merge.ts`，但它是系统级辅助模型选择：config 注释写的是「dictionary merge and future helper tasks」，`providers-admin.ts` 也读 `tool_model`。插件化后如果它跟着辞典走，核心的 `server.ts` 和 providers 管理就得反向依赖插件。所以把它移到 `src/platform/tool-model.ts`，辞典的 `merge.ts` 从 platform 引入。

## 实施步骤

每一步都单独保持 `pnpm run check` 与 `pnpm test` 通过，可以分开提交。

1. **抽出 Tool Model**：`resolveToolModel` → `src/platform/tool-model.ts`，更新 `server.ts` 与 `dictionary-admin.ts` 的 import。纯搬移。
2. **新增注入钩子（辞典暂不迁移）**：在 `plugin.ts` 加入 `ContextInjector`、`LoadedPlugins.contextInjectors`、`InvocationScope.orm`；`ContextBuilder` 接受 injectors 并按上面的规则调用；`AgentRuntime` 按注入器名维护 carried 集合。这一步辞典仍走旧分支，两条路径并存，只用测试插件验证钩子。
3. **迁移辞典**：
   - 文件搬到 `src/plugins/dictionary/`，并新建 `index.ts`
   - 删除 `ContextBuilder` 的 `#dictionaryInjection`/`#dictionaryTexts`、`InjectionInput` 和结果里的辞典字段，删除 `AgentRuntime` 的 `carriedDictionary`
   - 删除 `application.ts` 里的直接注册，`BUILTIN_PLUGINS` 加入辞典
   - `resolveDictionaryInjectionMode` 移入插件
   - `server.ts` 改为从插件 import admin
   - 审计字段改为 `injections`
4. **测试与文档收尾**（见下两节）。

第 2、3 步之间的双路径只在一个提交内短暂存在，第 3 步要把旧分支彻底删掉，不留 fallback。

## 风险与开放问题

1. **`lookup_dictionary` 被标为 `sideEffect: true`**：`application.ts:220` 把 3 个工具统一包成 `capability(tool, true)`，只读的查询也算有副作用。本计划保持原样以免顺带改行为，需要确认这是有意为之还是顺手的 bug。
2. **注入器顺序**：目前只有一个注入器。将来 sticker catalog 也迁过来的话，块的顺序由插件加载顺序决定，会影响稳定前缀之后的批文本。届时需要固定顺序，或者给注入器加显式顺序字段。
3. **Admin 仍硬接**：`server.ts` 的 `#dictionary` 路由分发仍在核心里，是本次刻意保留的耦合。等第二个插件也需要 Admin 路由时，再评估是否需要通用路由钩子。
4. **配置仍在核心 Schema**：要卸载辞典插件，仍需保留 `dictionary` 配置段的解析。如果以后需要真正的「可选插件」，插件配置 Schema 要单独设计。
