# Alarm Tool / Deferred Invocation 设计

## 背景

目前塑料碗的 Agent invocation 基本都是 reactive 的：群聊中出现新的消息后，调度系统根据消息和当前状态决定是否拉起 Agent。

这种模式意味着，只要群里没有新的消息，塑料碗就无法主动重新参与对话。

但在实际群聊中，有一些场景天然需要“过一段时间以后再回来”：

* 用户说自己去医院急诊了。塑料碗可以在两小时后主动 @ 用户，询问现在情况怎么样。
* 用户说自己 14:30 要坐高铁。塑料碗可以在 12:30 左右主动提醒用户准备出发。
* 用户说自己正在等待一个可能需要很长时间完成的任务。塑料碗可以在预计完成后询问结果。
* 用户说明天有面试。塑料碗可以在面试前提醒，或者在面试结束后询问情况。

这些行为并不都属于传统意义上的“提醒”。例如“两个小时以后问问急诊怎么样了”更接近 follow-up，而“12:30 提醒赶 14:30 的高铁”则更接近 reminder。

它们的共同点是：

> Agent 在当前 conversation 中判断，自己应该在某个未来时间重新参与这个 conversation，并处理一件现在已经知道的事情。

因此，本设计不将 Alarm 定义为“定时发送消息”，而是定义为一种 **Deferred Invocation（延迟调用）机制**。

Alarm 到期时不会直接发送预先生成的文本，而是重新拉起一次 Agent invocation，让 Agent 按照正常群聊方式决定具体应该发送什么。

---

## 目标

新增一个提供给 Agent 的 `alarm` tool，使 Agent 能够：

1. 指定未来的触发时间；
2. 指定需要联系的 Telegram 用户；
3. 保存未来 invocation 所需要的简短上下文；
4. 到达指定时间后，在原 Telegram chat 中重新拉起一次 Agent invocation；
5. 让新的 Agent invocation 按照正常群聊人格和输出流程完成提醒或 follow-up；
6. 即使正常 Agent budget 已经耗尽，已经创建的 Alarm 仍然能够执行。

Alarm 应当能够同时支持 reminder 和 follow-up，而不需要在底层区分两者。

---

## 非目标

Alarm 本身不负责：

* 保存一条未来需要原样发送的 Telegram 消息；
* 在指定时间绕过 Agent 直接调用 Telegram API；
* 判断提醒内容应该使用什么语气；
* 为 reminder、follow-up 等不同用途实现不同的 scheduler；
* 成为完整的日历或任务管理系统。

Alarm 的职责仅仅是：

> 在未来指定时间，携带必要上下文重新唤醒 Agent。

---

## 第一版已确认契约

第一版采用以下明确约束：

1. **Conversation 归属**：Alarm 绑定创建它的当前 conversation，而不只是 Chat。Forum 中创建的 Alarm 必须回到原 Topic；普通群聊和私聊沿用 thread ID `0`。
2. **目标用户授权**：`target_user_id` 必须属于当前 Invocation 实际可见消息中的 Telegram user sender。模型不能为当前 Context 未授权的任意 User ID 创建 Alarm。创建时保存目标用户的稳定 ID，并保存用于未来 mention 显示的名称快照；授权依据仍然是 User ID。
3. **内容与时间边界**：`summary` 必须为 1–500 字符。`datetime` 必须是带显式 timezone offset 或 `Z` 的 ISO 8601 绝对时间，必须严格晚于 Tool 执行时刻，且不得超过执行时刻后 365 天。非法输入 fail fast，并写入稳定 Tool 审计错误码。
4. **创建配额**：同一 Invocation 最多成功创建 3 个 Alarm。超出后拒绝创建并写入稳定 Tool 审计错误码。第一版不另设 Conversation 级 pending 总量上限。Alarm Invocation 仍然暴露 `alarm` Tool，允许安排后续 follow-up，并适用相同配额。
5. **取消范围**：第一版不提供 `cancel_alarm` Tool，但提供 Admin Panel 取消能力。管理员只能原子取消 `pending` Alarm（`pending → cancelled`）；已进入 `firing` 或其它终态时返回冲突，不尝试中止 Invocation。取消记录当前面板管理员账号、`cancelled_at` 与稳定原因 `admin_cancelled`。系统也可在 Alarm 到期时因 Chat/Topic 停用、移出配置或管理员 pause 将其置为 `cancelled`，此时管理员账号为空并记录对应稳定原因。
6. **调度与碰撞**：同一 Chat 的所有 Invocation 继续严格串行。Alarm 到期时不打断 running Invocation；Chat 空闲后，已到期 Alarm 优先于普通消息 Bucket，多个 Alarm 按 `scheduled_at, id` 排序。Alarm 不与消息 Bucket 合并。该优先级同样适用于已经 queued 的普通 Invocation：同一 Chat 空闲时，已 claim 的 Alarm Invocation 必须先于普通 queued Invocation 启动。
7. **调度精度**：Scheduler 的下一次等待时间必须同时考虑最近 Bucket deadline 与最近 pending Alarm 的 `scheduled_at`，动态等待到较早者，不采用固定一分钟 Alarm 轮询。
8. **失败与恢复**：到期 Alarm 必须先原子 claim `pending → firing`，再创建 Invocation。成功 claim 后绝不自动重试：Invocation 无论 completed、failed、aborted 或 outcome_unknown，Alarm 都进入不可再次调度的终态并保留 Invocation 结果；进程恢复发现遗留 `firing` 时将其关闭为 `fired` 并记录 `outcome_unknown`，不得退回 `pending`。
9. **Budget bypass**：Alarm Invocation 不预留或消耗 Chat 的 `max_invocations_per_day` 次数，并绕过全局每日 Token budget 的模型调用 gate 与预算触发的全局 `zzz`/sleep 状态。模型 Token 使用仍正常写入审计和 `daily_usage`。Alarm 不暴露 `zzz` Tool。该 bypass 覆盖 Alarm 从 claim 到启动的完整路径：全局 sleep 不得把已 claim 的 Alarm Invocation 标记为 `skipped_budget`。
10. **不可绕过项**：Alarm 仍受 Chat/Topic 配置、管理员 pause、同 Chat 串行、全局并发、Invocation timeout、最大轮次、Tool Call 数、send 次数、Telegram 错误及全部 capability 校验约束。到期时 Chat/Topic 已停用、移出配置或处于 pause，则不创建 Invocation，Alarm 进入 `cancelled` 并记录稳定原因。若 Alarm 已 claim 但尚未启动时发生管理员 pause，则其 queued Invocation 被中止，Alarm 必须立即进入 `cancelled` 并记录 `chat_paused`，不得停留 `firing`。
11. **目标 mention**：Alarm Invocation 第一次调用文本 `send` 时，发送层必须自动在文本开头加入 Alarm 保存的目标用户 text mention；模型不提交 User ID 或 mention 参数。该 mention 由保存的 `target_user_id` 与显示名快照生成，使用 Telegram 支持的实体或等价安全编码。后续文本 `send` 不强制重复 mention；Sticker 不能满足首次目标联系要求，首次成功的目标联系必须是文本。普通 Invocation 不获得此行为。若模型同时请求 `parse_mode: "MarkdownV2"`，发送层必须保留该语义：mention 实体与 MarkdownV2 解析共存，不得静默丢弃 parse_mode。
12. **历史隔离**：Alarm 触发不创建虚假 Telegram Update、Message 或 Revision。Alarm summary 只作为本次 Invocation 的临时 system prompt 任务说明，不写入 Telegram message history，也不在未来 Invocation 中作为消息重放。
13. **Admin 审计**：Admin Panel 增加 `Alarms` 导航与列表。管理员可以查看待执行和历史 Alarm，按状态、Telegram Chat ID、目标 Telegram User ID 过滤；默认全部展示，但 `pending` 按 `scheduled_at` 升序置顶，非 pending 历史按最近状态时间倒序。列表显示状态、计划时间、Chat/Topic、目标用户、摘要、创建/触发/取消时间和原因；完整摘要与诊断字段可在表格行内展开。存在关联 Invocation 时必须链接到现有 Tool Session 详情页。列表使用稳定游标分页，SQLite bigint 在 JSON 中字符串化。展开详情必须包含完整 summary、UTC 计划时间、conversation ID、Telegram Chat ID、thread ID、目标 User ID、创建/触发/取消时间、取消者、取消原因、Invocation 结果与 `updated_at`。
14. **Admin 取消交互**：只有 `pending` 行显示取消按钮，使用行内二次确认。`DELETE /api/alarms/:id` 在事务内执行 `pending → cancelled`，记录当前认证 Admin 用户与时间，然后唤醒 Scheduler；成功刷新 Alarm 列表。不存在返回 404，非 pending 返回 409 稳定错误码，跨站与认证规则沿用现有 Admin 写端点。

## Tool 设计

提供：

```ts
alarm({
  target_user_id: number,
  summary: string,
  datetime: string,
})
```

### `target_user_id`

需要在 Alarm 到期后提醒或联系的 Telegram User ID。

目标用户应当使用稳定的 Telegram User ID，而不是 username，因为 username 可能不存在或发生变化。

具体发送消息时，可以由现有 Telegram 层根据 User ID 生成适当的 mention。

### `summary`

描述未来 Agent invocation 需要处理的事情。

`summary` **不是需要发送给用户的消息文本**。

例如：

```text
用户两个小时前说自己去医院急诊了。现在关心一下他的情况怎么样了。
```

或者：

```text
用户今天 14:30 有一班高铁。现在需要提醒他准备出发赶车。
```

未来 invocation 应当根据 summary 自己生成符合塑料碗正常群聊风格的消息。

因此，不应该要求当前 Agent 提前生成：

```text
@tcdw 该出门赶高铁啦🥺
```

然后把这句话保存两个小时。

这样可以避免 Alarm 退化成普通的 delayed message queue，同时也让未来 Agent 保留正常的人格表现和一定的判断能力。

### `datetime`

Alarm 的绝对触发时间。

建议 tool schema 要求包含明确 timezone 的 ISO 8601 datetime，例如：

```text
2026-08-28T12:30:00+08:00
```

Scheduler 内部可以统一转换为 UTC timestamp 保存。

不建议让 scheduler 自己解释：

```text
"in two hours"
"tomorrow morning"
```

这类自然语言时间应当由调用 tool 的 Agent 根据当前时间转换为确定的 datetime。

## Chat 归属

Alarm 创建时自动绑定当前 Telegram chat。

因此 Agent 不需要显式提供 `chat_id`。

例如：

```ts
alarm({
  target_user_id: 123456,
  summary: "用户今天 14:30 有一班高铁，现在提醒他准备出发。",
  datetime: "2026-08-28T12:30:00+08:00",
})
```

实际数据库记录中仍然需要保存：

```ts
{
  chatId: -1001234567890,
  targetUserId: 123456,
  summary: "...",
  scheduledAt: "...",
}
```

这样即使同一个用户同时存在于多个塑料碗所在的 Telegram 群中，Alarm 也只会回到创建它的 conversation。

## Invocation Trigger

目前普通 invocation 可以视为由 Telegram messages 触发。

新增一种内部 trigger：

```ts
type InvocationTrigger =
  | {
      type: "telegram_messages";
      // ...
    }
  | {
      type: "alarm";
      alarmId: string;
      targetUserId: number;
      summary: string;
    };
```

Alarm scheduler 到达指定时间后，不构造虚假的 Telegram user message，而是直接创建 `alarm` 类型的 invocation。

这样可以避免：

* Alarm 内容污染 Telegram message history；
* Agent 误以为 summary 是某个用户刚刚发送的消息；
* 为了复用现有 pipeline 而制造不存在的 Telegram update。

---

## Alarm Invocation Prompt

当 invocation trigger 为 `alarm` 时，在 system prompt 中增加临时任务说明。

语义大致如下：

```text
This invocation was triggered by an alarm that you scheduled earlier.

Your immediate task is to follow up with Telegram user <target_user_id>.

Context for why you scheduled this alarm:
<summary>

Mention the target user and handle this naturally using the same
conversational style you normally use in this group.

The summary describes the purpose and context of the alarm. It is not
a message that must be repeated verbatim.

Do not explain the internal alarm or scheduling mechanism unless it is
actually relevant to the conversation.
```

这段 prompt 只存在于此次 invocation，不进入长期 conversation history。

---

## 正常输出流程

Alarm invocation 不应该拥有特殊的 Telegram 发送实现。

它仍然按照普通 Agent invocation 的方式：

```text
Alarm 到期
    ↓
Scheduler
    ↓
创建 alarm invocation
    ↓
构造 Agent context
    ↓
Agent reasoning
    ↓
send tool
    ↓
Telegram
```

因此现有的：

* MarkdownV2 处理；
* send tool；
* 消息长度限制；
* 输出风格限制；
* Telegram mention；
* 其他发送相关约束；

都可以继续复用。

Alarm 只改变 **为什么 Agent 被拉起来**，不改变 **Agent 如何说话**。

---

## Budget 行为

Alarm invocation 不受正常 conversation budget 耗尽的限制。

例如塑料碗已经因为当天预算耗尽进入 `zzz` 状态：

```text
normal invocation → blocked
alarm invocation  → allowed
```

原因是 Alarm 是 Agent 之前已经承诺执行的 deferred action。

如果用户在 12:00 得到了“两个小时以后提醒你”的行为，但 13:50 塑料碗恰好耗尽当天 budget，那么 14:00 的 Alarm 不应该因此静默消失。

这个 bypass 应当在 invocation scheduler / budget gate 实现，而不是通过 system prompt 要求模型忽略 budget。

例如：

```ts
const bypassBudget =
  invocation.trigger.type === "alarm";
```

Alarm bypass 的范围应当尽可能窄。

它不意味着 Alarm invocation 可以自动绕过：

* send tool 限制；
* Telegram API 错误；
* chat 被禁用；
* 管理员级 pause；
* 其他与 budget 无关的系统约束。

Budget exhaustion 和 administrative pause 应当是两个独立概念。

## 数据模型

初始版本可以使用类似：

```ts
interface Alarm {
  id: string;

  chatId: number;
  targetUserId: number;

  summary: string;

  scheduledAt: Date;
  createdAt: Date;

  status:
    | "pending"
    | "firing"
    | "fired"
    | "cancelled";
}
```

未来如果需要诊断，也可以记录：

```ts
firedAt?: Date;
invocationId?: string;
error?: string;
```

但这些不是第一版的必要字段。

## 执行语义

Alarm 应尽量保证 **at-most-once user-visible delivery**。

最需要避免的问题不是漏掉一次无关紧要的 Alarm，而是 scheduler 或进程发生异常后，在群里连续多次 @ 同一个用户。

Scheduler 发现到期 Alarm 后，应当首先原子地 claim：

```text
pending → firing
```

只有成功 claim 的 worker 可以创建 invocation。

Invocation 正常完成后：

```text
firing → fired
```

如果 Agent invocation 或进程中途失败，可以根据实际实现增加有限 recovery。

Recovery 必须避免简单地：

```text
发现 scheduledAt < now
→ 再执行一次
```

否则 crash loop 可能导致同一个 Alarm 被重复发送。

---

## Agent 创建 Alarm 的原则

Agent 可以在用户明确要求提醒时创建 Alarm，例如：

```text
用户：
我 14:30 的高铁，12:30 提醒我出门。

Agent：
→ alarm(...)
```

也允许 Agent 根据 conversation 自主创建合理的 follow-up，例如：

```text
用户：
我去医院急诊了。

Agent：
→ 正常回复
→ alarm(
     datetime = now + 2h,
     summary = "用户之前说自己去医院急诊了，过一会儿关心一下情况。"
   )
```

这是 Alarm 对塑料碗最重要的能力之一：用户不必使用明确的“提醒我”命令，Agent 可以像一个真实参与群聊的人一样，判断某件事情值得稍后回来继续关注。

但是 Agent 不应把所有包含未来时间的消息都转换成 Alarm。

例如：

```text
我明年可能去日本。
```

通常没有必要因此创建 Alarm。

Alarm 应当用于存在明确、合理的未来交互价值的场景。

---

## 推断与事实

Agent 可以根据上下文合理选择 Alarm 时间，但应避免把自己的推断保存成用户事实。

例如用户只说：

```text
我 14:30 的高铁。
```

Agent 可能根据常识决定提前一段时间提醒。

但 summary 更适合写成：

```text
用户说自己 14:30 有一班高铁。提醒他注意时间并准备出发。
```

而不是：

```text
用户必须在 12:30 出门。
```

除非用户自己明确说过 12:30 需要出门。

这样未来 invocation 仍然能够区分：

* conversation 中明确存在的事实；
* 当前 Agent 为了安排 Alarm 做出的判断。

## 示例：医院 follow-up

### T0

用户：

```text
我去医院急诊了。
```

Agent 正常回复，并调用：

```ts
alarm({
  target_user_id: 123456,
  summary:
    "用户刚才说自己去医院急诊了。过一段时间关心一下现在情况怎么样。",
  datetime: "2026-08-28T23:20:00+08:00",
});
```

### T+2h

Scheduler 拉起 alarm invocation。

Agent 得到：

```text
target_user_id: 123456

summary:
用户两个小时前说自己去医院急诊了。
现在关心一下情况怎么样。
```

Agent 通过正常 `send` tool 发送类似：

```text
@tcdw 现在怎么样了🥺 急诊那边处理完了吗
```

## 示例：赶高铁

用户：

```text
我今天 14:30 的高铁，12:30 得准备出发。
```

Agent 创建：

```ts
alarm({
  target_user_id: 123456,
  summary:
    "用户今天 14:30 有一班高铁，并说 12:30 左右需要准备出发。提醒他该出发赶车了。",
  datetime: "2026-08-28T12:30:00+08:00",
});
```

12:30 时重新拉起 Agent。

Agent 可以按照正常群聊方式发送：

```text
@tcdw 差不多该出发啦🥺 14:30 的车别给自己玩极限赶车ww
```

## 核心抽象

虽然对 Agent 暴露的 tool 名称可以保持简单的 `alarm`，但系统内部更准确的抽象实际上是：

**Deferred Agent Invocation**

即：

```text
现在的 Agent
    ↓
认为未来需要再次处理某件事
    ↓
创建 Alarm
    ↓
持久化 deferred invocation
    ↓
到达指定时间
    ↓
未来的 Agent 被重新唤醒
    ↓
根据保存的 context 自己决定如何处理
```

因此，Alarm 并不是一个“延迟发送 Telegram 消息”的功能。

它赋予塑料碗的是一种此前不存在的能力：

> **即使没有任何人发送新消息，也能够因为之前发生过的事情，在未来主动重新进入 conversation。**

这使塑料碗从纯粹 reactive 的群聊 Agent，开始具备有限的 proactive interaction 能力。
