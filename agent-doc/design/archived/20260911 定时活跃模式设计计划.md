# 塑料碗 定时活跃模式设计计划

---

## 1. 背景与目标

需求原文：

> 我希望为塑料碗增加定时活跃模式。管理员可以指定多个时间段让塑料碗主动参与全局群聊会话（总是触发 invocation）。
> 在时间段之外，默认不触发 invocation，只有群里的消息触发了管理员设置的关键词，或者是直接 at 塑料碗，或者是直接 reply 塑料碗之前发布过的消息，才会触发 invocation 进入一个 5 分钟（配置文件可调）的时间窗口，在这个时间窗口内就会像指定时间段一样，在这个群聊里始终触发 invocation，如果在时间窗口内出现上述三种触发条件的消息，时间窗口的计时器会重置。

今日行为是「任何合规人类消息都会创建 Bucket 并触发 Invocation，是否发言由模型自己决定」。本特性把「是否触发」的一部分决定权交回给管理员：

1. 管理员可以指定**活跃时段**（每天重复、可选星期几、支持跨午夜）。时段内行为与今日完全一致。
2. 时段之外默认**静默**：只有 `trigger_keywords` 命中、直接 @ Bot、直接 Reply Bot 自己发过的消息这三类消息能创建 Bucket。
3. 任意一条命中消息把该会话推进**注意力窗口**（默认 300 秒，可配置）。窗口内该会话像时段内一样始终触发；窗口内再次命中则重置计时。

产物是一个「管理员可控的互动活跃度」开关，不改变模型的表达自由：静默期只是不给模型开会话，窗口内的会话仍然可以自己选择沉默。

## 2. 已定设计决策

| 决策 | 取值 | 理由 |
| --- | --- | --- |
| 配置载体 | `config.jsonc`：`telegram.participation` 全局默认 + `telegram.chats[].participation` 每群覆盖 | 沿用「配置只在 `serve` 启动时加载、不热重载」的既有不变量；不引入运行时写入面与第二套状态源 |
| 窗口粒度 | **Conversation**（chat + Forum Topic） | 话题是塑料碗的隔离单位，Bucket/Context/记忆/预算都按 Conversation 隔离；触发不应把无关话题一起唤醒 |
| 关键词 | 全局 + 每群**追加** | 「管理员统一指定」与「某群专属触发词」两种需求都能表达 |
| 时段形状 | 每天重复 `HH:MM-HH:MM`，可选 `days`，支持跨午夜 | 覆盖日常作息；不引入日期范围与一次性时段，避免配置与语义复杂化 |
| 列表上限 | `active_windows` / `trigger_keywords` **不设条数上限** | 见下 |

### 为什么不给列表设上限

`src/platform/config.ts` 里管理员手写的数组（`chats`、`topic_ids`、`admins`、`sticker_sets`、MCP `tools` / `tool_policies`、`provider.models`）全部没有 `maxItems`，只按语义需要加 `minItems` / `uniqueItems`；带 `maximum` 的字段一律是 runtime 直接消费的参数（`bucket_window_seconds` ≤ 300、`timeout_seconds` ≤ 90、`max_turns` ≤ 8、`session_ttl_hours` ≤ 720）。

列表长度不改变任何行为语义，写多少是管理员自己的责任，因此不设上限。代价用**启动期预计算**消除，而不是用 `maxItems` 兜底（见第 6 节）。

只有 `attention_window_seconds` 保留上界：它直接决定会话时序，超过 86400 后语义退化为「永久活跃」，而表达该意图的正确写法是 `00:00-24:00`。

## 3. 行为语义

对一条已入库消息：

```text
gatingEnabled = chat.type !== 'private' 且（全局 participation 或该 chat 的 participation 存在）
inPeriod      = 命中 active_windows（按 chat 时区解释 receivedAt）
triggerKind   = mention | reply_to_bot | keyword | null      （仅对非编辑、eligibleHuman 消息计算）
allowBucket   = !gatingEnabled || inPeriod || attentionWindowActive
```

规则：

1. **窗口只在时段外维护。** `inPeriod` 为真时不写窗口行；时段结束后立即回到静默，不会因为时段末尾的一次 @ 而延续。
2. **写入先于判定。** 命中消息先写入/刷新窗口（`expires_at = receivedAt + attention_window_seconds`），因此它自己必定被放行；判定与窗口状态永远一致，实时路径与启动追赶路径不可能分叉。
3. **命中需要 eligibleHuman。** 不能创建 Bucket 的消息（例如 `sticker_trigger_enabled = false` 时的单独 Sticker）也不能开窗口。
4. **编辑消息不命中、不刷新、不建 Bucket**（沿用「编辑只进 history」的既有约定）；编辑内容照常写 Revision，并在后续 Invocation 中作为 history 出现。
5. **被闸门拦下的消息照常入库**（`telegram_updates`、`messages`、`message_revisions`、`media`），只是不创建 Bucket。它们会在下一次触发时作为 Invocation 的 history 区段进入 Context，因此静默期不会丢上下文。
6. **已有 collecting Bucket 时不拦消息**：闸门只阻止**创建** Bucket，companion 消息仍会追加进已有 Bucket（与今日 `companionOnly` 行为一致）。
7. **命中优先级**：mention > reply_to_bot > keyword（只影响记录下来的 `trigger_kind`，不影响授权结果）。
8. **私聊不受影响**（`chat.type === 'private'` 一律 `gatingEnabled = false`），符合「私聊积极、群聊克制」的既有产品取向。
9. **`/pause` 优先**：暂停期间既不创建 Bucket 也不写窗口行。
10. **时段是 Chat 级、窗口是 Conversation 级**：时段内该群所有 Topic 都活跃；窗口只覆盖命中发生的那个 Conversation。
11. **Alarm 不受闸门影响**：`alarm` 是模型显式排期的任务，`processAlarmsDue` 保持原样。
12. **启动追赶同样受闸门约束**：追赶 Bucket 只在 `inPeriod(now) || attentionWindowActive` 时创建，否则记 `skipped_budget` / `participation_gated`（与 `sleeping`、`chat_paused` 同一机制）。追赶期间收到的命中消息同样会写窗口，因此「重启期间被 @」不会漏。
13. **无 participation 配置时行为与今日完全一致**（回归底线）。
14. **墙钟边界**：窗口为半开区间 `[start, end)`；`end < start` 表示跨午夜且归属开始日；`end = "24:00"` 表示到当日结束。DST 跳变按时区本地时间自然处理（不存在的本地时刻天然不命中）。

## 4. 配置契约

```jsonc
{
  "telegram": {
    "participation": {
      "active_windows": [
        { "start": "09:00", "end": "12:00" },
        { "start": "20:00", "end": "01:00", "days": [5, 6, 7] },
      ],
      "trigger_keywords": ["塑料碗", "wan"],
      "attention_window_seconds": 300,
    },
    "chats": [
      {
        "id": -1001234567890,
        "participation": {
          "active_windows": [{ "start": "00:00", "end": "24:00" }], // 覆盖全局：本群全天活跃
          "trigger_keywords": ["运维"], // 追加到全局关键词
        },
      },
    ],
  },
}
```

字段：

- `participation`（可选）挂载在 `telegram` 与 `chats[]` 两处，均使用 `Strict`（未知字段拒绝）。
- `active_windows`（可选，**不设条数上限**）：**每群覆盖全局**（存在即替换）。`[]` 是合法取值，表示该群无时段、只能靠触发进入，因此不设 `minItems`。`start` 为 `HH:MM`（`00:00`–`23:59`），`end` 同格式或 `24:00`；`days`（可选）为 ISO 星期 `1`–`7`（1 = 周一），省略表示每天。
- `trigger_keywords`（可选，**不设条数上限与长度上限**）：每条为 `Type.String({ minLength: 1 })`（与仓库其他字符串字段一致），`uniqueItems: true`（与 `topic_ids` / `admins` 一致）。**每群追加**到全局列表。`[]` 同样合法。
- `attention_window_seconds`（可选，默认 `300`）：`Type.Integer({ minimum: 1, maximum: 86400 })`。

语义校验（`validateSemantics`，两个层级都执行）：

- `start !== end`：零长度区间恒不命中，等价于写了一个不生效的字段，按配置错误拒绝。
- 带 `participation` 的 chat 必须是负数 ID（负 ID = 群组 / Supergroup），否则报错「私聊不支持 participation」。
- 时区已由现有 `validateTimezone` 覆盖（`chat.timezone` 与顶层 `timezone`），无需重复校验。

**合并规则**（`resolveParticipation`）：

| 项 | 合并方式 |
| --- | --- |
| `windows` | chat 覆盖全局（存在即替换） |
| `keywords` | 全局 + chat 追加 |
| `windowSeconds` | chat 覆盖全局，否则 300 |
| `timezone` | `chat.timezone ?? config.timezone`（与 `context-builder.ts` 现有写法一致） |

## 5. 数据层

新表（迁移 `016_participation.sql`，只新增表、不改既有表）：

```sql
CREATE TABLE conversation_attention (
  conversation_id INTEGER PRIMARY KEY REFERENCES conversations(id) ON DELETE CASCADE,
  expires_at TEXT NOT NULL,
  triggered_at TEXT NOT NULL,
  trigger_kind TEXT NOT NULL,
  trigger_telegram_message_id INTEGER,
  updated_at TEXT NOT NULL
) STRICT;
```

- 每 Conversation 至多一行；命中即 `ON CONFLICT(conversation_id) DO UPDATE`。
- `trigger_kind` 取值 `mention` / `reply_to_bot` / `keyword`（应用层写入，`schema.ts` 用 CHECK 表达同集合）。
- 过期即无意义：`purgeExpiredData` 增加 `DELETE FROM conversation_attention WHERE expires_at <= <now>`；读路径只比较 `expires_at > now`，不做惰性删除，因此读操作永远不写库。
- `conversations` 删除时级联清理。
- 窗口状态跨进程重启保持（与 `chat_pause` / `bot_sleep_until` 同一取向），重启不丢窗口。

选择新表而不是给 `conversations` 加列：`conversations` 是热表（每个 Update 都会 upsert），加列会无谓放大写入。

## 6. 模块边界

**`src/platform/participation.ts`（新，纯函数，无 Store 依赖）**

- `type TriggerKind = 'mention' | 'reply_to_bot' | 'keyword'`
- `compileParticipation(config)` —— **启动期预计算**：关键词统一小写；`HH:MM` 解析成当日分钟数；按 timezone 缓存 `Intl.DateTimeFormat` 实例（构造 Formatter 才是昂贵的那步，不能每消息新建）。
- `isWithinActiveWindows(windows, timezone, now): boolean`
- `matchTriggerKind(message, bot, keywords): TriggerKind | null`
- 本地时间解析统一用 `Intl.DateTimeFormat(..., { hourCycle: 'h23' })` + `formatToParts`；已在 Bun 1.4 实测：午夜返回 `00` 而非 `24`，DST 跳变按本地墙钟正确。仓库已有 `hourCycle: 'h23'` 先例。

预计算的实际意义：逐消息判定退化为整数区间比较 + 预小写数组 `includes`，成本与列表长度近乎无关。这是第 2 节「列表不设上限」成立的前提。

**`src/store/participation.ts`（新，配置解析 + 窗口状态）**

- `resolveParticipation(config, orm, telegramChatId, chatType): ParticipationRule`
- `evaluateParticipation({ orm, rule, conversationId, message, receivedAt, eligibleHuman, edited })` → `{ bucketCreationAllowed, triggerKind, expiresAt }` —— **单一决策入口**，内部完成「时段判断 → 关键词 / @ / Reply 匹配 → 命中则 upsert 窗口 → 读窗口」。
- `attentionWindowUntil(orm, conversationId, now): string | null`
- `purgeExpiredAttention(orm, now)`
- 命中时打印结构化事件 `agent_attention_triggered`（`chat_id`、`conversation_id`、`trigger_kind`、`telegram_message_id`、`expires_at`）。**不**为被抑制的消息打日志：静默期会每消息一行，噪音过大。

## 9. 测试计划

新增 `test/participation.test.ts`，自带 `mkdtemp` + `testConfigJsonc` + `loadConfig` + `SqliteStore.open`；断言沿用 `store.db` 原始 SQL 计数与 ISO 字符串精确比对。

- **纯规则**：时段内外；`start` 含 / `end` 不含的边界；跨午夜两侧；`days` 限定；`00:00-24:00` 全天；空时段列表；多时段并集；时区换算（同一 UTC 时刻在 `Asia/Shanghai` 与 `UTC` 判定不同）。
- **命中判定**：`entities` 的 `mention` 与 `text_mention`；大小写不敏感的用户名；`caption_entities`；text / caption 中的关键词（大小写不敏感）；Reply 到 Bot 消息；Reply 到他人消息；普通文本；Bot 自己发的消息。
- **配置**：合并规则（时段覆盖 / 关键词追加 / 秒数覆盖）；私聊不复用；无配置不复用；`check-config` 拒绝零长度时段、非法 `days`、空关键词、带 `participation` 的正数 chat ID。
- **实时闸门**（对照 `sticker_trigger_enabled` 的既有测试骨架）：
  - 无配置 → 照常创建 Bucket（回归）。
  - 时段外普通消息 → 消息入库、`buckets` 计数为 0、无 `conversation_attention` 行。
  - 时段外 @ / 关键词（text 与 caption）/ Reply Bot → 创建 Bucket + 窗口行（`expires_at` 与 `trigger_kind` 精确断言）。
  - 窗口内普通消息 → 创建 Bucket；窗口内再次命中 → `expires_at` 重置。
  - 窗口过期后普通消息 → 不再创建 Bucket；过期后再次命中 → 重新开窗。
  - 时段内普通消息 → 创建 Bucket 且**不**写窗口行。
  - 编辑消息 → 不创建 Bucket、不刷新窗口、但产生新 Revision。
  - 已有 collecting Bucket 时被抑制的消息仍进入 `bucket_messages`。
  - 私聊（正 ID、`type: 'private'`）→ 不受影响。
- **启动追赶**：时段外无命中 → `buckets` 记 `skipped_budget` / `participation_gated` 且无 Invocation；窗口内 → 创建 `startup_catch_up` Bucket；追赶期间收到的命中消息会写窗口。
- **清理**：`purgeExpiredData` 删除过期窗口行，未过期保留。

## 11. 风险与已知边界

- **回归风险集中在 `#ingestTransaction`**：闸门必须只在「创建新 Bucket」这一条路径上生效。靠「无配置即 `gatingEnabled = false`」保持既有测试与线上行为不变，并跑完整 `bun test` 兜底。
- **列表不设上限，但没有性能陷阱**：关键词与时段在启动期预计算（小写化、分钟数、缓存 Formatter），逐消息判定成本与列表长度几乎无关。只有「管理员写入上千条关键词」这种极端配置会让启动校验变慢——那是他自己的责任，不做限制。
- **窗口状态跨进程保持**，但**配置改动需要重启**，改关键词不追溯已入库消息。
- **Reply 命中依赖原始 Update 的 `reply_to_message.from.id`**：被回复消息在 Telegram 侧删除后该对象可能缺失，此时不命中（只会漏触发，不会误触发）。
- **Bucket 与窗口时长不联动**：窗口只剩 1 秒时命中仍会创建出一个完整 `bucket_window_seconds` 节拍的 Bucket（Bucket 一旦创建就走原有时序）。
- **DST 跳变**：窗口若整段落在「不存在的本地时间」内（如纽约春季 `02:00-03:00`），当天不激活，属时区语义的自然结果，不做补偿。
- **模式开启后群聊会明显变安静**，这是本特性的目的；排障顺序应加上「检查是否在时段内 / 是否有活跃窗口 / `/status` 的互动行」。
- 模型侧 Prompt 不改：模型看不到「自己为什么被唤醒」，仍按既有群聊克制策略决定是否 `send`。窗口内被唤醒不等于必须发言。
