## 目标

在 Admin Panel 提供一个类似 Cherry Studio「模型服务」页的管理器：

1. 左栏列出 Provider，右栏编辑连接信息和模型列表。
2. 新增 Provider 走向导；编辑连接字段；删除 Provider。
3. 「获取模型列表」：从 Provider 拉取可用模型，自动补全元数据，勾选后加入配置。
4. 编辑单个模型的元数据和 compat 高级设置。
5. 把当前 Model 页（切换 agent 模型）合并进来，Model 页删除；vision 模型也可以在同一个页面切换。
6. 有字段等待重启时，面板可以直接重启服务端。

## 用户已确认的约束

### C1. 屏蔽 Pi 的内置模型目录，保留 Pi 的内置供应商目录

- `kind: "builtin"` 继续存在，并且继续由 Pi 提供 baseUrl、API 适配器和供应商特有逻辑。
- builtin Provider 必须像 custom 一样在配置里显式写 `models[]`（至少 1 个）。Pi 目录里有、但配置里没写的模型，运行时不可用。
- 理由：Pi 的模型目录是写死的，跟不上 OpenRouter 等平台频繁上新；配置里的 `models[]` 同时充当「启用模型」子集，Telegram `/model 序号` 的列表也不会被几百个模型淹没。
- 不要提出「连 builtin 一起删掉」的方案。

### C2. 元数据来源

添加模型时，按 Provider 选择元数据来源：

| Provider | 来源 |
| --- | --- |
| OpenRouter、Vercel AI Gateway | 它们自己扩展过的 `/v1/models` 字段 |
| 其它已知 Provider | models.dev |
| 不知名的中转站 | 在 models.dev 里 best effort 匹配 |

### C3. compat：best effort 预填 + 高级设置

参考 Cherry Studio：best effort 预填 compat，并提供 per-model 的「高级设置」让管理员手动开关。在此基础上细化出三条：

1. **三态**：每个字段都是「自动 / 开 / 关」（枚举字段是「自动 / 具体值」）。「自动」等于配置里不写这个字段，交给 Pi 的检测。二态开关会把值冻结，以后 Pi 升级改进检测也覆盖不到。
2. **预填只填检测不知道的字段**。目前只有 reasoning content 回放这一个，其余字段一律留在「自动」。
3. **只开放精选字段，并按 API 显示**。只显示当前模型 API 适用的字段；后端校验同样拒绝不适用的字段。

v1 只做 per-model 级别，不做 provider 级默认值。

### C4. SecretRef 在面板中只能写成明文，并且单向

- 面板只能把 SecretRef 设为明文字符串。不能写 `{ env }` 或 `{ command }`：`command` 等于让面板在宿主机上执行命令；`env` 配合可编辑的 `base_url`，等于能外泄进程里任意一个环境变量。等 Electron 版再讨论。
- 文件里已有的 env / command 引用可以保持不动，也可以整个替换成明文。
- 输入 key 是单向操作。Admin API 永远不返回任何 SecretRef 的值，也不返回来源类型（literal / env / command）：
  - `GET` 响应里完全省略 `api_key`（schema 要求必填，返回「已设置」没有信息量）。
  - `headers` 只返回名称列表。
  - 前端输入框固定提示「已设置，留空以保持当前设置」：留空表示保持，非空表示替换成明文。
- 已接受的代价：
  - 原来用 env 的 Provider 在面板里被替换成明文后，页面上看不出环境变量不再生效。只在 [admin-panel.md](../admin-panel.md) 里写明，不为此暴露字段。
  - 与 C5 叠加后，**在面板里改 `base_url` 会把 env / command 引用强制降级成明文**。要继续用 env 管理 key 的人，只能手改配置文件。这是 C5 的必然结果，已确认接受。

### C5. 密钥与地址绑定

- 修改 `base_url` 时，`api_key` 和所有 header 值都必须在同一次提交里重新填写，否则返回 400。header 的类型也是 SecretRef，服务端分不出哪些是敏感的，只能一视同仁。
- 「检测 / 获取模型列表」时，已保存的凭据只能发往已保存的地址。请求的是新地址，就只能使用请求体里提交的凭据。
- 理由：面板被盗用时，把 `base_url` 改到攻击者的服务器，就能拿到原来的 key 和全部对话内容。只允许写明文堵不住这条路。

### C6. 先做「改完要重启」

- Provider 的新增、删除以及连接字段（`base_url`、`api`、`api_key`、`headers`）保存后需要重启服务端才生效，界面显示「已保存，待重启」。
- 这不是最终形态。连接字段的热更新放到下一阶段（见「后续阶段」）。
- 因此本计划**包含「立即重启」端点**（规格见 R5）：否则新建 Provider 的流程最后一步是断的，用户得自己去敲命令。

### C7. 只支持四种 API 格式

- 支持：`openai-completions`、`openai-responses`、`anthropic-messages`、`google-generative-ai`。custom 与 builtin 预设都以这四种为限。
- `mistral-conversations` 等其它 Pi 适配器现阶段不支持。
- custom 目前只能选前三种，本计划要把 `google-generative-ai` 加进来（见「配置 Schema 变化」）。

### C8. 模型列表不预置

- 新建 Provider 时，模型列表是空的。只有管理员填了 API Key 并成功拉取（或手动输入模型 id）之后，模型才会进入配置。
- 不允许任何「预置几个模型」的行为：预置意味着又一份会过时的硬编码清单，和 C1 是同一个问题。
- 新建的 Provider 在重启之前不在 registry 里，所以它的「获取模型列表」只能用临时模式，需要再填一次 Key（面板读不回已保存的 Key）。界面要说明这一点，并引导用户先重启。

### C9. Vision 模型可以从面板切换

- 面板可以写 `vision.provider` / `vision.model`。`vision.*` 是 restart 字段，所以结果是「已保存，待重启」。
- 写入前必须预检（见 `PUT /vision`）：`vision.*` 在启动时才由 `createModelRegistry` 校验，选错了会导致下次启动直接失败，bot 起不来。

## 本计划的实现选择

### S1. 配置文件仍然是唯一事实来源

- 所有写入走 `src/platform/config-file.ts` 的 `writeConfigEdits`，写完调用 `ConfigReloader` 应用，与 `/model` 的「先写文件、再 reload」流程一致。
- 尽量按叶子路径写：连接字段写到 `['providers', alias, 'base_url']` 这一级，单个模型写到 `['providers', alias, 'models', index]` 这一级，避免整块替换 Provider 对象而丢掉其中的注释。
- `GET` 读的是**磁盘上的文件**（目标配置），不是 active 配置。界面按 `ConfigReloader.status().restartRequired` 给对应的 Provider 或模型标「待重启」。
- 磁盘文件无效时（例如手改改坏了），`GET` 返回 422 并附脱敏后的错误。

### S2. 乐观并发：revision

- `revision` 是 `config.jsonc` 原始字节的 SHA-256（不含 Prompt 文件）。`GET /providers` 会返回它。
- 所有写端点通过 `If-Match` 请求头带上 revision。缺少时返回 400 `revision_required`；不一致时返回 409 `config_conflict`，前端提示「配置文件已被修改」并重新拉取。
- `writeConfigEdits` 增加一个 expected revision 参数：读取源文件后先比对，一致再修改。比对和 rename 之间仍有极短的 TOCTOU 窗口，面板写入之间已经由 `ConfigReloader` 的锁串行化，手改文件恰好落进这个窗口的情况可以忽略。

### S3. 模型列表的热更新扩展到 builtin

- `models[]` 的增删改对 custom 已经是热的。本计划把它扩展到 builtin，让「模型列表 = 热更新」对两种 kind 一致。
- `config-diff.ts` 的 `mergeProviders` 去掉 `kind === 'custom'` 的限制，热更新白名单路径改为 `providers.<alias>.models[<id>]`（不分 kind）。在用模型保护照旧：`isInUse` 命中时按 restart 处理。
- `providers.ts` 新增 builtin 版本的重建函数：沿用 registry 里已有的 auth，不重新解析 SecretRef，只替换模型列表。`ConfigReloader.#rebuildProviders` 两种 kind 都要处理。
- 这一条已确认，不要退回「builtin 的模型改动要重启」。

### S4. builtin 预设的收录规则

收录规则的精确谓词见 R2。按该谓词被排除的代表：`mistral`、`opencode`、`opencode-go`、`github-copilot`、`cloudflare-ai-gateway`、`fireworks`、`xai`（API 不唯一或不属于 C7 四种）；`cloudflare-workers-ai`、`google-vertex`（`baseUrl` 无定义）；`azure-openai-responses`、`amazon-bedrock`、`openai-codex`（API 不属于四种，或没有 `auth.apiKey`）。

配置里写了不满足条件的 builtin 时，`check-config` 直接拒绝，与 C7 保持一致。

### S5. alias 创建后不可改名

agent / vision 按 alias 引用 Provider，审计里也记录了 provider alias。改名等于删除再新建，界面不提供改名。

### S6. 在用保护

- 删除 Provider：如果文件里的 `agent.provider` 或 `vision.provider` 指向它，返回 409 `provider_in_use`。
- 删除模型：如果文件里的 agent 或 vision 模型是它，返回 409 `model_in_use`。
- 编辑在用模型：允许。reload 会按现有的在用模型保护把它标成待重启。
- 以上预检只为了给出明确的错误码；最终仍然由 `validateSemantics` 兜底。

## 评审决议（2026-09-20）

实施前评审发现的五处歧义与缺口，逐条定稿如下。本节与上文冲突时以本节为准。

### R1. builtin 的 API 从模型目录推导

Pi 的 `Provider` 对象上没有 `api` 字段；`api` 长在每个 `Model` 上。新增辅助函数 `builtinProviderApi(source): Api | null`：取 `source.getModels()` 全部条目的 `api` 去重，恰好一种才返回该值，否则返回 `null`。三处共用它：

- `GET /provider-presets`：目录为空或 API 不唯一的 Provider 不进入预设列表。
- builtin 的模型注册：配置里每个模型的 `api` 填这个推导值。
- `GET /providers` 响应里的 `api` 字段：同源推导。discover 需要知道 API 时同样从这里取。

### R2. S4 收录规则的精确谓词

`isSupportedBuiltinPreset(source)` 要求同时满足四条：

1. `source.getModels().length > 0`（排除空目录，例如 `radius`）。
2. 目录内 API 唯一，且属于 C7 的四种。
3. `baseUrl` 有定义且不含 `{`。注意 `cloudflare-workers-ai`、`google-vertex` 的 `baseUrl` 是 `undefined`，不是含占位符。
4. `auth.apiKey` 存在。是否同时带 `oauth` 不影响判定：`openrouter`、`anthropic`、`kimi-coding` 都有 `oauth`，仍然入选。

### R3. Provider alias 字符集

`validateSemantics` 对 `providers` 的每个 key 断言以下 pattern（与 sticker / MCP alias 的现有 pattern 一致）：

```text
^[A-Za-z][A-Za-z0-9_-]{0,63}$
```

理由：alias 出现在 Admin API 的路径段里，也出现在 `restart_required` 的 `providers.<alias>.models[<id>]` 字符串里；不限制字符集，路由和前端反解都不可靠。配置格式的 breaking change 已声明可接受。

### R4. `PUT /model` 也带 revision

`ConfigReloader.setAgentModel(provider, model, expectedRevision?)` 增加可选第三参，透传给 `writeConfigEdits` 的 revision 检查。Admin 的 `PUT /model` 强制 `If-Match`（前端从 `GET /providers` 已拿到 revision）；Telegram `/model` 命令不传该参数，行为不变。

### R5. `POST /restart` 的自包含规格

热更新方案 §12 位于 `design/` 归档区，实施 agent 默认不读，相关内容摘抄并定稿于此：

- 写端点 `POST /api/restart`，加入 [admin-panel.md](../admin-panel.md#api) 写端点白名单并校验 `Origin`。
- 执行前按启动流程校验磁盘上的配置（权限检查与完整 `loadConfig`）。配置无效时拒绝重启并返回错误，否则进程退出后起不来，bot 就停了。
- 复用 `application.ts` 的优雅关闭流程（依次停止 Admin、等待 Scheduler 最多 30 秒、停止 Sticker 与 MCP、关闭 SQLite、释放锁），然后以专用退出码 **75**（`EX_TEMPFAIL`，与崩溃区分）退出。
- 进程由外部重新拉起：Docker 靠 `restart: unless-stopped`，Electron 由主进程重启 server。部署方通过环境变量 **`PLASTICWAN_SUPERVISED=1`** 声明有监督（写进 Dockerfile 与 Electron）；未设置时端点返回 409，界面不显示按钮。
- 响应时机：先返回 202，等响应流结束后用 `setImmediate` 启动关闭流程。
- 重启期间 Admin 页面断开，界面轮询等待服务恢复；这段时间收到的 Telegram 消息由启动补偿拉取。

已知并接受的风险：本期没有「上次可用配置」回退。启动期才失败的情况（SecretRef 解析失败、Pi 升级导致 builtin 模型消失等）会让 bot 停止，等待人工修复。交付报告需再次确认此风险。

## 已核实的事实（2026-09-20）

### compat 是什么，屏蔽模型目录会丢什么

所谓「OpenAI 兼容接口」在细节上各有方言。compat 就是描述这些差异的一组开关，例如系统提示用 `developer` 还是 `system` 角色、输出上限的字段名、打开思考的参数格式、是否加 Anthropic 风格的 `cache_control`、回放历史 assistant 消息时是否必须带 `reasoning_content`。

Pi 分两层决定最终的 compat（`api/openai-completions.js`）：

1. `detectCompat(model)` 按 `model.provider` 和 `model.baseUrl` 自动检测。
2. `getCompat(model)` 用模型目录里 per-model 的 `compat` 覆盖检测结果（用 `??` 合并）。

屏蔽模型目录，等于去掉第 2 层。对 OpenRouter 目录里 346 个模型逐个对比的结果：

| 字段 | 结论 |
| --- | --- |
| `thinkingFormat`、`supportsDeveloperRole` | 自动检测完全覆盖，0 个不一致 |
| `cacheControlFormat` | 只检测 `provider === "openrouter"` 且 id 以 `anthropic/` 开头的模型；漏掉 4 个 `~anthropic/*-latest` 别名 |
| `requiresReasoningContentOnAssistantMessages` | **丢失 6 个**：`deepseek/deepseek-v4-flash`、`deepseek/deepseek-v4-flash-0731`、`deepseek/deepseek-v4-pro`、`deepseek/deepseek-v4-pro-0813`、`moonshotai/kimi-k2.6`、`~deepseek/deepseek-v4-flash-latest`。自动检测只认 deepseek.com 的地址或 provider id。dev 配置当前的 agent 模型就在其中 |

由此得出两条约束：

- **builtin 发请求时必须继续用 Pi 的 provider id。** 现在的 `aliasBuiltinProvider` 在 `stream` / `streamSimple` 里把 `provider` 换回 `source.id`，自动检测依赖这一点（例如 OpenRouter 的 `cacheControlFormat` 只认 provider id）。重写 builtin 注册时必须保留这个行为。
- **Pi 没有导出 `detectCompat` / `getCompat`**，面板无法显示「自动」最终解析成什么值，只能显示「自动（由 Pi 根据地址判断）」。不要把检测逻辑复制一份过来。

### Pi 的 Provider 结构

- `createProvider` 的 `api` 可以是单个适配器，也可以是按 `model.api` 分发的映射表；发请求时按 `model.api` 选择适配器，不要求模型在目录里。因此 builtin 用配置里的模型直接发请求是可行的。
- 有些 builtin 在一个 Provider 下混用多种 API：`opencode`、`opencode-go`、`github-copilot`、`cloudflare-ai-gateway`、`fireworks`、`xai`。见「待决问题」。
- `vercel-ai-gateway` 在 Pi 里走 `anthropic-messages`，baseUrl 是 `https://ai-gateway.vercel.sh`（不带 `/v1`）。
- Pi 的 Gemini 适配器导出为 `googleGenerativeAIApi`（`api/google-generative-ai.lazy.js`）。它要求 baseUrl 已经带上版本路径（builtin `google` 是 `https://generativelanguage.googleapis.com/v1beta`），不会再追加版本。
- compat 的适用范围：Responses 适配器只读 `supportsDeveloperRole`，而且没有 URL 检测，默认值写死为 `true`。只有在模型 `reasoning` 为真时才会使用 `developer` 角色，否则用 `system`（`openai-responses-shared.js`）。Pi 没有 Gemini 的 compat 接口；Anthropic 的 compat 字段与本计划的精选字段没有交集。

- `interleaved: { field: "reasoning_content" | "reasoning_details" }`：全库有 1105 个模型带这个字段，是 reasoning content 回放的唯一预填来源。只把 `field === "reasoning_content"` 映射成 `requires_reasoning_content: true`，其它情况留在「自动」。已知有不一致：Pi 给 `moonshotai/kimi-k2.6` 标了需要 `reasoning_content`，models.dev 写的是 `reasoning_details`。
- models.dev 的 provider id 和 Pi 的不完全相同，例如 Vercel 在 models.dev 里是 `vercel`，在 Pi 里是 `vercel-ai-gateway`。需要维护一张小映射表，查不到时按「中转站」处理。
- `openrouter` 下存在 `deepseek/deepseek-v4-flash-0731`，dev 配置的 agent 模型可以精确匹配。

## 配置 Schema 变化

### builtin 增加 `models`

```ts
const BuiltinProviderSchema = Type.Object(
  {
    kind: Type.Literal('builtin'),
    provider: Type.String({ minLength: 1 }),
    api_key: SecretRefSchema,
    models: Type.Array(ModelSchema, { minItems: 1 }),
  },
  Strict,
);
```

- `validateModelReference` 不再对 builtin 提前 `return`，与 custom 一样检查模型存在和输入能力。
- builtin 的模型注册：`api` 由 R1 的 `builtinProviderApi` 推导，`baseUrl` 取自 Pi Provider，其余字段取自配置，`provider` 字段设为 alias，发请求时换回 `source.id`。
- 同一 alias 下模型 id 唯一、`max_tokens ≤ context_window` 等校验对 builtin 同样生效。
- 同步修改的调用方：`createModelRegistry`、`doctor.ts`（按 alias 列模型）、`AgentModelSwitcher.list`（自动变成只列配置里的模型）、TUI `configure` 的 builtin 向导（必须能录入 `models[]`，复用现有的模型向导）。

### custom 的 `api` 增加 `google-generative-ai`

- `CustomProviderSchema.api` 的联合类型、`providers.ts` 的 `CUSTOM_ADAPTERS`（接入 `googleGenerativeAIApi`）、TUI 的 `ApiAdapter` 类型同步增加这一项。
- custom Gemini 的 `base_url` 必须包含版本路径（例如以 `/v1beta` 结尾）。文档和面板提示里写明这一点。

### 模型 compat 精选字段

```jsonc
"compat": {
  "supports_developer_role": false,          // 已有
  "thinking_format": "openrouter",
  "max_tokens_field": "max_tokens",
  "requires_reasoning_content": true,
  "cache_control_format": "anthropic"
}
```

| 配置字段 | Pi 字段 | 适用 API | 取值（省略即「自动」） |
| --- | --- | --- | --- |
| `supports_developer_role` | `supportsDeveloperRole` | openai-completions、openai-responses | `true` / `false` |
| `thinking_format` | `thinkingFormat` | openai-completions | 只允许不需要额外参数的值：`openai`、`openrouter`、`deepseek`、`together`、`zai`、`qwen`、`string-thinking`。`baseten`、`chat-template`、`qwen-chat-template` 需要 kwargs，不开放 |
| `max_tokens_field` | `maxTokensField` | openai-completions | `max_completion_tokens` / `max_tokens` |
| `requires_reasoning_content` | `requiresReasoningContentOnAssistantMessages` | openai-completions | `true` / `false` |
| `cache_control_format` | `cacheControlFormat` | openai-completions | 只有 `anthropic`。Pi 用 `??` 合并，无法强制关闭，所以这个字段是「自动 / anthropic」二态 |

- `anthropic-messages` 和 `google-generative-ai` 没有可开放的字段，这两种 API 的模型不显示「高级设置」。
- 所有字段都是可选的；`compat` 为空对象时整体省略。
- 模型的 API 不适用某个字段时，`validateSemantics` 直接拒绝，沿用现在「`supports_developer_role` 在 `anthropic-messages` 上被拒绝」的做法。builtin 的 API 来自 Pi Provider，因此校验要能查到 Pi 的 builtin 定义。
- `customProviderModels` 与 builtin 的模型构造共用一个 snake_case → camelCase 的映射函数。

## 元数据解析

### 模块归属

- 把 `src/tui/models-dev.ts` 和 `src/tui/provider-models.ts` 迁到 `src/platform/`，TUI 和 Admin 共用，删除旧路径。
- 新增一个解析模块（命名自定），输入「Provider 描述 + 模型 id 列表或 `/models` 响应」，输出每个模型的元数据草稿：
  - 每个字段带来源标记：`openrouter` / `vercel` / `models.dev` / `models.dev-fuzzy` / `missing`。
  - 附带匹配信息，例如模糊匹配命中的 models.dev provider/model id。
- 元数据只在「添加模型」和「刷新元数据」时解析，结果写进 `config.jsonc`。**运行时只读配置**，不在线访问 models.dev 或 `/models`，这样启动不依赖外网，行为也确定。
- models.dev 目录在服务端内存缓存（建议 1 小时）；拉取要加超时和大小上限（现在的 `fetchModelsDevCatalog` 两者都没有）。

### 规则

1. OpenRouter（builtin `openrouter`，或 custom 的 base_url 主机是 `openrouter.ai`）和 Vercel AI Gateway（builtin `vercel-ai-gateway`，或主机是 `ai-gateway.vercel.sh`）：基础元数据取自扩展字段。
   - Gemini 原生列表自带 `inputTokenLimit` / `outputTokenLimit`，可以作为同类的第三个来源：上下文与输出上限取自列表，其余字段查 models.dev。响应字段凭记忆整理，尚未用真实 key 验证，实施时核实，尤其是否有表示思考能力的字段。
2. 其它 builtin：按映射表找到 models.dev provider，用模型 id 精确匹配。
3. custom 中转站：先精确匹配，再做模糊匹配（例如去掉 `vendor/` 前缀、统一大小写、去掉 `:free` 之类的后缀），给出候选，由管理员确认。
4. `requires_reasoning_content` 对所有 Provider 都查 models.dev 的 `interleaved`，OpenRouter 和 Vercel 也不例外。
5. 必填字段缺失（例如 `max_completion_tokens` 为 `null`）或来自模糊匹配时，标记为「需确认」，管理员确认或手填后才能保存。不要静默填默认值：现在的 `toModelDefaults` 会默认填 `128000` / `4096`，Admin 路径不能沿用这个行为。

### `/models` 端点的路径

现在的 `modelsEndpoint` 一律拼接 `${baseUrl}/models`，认证也只处理 Bearer 和 `x-api-key`。这对 OpenAI 系的 baseUrl（通常以 `/v1` 结尾）成立，但 Anthropic 系的 baseUrl 不带 `/v1`（例如 Pi 里的 `https://api.anthropic.com`），直接拼接会请求到错误的地址。改为按 API 分派，外加一个特例：

| Provider / API | 列表端点 | 认证 | 响应与翻页 |
| --- | --- | --- | --- |
| **特例**：builtin `vercel-ai-gateway`，或 custom 的 base_url 主机是 `ai-gateway.vercel.sh` | `${base}/v1/models` | `Authorization: Bearer` | OpenAI 风格 `{ object: "list", data: [...] }` 加 Vercel 扩展字段（`context_window`、`max_tokens`、`type`、`tags`、`pricing`），无翻页；只保留 `type === "language"` 的模型 |
| `openai-completions`、`openai-responses` | `${base}/models` | `Authorization: Bearer` | `{ data: [{ id }] }`，OpenRouter 带扩展字段 |
| `anthropic-messages` | `${base}/v1/models` | `x-api-key` + `anthropic-version` | `{ data, has_more, last_id }`，需要翻页 |
| `google-generative-ai` | `${base}/models`（base 已含 `/v1beta`） | `x-goog-api-key` | `{ models: [{ name: "models/…", … }], nextPageToken }`，需要翻页；id 去掉 `models/` 前缀；只保留 `supportedGenerationMethods` 含 `generateContent` 的模型 |

特例必须先于 API 分派匹配：vercel-ai-gateway 在 Pi 里走 `anthropic-messages` 发请求，但它的列表端点不是 Anthropic 的 `{ data, has_more, last_id }` 格式，认证也不用 `x-api-key`。2026-09-20 已验证：该端点无凭据也返回 200 与上述结构，与「各来源的字段」一节的 Vercel 元数据来源一致。

这张表里 Anthropic 与 Gemini 的细节同样凭记忆整理，实施时用 Anthropic、Vercel、Gemini 各验证一次。翻页要设上限（页数和总条数），与现有的响应大小上限一起防止失控。

## Admin API

所有端点在 `/api` 下；写端点校验 `Origin`，并加入 [admin-panel.md](../admin-panel.md#api) 的写端点白名单。模型 id 可能含 `/`，路径里用 `encodeURIComponent` 编码；服务端必须先按 `/` 切分路径段，再逐段解码。

### 读

`GET /providers`

```jsonc
{
  "revision": "<sha256 of config.jsonc>",
  "agent": { "provider": "openrouter", "model": "deepseek/deepseek-v4-flash-0731" },
  "vision": { "provider": "google", "model": "gemini-3.7-flash" },
  "restart_required": ["providers.oproxy.base_url"],
  "providers": [
    {
      "alias": "openrouter",
      "kind": "builtin",
      "provider": "openrouter",          // builtin 才有
      "api": "openai-completions",       // builtin 由 R1 从 Pi 模型目录推导
      "base_url": "https://openrouter.ai/api/v1",  // builtin 取自 Pi，只读
      "header_names": [],
      "models": [ /* 完整模型配置，含 compat */ ]
    }
  ]
}
```

- 响应里不出现 `api_key`，也不出现任何 header 值（C4）。测试要断言：整个响应的 JSON 文本里不包含测试用的 key 字符串。
- `GET /provider-presets`：列出可选的 builtin Provider（id、name、api、baseUrl），数据来自 Pi，过滤规则见「待决问题」1。

### 写

写端点都需要 `If-Match: <revision>`；都在 `ConfigReloader` 的锁里「写文件 → 应用」；响应都带上 apply 摘要（`applied`、`restart_required`）和新的 revision。

| 端点 | 语义 |
| --- | --- |
| `POST /providers` | 新建。body 包含 `alias`、`kind`、builtin 的 `provider` 或 custom 的 `base_url` + `api`、`api_key`（必填）、`headers?`、`models`（至少 1 个）。结果为待重启 |
| `PUT /providers/:alias` | 修改连接字段。`api_key` 省略表示保持；`headers` 按名称逐项处理（省略表示保持，字符串表示替换，`null` 表示删除）。修改 `base_url` 时强制重填（C5）。`kind`、`alias`、builtin 的 `provider` 不可修改 |
| `DELETE /providers/:alias` | 删除。在用时返回 409 `provider_in_use` |
| `POST /providers/:alias/models` | 批量追加模型，id 重复返回 409。热更新 |
| `PUT /providers/:alias/models/:id` | 替换单个模型的定义，`model.id` 必须等于 `:id`。热更新，在用模型为待重启 |
| `DELETE /providers/:alias/models/:id` | 删除模型。在用时返回 409 `model_in_use` |
| `POST /providers/discover` | 拉取模型列表并解析元数据，同时充当「检测」。见下文 |
| `POST /providers/lookup-metadata` | 给定一组手动输入的模型 id，只做元数据解析（用于没有 `/models` 的中转站） |
| `PUT /model` | 保留，前端改为在模型行上调用；需要 `If-Match`（R4） |
| `PUT /vision` | 切换 vision 模型（C9）。写入前预检：模型在文件配置的该 Provider 下存在、支持 image 输入、且 `vision.max_output_tokens ≤ 该模型的 max_tokens`。不满足返回 400。结果为待重启 |
| `POST /restart` | 「立即重启」（C6）。规格见 R5：先按启动流程校验磁盘上的配置（权限 + 完整 `loadConfig`），再复用 `application.ts` 的优雅关闭，以退出码 75 退出，由外部监督拉起；`PLASTICWAN_SUPERVISED` 未设置时返回 409、界面不显示按钮 |

- `GET /model` 与 `pages/model.tsx` 在新页面接管之后删除（清理式切换）；删除前确认 e2e 与其它调用方都已迁移。
- 服务端一收到明文 key 或 header 值，**先调用 `secrets.resolve(value)` 注册进 `SecretStore`**，再写文件或发请求。否则 key 在重启前不会被 resolve，`last_error`、写端点错误或 discover 报错如果带出它，就无法脱敏。目前 `AdminServer` 手里没有 `SecretStore`，需要在组合根里注入。

### `POST /providers/discover`

两种模式，二选一：

- **已保存模式** `{ "alias": "..." }`：使用运行中 registry 里这个 Provider 的 baseUrl 和凭据（`models.getProvider(alias)`），不重新解析文件里的 SecretRef（env / command 不会被执行）。registry 的 Provider 上没有 `api` 字段：custom 从 active 配置读取，builtin 由 R1 推导。如果这个 alias 的连接字段处于待重启状态，返回 409 `restart_pending`，前端提示重启或改用临时模式。
- **临时模式** `{ "kind", "provider" | "base_url" + "api", "api_key", "headers"? }`：完整的连接信息，凭据来自请求体（C5）。新建 Provider 的向导走这个模式。

响应返回模型草稿列表：每个模型带元数据、来源标记和「已在配置中」标记。上游错误经过脱敏后原样返回，作为「检测」失败的原因。出站请求沿用 `provider-models.ts` 已有的保护：`redirect: 'error'`、超时、响应大小上限。

## 测试

- **config**：builtin 缺少 `models` 被拒绝；builtin 的 agent / vision 模型引用校验；compat 字段按 API 的适用性；`thinking_format` 枚举；`cache_control_format` 只接受 `anthropic`。
- **providers**：builtin registry 只注册配置里的模型（Pi 目录里有、配置里没有的 id，`getModel` 返回 `undefined`）；发请求时的 provider 是 Pi 的 id；compat 映射正确。
- **config-diff / config-reload**：builtin 的 `models[]` 走热更新；在用模型保护对 builtin 生效；重建时不重新解析 SecretRef（沿用现有测试的计数手法）。
- **config-file**：revision 不一致时拒绝写入，文件保持不变。
- **元数据解析**：用 OpenRouter / Vercel / models.dev 的 fixture，不访问网络；价格换算；`max_completion_tokens` 为 `null` 时标记为需确认；`interleaved` 的映射；模糊匹配的候选。
- **Admin API**：
  - `GET /providers` 的响应文本不包含 key 和 header 值。
  - 创建、修改、删除；修改 `base_url` 但不带 key 时返回 400。
  - `If-Match` 缺失返回 400、不一致返回 409。
  - `provider_in_use` / `model_in_use`。
  - discover 的已保存模式在待重启时拒绝。
  - discover 的临时模式：用 fixture 上游在错误体里回显 key，断言返回的错误已经脱敏。
  - `PUT /vision` 的三项预检：模型不存在、不支持 image、`max_output_tokens` 超过模型上限，各返回 400；成功时结果是待重启。
  - `POST /restart`：磁盘配置无效时拒绝且不退出；部署方未声明监督时返回 409。真正的退出路径用注入的关闭钩子断言，不在测试里真的杀进程。
  - `Origin` 校验。
- **e2e**：页面渲染；key 输入框的提示文案；DOM 中不出现任何 secret；写操作经过真实 AdminServer。discover 用本地 fixture 上游，不访问外网。
