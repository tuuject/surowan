## 与方案 / 交接说明不一致之处

1. **candidate 的构造方式**：交接说明描述为「先 `structuredClone(active.file)`，再把 hot/outside_serve 路径的值按字符串路径复制过来」。按字符串路径复制需要一套路径解析/写入器，且与差异遍历会重复一套对齐规则；实际实现把差异与 candidate 放在同一次递归遍历里产出（`diffConfig` 返回 `{ changes, candidate }`），语义与说明一致（restart 保留 active、hot 与 outside_serve 取文件、文件里不存在的 hot 字段从 candidate 删除、models 按文件顺序重建、Prompt 文本不重新读盘）。
2. **例外 2 的删除分支**：说明只写了「修改在用模型的定义」。实现里对「文件删除了一个 candidate 仍然引用的在用模型」也按 restart 处理（保留 active 定义）。这条路径只在同一次修改里把 `agent.provider` 换成一个全新 Provider、同时删掉原 agent 模型时才会走到；不处理的话 candidate 会缺模型而报 `candidate_invalid`。
3. **重建 Provider 的判定**：说明写「candidate 的 models 与 active 不同」。实现按 custom alias 比较两边 `models` 数组的深相等（`deepEqual`）；因此「只调整模型顺序」也会重建一次 Provider（candidate 的 models 已是文件顺序，注册表随之对齐）。
4. **`POST /config/apply` / `GET /config/status` 未接线时**：说明只规定了 `PUT /model` 的 503。这两个端点同样在 `ConfigReloader` 缺失时返回 503（`config_reload_unavailable`）。
5. **无变化时的日志**：说明把 `config_reloaded` 列在 publish 之后。实现里「只有 restart 字段变化」与「完全无变化」也会输出 `config_reloaded`（`applied` 为空、generation 不变），这样运维仍能看到 file hash 前移；失败路径不变。
6. **只改 `outside_serve` 会 publish**：说明写「没有 hot 与 outside_serve 变化时不 publish」，因此只改 `retention.*` / `paths.backups` 时仍会 publish、generation + 1（candidate 与 active 只在这些 `serve` 从不读取的字段上不同），active hash 等于文件 hash。测试 23 按此断言。
7. **`validateAgentModel` 的第三个实参**：说明给的接线片段是 `additionalTools(preview, Number.MAX_SAFE_INTEGER)`，但 `ToolFactory` 需要 `(context, deadline, capabilities)`；实际传 `unavailableCapabilities()`，与 `validateAdditionalTools` 内部构造 send 工具时用的解析器一致。
