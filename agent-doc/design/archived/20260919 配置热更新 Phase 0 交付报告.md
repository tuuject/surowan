## 与方案 / 交接说明不一致之处

1. **交接说明只列了 9 个类与 `application.ts`，但 `src/doctor.ts` 与 `apps/admin-next/e2e/server.ts` 也构造这些类**：两者各自新建 store 后传入（doctor 用 `{ config, hash: configHash }`），未改动其行为。
2. **`BucketScheduler` 的 handler 参数位置变化会波及测试的类型引用**：`test/scheduler.test.ts`、`test/bot-commands.test.ts` 的 `ConstructorParameters<typeof BucketScheduler>[3]` 改为 `[2]`。
3. **`validateAdditionalTools` 修复会让一处既有测试的夹具失效**：`test/agent-runtime.test.ts` 的 registry 上限测试把 faux 模型注册为 `tiny-context`，而配置里的 `agent.model` 是 `agent-model`；改用 switcher 解析后在用模型时解析失败。处理方式是让夹具模型 id 与配置一致（仍为 1000 token 窗口），断言 `'Tool registry exceeds 10%'` 未变。
4. **快照显式化后，`test/context-hot-inject.test.ts` 的 prompt 重建测试需要与 override 匹配的快照**：该测试原本用「改了 system prompt 的 runtime」配「默认 config 的快照」，会导致两次运行同 prompt。夹具新增 `runtimeAndSnapshot()`（`runtimeWith()` 保持原签名），测试改用匹配的快照；断言未变。
5. **`MediaService` 的 `prompt_version` 也随构造冻结**：它参与 `analysis_version` 缓存键，属于「Vision 模型描述」的一部分，因此与 semaphore 一起在构造时取值，而不是每次 `current()`；运行期仍按 `current()` 读的只有 media_cache 路径、`vision.max_output_tokens` 与两处日预算。

## 说明未覆盖、自行决定的地方

- `ContextBuilder` 三个方法的 `config` 参数放在首位；`AgentRuntime` 四个私有方法的 `config` 参数同样放在首位。
- `scheduler.#execute` 在 handler 结束后推 bucket deadline 时读 `current()`（不属于 invocation 运行期，按读取规则表「其它所有地方」处理），快照只交给 handler。
- `MediaService` 新增私有字段 `#visionPromptVersion` 与 `#analysisVersion`（见上）。
- 新测试放在新文件 `test/runtime-config-snapshot.test.ts`；其中「scheduler 在 `queued → running` 取快照」一条通过在测试里覆盖 store 实例的 `current()` / `beginInvocation()` 模拟一次「发布」（Phase 0 没有 reload 入口），从而断言快照取自转换时刻而不是构造时刻。
- 既有测试需要 store 时，一律通过各自 fixture 暴露 `configStore` 字段；`test/helpers.ts` 的 `renderInvocationContext` 保持 `config` 参数不变（内部传给 `ContextBuilder` 方法）。
