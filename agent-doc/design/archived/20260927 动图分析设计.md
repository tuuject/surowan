# 动图分析：Storyboard、按时间补帧与观察缓存

设计记录：2026-09-27；同日修订：首期只处理 Telegram 无声 MP4、删除 focus 与增量合并缓存、vision 循环并入统一 Invocation 审计。目标是让聊天模型按需理解 Telegram animation 的内容、动作顺序和文字变化，同时限制解码、模型调用和重复分析成本。

## 1. 已认可方向与待定项

| 层级 | 内容 |
| --- | --- |

12 是单张 storyboard 的上限，不是单次分析总帧数，也不是准确率保证。[前期研究](../../docs/research/im-gif/README.md#对-llm-输入的建议有界起点不是已验证最优方案)中的“总计 24 张”只是实验建议，**没有被批准为产品预算**。

研究得到的 381 个有变化样本记录来自三个便利选取的公开仓库，不是 IM 流量分布；存在跨库重复。中文合集时长中位数约 1.5 秒，reaction 收藏约 2.82 秒，最长观测为 36.6 秒。它们支持“短片段优先、长尾另设预算”，不证明 12 帧足够。研究对象是 GIF 文件，其时长分布可作参考，但 GIF 专有的 delay/disposal 结论不适用于首期 MP4 路径。尚未进行 LLM 准确率评测或 Telegram 转码前后时序对照。

## 2. 输入范围与现有接入点

首期只支持 Telegram `message.animation`，且声明 MIME 为 `video/mp4`（或缺失、待下载后验证），实际容器为 MP4、视频编码为 H.264、无音轨。[Telegram GIF 说明](https://core.telegram.org/api/gifs)说明上传的 GIF 会被转成无声 MPEG-4；[Bot API Animation](https://core.telegram.org/bots/api#animation)的定义同时覆盖两者，但聊天中实际流通的主体是 MP4。

以下不在首期范围，维持现状（不作为可分析媒体入库）：作为 `document` 发送的 GIF、声明为 `image/gif` 的 animation、普通 `video`、任意 MP4 Document、APNG、动态 WebP、音频理解和动图发送。Sticker 搜索/索引的代表帧路径保持不变。

### 2.1 GIF 的技术预留

只保留不增加首期代码量的预留，不写 GIF 分支、配置项或额外 kind：

- 时间轴、`frameAt`、状态合并、storyboard、结果协议都以“完整显示状态 + `[start, end)` 区间”表达，与容器无关。
- 动画模块内部按**已验证的**容器选择解码器；首期只有 MP4 一种实现，其他容器一律明确拒绝。
- `metadata_json` 记录 `container` / `codec`，`analysis_version` 包含解码器版本；将来加入 GIF 时不会与 MP4 缓存混淆。
- 研究中 GIF delay 归一化与 disposal 合成的发现保留在[研究文档](../../docs/research/im-gif/README.md#交叉验证发现的坑)，作为将来重新评估的输入，不在本设计中定案。

## 3. 整体流程与入库分流

```text
Telegram animation (MP4)
  → allowlist、消息 Revision 与 media(kind=animation)
  → Context 只注入媒体标记 + img_ 引用（不自动附图）
  → 主模型通过 execute.call → read_image({ image_ref })
  → 校验引用、TTL、媒体仍存在 → 当前分析版本缓存
  → 未命中：有界下载 → 验证容器/编码 → 单次解码建状态索引 → 首张 storyboard
  → Vision 局部循环：请求时间帧 或 提交结构化观察
  → 校验观察与 runtime 覆盖记录 → 保存 → 返回不可信观察
```

入库建议：

- `message.animation` 优先于 `message.document`。[Message 契约](https://core.telegram.org/bots/api#message)明确 animation 会同时设置 document 以兼容旧客户端，必须只入一份媒体，不能重复计费或重复生成引用。
- 规范化为 `media.kind = animation`；保留原始 Telegram 元数据，沿用消息修订和快照机制。
- MIME、文件名、声明时长/尺寸只是线索，不是安全判断。声明 MIME 为非 `video/mp4` 的 animation 不入库为可分析媒体；MIME/大小缺失时仍入库，由下载器限流，并在转换前验证实际容器和编码。
- 声明大小已超限时提前拒绝；容器不是 MP4、含音轨、编码不是 H.264、时间轴不可确定时返回明确的不支持/分析失败，不偷偷当一张缩略图成功。
- 保持静态图片现有分流：支持图片的主模型仍直接接收静态图。无论主模型是否支持图片，动图均走受限分析入口，避免两套不同的帧选择、缓存与计费语义。
- Context 继续由 `ConversationContextStore` 单写者维护；不把 vision 的局部逐轮 transcript 或 storyboard 二进制写入 canonical history，只保留外层工具调用、观察结果及必要引用。

## 4. 时间轴与取帧契约

### 4.1 完整显示状态

统一使用相对首帧显示时刻的秒数，源时间基和精度保留在 metadata。单轮时长 `T` 不乘循环次数；Telegram animation 在客户端循环播放，只分析一轮。

- 按解码后的 presentation timestamps 排序，归零后建立显示区间；不能用 DTS、固定 FPS、关键帧位置或整数声明 duration 替代实际显示时间。末帧结束时间须来自可验证的时间信息（如末帧 duration 或流结束时间），不可凭空补时长。
- 只合并**连续**像素完全相同的画面，保留合并后的 `[start, end)`。非相邻 A→B→A 必须保留两次 A；首期不增加感知去重或复杂场景检测。
- **解码一次**：顺序解码时建立状态索引，并把每个去重后的状态按预算缩放后写入本次分析的临时目录；首张 storyboard 和后续补帧都按索引取图，不再按时间 seek，也不重复解码。这样取帧结果与标注时间轴天然一致。
- 不把全部 RGBA 帧常驻内存；状态数、临时磁盘和解码像素都受硬上限约束。超出上限时分析失败或明确标记截断，不能截前几秒后伪称完整单轮。

研究发现容器 `format.duration` 可能不等于显示区间之和，帧数必须来自真实解码图片，不能拿 packet 数代替。依据与复现见[研究的交叉验证记录](../../docs/research/im-gif/README.md#交叉验证发现的坑)；MP4 路径须用自己的 fixture 重新验证。

### 4.2 按时间请求

`frameAt(t)` 的语义为返回满足 `start <= t < end` 的完整显示状态，而不是“最近的编码帧”或“最近关键帧”。

- `t` 必须有限且 `0 <= t < T`；负数、非有限数、越界和 `t = T` 明确报错，不静默夹取或取模。
- 初始采样直接选取已知末状态，不用请求 `T` 来凑末帧。
- 每项结果包含 runtime 生成的 `frame_id`、请求时间、实际显示起止时间、规范化尺寸及图片；同一状态命中多个时间点时复用帧并返回对应映射。
- 首轮 storyboard 中已出现的状态仍可按时间返回独立大图，以查看小字；不能因为时间相同就只返回“看过了”。复用像素文件不等于免除再次给模型看图的成本。
- `frame_id` 只是本次分析内的证据标识，不是可跨会话、跨媒体读取的 capability。补帧函数由外层已授权媒体闭包绑定，不接受 file ID、路径、URL 或另一份 `image_ref`。

## 5. 首轮采样与 Storyboard

以研究中的时间均匀策略为最小基线，先评测再调参。令 `S` 为连续去重后的状态段数：

1. `S = 1`：视觉上按单张静态内容处理，仍保留动图来源、时间轴和分析版本，不回落到未授权的直传路径。
2. `2 <= S <= 12`：每个状态一格。
3. `S > 12`：取 `K = 12`；首尾占两格，内部目标 `i*T/(K-1)`，`i=1..K-2`。
4. 时间点映射到状态段后按时序去重，实际格数可以小于 `K`；不为凑满 12 格重复图片，也不跨时间去掉 A→B→A 中的 A。

修订说明：原公式 `K = min(S, 12, max(4, ceil(2*T)))` 会在 `S = 12`（12 格）与 `S = 13, T = 1.5s`（4 格）之间出现断崖：状态越多、画面越忙，格数反而骤降。评测前先用 12 格；如果要按时长减少格数，应基于评测数据，而不是当前公式。

Storyboard 按行从左到右、从上到下排序；布局随格数选择，不固定拉伸成 12 格。等比缩放、留边、不裁掉字幕。

### 5.1 时间标注与时长

模型必须同时从图像和文字两处知道每一格的时间位置，以及整个动画有多长：

- **动画时长**：统一使用 4.1 的单轮显示时长 `T`（秒），由解码后的显示区间计算。Telegram `animation.duration` 是整数秒声明值，只作线索，不作为告诉模型的时长；容器 `format.duration` 同理。
- **图上标注**：storyboard 顶部留出标题条，写明总时长和格数，例如 `duration 2.84s · 12 frames`。每格在画面**外**的标签条写明 `frame_id`、采样时间点及该状态的显示区间，例如 `f07 @1.29s [1.27–1.33s)`。标签不能覆盖画面，以免遮住字幕。
- **文本 manifest**：与 storyboard 一同发送，是权威来源（图上的数字只是方便对照）。内容包括：`duration_seconds`、状态段数 `S`、实际格数；每格的 `frame_id`、采样时间点、`start` / `end`；以及未采样区间。时间统一以秒为单位，保留到毫秒。
- **补帧结果**：独立大图采用同样格式的标签条，tool result 文本中给出同样的时间字段，让模型知道每张图对应的时刻。
- **返回主模型**：最终观察中包含 `duration_seconds`，时序事件和可见文字都带秒级时间位置，让主模型能说出“最后 0.5 秒出现了字幕”这类结论。
- **渲染依赖**：标签用 Sharp 叠加 SVG 文字，只使用 ASCII 数字与字母，避免依赖 CJK 字体；Docker 镜像中必须有可用字体，并在 `doctor` 或测试中验证文字确实渲染出来（缺字体时 libvips 可能静默输出空白或方框）。

每张最多 12 格不代表“拼成一张图就不花视觉 Token”。整图尺寸、单格可读分辨率、编码字节和每轮图片总量都要限额；不能套用静态图缩放后让文字小到不可读却报告看清。需要细节时用独立补帧图。首期不把多张 12 格拼版当绕过总帧预算的方法。

覆盖整条时间轴的**采样范围**不等于覆盖所有状态。对快闪文字、短动作与反转保持不确定性。

## 6. 受限 Vision 循环与结果协议

这里的 vision subagent 指 `MediaService` 内的一段有界模型循环，不新增通用 agent 平台。沿用已配置的 vision 模型和[分析开始时的配置快照](../../src/capabilities/media/media.ts#L92)，整个循环固定模型、prompt、schema 和策略版本。

主模型的调用契约不变：`read_image({ image_ref })`，不增加任何参数。

Vision 仅获得当前媒体的 storyboard / 帧和 runtime manifest，不获得聊天历史、发送者身份、记忆或主模型工具。仅暴露两个局部工具（名称为建议契约）：

| 工具 | 输入与行为 |
| --- | --- |
| `request_animation_frames` | `{ times_seconds: number[] }`，非空、有界数组；逐项校验实际时轴和总预算，返回按时间定位的画面与映射。 |
| `report_animation_analysis` | 一次提交结构化中立观察：内容概述、动作顺序、可见文字、每项观察的证据 frame ID、未确定项。 |

一次模型回复只接受一个协议动作。未知工具、混合提交/补帧、非法时间和额外字段不得执行；错误可作为有界工具结果供下一轮纠正，但也消耗轮数。普通文字不是最终成功报告。达到预算时可以要求提交已有观察，但仅当总 deadline/轮数仍有余量，不能为了收尾无界追加调用。

补帧结果以图片形式放在 tool result 中。pi-ai 在不支持 tool result 图片的 API（如 openai-completions）上会拆成附带图片的 user 消息；实施时依赖这一行为，并用真实 vision Provider 验收。

最终返回与缓存建议包含：

| 字段组 | 来源与校验 |
| --- | --- |
| `summary`、时序事件、`visible_text` | 模型提供；每个具体断言引用实际提供过的 `frame_id`，文字与事件保留时间位置，不缓存“发送者在讽刺谁”等语境解释。 |
| `uncertainties` | 记录看不清、缺少动作中段等限制；不要求伪精确的概率分数。 |
| 媒体/策略元数据 | runtime 生成容器、编码、尺寸、时长、时间策略和分析版本。 |
| `observed_frames` / `observed_intervals` | runtime 记录本次实际呈现过的状态区间、呈现方式/分辨率；不允许模型虚构已看范围。 |
| `coverage` / `stop_reason` | runtime 区分 sampled / all-states-observed / partial，以及正常收尾、预算限制等；“全部状态看过”也不保证语义理解完整。 |

输入和输出均用 TypeBox 校验，并限制数组长度、文本长度、JSON 总大小、时间顺序和证据引用。所有观察继续作为不可信媒体数据交给主模型；画面/字幕中的指令不能获得任何执行权限。

## 7. 缓存与并发

### 7.1 键与存储

复用 `media_analyses` 的 `(file_unique_id, analysis_version)` 唯一键，新增 `kind = animation`，`description` 保存紧凑概述，`metadata_json` 保存上述经校验的结构。不新增逐帧永久存储表，不按聊天制造多份缓存。

动画 `analysis_version` 须有独立 namespace，并包含模型/Provider 身份、prompt、输出 schema、解码器、采样与 storyboard 策略版本；会改变产物的预算 profile 也需进入指纹。热切换不能把旧模型分析当作新模型缓存。具体编码格式在实施时集中维护，不拼入凭据。

当前[静态图片实现](../../src/capabilities/media/media.ts#L34)是固定 30 天缓存，Sticker 无过期；**不是已经存在的动图策略**。建议动图 TTL 与必填 `retention.online_days` 对齐，具体规则待定；不得无限期留下用户动画观察。保留清理同步覆盖 animation，缓存过期和引用过期是两个独立条件。

### 7.2 读取

- 先 `resolveMedia`、校验当前 Context/TTL/媒体存在，再查缓存或加入 in-flight；缓存命中路径也不能绕过授权。失效引用不能靠 `file_unique_id`、旧结果或另一会话补活。
- 缓存有效时直接返回中立观察及覆盖限制，包括明确标记的 partial；不自动重跑，也没有“补看/升级”路径。partial 结果在版本或 TTL 失效前保持原样，主模型据 `coverage` 与 `uncertainties` 自行措辞。
- 未命中时完整跑一次分析。沿用现有 pending → success/error 写法：因为只有在没有有效 success 行时才会分析，覆盖的只可能是过期或失败的旧行。
- `state = success` 表示协议完成、结果可用，不表示已看全。受预算限制但提交了有效部分观察可保存为 success + partial；未提交有效报告、超时或解码失败不能保存为成功观察。

### 7.3 单次复用与并发

一次分析内保留源文件、状态索引和有界帧文件，结束后清理临时目录。持久媒体/拼版缓存不做。

复用现有同键 in-flight 思路：相同媒体/版本的分析合并为一个共享作业。共享作业与各调用的等待必须分离：等待者用自己的 deadline/AbortSignal 截止等待并完成自身工具审计，不能直接返回共享 Promise 而忽略自己的超时，也不能因此取消共享作业。等待者退出不延长作业；发起者取消则共享作业失败，其他调用得到明确可重试结果，不创建脱离 Invocation 的后台分析。

发起者负责本次预算与模型审计；等待者不重复记模型 Token，但其审计记录须能关联到共享的分析（见 8.3）。

## 8. 资源、安全与审计边界

### 8.1 预算与资源

| 预算/边界 | 要求 |
| --- | --- |
| 每张 storyboard | 最多 12 个关键帧；含首尾。 |
| 下载 | 不放宽现有 20 MiB 下载上限；实际流量计数，不仅检查声明大小。 |
| 解码 | 单帧像素、状态数、累计解码像素、源时长、临时磁盘与子进程墙钟均有硬上限，定值前不得上线。新增解码并发上限（现在不存在）。 |
| 模型输入 | 总呈现状态数、补帧调用数、累计呈现图片/像素/字节和 Token 分别计数；重复请求同一状态也消耗调用/输入预算。 |
| 轮数与超时 | 整个 `read_image` 共用一个绝对 deadline，包含下载、排队、解码、模型重试和补帧；受父 Invocation 取消约束，不逐轮续期。**现有 30 秒上限（`media.ts:199`）与 `runExternal` 的固定 30 秒（`media-image.ts:177`）装不下多轮循环**：动画路径需要单独的总时长（仍不超过 Invocation deadline），子进程超时和 vision 重试延迟都按剩余时间收紧。主模型在此期间阻塞等待工具结果，这个代价计入取值考量。 |
| 输出 | 拼版与独立图的尺寸/字节、结果 JSON 大小均有界；现有静态图的 40M 解码像素和 10 MiB 输出不能被当成多帧总预算。 |
| 并发与费用 | 沿用 Vision semaphore 与 modelGate；预算改用独立的看图预算（8.4），不再使用 `agent.daily_budget`。`modelGate` 按 chat 与主 agent 共用：**每轮获取、每轮释放**，解码和轮间处理期间不持有。动画循环每轮请求前检查剩余预算，每轮结果计费；现有单次分析入口检查不构成多轮保障，不能只记最后一轮。 |

解码复用[既有 subprocess 边界](../../src/capabilities/media/media-image.ts#L51)：固定可执行文件和 argv、仅受控本地临时文件、最小环境、禁止 shell、禁止网络/播放列表/外部文件引用。显式指定 MP4 demuxer（参照 Sticker 的 `VIDEO_STICKER_INPUT` 写法）并验证单文件结构；`file` 协议白名单本身不等于只允许当前路径。取消/超时要回收进程和文件，不能仅返回错误而遗留 FFmpeg。

局部补帧/报告工具没有 `send`、`execute`、MCP、任意文件访问或发布能力。它们不加入主模型的 capability 注册表。工具文档只说明能力，不扩大授权。

### 8.2 突发与斗图

群聊斗图会在短时间内刷出大量动图，而此时模型恰恰最想逐个看懂。仅靠 8.1 的单次分析预算挡不住，因为现状有四个放大因素：

- **次数不设限**：Invocation 内的工具调用只计数不限次（[agent-runtime.ts:617](../../src/orchestration/agent-runtime.ts#L617)）；`idle_grace_seconds > 0` 时新 Bucket 会持续 attach 到同一 Invocation，每张新动图都可能触发一次 `read_image`。
- **单张成本被放大**：多轮设计下一张动图是 storyboard 加补帧，要 2～3 次 vision 调用、十几张图。
- **日预算是全局共享的**：[sleep.ts:48](../../src/store/sleep.ts#L48) 把所有 chat 的 `model_tokens` 加总后与 `agent.daily_budget` 比较。一个群斗图可以烧光全部额度并触发 sleepy，所有群一起失声。8.4 把看图用量从这份预算中拆出，解决的是“看图拖垮聊天”；本节其余要求解决的是“一个群的看图挤占其他群的看图”。
- **排队拖垮 deadline**：`modelGate` 按 chat 串行，同一 chat 并发的多个分析会排队，一起耗尽各自的 deadline，主模型全程阻塞。

要求（阈值见第 10 节）：

1. **缓存优先，命中免费**：缓存命中不消耗下面的闸门和动图预算，in-flight 等待者同样不计。斗图素材重复率高，从收藏夹重发同一动图预期复用同一文件、得到相同的 `file_unique_id`，**须用真实 Telegram 验证**；若不成立，缓存对斗图帮助有限，需要重新评估，但首期不引入感知哈希等跨文件去重。热切 vision 模型或 prompt 版本会让动图缓存整体失效，运维文档需要提示这一点。
2. **动图分析闸门**：在授权与缓存检查之后、加入 in-flight 或开始下载之前检查，只统计缓存未命中且真正发起的分析。
   - 每个 Invocation 的动图分析次数上限。
   - 每个 chat 的滑动时间窗口次数上限。计数优先从已有审计行推导，不新增状态表，重启也不清零。
   - 每个 chat 同时进行的未命中分析数上限（建议 1）。
   - 超限**立即拒绝，不排队**，返回可区分的错误码（如 `animation_rate_limited`）。工具结果说明这是限流而不是内容问题，模型可以自然地表达“刷太快了看不过来”；不得退回缩略图冒充已理解动画。
3. **按群的看图额度**：在 8.4 的全局看图预算之内，再给每个 chat 设每日看图 Token 上限，防止一个群斗图把全局看图预算用光、别的群连静态图都看不了。每轮 vision 请求前同时检查按群额度和全局看图预算。超出时返回可区分的错误码（如 `vision_budget_exhausted`，并注明是本群额度还是全局额度）。
4. **默认一轮为主**：斗图动图多为短片、大字，首轮 storyboard 通常就够。首期补帧预算从很小的值起步（例如 0～1 次补帧调用），让多数动图只花一次 vision 调用；是否放宽由评测决定。
5. **Skill 引导**：[image-inspection Skill](../../src/system-resources/skills/image-inspection/SKILL.md) 说明刷屏时不需要逐张查看，优先看回复或提及自己的、或最新的一张。这只是弱约束，硬边界仍由第 2、3 条保证。

限流和预算拒绝都照常写外层 `read_image` 的 `tool_calls` 拒绝行和错误码，在 Invocation 审计页面可见；此时不产生 vision `model_calls`，也不发起下载。

### 8.3 审计：并入统一 Invocation 页面

不为 vision 循环创建独立的 `invocations` 行（那会牵动调度、队列和预算语义）。循环属于发起 `read_image` 的 Invocation，在该 Invocation 的审计页面中嵌套展示。

- **外层**：`read_image` 仍是主模型 Invocation 中的一行 `tool_calls`，记录参数、成功/拒绝/错误和错误码。
- **每轮模型调用**：单独写一行 `model_calls`，沿用 `invocation_id`、`role = vision_chat`、`media_analysis_id`；新增可空列 `parent_tool_call_id` 引用外层 `read_image` 的 `tool_calls.id`，并记录轮次序号。`tools_json` 记录本轮实际提供的两个局部工具，不要误记主模型全部工具，也不要只记首轮。
- **请求/响应**：vision 调用目前不写 `request_json` / `response_json`，需要按[主模型的传输审计方式](../../src/orchestration/agent-runtime.ts#L551)补上 `onPayload` / `onResponse`，并经过[图片脱载](../../src/platform/model-request-audit.ts#L12)。现有脱载只识别 `data:image/…;base64,` 形式的字符串；须确认所配置 vision Provider 的 payload（例如裸 base64 字段）同样会被脱载，不得把 storyboard base64、Telegram 下载凭据、未脱敏 Provider 错误写入审计。
- **局部协议动作不写 `tool_calls`**：这些动作没有副作用；vision 模型发出的 tool call 本体已在该轮 `response_json` 中，runtime 返回的结果（帧映射、校验拒绝）在下一轮 `request_json` 中。最后一轮之后的终止原因写入 `metadata_json.stop_reason`，并体现在外层 `read_image` 的状态与错误码上。这样 `tool_calls` 仍只代表主模型的工具面，不影响工具计数、工具统计（[audit.ts:840](../../src/ingress/admin/audit.ts#L840)）和 `tool_call_id` 唯一约束。
- **Admin Panel**：Invocation 详情 API 的 model call 条目增加 `media_analysis_id`、`parent_tool_call_id` 和轮次；时间线把带父级的 vision 轮次嵌在对应 `read_image` 卡片下，显示轮次、Token 和 `stop_reason`。Invocation 列表的 Token/费用汇总本就按 `invocation_id` 统计，vision 用量会自然计入。
- **缓存命中与 in-flight 等待者**：本 Invocation 中没有 vision `model_calls`，但其 `read_image` 行须能关联到 `media_analyses.id`，从而跳转到发起分析的 Invocation。具体落点（如 `tool_calls` 新增可空 `media_analysis_id`）实施时决定。
- **状态语义**：模型传输成功与结构化报告有效是两件事；报告解析/证据校验失败必须反映在外层工具/分析的错误状态上，不因模型返回普通文字就记为业务成功。缓存命中没有新的模型账单；累计失败也要保留已经发生的用量。格式错误、越界、未授权、解码超限、超时、模型失败和协议错误应有可区分的错误码。

### 8.4 看图预算与群聊预算拆分

现状：`agent.daily_budget.max_tokens` 是主 Agent 与聊天触发的 `read_image` 共享的全局 Token 熔断（[configuration.md](../configuration.md)）；`vision.daily_budget` 只约束后台 Sticker 索引。看图用量越大，留给聊天的额度就越少，额度偏低时还会触发 sleepy。

改为：

- **范围**：所有聊天触发的 vision 调用（`model_calls.role = vision_chat`），包括现有静态图 `read_image` 和新增动图。它们属于同一个识图 subagent，放在同一份预算下，避免“静态图算聊天、动图算看图”这种两套口径。支持图片的主模型直接收到的 `figure_N` 图片属于主模型输入，仍计入 `agent.daily_budget`。
- **计量**：沿用 Token 口径（`meteredTokens`），不改成金额。理由与 `agent.daily_budget` 相同：免费模型的 `cost` 恒为 0，按金额计就等于给它们拆掉闸门。
- **记账**：`vision_chat` 用量从 `daily_usage` 的 `model_tokens` 移到独立 metric（例如 scope `chat`、resource 为 chat、metric `vision_tokens`）。`readDailyTokenBudget` 只汇总 `model_tokens`，因此不再包含看图用量；sleepy 判断也随之不受看图影响。已有历史数据不回填，从上线当天起按新口径记。
- **配置**：新增聊天看图的全局日预算，与 `agent.daily_budget` 并列；不复用 `vision.daily_budget`，避免斗图挤掉 Sticker 后台索引。8.2 的按群额度是它之下的子上限。新字段是否热更新与 8.2 的阈值一起定。
- **优雅降级**：看图预算耗尽后，`read_image` 对缓存命中仍然正常返回（不花额度）；未命中则立即返回 `vision_budget_exhausted`，不下载、不调用模型。主模型照常聊天，Skill 与工具描述说明此时应如实说看不了，不能编造画面内容。
- **可见性**：Admin 用量统计与 `/status` 需要分别展示聊天用量与看图用量；Invocation 列表的 Token/费用汇总按 `model_calls` 计，本来就包含 vision，不受影响。

实现后的最低验证：受影响测试、`pnpm run check`、`pnpm run lint`、`git diff --check`；这是跨模块改动，最终还需完整 `pnpm test`。真实 Telegram/Provider/转换链路未执行时单列“未执行”，不能用自然语言回复或 mock 代替验收证据。

## 10. 开工前需要定值的参数

- **预算**：首轮以外的总状态/呈现图片数、单次补帧数组长度、总轮数、重试与 Token 上限；24 不自动生效。补帧从 0～1 次起步。
- **斗图闸门**（8.2）：每 Invocation 动图分析次数、每 chat 滑动窗口的长度与次数、每 chat 并发数；每 chat 每日看图 Token 上限；这些字段是否进入热更新白名单。
- **看图预算**（8.4）：聊天看图全局日预算的字段名、默认值与热更新归类；metric 命名；Admin/`/status` 的展示方式。
- **时长**：动画 `read_image` 的总 deadline（高于现有 30 秒）、子进程超时如何按剩余时间派生。
- **时间策略**：MP4 末帧结束时间的可接受来源；时间精度与归一化规则的版本。
- **图像/解码资源**：拼版布局与单格分辨率、整图尺寸/输出字节、源时长、每帧与累计像素、状态数、临时磁盘、解码并发上限。
- **缓存**：与 online retention 的 TTL 对齐方式、版本指纹字段。
- **审计落点**：缓存命中/等待者关联共享分析的具体列。

这些参数应由受控 fixture 和小型人工标注评测定案；不要把便利样本最大值或“12 格”反推为服务器安全上限。可以先开展 fixture/纯解码实验，未决项没有定案前不应默认放大生产预算。
