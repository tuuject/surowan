## 1. 目标与范围

### 1.1 长期愿景：两条插件接入渠道

长期区分两类插件，按不同职责与接入契约演进：

- **IM 接入插件**：对接通信平台，处理外部事件接收、平台会话与参与者映射、消息发送和媒体适配等接入职责。Telegram 接入模块化及未来其他 IM 接入属于这条渠道。
- **Agent 插件**：扩展 Agent 在已有会话中的业务能力，提供工具、Skill、业务状态、上下文贡献及必要生命周期行为。`web_fetch`、memory、alarm 属于这条渠道。

两类插件不强行合并为一套万能功能接口。是否复用定义辅助函数或生命周期基础设施留待实际需求验证；本轮不设计或实现 IM 插件接口。

### 1.2 本文只计划内置 Agent 插件

将现有内置 Agent 能力按插件形态组织，为未来用户自行开发 Agent 插件保留合理的技术空间，但本轮不交付用户插件平台。除明确讨论 IM 接入时外，本文后续的“插件”均指 Agent 插件。

首批候选能力：`web_fetch`、memory、alarm。IM 接入插件只是远期方向，不是这三个 Epic 的交付项或前置条件；不要求本轮把 Telegram 接入、发送路径或数据模型平台无关化。

当前没有向用户（Bot 管理员）开放插件系统的时间表。技术预留的目标是避免依赖关系阻碍未来演进，而不是提前实现安装、分发、兼容与隔离体系。

验收标准是：这些内置 Agent 能力具备清楚、可测试的模块边界，而不是“第三方现在就能写插件”或“增加能力不需要修改主仓库”。

## 2. 已确认的方向

### 2.1 Agent 插件的作者形态

一个 Agent 插件是一个 ES Module，导出由 `definePlugin` 定义的 type-safe object，在对象中声明功能、必要生命周期钩子与 Skill 暴露。

建议采用如下形状；键名和具体类型尚未定案，也不代表现有 API：

```ts
export default definePlugin({
  id: "memory",
  skills: [memorySkill],

  setup(host) {
    const memory = createMemoryService(host.storage);

    return {
      capabilities: (scope) => memory.createTools(scope),
      context: {
        injection: (scope) => memory.render(scope),
      },
    };
  },
});
```

配套边界建议：

- 模块顶层只声明定义；实例初始化与启动在宿主控制下进行，导入模块不启动后台任务或自行打开数据库。
- 插件定义与运行实例分开；必要的 `setup`、启动和关闭接口由真实需求决定，不要求每个插件实现空钩子。
- 功能贡献与生命周期分开：工具、Skill、上下文贡献是明确接口，不做任意 `beforeX` / `afterX` 事件钩子总线。
- 工具按 Invocation 装配；运行中的会话状态由宿主提供，支持热注入刷新，不捕获一份永不更新的启动期上下文。
- `definePlugin` 负责类型推导，不代替加载时的定义校验、配置校验和重名检查，更不构成安全沙箱。

本轮只需要显式 import 内置模块并装配，不需要动态扫描、安装或加载用户代码。

### 2.2 只抽象真实接入点

沿用现有 `execute` 能力调用与审计路径，不新增另一套工具分发体系。

- 单个能力独有的业务逻辑留在能力模块内。
- 确有共同需求的机制，再通过窄宿主接口提供。
- 插件不持有整个 Runtime、全局配置或全局数据库作为默认业务依赖。
- 上下文贡献由宿主统一装配与写入；插件不直接修改 canonical history。
- 稳定提示说明与每批动态注入分开，维持 system prompt 稳定性。
- 插件声明 Skill 资源，宿主统一提供索引、只读解析与校验；Skill 不授予权限。

插件化不改变 `send`、授权、预算、审计、引用隔离与上下文单写者等安全和一致性边界。

## 3. 存储与 migration 的最终收敛

### 3.1 本轮保留现有数据库机制

继续使用现有单 SQLite、Drizzle、核心迁移编号、迁移执行流程、保留清理与备份机制。

- 不新增插件迁移器、插件版本账本或升级命令。
- 不修改已发布迁移，不为了插件化重写历史。
- 不为了表名前缀、独立数据库文件或形式统一而搬迁已有数据。
- 如实际重构确实要求 Schema 变化，沿用现有迁移机制并验证旧数据库升级。
- 不承诺数据库无关存储层，不另造通用 ORM，也不把所有插件限定为 JSON KV。

### 3.2 现在要做的数据边界

明确插件业务数据的归属，把查询和写入收拢到该能力自己的 Repository / Service 内。其他模块不应散落着操作这些业务表的实现。

例如：

- memory 的内容、期限及业务查询归 memory 模块；上下文与管理入口调用其服务。
- 工具审计仍由既有宿主审计机制承载，web fetch 不需要为了成为插件新增业务存储。
- alarm 业务数据与入队、恢复等运行机制之间的事务边界需要保留，不能只按文件位置强行拆开。

逻辑归属清楚不等于必须立即物理拆表或拆库；表定义和迁移执行仍可留在现有中央机制中。全局保留清理若仍需要认识这些表，可作为明确记录的内部耦合，不因此引入通用维护插件协议。

### 3.3 独立 migration 仅作为未来议题

讨论过“插件独立迁移历史、宿主统一执行”的方向，但最终决定当前不实现，也不把它列为首轮验收条件。

将来确实需要独立分发插件时，再决定迁移声明、版本账本、校验值、升级入口以及现有表与数据的接管方式。接受届时需要一次有计划的迁移工作，不提前消灭全部未来成本。

## 4. 前端与功能开关

前端继续作为固定的产品界面实现，不为插件贡献前端内容设计接口。

- 页面、菜单、路由、组件和 API 请求均可写死。
- 新增一个内置能力时，允许同步修改前后端。
- 不做动态加载插件前端包、插件 UI SDK、菜单/路由/组件插槽或 Schema 自动生成页面。

如果本轮引入功能开关，使用最小实现：

- 后端给出实际生效的功能状态，前端据此隐藏菜单、停止无意义的对应请求。
- 直接访问关闭功能的页面时明确显示不可用，不仅隐藏入口。
- 后端执行开关约束；关闭后的工具、Skill、动态上下文贡献、后台触发及管理写入不能继续提供被关闭的功能。
- 停用不等于删除业务数据或历史审计。停用时待执行 alarm、恢复启用后的到期任务处理，需要单独定清楚。
- 管理写入与历史只读审计分开，不把停用做成绕过认证或删除审计记录。

这不是插件管理面板需求。开关的配置位置、作用域及是否本轮新增仍需在实施对应 Epic 时确定；不自动引入运行期热启停。

## 6. Agent 插件的建议 Epic 拆分

以下三个 Epic 仅覆盖 Agent 插件，建议按 `web_fetch → memory → alarm` 推进。该顺序用于逐步验证真实接口，不是三个并行开发任务，也不先独立建设一套完整插件框架。IM 接入插件另行规划，不并入本轮。

### Epic 1：最小定义与装配 + web fetch

目标：验证 ESM / `definePlugin` 形态和完整工具贡献链路。

工作：

1. 定义最小插件描述、运行实例与必要类型；确定符合现有分层的目录与依赖方向。
2. 在组合根显式装配内置插件，保留现有原语、MCP 与内部能力的区别。
3. 将 web fetch 迁为首个模块，接入既有 `execute` 与审计，不另建业务数据库。
4. 支持该模块实际需要的只读 Skill 贡献及冲突校验；不做通用资源扩展平台。
5. 将依赖限制在实际所需的宿主服务，不暴露整个 Runtime。

验收：

- 通过注册接入能力，不为该能力修改 Agent 循环的业务分支。
- 原有名称、参数校验、返回边界、网络限制、超时、取消与审计语义不退化。
- 不导入第三方插件加载、安装或兼容体系。

### Epic 2：memory 模块化

目标：验证有状态能力、每批上下文贡献与管理入口的边界。

工作：

1. 收拢记忆读写、TTL 规则及业务 Repository，迁移现有 Tool 调用方。
2. 通过最小上下文贡献接口提供稳定说明和每批记忆列表，移除 ContextBuilder 内嵌的具体记忆业务实现。
3. 管理后端复用记忆服务；前端页面保持固定实现。
4. 维持现有表、迁移、清理和备份；如引入功能开关，同时覆盖工具、Skill、注入与写入入口。

验收：

- Conversation 隔离、TTL、创建顺序、持久化审计和管理 CRUD 行为保持一致。
- 动态记忆不进入稳定 system prompt，canonical history 仍由宿主唯一写入。
- 不出现只搬 Tool、核心仍复制一份记忆业务逻辑的双路径。
- 若支持停用，不继续注入记忆或接受该功能写入，数据保留规则明确。

### Epic 3：alarm 模块化

目标：分清提醒业务与宿主执行机制，在保持可靠性的前提下收拢耦合。

工作：

1. 梳理创建、列举、删除、owner 校验、任务说明、隐藏观察与管理查询的归属。
2. 通过最小调度/入队接入点衔接现有 Scheduler，不让插件另起调度循环。
3. 保持 `pending → firing` 认领、Invocation 创建及关联的原子性，维持终态收尾与重启恢复规则。
4. 处理暂停、Chat/Topic 允许范围、睡眠及预算等既有边界；如新增停用开关，先定清待执行任务语义。

验收：

- 同 Chat 串行、可信 caller/owner 派生和会话隔离不退化。
- 重启后遗留 `firing` 按既有规则收尾为 `fired` / `outcome_unknown`，不退回 pending 盲目重发。
- `list_alarm` 的隐藏映射可跨 Invocation 恢复，后续操作仍重新验证 ownership 与状态。
- 不把两个独立提交的“业务状态更新”和“入队”当成一个事务。

曾讨论通用 `host.tasks`、事务发件箱和独立任务存储，但它们不是本 Epic 的必做项。先使用现有数据库事务和调度机制；只有实际接口需要时才抽取最小共享部分，不借 alarm 重构建设通用任务平台。

## 7. 明确不做与尚未定案

### 本轮不做

- IM 接入插件接口、Telegram 接入插件化、第二个 IM 适配，以及为多平台预先统一消息/会话模型。
- 用户插件安装、发现、分发、市场、依赖解析、热加载或热卸载。
- 对外稳定 SDK、跨版本兼容承诺和不可信代码沙箱。
- 插件独立数据库、独立 migration 账本、升级命令或自动降级。
- 通用 ORM、全功能 KV/文档存储平台、任意生命周期钩子总线。
- 动态前端插件机制或插件管理面板。
- 为未来需求提前拆出通用持久任务平台。

### 实施前按 Epic 决定

- `definePlugin` 的具体类型、字段、目录布局和依赖注入方式。
- Skill 的物理组织方式，以及最小上下文/调度接口。
- 功能开关是否本轮落地、配置位置与作用域。
- 若支持 alarm 停用，待执行任务是暂停还是取消，以及重新启用策略。
- 为实现模块边界确实需要的 Schema 调整；默认不进行数据结构迁移。

这些问题不影响当前范围结论，也不需要为了保存本次计划而提前定案。

## 8. 验证与风险

各 Epic 至少运行受影响行为测试与 TypeScript 检查；跨模块改动运行完整测试，并保持 lint 与差异检查通过：

```bash
pnpm run check
pnpm run lint
pnpm test
git diff --check
```

针对性验证入口：

- 定义、注册与 Skill：`test/skills.test.ts`、`test/system-resources.test.ts`、`test/agent-runtime.test.ts`。
- web fetch：`test/web-fetch.test.ts`，断言网络拒绝、响应边界和审计状态。
- memory：`test/memory.test.ts`、`test/admin.test.ts`，并覆盖 Context 注入及落盘状态。
- alarm：`test/alarm.test.ts`、`test/alarm-internal-context.test.ts`、`test/scheduler.test.ts`、`test/sleep.test.ts`，覆盖事务、恢复与所有权。
- 数据机制：`test/schema.test.ts`、`test/foundation.test.ts`、`test/operations.test.ts`，确认迁移、数据保留与备份不退化。
- 若调整固定前端或功能开关：运行 `pnpm run admin:build`，验证隐藏入口、直达页面与请求行为；后端另验证停用边界。

主要风险：

1. 将“模块化”扩大成未承诺的用户插件平台；以本轮不做清单控制范围。
2. 只移动文件而不收拢业务依赖，或留下新旧两套路径；迁移调用方后删除旧业务路径。
3. 抽象拆断 alarm 的事务与恢复语义；以数据库落盘状态和失败恢复测试验收，不只看返回文本。
4. 功能状态、工具注册、Skill 索引和上下文贡献不一致；需要验证同一装配结果。稳定提示变化还会触发现有 Context 重建语义，不得假装无影响热切换。
5. 将类型或表命名规则当安全隔离；本轮内置插件是可信代码，未来不可信插件是独立设计议题。

运行契约实际变化后，再同步 [architecture.md](../architecture.md)、[data-layer.md](../data-layer.md)、[telegram-agent-flow.md](../telegram-agent-flow.md)、[admin-panel.md](../admin-panel.md) 等对应主题文档；不把尚未实现的设计写成当前行为。
