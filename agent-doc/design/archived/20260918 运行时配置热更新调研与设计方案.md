# Plastic Wan Runtime Configuration Hot Reload 调研与设计方案

> 状态：方案已确认；Phase 0 已实现（`1a08eae`，见 [Phase 0 交付报告](20260919%20配置热更新%20Phase%200%20交付报告.md)），Phase 1 起尚未实现；决策汇总见 §15。
> 日期：2026-09-18（同日已对照源码复核并修订）

## 1. 背景与动机

Plastic Wan 当前主要在进程启动时加载配置。修改配置后通常需要重启 `serve`，这会同时影响 Telegram polling、Scheduler、MCP、Sticker worker、Agent cache 和其他进程级组件。

热更新的目标不是把所有配置都变成可变状态，而是让适合 invocation 级生效的配置，在不重启进程的情况下影响后续工作。主要使用场景包括：

- 桌面客户端修改 Agent 配置后立即生效。
- 未来 Web / GUI configuration editor 保存后立即生效。
- Playground 临时调整 Prompt、模型和 Agent policy。
- 未来通过 HTTP / IPC configuration API 提交配置更新。
- 修改 Prompt、模型或运行策略时，避免为了简单配置变更而重启 Telegram polling 和整个 runtime。

该能力也为未来的多种更新来源提供统一应用入口：文件加载、桌面客户端、HTTP / IPC、测试代码和 Playground 都应能够复用同一个 parse / validate / apply 流程，而不是各自直接修改运行时组件。

热更新必须服从清晰的生命周期边界。它不意味着正在执行的 invocation 会突然切换 Prompt、model 或 tools，也不意味着 Provider、Telegram client、数据库路径、MCP topology 等所有进程级资源都必须支持替换。

因此，本设计的核心问题是：

> 哪些配置适合在 invocation 边界更新，哪些配置需要 component recreation，哪些配置仍应保持 process restart 边界？

## 2. 已确认的目标语义

Plastic Wan 未来支持 runtime configuration hot reload，但配置更新只影响更新之后开始执行的 invocation：

```text
配置版本 A
  → invocation queued
  → queued → running：取得 configuration snapshot A
  → 配置更新为 B
  → 已运行 invocation 继续使用 A
  → 后续 invocation 使用 B
```

本方案明确采用：

- **Configuration snapshot boundary**：`queued → running`，适用于 §6.1 中的 invocation 快照字段；实时全局策略不进入快照（§6.1 B 类）。
- **Prompt 更新行为**：新 invocation 使用新 Prompt；现有 `systemPromptHash` 机制继续负责检测变化并重建 Conversation Context。
- **MVP 范围**：Agent / Prompt / invocation policy，以及已有自定义 Provider 的模型列表，以白名单形式列出（§6.1）。
- **更新入口**：只提供显式 `reloadFromFile()`，不实现 filesystem watcher。调用方是 `/model`（§9.4）和「应用配置文件」（§12）。
- **失败处理**：validate-before-swap；新配置失败时继续使用最后一个有效配置。
- **模型切换**：`/model` 与 Admin Model API 直接改写 `config.jsonc` 的 `agent.provider` / `agent.model` 并 reload；删除内存态 override 与 `/model reset`（§9.4）。
- **在用模型保护**：配置中 `agent.provider` / `agent.model` 与 `vision.provider` / `vision.model` 指向的模型不能禁用、修改参数或删除，它们所在的 Provider 不能删除；必须先切换到其它模型（§9.4）。

## 3. 当前配置生命周期

### 3.1 加载入口

配置当前在 `serve()` 启动时加载：

- `src/cli-options.ts`：解析显式 `--config`。
- `src/cli.ts`：加载 dotenv 文件并分发 CLI 命令。
- `src/application.ts:41-43`：调用 `loadConfig()` 和 `assertConfigPermissions()`。
- `src/platform/config.ts:287-318`：完成配置读取、解析、校验、Prompt 加载和 hash 计算。

当前 `serve` 启动后不会再次调用 `loadConfig()`。

### 3.2 parse / validation / normalization

`src/platform/config.ts` 的处理顺序：

1. `resolve(path)` 得到绝对配置路径。
2. UTF-8 读取配置文件。
3. 去除 BOM 后用 `jsonc-parser` 解析 JSONC，允许 trailing comma。
4. 使用 TypeBox 严格 Schema 校验，未知字段拒绝。
5. 执行语义校验：timezone、ID 唯一性、Provider/Model 引用、MCP policy、Context 参数关系等。
6. 读取 `agent.system_prompt_file` 和各 Chat 的 `instructions_file`。
7. 去 BOM、拒绝 NUL、剔除 HTML 注释、校验 Prompt template。
8. 将文件路径字段归一化为 Prompt 文本，生成 `RawConfig`。
9. 对原始 JSONC 和 Prompt 原始内容计算 SHA-256，生成 `LoadedConfig.hash`。

`loadConfig()` 不解析 SecretRef；Secret 在各组件装配时才解析。

补充两点：去掉 HTML 注释后为空的 system prompt 会被拒绝（`config.ts:345-349`）；语义校验只检查自定义 Provider 的模型引用，builtin Provider 直接跳过（`config.ts:504-506`），builtin 模型是否存在要到 `createModelRegistry` 的 `requireModel` 才检查。

主要类型：

- `FileConfig`：文件形状，保留 Prompt 文件路径。
- `RawConfig`：运行时形状，包含已加载 Prompt 文本。
- `LoadedConfig`：`RawConfig`、`FileConfig`、配置路径和 hash。

当前没有统一的完整 `normalizeConfig()`；部分默认值散落在消费者中，例如 `admins ?? []`、`mcp.servers ?? []`、`sticker_trigger_enabled === true`、Admin static dir 和 memory warning days。

### 3.3 启动期装配

`src/application.ts` 使用启动时的 `loaded.config` 构造：

- `SecretStore` 和 Telegram Bot。
- `SqliteStore`、ServeLock。
- `createModelRegistry()`。
- `AgentModelSwitcher`。
- `TelegramIngestion`。
- `MediaService`、`StickerService`、`McpManager`。
- `SystemResources`。
- `ConversationRuntime`。
- `AgentRuntime`。
- `BucketScheduler`、`BotCommandService`、`AdminServer`。

这些对象大多直接持有或复制启动时的 `RawConfig`。

## 5. 当前已有的 snapshot 机制

当前架构已经有几个可复用的边界。

### 5.1 消息 snapshot

`src/store/invocation-snapshot.ts:36-90` 在 invocation 创建或 attach 时，把当前 Message Revision 写入 `invocation_messages.snapshot_json`。

后续 Telegram 编辑不会改变已经冻结的 invocation 输入。注意这个快照发生在 queued / attach 时，而不是 queued → running 时；它使用的 `history_messages` 因此不受 running 边界的快照约束（见 §6.1 B 类）。

### 5.2 模型在 invocation 开始时读取

`src/orchestration/agent-runtime.ts:210-213` 在 `runInvocation` 开始时调用 `modelSwitcher.model()`。

现有 `/model` 和 Admin Model API 已经满足：

- 已运行 invocation 不换模型。
- 后续 invocation 使用新模型。
- 重启后恢复配置文件默认模型。

本方案保留前两条，删除第三条：切换改为写入配置文件，重启后仍然生效（§9.4）。

每次模型调用的实际 provider/model 已记录在 `model_calls`（`src/store/schema.ts:324-325`）。

### 5.3 Tool registry 在 invocation 开始时建立

`src/orchestration/agent-runtime.ts:266-290` 为每次 invocation 创建并校验工具注册表，包含 runtime tools、internal capabilities、MCP tools 和条件暴露的 `zzz`。

工具 registry 被写入 invocation 审计；运行中除 `zzz` 的条件暴露和收尾模式的工具裁剪外不切换。

### 5.4 Stable Prompt 与 Context rebuild

`src/orchestration/agent-runtime.ts:214-226` 根据当前模型能力、Agent Prompt、Chat instructions 等生成 stable system prompt 和 hash。

如果 `systemPromptHash` 改变，当前实现会：

1. 重建 Conversation Context。
2. 驱逐 ConversationRuntime 中的 Agent cache。
3. 以新 stable prompt 开始后续运行。

该行为是 Prompt hot reload 的自然落点，不需要另造 Prompt migration 机制。

### 5.5 缓存 Agent 只重绑部分状态

复用缓存 Agent 时（`src/orchestration/agent-runtime.ts:354-356`），只重新设置 `systemPrompt`、`model` 和 `tools`；`thinkingLevel` 只在 `#createCachedAgent` 创建时写入（`:830`），且不参与 `systemPromptHash`。

因此 `thinking_level` 变化在当前实现下不会影响已有缓存 Agent 的会话，直到缓存被驱逐或 Prompt hash 变化。热更新 `thinking_level` 必须在每次 run 开始时同时重绑 `agent.state.thinkingLevel`。

## 6. MVP 支持范围

### 6.1 支持热更新（白名单）

本节是白名单：未列出的字段一律按 restart-only 处理（§6.2），新增配置字段默认也是 restart-only，除非显式加入本节。

按生效时点分为两类。

**A. invocation 快照字段**：在 `queued → running` 时冻结，运行期间（包括 attach 的 Bucket）不变。

- `agent.system_prompt_file` 及加载后的 Prompt。
- `chats[].instructions_file` 及加载后的 instructions：按 chat id 对比，只有已存在 chat 的 instructions 变化可热更新；新增或删除 chat、以及 chat 的其他字段变化都属于 restart-only。
- `agent.provider` / `agent.model`：`/model` 的写入目标（§9.4）。只能指向当前生效的模型注册表中已存在且支持文本输入的模型（`/model` 与 Admin 切换时还要求该模型未禁用，§9.4）；同一次 reload 里给已有自定义 Provider 新增的模型，先更新模型列表再校验此字段；若目标模型属于新增的 Provider（restart-only），该字段也按 `restart_required` 处理。
- `agent.thinking_level`：需要按 §5.5 重绑缓存 Agent。
- `agent.context_stop_ratio`：运行中的停止判定和每批注入（`context-builder.ts:365`）都必须读快照值。
- `agent.context.max_wall_clock_seconds`。
- `agent.context.idle_grace_seconds`。
- `agent.rate_limits`。
- `agent.send_max_text_length`。
- `agent.send_disallow_blank_lines`。
- `agent.send_nudge_enabled`。

**B. 实时读取的全局策略**：不进入快照，更新后在下一次读取时生效。

- `agent.daily_budget.max_tokens`：当前每次模型调用都实时读取（`agent-runtime.ts:434/514/570`），`media.ts:318` 与 `/status` 也读取。它是全局配额；冻结到快照会让长时间运行的 invocation 在预算调低后继续消耗，直到 wall-clock 结束。
- `agent.max_concurrency`：scheduler 每轮循环读取（`scheduler.ts:221`）；调低不会中止正在运行的 invocation。
- 已有自定义 Provider 的 `models[]`（增删改模型）：reload 时用新的模型列表重建该 Provider，在共享的 `registry.models` 上调用 `setProvider()` 原地替换（pi-ai 的 `createModels()` 返回 `MutableModels`，`setProvider` 按 provider id 新增或替换，见 `node_modules/@earendil-works/pi-ai/dist/models.d.ts:148`）。
  - `AgentModelSwitcher`、`AgentRuntime`、`MediaService` 共用同一个实例（`application.ts:77-78`、`:109`、`:147`），所以立即看到新列表，`/model` 马上可以选到新模型。
  - 凭据复用启动时已解析的值，不重新解析 SecretRef：从注册表里现有的 Provider 对象（`Models.getProvider(alias)`）取 `baseUrl`、`headers`、`auth` 重建，pi-ai 的 `createProvider` 把它们原样保存在 Provider 对象上。`ModelRegistry.models` 的类型要改为 `MutableModels`。
  - 正在运行的 invocation 持有快照里的模型描述，请求按 provider id 转发，不受影响。
  - 在用模型受 §9.4 保护，不会被修改或删除。Vision 模型的描述在 `MediaService` 构造时固定（`media.ts:70`），修改它的参数不会反映到运行中，这也是 Vision 模型同样受 §9.4 保护的原因之一。
  - 模型改名（`id` 变化）等同于删除后新增。builtin Provider 的模型来自 pi-ai 目录，不在配置里增删。
  - Provider 的其它字段变化仍然需要重启（§6.2）。
- `agent.history_messages`：只在创建 invocation 时读取一次，决定带多少条历史消息（`invocation-queue.ts:651`）；启动补偿（`:182`）与入库（`telegram-ingestion.ts:553`）也读当前值。attach 虽然把它传给 `snapshotInvocation`（`:359`），但 `includeHistory = false`，不读取历史，所以同一个 invocation 内不会混用新旧值。已经在排队的 invocation 使用排队时的值。

对用户可以统一说明：A、B 两类字段保存后，从 bot 下一次开始处理新消息时生效。

### 6.2 需要重启的配置：保存但不立即生效

不在 §6.1 白名单内的字段都需要重启才生效。按原因分为两类，另有一类字段 `serve` 运行期根本不使用。

**依赖进程级资源，需要重建组件或进程**：

- `telegram.token`：Bot 实例与 `getMe` 身份在启动时建立（`application.ts:71-79`）。
- `data_dir`、`paths.database`：`ServeLock` 与 SQLite 连接（`application.ts:72-73`）。
- `admin.enabled`、`admin.host`、`admin.port`：HTTP listener（`application.ts:191-196`）。
- `mcp.servers`：`McpManager` 管理的子进程与连接。第一版不做热更新；已评估过可行性，工作量中等偏低，见 Phase 3。
- 新增或删除 Provider，以及 Provider 的 `base_url`、`api`、`headers`、`api_key`：`createModelRegistry` 在启动时解析 SecretRef（`providers.ts:34`、`:45`），command SecretRef 有副作用。
- `telegram.sticker_sets`：启动时同步（`stickers.ts:90`）并启动后台视觉索引 worker。
- `vision.provider`、`vision.model`、`vision.max_concurrency`：`MediaService` 构造时固定 Vision 模型描述和 semaphore（`media.ts:70-73`）。

**范围选择：技术上可热更新，MVP 暂不做**。这些字段要么每次使用时直接读配置，要么只是在构造时派生了一份简单状态，reload 时重建即可。是否纳入由产品需要决定，按需逐项加入 §6.1：

- Telegram Chat / Topic allowlist 与 `participation`：`TelegramIngestion`、`InvocationQueueService`、`BotCommandService` 在构造时派生 allowlist 与 `ParticipationRegistry`（`telegram-ingestion.ts:79-85`）。排队与 prompt 构建已经处理「chat 不再配置」的情况（`invocation-queue.ts:203`、`:612`，`context-builder.ts:278`）。
- `ignored_user_ids`、`process_bot_messages`、`sticker_trigger_enabled`、`telegram.bucket_window_seconds`：每次使用时直接读配置（`telegram-ingestion.ts:143`、`:268`、`:312` 等）。
- `agent.context.hard_token_ratio`、`retained_sends_target`、`retained_sends_max`：Context GC 时直接读配置（`agent-runtime.ts:917-919`），可以作为快照字段。
- `agent.context.ref_ttl_hours`、`agent.context.agent_cache_size`：构造 `ContextRefStore`、`ConversationRuntime` 时固定（`agent-runtime.ts:155`、`application.ts:122-124`）。
- `agent.memory_ttl_warning_days`：只影响 Admin 显示（`server.ts:100`）。
- `timezone` 与 `chats[].timezone`：进入 prompt 模板值（`context-builder.ts:264`），变化会触发 Context 重建。
- `paths.media_cache`：每次使用时读取，只用作临时目录（`media.ts:80`、`:322`）。
- `vision.prompt_version`、`vision.max_output_tokens`、`vision.daily_budget`：每次调用时读取（`media.ts:180`、`:400`、`:582`）。
- `telegram.admins`：启动时播种到 `bot_admins`，只增不减。

**`serve` 运行期不使用**：`paths.backups` 与 `retention.*` 只在启动时的迁移前备份（`database.ts:143`）和 `backup` 命令（`database.ts:184`、`:192`）中读取。修改后下一次运行 `backup` 就生效，界面不应把它们标成「需要重启」。

这些配置可以由未来 Admin Panel 表单编辑和保存，但保存后**不会立即改变当前运行中的服务**。后端应在校验后返回 `restart_required`，并说明具体变更字段；表单需要明确标注“重启后生效”或等价提示。

因此需要区分两个状态：

```text
active runtime configuration：当前进程正在使用的配置 A
saved/desired configuration：配置文件中已保存、下次启动将使用的配置 B
状态：B 已校验，但 pending restart
```

配置文件本身就是 desired configuration。pending restart 字段由「文件与 active 的 restart-only 部分之差」派生，不需要单独存储。

在服务重启前：

- 当前进程继续使用 active configuration A 的 restart-only 部分。
- Agent / Prompt / policy 的热更新仍可按正常规则发布，不因存在 pending restart 字段而被阻塞（§9）。
- restart-only 配置 B 不得被部分应用。
- Admin Panel 应显示待重启状态和受影响字段。

需要重启的字段采用“保存、告知重启、重启后生效”的生命周期，而不是“拒绝保存”。

## 7. 推荐 ownership / lifecycle 模型

配置不应继续由多个组件分别持有一个可变的 `RawConfig`，也不应通过修改共享对象实现热更新。

建议增加轻量的 runtime configuration owner，例如：

```text
src/platform/runtime-config.ts
```

建议抽象：

```ts
RuntimeConfigurationStore
  current(): RuntimeConfiguration
  beginInvocation(): InvocationConfigSnapshot
  reloadFromFile(): Promise<ApplyResult>
```

`RuntimeConfigurationStore` 负责：

- 当前 active configuration。
- configuration generation。
- active hash 与文件 hash（两者在存在 pending restart 字段时不同，见 §9）。
- 已准备好的 invocation policy / Prompt / model 引用。
- validate-before-swap。
- last-valid configuration。
- 按 §6.1 白名单拆分 hot diff 与 restart diff，派生 pending restart 字段。
- 串行化 reload：`loadConfig()` 是异步的，一旦有 Admin/API 调用方，并发 reload 可能乱序发布，需用进程内 mutex。

§4.1 表中所有读取热字段的消费者都改为从 store 或快照取值。

不要引入完整 dependency injection framework。组合根 `src/application.ts` 仍然负责装配组件；新 store 只负责配置生命周期和 snapshot 发布。

## 8. Invocation snapshot 设计

建议新增 `InvocationConfigSnapshot`，在 scheduler 把 invocation 从 `queued` 原子转为 `running` 时取得。

snapshot 至少应包含 §6.1 A 类字段：

```text
configuration generation
active configuration hash
agent provider/model
thinking level
Agent Prompt 与 Chat instructions
context stop ratio
max wall-clock deadline
idle grace
rate limits
send policy
```

stable system prompt 依赖 chat 和模型能力，仍在 run 开始时由快照中的 Prompt 构建，不在全局预先计算。工具注册表仍按现状在 run 开始时建立并审计；MVP 不重建组件，快照不需要 component generation。

实现上不要求把所有对象序列化进 SQLite；snapshot 可以是内存中的不可变对象引用。

审计方面：

- 当前 `invocations.config_hash` 在 queued 时写入启动 hash（`invocation-queue.ts:636`）。改为 running 时取快照后，该字段必须改在 queued → running 事务中写入快照的 active hash，否则记录的不是实际使用的配置。
- 实际 provider/model 已由 `model_calls` 按调用记录，MVP 不需要给 `invocations` 加列。
- 不给 `invocations` 加 generation 列；generation 只存在于内存和 `config_reloaded` 日志中。

### 8.1 边界顺序

建议 scheduler 的执行顺序为：

```text
1. 在 scheduler.ts:222 的同步事务内选中 queued invocation。
2. 同一事务内读取 RuntimeConfigurationStore 当前快照。
3. 同一事务内完成 queued → running 状态转换，并写入快照的 config_hash。
4. 把 snapshot 传给 AgentRuntime.run()（InvocationHandler 签名需增加快照参数）。
5. 运行期间不再从全局 store 读取 A 类字段。
```

Node 单线程事件循环可以保证在没有 `await` 的连续代码中取得一致引用；reload 的串行化见 §7。

### 8.2 Long-lived invocation

一个长生命周期 invocation 可以 attach 后续 Bucket。所有 attach Bucket 必须继续使用第一次进入 `running` 时取得的 snapshot：

```text
Invocation I + Snapshot A
  ├── Bucket 1 → A
  ├── 配置更新为 B
  ├── Bucket 2 attach → A
  └── Bucket 3 attach → A

I 结束后
  └── next invocation → B
```

不能在 `injectPending()` 或每个 turn 中重新生成 Prompt、tools 或 policy，否则同一 invocation 会混合新旧语义。

attach 路径中，`ContextBuilder.renderInjection` 读 `context_stop_ratio`（`context-builder.ts:365`），必须改为使用所属 invocation 的快照。attach 虽然把 `history_messages` 传给 `snapshotInvocation`（`invocation-queue.ts:359`），但不读取历史，不受影响。

## 9. reloadFromFile 流程

初版只需要显式调用，不绑定 filesystem watcher：

```text
reloadFromFile()
  → 取得 reload mutex
  → 检查配置文件权限（与启动时的 assertConfigPermissions 相同；编辑器保存后可能改变文件权限）
  → loadConfig(path)：JSONC / Schema / 语义校验 / 读取 Prompt
       失败：文件无效，active 不变（同时暴露“磁盘配置无效，下次启动会失败”）
  → 按 §6.1 白名单对比文件与 active：
       hot diff：白名单字段变化
       restart diff：其余字段变化
  → 构造 candidate（FileConfig 与 RawConfig 两层，见下文）
  → 对 candidate 的 FileConfig 再执行语义校验（跨字段约束）
  → prepare：agent 模型存在且支持文本输入（自定义 Provider 查 candidate 的 models[]，builtin 查当前注册表），且能容纳工具注册表
  → 成功：原子发布 candidate，generation + 1
  → 失败：保留 active
  → 返回 applied 字段、restart_required 字段（restart diff）、active hash、文件 hash
```

要点：

- **restart diff 不阻塞 hot diff。** 每次 reload 都拿文件与 active 对比；如果“只要存在 restart-only 变化就整体不应用”，那么文件中一旦存在 restart-only 改动，重启前任何 Prompt / policy 修改都无法生效。
- **语义校验执行两次。** 完整文件校验保证下次启动可用；candidate 校验保证当前进程可用。跨字段约束在两者中结果可能不同，见下文。
- **candidate 在两层上构造。** `LoadedConfig` 同时保留了 `FileConfig` 和 `RawConfig`（`config.ts:266-271`），active 与文件各有一份：
  - `FileConfig` 层：active 的 FileConfig 中白名单字段替换为文件里的值，用于第二遍语义校验。`validateSemantics` 目前是模块私有函数，只在 `loadConfig` 里调用（`config.ts:310`、`:411`），需要导出。
  - `RawConfig` 层：复用已加载的 Prompt 文本，不重新读盘。两边都有的 chat 用文件这次读到的 instructions；只在 active 里的 chat（删除待重启）保留 active 的文本。如果按 active 的 `instructions_file` 路径重新读盘，这个文件和 chat 一起被删掉时，整个 reload 会失败。
- **candidate 校验失败时整次 apply 失败。** 错误信息要指出是哪条约束依赖了尚未生效的重启字段，并说明重启后会一起生效；不尝试自动把某些热字段降级为待重启。当前真实存在的跨字段约束（`config.ts:447-451`、`:554-570`）：
  - `agent.context_stop_ratio`（热）不能小于 `agent.context.hard_token_ratio`（重启）。
  - `agent.context.idle_grace_seconds`（热）必须为 0 或不小于 `telegram.bucket_window_seconds`（重启）。
  - `agent.context.max_wall_clock_seconds`（热）必须大于 `idle_grace_seconds`（热）。
  - `agent.provider` / `agent.model`（热）引用 Provider 集合（重启）和 `models[]`（热）。
  - `vision.provider` / `vision.model`（重启）引用 `models[]`（热）：从模型列表里删掉 Vision 模型会让 candidate 校验失败。
- **reloadFromFile 不写文件。** 文件本身就是 desired configuration；写入是独立操作（§9.3）。
- **active hash 与文件 hash 分离。** 存在 restart diff 时，active 配置不等于任何文件版本，文件 hash 不能代表 active。active hash 应对 candidate 的规范化序列化与 Prompt 内容计算。reload 成功时输出 `config_reloaded` 日志事件，带 active hash 与文件 hash，便于与 `check-config` 输出对比。

`restart_required` 不是校验失败：候选配置可以合法并成功保存，只是不能在当前进程内立即应用。服务重启后，启动流程再次加载已保存配置并使其生效。

### 9.1 失败分类

静态 validation 错误：

- JSONC 语法错误。
- Schema / unknown field 错误。
- 类型、范围、唯一性错误。
- Prompt template 错误。
- Context 配置关系错误（包括 candidate 跨字段校验失败）。
- 自定义 Provider / MCP 静态引用错误。

MVP 的 prepare 错误：

- `agent.provider` / `agent.model` 不在当前注册表中，或不支持文本输入（可复用 `AgentModelSwitcher` 的校验）。reload 不查模型禁用表（§9.4）。
- 新模型的 context window 容纳不下当前工具注册表（当前 `/model` 切换也有这个风险；可参照 `AgentRuntime.validateAdditionalTools` 预检）。

SecretRef 解析、Vision 限制、MCP 初始化、路径创建属于 Phase 3 组件重建的 prepare 错误；MVP 热字段不涉及它们，reload 也不应解析 SecretRef（command SecretRef 有副作用）。

Invocation-time 错误：

- Provider timeout。
- Telegram API 错误。
- MCP call 失败。
- Vision 外部服务失败。
- 外部 rate limit。

前两类应使本次 apply 失败；第三类属于 invocation 运行错误，不应阻止已验证配置发布。

### 9.2 Atomic apply

采用 candidate-first：

```text
active A
  │
  ├── load/validate/prepare candidate B
  │
  ├── B 失败 → A 继续 active
  │
  └── B 成功 → 一次性 publish B
```

不要先覆盖旧配置再尝试初始化新组件。这样不需要复杂 rollback，也不会出现 Prompt 已换、model registry 仍旧、MCP 又是另一版的半更新状态。

失败需要记录清晰的 configuration update error，并通过 `SecretStore.redact` 处理错误文本，不能泄露 credential。

### 9.3 配置写入

保存配置与 reload 是两个操作：先写文件，再调用 `reloadFromFile()`。`/model`（§9.4）与未来 Admin 表单都走这条路径。写入需要：

- 用 jsonc-parser 的 `modify` / `applyEdits` 修改原文，保留注释和格式。现有 `configure` 向导（`src/tui/configure.ts:71`）用 `JSON.stringify` 整体回写，会抹掉 JSONC 注释，不能照搬。
- 写入前先对修改后的文本执行完整校验，校验失败不写文件。
- 先写临时文件再 rename，保持配置文件 `0600` 与父目录 `0700`。`serve` 因此需要对配置目录有写权限；Docker 部署的 entrypoint 已把 `/config` 交给容器内的 `plasticwan` 用户。
- 提交整份表单的写入携带基准文件 hash 做乐观并发控制：文件已被外部修改时拒绝覆盖。只在最新文件内容上修改个别字段的写入（如 `/model`）不需要这一步。
- 写入失败（文件系统只读、权限不足）时返回错误，active 配置不变。

### 9.4 模型切换与在用模型保护

`/model <序号>` 与 Admin `PUT /model` 改为：读取当前配置文件，只修改 `agent.provider` 与 `agent.model`，按 §9.3 写入，再调用 `reloadFromFile()`。新模型从下一个 invocation 开始使用，已运行的 invocation 不受影响。

由此删除以下设计：

- `AgentModelSwitcher` 的内存态 `#override`：「正在使用的模型」恒等于 active 配置中的 `agent.provider` / `agent.model`，重启后仍然生效。
- `/model reset` 与 Admin `DELETE /model`：不存在另一个可恢复的默认模型。
- 「重启后恢复配置文件默认模型」的语义（§5.2）。

在用模型保护（在后端保存接口中强制，不只在界面上限制）：

- 配置中 `agent.provider` / `agent.model` 与 `vision.provider` / `vision.model` 指向的模型不能禁用、修改参数或删除。未配置 Vision 时只保护 agent 模型。
- 这些模型所在的 Provider 不能删除。
- 要修改或删除 agent 模型，必须先用 `/model` 或 Admin 切换到其它模型。Vision 模型的切换属于重启字段（§6.2），要修改或删除当前的 Vision 模型，先把 `vision` 指向其它模型并重启。
- 手改配置文件不受这些限制约束：删除在用模型会让校验失败，继续使用上一份有效配置；修改在用模型的参数属于 Provider 变更（restart-only），重启后生效。

因为在用模型不能被禁用、修改或删除，也就不存在「正在用的模型失效后回退到哪里」的问题；禁用其它模型只影响可选列表。

模型禁用状态：

- 存在 SQLite 的独立表中（provider 与 model id），不写进配置文件，也不经过 reload；改动立即影响 `/model` 与 Admin 的可选列表。builtin Provider 在配置里没有模型列表（直接使用 pi-ai 的模型目录），独立表也能覆盖它们；pi-ai 升级后新增的模型默认启用。
- 需要新增 Drizzle 表定义与迁移；Admin 的开关端点加入 [admin-panel.md](../admin-panel.md#api) 写端点白名单。
- `/model` 与 Admin 切换拒绝已禁用的模型；禁用端点拒绝在用模型。
- 配置文件优先：手改文件让 `agent.model` 指向一个已禁用的模型时，reload 不查禁用表，该模型照常使用，Admin 中显示为在用（开关锁定）。
- 通过 Admin 删除或改名 Provider / 模型时同步清理对应的行；手改文件留下的孤儿行在读取时忽略。

尚未配置模型的全新 setup：

- `agent.provider` / `agent.model` 改为可选。当前 Schema 把它们设为必填（`config.ts:183-184`），`createModelRegistry` 启动时也要求 agent 模型存在（`providers.ts:83`），两处都要调整。
- 未配置时不发起 invocation，消息照常入库。Bucket 以 `no_agent_model` 之类的原因标记为跳过（参照 sleep 的 `skipQueuedInvocations`，`invocation-queue.ts:483`），不留在 queued；否则选定模型的那一刻，积压的 Bucket 会一次性全部触发。
- 管理员用 `/model` 选定模型后写入配置，从下一个 Bucket 开始运行。
- `/status` 与 Admin 显示「未配置模型」。

尚未配置 Vision 模型的全新 setup：

- `vision` 整体改为可选。当前 Schema 把它设为必填（`config.ts:225-228`），`createModelRegistry` 也要求 Vision 模型存在（`providers.ts:84`），`doctor` 会探测它（`doctor.ts:127`），都要调整。
- 未配置时对模型屏蔽依赖 Vision 的能力：不注册 `read_image` 与 `search_stickers`（`read_image` 使用 Vision 模型，`media.ts:70`；Sticker 搜索依赖 Vision 索引），System Skill 索引中不列 `image-inspection` 与 `sticker-search`，system prompt 中相应的图片与 Sticker 说明一并调整。
- Sticker 视觉索引 worker 不启动，也不注入 Sticker catalog。
- 多模态 Agent 仍能直接看到新消息里的图片，只是无法查看旧图；text-only Agent 完全看不到图片。
- Admin Panel 显示警告。
- Skill 与能力的对应关系目前只写在 SKILL.md 正文里（`Capability: read_image`），按能力过滤 Skill 需要机器可读的关联，建议在 frontmatter 中声明依赖的能力。
- Vision 配置属于 restart-only（§6.2）：之后补配 Vision 需要重启；重启后工具注册表和 system prompt 变化，会触发 Context 重建。

副作用：`/model` 写入后触发的 reload 会读取整个文件，所以文件里其它尚未 reload 的热字段修改会一并生效。

## 10. Prompt 与 Context 语义

Prompt 文件内容参与配置 hash；Prompt 内容变化后：

- 正在运行的 invocation 继续使用旧 stable prompt。
- 后续 invocation 取得新 stable prompt。
- 若 system prompt hash 改变，现有 Conversation Context 按当前实现重建。
- Context rebuild 会丢弃保留 transcript 和 capability refs，这是当前 Context 设计的既有语义。

热更新让修改 Prompt 变得很便宜，每次修改都会让**所有**会话在下一次运行时重建 Context。Admin 在保存 Prompt 时应提示这一点，但语气平和、作为说明而不是警告，因为后果有限：

- 该会话的 canonical history 与引用被清空（`context-store.ts:104-121`）。下一次运行照常按 `history_messages` 带上最近的聊天记录（`invocation-queue.ts:626`），丢失的是更早的连续上下文、模型自己的工具调用记录和旧图片引用。
- Provider 的 prompt 缓存失效，这一次享受不到缓存价。
- 模型表现可能短暂下降，随后自然恢复；记忆（`add_memory`）不受影响。
- 比 `/cut_topic` 更温和：`/cut_topic` 连之前的聊天记录也会截断（`invocation-snapshot.ts:45-47`）。

`thinking_level` 不参与 system prompt hash，不会触发重建，靠 §5.5 的重绑生效。

MVP 不设计 Prompt migration、旧 transcript 跨 Prompt replay 或配置版本历史。

## 11. Filesystem watcher 边界

不实现 watcher。直接修改原始配置文件是面向高级用户的功能，由显式的「打开配置文件」和「应用配置文件」支持（§12），不自动监听文件变化。

未来 watcher 只能作为 adapter：

```text
filesystem watcher
  → debounce
  → RuntimeConfigurationStore.reloadFromFile()
```

watcher 不应负责：

- JSONC 解析。
- Prompt 校验。
- Provider 初始化。
- 直接修改 AgentRuntime / Scheduler / MCP。
- 自己处理 last-valid 状态。

未来 Electron、GUI、HTTP、IPC、测试代码都应调用同一个 reload/apply 核心入口。

## 12. 未来扩展点

### Electron / GUI / HTTP API

外部更新来源只负责提供配置候选值或文件路径，统一进入：

```text
write file（§9.3）
  → RuntimeConfigurationStore.reloadFromFile()
```

API 应返回：

- apply 成功或失败。
- active generation。
- active hash。
- 文件 hash。
- `restart_required` 状态。
- 需要重启后生效的字段路径。
- 脱敏后的错误信息。

Admin Panel 表单应在字段级或分组级标注：

```text
此配置修改后需要重启服务端才能生效
```

保存 restart-only 字段后，界面应同时显示：

```text
已保存，等待重启生效
```

不能把“保存成功”显示成“当前运行时已生效”。

存在待重启字段时，Admin 提供「立即重启」操作：

- 写端点（例如 `POST /api/restart`），加入 [admin-panel.md](../admin-panel.md#api) 写端点白名单并校验 `Origin`。
- 执行前按启动流程校验磁盘上的配置（权限检查与完整 `loadConfig`）。配置无效时拒绝重启并返回错误，否则进程退出后起不来，bot 就停了。
- 复用现有的优雅关闭流程（`application.ts:54-67` 的 `shutdown`，随后 `finally` 中依次停止 Admin、等待 Scheduler 最多 30 秒、停止 Sticker 与 MCP、关闭 SQLite、释放锁），然后以专用退出码退出，与崩溃区分开。
- 进程由外部重新拉起：Docker 部署靠 `restart: unless-stopped`（`docker-compose.yml:24`），Electron 由主进程重启 server。直接运行 `node src/cli.ts serve` 且没有进程监督时，退出就是停止；服务端无法自己判断有没有被监督，由部署方声明（例如 Dockerfile 与 Electron 设置一个环境变量），未声明时界面不提供这个操作。
- 重启期间 Admin 页面会断开，界面轮询等待服务恢复；这段时间收到的 Telegram 消息由启动补偿拉取。

「立即重启」前的检查只能拦住解析与校验错误。配置合法、但启动时才失败的情况（SecretRef 解析不出来、builtin 模型不存在、Vision 输出上限超过模型限制等）由上次可用配置兜底：

- **保存**：`serve_started` 之后，把这次启动使用的 `config.jsonc` 与它引用的全部 Prompt 文件复制到 `data_dir` 下的独立目录。Prompt 路径可能是绝对路径或在配置目录之外，复制时把副本里的路径改写为指向副本。hot reload 成功不更新副本：文件里可能还有没经过启动验证的待重启字段。从副本启动时也不更新副本。
- **权限**：SecretRef 允许直接写明文字符串（`config.ts:15`），副本可能包含明文 secret，文件保持 `0600`、目录保持 `0700`。
- **回退**：只在与配置有关的启动步骤失败时回退，即配置加载与校验（含文件权限与 Prompt）、SecretRef 解析、模型列表构建。网络、Telegram API、`ServeLock`、数据库、MCP 初始化等失败不回退，否则一次临时故障就会让新配置被悄悄换回旧的。没有副本或副本也启动失败时，按原错误退出。
- **不覆盖用户的配置文件**：回退时临时使用副本作为 active 配置启动，`config.jsonc` 保持原样，方便用户查看错误并修复。
- **可见性**：输出 `config_fallback` 日志（带原错误、文件 hash 与副本 hash），Admin 显示「配置文件启动失败，正在使用上次可用的配置」并附上脱敏后的错误。
- **回退期间**：文件仍然无效时，`/model`、「应用配置文件」与「立即重启」都会因为文件校验失败被拒绝。文件修好后它们照常工作：「应用配置文件」按 §9 与副本比较，热字段立即生效，其余字段待重启；重启后从文件启动，退出回退状态。
- 第一版不检测启动成功之后的运行期崩溃：很难判断是不是配置导致的。

本轮不设计配置历史、多用户协作、分布式同步或完整 rollback API。

### 手改配置文件

直接修改原始配置文件是面向高级用户的功能，UX 可以简单一些，分成两个独立操作：

- **打开配置文件**（仅 Electron）：用系统默认编辑器打开当前使用的配置文件。由 Electron 端自己完成，不需要后端端点。
- **应用配置文件**（Electron / Web）：调用后端 reload 端点（例如 `POST /api/config/apply`）执行 `reloadFromFile()`，并在界面上显示上面列出的 API 返回内容：已生效的字段、需要重启后生效的字段、脱敏后的错误。

建议 Electron 与 Web 调用同一个 Admin HTTP 端点，不另建 IPC 通道。该端点须加入 [admin-panel.md](../admin-panel.md#api) 写端点白名单并校验 `Origin`。

### Provider 与模型列表编辑

管理员在 Admin 中编辑 Provider 列表和模型列表时，从 models.dev 自动拉取模型技术参数（输入能力、reasoning、context window、max tokens、费用），用于解决第三方 LLM Gateway 的 `/models` 只返回模型 ID 的问题：

- 复用 `src/tui/models-dev.ts` 已有的拉取与映射（`fetchModelsDevCatalog`、`findModel`、`toModelDefaults`）。Admin 后端使用时把它迁到 `src/platform/`，由 `configure` 向导和 Admin 共用，不另写一套映射。
- Gateway 的模型 ID 常与 models.dev 不一致（带前缀或别名），匹配结果需要管理员确认；拉取失败或找不到时由管理员手填。
- 已有自定义 Provider 的模型列表变更可热更新（§6.1）：保存并 reload 后，新增的模型立即可以被 `/model` 选择。新增 Provider 或修改连接字段仍需重启（§6.2）。

### Playground

未来可以从 production runtime configuration 创建 invocation snapshot，再对 snapshot 应用临时 override：

```text
production config
  → invocation snapshot
  → fork snapshot
  → temporary overrides
  → Playground invocation
```

关键约束是 Playground 不得修改 global production configuration。

#### MCP 热更新（已评估，第一版不做）

`McpManager`（`src/capabilities/mcp.ts`）已经具备大部分运行时替换能力：

- 单个 server 可以断开重连：`#connect` 先关闭旧 client 再建立新连接（`:138-144`），用 `generation` 让旧连接的回调失效（`:163`）；断线自动重连已经在运行时工作。
- 运行时工具列表变更：收到 `listChanged` 后，`#refreshTools` 先换上候选列表，校验失败就换回原来的（`:214-222`）。
- SecretRef 本来就在运行时解析：stdio 的 `env` 与 HTTP 的 `headers` 在每次建连时解析（`:237`、`:251`），热更新不会引入新的副作用。
- MCP 工具在每个 invocation 开始时生成（`application.ts:142`），运行中不变；server 不存在时调用返回 `server_unconfigured` 并记入审计（`mcp.ts:386-392`）。
- 每个 server 有一个容量为 1 的 semaphore，调用与重连都要先取得它。reload 时持有它进行替换，进行中的调用会先完成，新调用排队，不会直接失败。

需要补的部分：

- `ManagedServer.config` 是 `readonly`（`:49`），目前只有整个 manager 的 `stop()`，需要单个 server 的停止与配置替换。
- 按 alias 对比新旧配置：新增则创建并连接；删除则等进行中的调用结束、关闭连接并清理 `mcp_server_state` 对应行；只改 `tools`、`tool_policies`、`default_tool_policy`、`result_max_bytes` 时替换配置并重新列工具即可；改 `transport`、`command`、`env`、`url`、`headers`、`payload_max_bytes` 时需要重连。
- `required` server 在 reload 时连不上：这次 MCP 变更整体失败，用旧配置重连回去；非 required 的按现有逻辑标记 degraded 并自动重连。
- 新增 server 可能让工具总数超过 61 个的上限，走现有的 `#validateCandidateRegistry` 校验。

一个与热更新无关的现存问题：连接不可用时 `#call` 抛出的错误（`:467`）被记为 `outcome_unknown`（`:443`），但这时请求没有发出，结果其实是确定的「未执行」。断线重连时已经会遇到。

## 14. 关键测试范围

至少覆盖：

1. 合法配置 reload 后 generation 增加。
2. 非法 JSONC / Schema / Prompt 配置不会替换 active config。
3. 模型 prepare 失败（不在当前注册表、不支持文本输入、容纳不下工具注册表）不会替换 active config。
4. 文件本身合法、但 candidate 跨字段校验失败时不会替换 active config，错误指出依赖的重启字段（例如当前两者都是 30，文件把 `bucket_window_seconds` 与 `idle_grace_seconds` 同时调小到 5 和 10：文件合法，candidate 中 10 < 30 不合法）。
   另需覆盖：chat 从文件中删除（待重启）且它的 instructions 文件也被删除时，reload 仍然成功。
5. 文件同时包含热字段与 restart-only 字段变化时：热字段生效，restart-only 字段报 `restart_required`；之后再次修改热字段并 reload 仍能生效。
6. `chats[]` 中新增 chat 或非 instructions 字段变化归为 `restart_required`。
7. invocation 在 `queued → running` 时取得 A，之后 reload 到 B，仍使用 A。
8. 后续 invocation 使用 B。
9. long-lived invocation attach 的 Bucket 继续使用 A（包括注入时的 `context_stop_ratio`）。
10. Prompt 变化导致下一次运行按 system prompt hash 重建 Context。
11. `thinking_level` 变化对已有缓存 Agent 的会话生效。
12. model、Prompt、tool registry 不在 invocation 中途变化。
13. running invocation 的 wall-clock deadline 不因新配置改变。
14. 调低 `daily_budget` 后，运行中的 invocation 在下一次模型调用时即受限。
15. reload 后 `/status` 与 Admin 显示新模型与新的 `thinking_level`。

18. 保存接口拒绝禁用、修改或删除在用的 agent 模型与 Vision 模型，拒绝删除它们所在的 Provider；切换到其它模型后允许。

20. `invocations.config_hash` 记录的是 running 时快照的 active hash。
21. 失败错误经过脱敏，不输出 secret。
22. 配置更新不依赖 filesystem watcher，测试直接调用 `reloadFromFile()`。
23. reload 后新创建的 invocation 按新的 `history_messages` 带历史；已在排队的 invocation 与 attach 的 Bucket 不受影响。
24. 「应用配置文件」端点校验 `Origin`；返回已生效字段、`restart_required` 字段与脱敏后的错误。
25. 配置文件权限不是 `0600`、或父目录不是 `0700` 时 reload 失败，active 配置不变，错误说明原因。

## 15. 已确认决策

- snapshot boundary：`queued → running`（§6.1 A 类字段）。
- Prompt 更新触发既有 Context rebuild。
- MVP 更新 Agent / Prompt / policy 与已有自定义 Provider 的模型列表，以白名单为准。
- 只提供显式 `reloadFromFile()`，不实现 watcher；手改配置文件后由「应用配置文件」触发 reload，Electron 另提供「打开配置文件」（§12）。
- 失败保留最后有效配置。
- `/model` 写配置再 reload；删除内存态 override、`/model reset` 与 Admin `DELETE /model`（§9.4）。
- 在用模型不能禁用、修改参数或删除，它所在的 Provider 不能删除；必须先切换到其它模型（§9.4）。
- 模型禁用是 Provider 下按模型的开关：模型和参数留在配置里，只是不出现在可选列表中；禁用状态存在 SQLite 独立表（provider、model id）中，不写进配置文件（§9.4）。
- 全新 setup 可以不配 Vision 模型；未配置时对模型屏蔽图片与 Sticker 相关的能力和 Skill，Admin 显示警告（§9.4）。
- `invocations` 不加 generation 列。
- 管理员编辑 Provider 与模型列表时，从 models.dev 拉取模型技术参数（§12）。
- 尚未配置模型时不发起 invocation，只入库消息（§9.4）。
- `agent.history_messages` 热更新，在创建 invocation 时读取当前值（§6.1 B 类）。
- 保存 Prompt 时平和地提示会重建 Context，不做成警告（§10）。
- Admin 提供「立即重启」操作（§12）。
- Vision 模型与 agent 模型同样受在用模型保护（§9.4）。
- 程序保存上次成功启动的配置；配置导致启动失败时临时使用副本启动，不覆盖用户的配置文件。与「立即重启」一起在 Phase 2 实现（§12）。
- MCP 配置热更新放到后续阶段，第一版不做（§13 Phase 3）。
- agent 与 Vision 模型可选（全新 setup）从 Phase 1 拆出，单独作为 Phase 1b（§13）。
- 「应用配置文件」在 Phase 1 就提供最小的 Admin 按钮，不只提供后端端点（§13）。
