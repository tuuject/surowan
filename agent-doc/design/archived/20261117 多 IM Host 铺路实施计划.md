# 多 IM Host 铺路实施计划

本文是 AI 直出的实施契约，未经用户逐条审核，也没有对应的 PRD。用户确认过的只有[已确认](#已确认)一节，其余选择集中在[实施默认](#实施默认)，用户可以逐条推翻。文中的文件路径、行号、数量与行为描述取自写作时的 `develop`（`a4fa653e`），动手前请核对源码。

## 目标

让 core 不再假设「IM 只有 Telegram 一种」，使以后接入 Discord 这类 Host 时，工作量收敛为「新增一个 adapter 目录、一段配置、一条 Host 特征表记录」，而不是修改几十个 core 文件、重建三张大表。

本轮只做铺路：

- 不新增任何 Host，`HostKind` 仍是 `'telegram' | 'playground'`。
- Telegram 与 Playground 的外部可见行为不变：模型看到的 Prompt、工具 Schema 与工具结果逐字节不变；`config.jsonc` 格式不变；Admin HTTP 响应不变；审计行语义不变。
- 不做通用 IM 协议、不做跨平台身份合并、不新增产品能力。

## 已确认

以下各条于 2026-11-17 在对话中确认。

1. 这一轮不增加 Discord 支持，只对 core 层铺路。
2. 要解决的是此前评估列出的阻塞项：snowflake 精度、模型可见消息 id、二分 Host 分支与库约束、入站链路绑定 grammy、配置全在 `telegram.*` 下、补偿拉取、功能映射空缺。
3. 归档的 [20260928 Core 与 Telegram Adapter 分离 Epic](archived/20260928%20Plaswan%20Core%20与%20Telegram%20Adapter%20分离%20Epic.md) 已经实施过，但不彻底，很多地方仍只假设 Telegram 一个 IM。[agent-doc/README.md](../README.md) 索引里它的状态仍写着「规划完成，未实施」，与事实不符，由 IMH-06 更正。
4. （2026-11-18 确认）`config.jsonc` 的格式一个字段都不动，只加投影层，即下文的 D1。以后的 Host 在配置里新增与 `telegram` 并列的一段。
5. （2026-11-18 确认）一个实例可以同时接多个平台，每个平台至多一个 bot 账号：一个 Telegram bot 可以，一个 Telegram bot 加一个 Discord bot 可以，两个 Telegram bot 不行。即下文的 D12。

## 目标模型

### 标识

| 概念 | 目标 | 说明 |
| --- | --- | --- |
| Chat | core 一律用内部 `chats.id`。Host 原生 id 存 `chats.host_chat_id`（可空），只给 adapter、配置查找与 Admin 展示用 | `(host_kind, host_chat_id)` 唯一 |
| Sender | `senders.host_sender_type` + `senders.host_sender_id`（可空） | `(host_kind, host_sender_type, host_sender_id)` 唯一 |
| Topic | `conversations.message_thread_id`，bigint，`0` 表示整个 Chat。TS 侧 `topicId: bigint \| null` | 列名不改，见 D6 |
| 消息编号 | `messages.message_no`：Chat 内唯一、正整数、随时间递增。它是模型看到的唯一消息 id，reply 目标、`/cut_topic` cutoff、注意力触发、群聊记忆区间全部用它 | Telegram 用 wire message id；Playground 用 `rooms.next_seq` 分配的序号。合并掉 `telegram_message_id` 与 `local_sequence_no` |
| 发送时间 | `messages.sent_at` | 原 `telegram_date` |

消息编号这一条直接解决「snowflake 当消息 id」的问题：以后 wire id 不适合给模型看的 Host（Discord 的 19 位 snowflake）自己分配编号，wire id 另存一列。那一列和分配器到时再加，`ALTER TABLE ADD COLUMN` 即可，不必重建表。`GROUP_MEMORY_READ_MAX_SPAN`（`context/group-memory/index.ts:33`）按编号差值限宽的做法因此继续成立，本轮不改。

### 配置投影

`config.jsonc` 的格式一个字段都不动（见 D1）。新增一层中性访问器，放在 `src/platform/config/`：

- `ChatConfigEntry`：`ChatSchema` 的静态类型，替换所有 `RawConfig['telegram']['chats'][number]`。
- `configuredChats(config, host)`、`allConfiguredChats(config)`、`mapConfiguredChats(config, fn)`：读取与改写「某个 Host / 全部 Host 的 chat 条目」。
- `hostIntakeSettings(config, host)`：Bucket 窗口（已有 `resolveBucketTiming(config, host)`，并入）、`process_bot_messages`、`sticker_trigger_enabled`、`mention_typing_enabled`、全局 `participation`、全局 `proactive_reply`、`admins`。
- `resolveChatConfig(config, orm, { hostKind, hostChatId })`：按 Host 分派。Telegram 的 `chat_migrations` 别名解析留在 Telegram 那一支里；`chatSource: 'room'` 的 Host 返回 `undefined`。

之后只有这些地方可以写 `config.telegram`：`src/platform/config/`、`src/adapters/local-monolith/config/`、`src/adapters/local-monolith/telegram/`、`src/ingress/telegram-ingestion/`、`src/ingress/admin/`（产品 API 层）、`src/tui/`、`src/doctor.ts`、Sticker 集相关模块（Telegram 专属子系统）。

以后的 Host 在配置里各有一段，`chats[]` 复用 `ChatSchema` 的形状。

### 入站契约

发送侧已有 `ImHost`，入站侧补上对称的三样东西：

1. **`MessageCues`**（放 `platform/im-host/`）：`{ mentionsBot, repliesToBot, texts }`。参与闸门与主动回复只看 cues，不看 transport 消息对象。
2. **`InboundMessage` 与中性入库路径**（建议 `src/ingress/intake/`）：adapter 把平台消息归一化成 `InboundMessage`（内部 chat id、topic id、消息编号、时间、sender、来源类别、正文与回复信息、媒体描述、原始片段、cues），中性路径负责 sender / conversation / message / revision / media 写入、`eligibleHuman` 判定、参与闸门、Bucket 追加，并返回与现在相同的 `IngestResult`。
3. **原始片段读取器**：`raw_fragment_json` 的格式归写入它的 Host 所有。core 读它时按 Host 分派到 `{ cues(raw, bot), body(raw, fallback) }`，Telegram 的实现包住现有 `platform/telegram-markdown`。

Telegram 侧保留：`telegram_updates` 去重流水、allowlist 与 Topic 校验、群迁移通知、命令解析（entity）、被忽略用户、内容种类与 rich message 归一化。

## 工作包

依赖顺序：IMH-01 → IMH-02 →（IMH-03、IMH-04 可并行）→ IMH-05 → IMH-06。每个工作包一个 feature 分支、一个 PR；IMH-05 可以按小节拆成多个 PR。

所有工作包共同遵守：

- 先把「先写下的失败方式」落成测试，再写实现（[AGENTS.md](../../AGENTS.md#testing-guidelines)）。断言落盘状态与审计行，不只断言返回值。
- `test/im/pinned-surface.test.ts` 的期望值不许改。它一旦要改，说明模型可见行为变了，停下来报告。
- 清理式切换：迁移全部调用方并删除旧路径，不留别名与隐藏 fallback。
- 不删除、不移动任何 `config.jsonc` 字段。
- 源码保持 Node type stripping 可擦除语法；业务查询走 `store.orm`；新增迁移同步更新 `src/store/schema/`。
- 完成后运行 `pnpm run check`、`pnpm run lint`、`git diff --check`、完整 `pnpm test`；动到 Admin API 或其查询的包另跑 `pnpm run admin:test:e2e`。

### IMH-01 标识精度与 Host 解析

规模：小。不动数据库。

范围：

- `ImConversationRef.topicId` 改为 `bigint | null`。清掉 core 里所有 `Number(threadId)`（A1 列出的位置）。Telegram adapter 在 `telegram/host.ts` 落到 wire 的那一处转 number，并断言 `Number.isSafeInteger`。
- 在 `platform/im-host/identity.ts` 增加 `parseHostKind(value)`：未知值抛错。替换 A2 的全部强转与 `as HostKind`。

### IMH-02 存储标识中性化

规模：大，但几乎全是机械改动。不改变任何行为。

迁移 `063`（`@rebuild-tables`，参照迁移 037 的写法）：

| 表 | 变更 |
| --- | --- |
| `chats` | `telegram_chat_id` → `host_chat_id`；去掉两条枚举 Host 的 CHECK；去掉 `host_kind` 的 DEFAULT；唯一索引改为 `(host_kind, host_chat_id)` |

| `conversation_attention` | `trigger_telegram_message_id` → `trigger_message_no`（`RENAME COLUMN`） |

`message_no` 的 `NOT NULL` 同时是迁移的天然闸门：存量里只要有一行两个旧列都为空，`INSERT … SELECT` 就会失败并整体回滚。动手前先读 Playground 的全部写入路径（`store/playground/admission.ts`、`adapters/local-monolith/playground/delivery.ts`），确认每条房间消息都带序号；如果发现存在合法的空值路径，停下来报告，不要自行补默认值。

代码侧：

- `src/store/schema/` 同步；所有 insert 显式写 `hostKind`。
- core 里的 TS 标识符随之改名：`telegramMessageId` → `messageNo`、`telegramChatId` → `hostChatId`、`telegramDate` → `sentAt`、`telegramId` → `hostSenderId`、`telegramType` → `hostSenderType`。adapter 内部确实表示 Telegram wire 值的局部变量可以保留原名。
- Playground：`rooms.next_seq` 分配出的序号写入 `message_no`，按序号查 reply 目标的查询改读 `message_no`。`local_reply_to_message_id` 不动。
- Admin 审计查询（`ingress/admin/audit/*`、`ingress/admin/chats.ts` 等）用列别名保持响应字段不变；原先来自 `local_sequence_no` 的 `room_seq` 改为在房间行上取 `message_no`。
- `scripts/` 下直连 SQLite 的脚本（`scripts/audit*` 等，写作时 2–3 个文件引用旧列名）同步。
- 不改：冻结快照里的 JSON 键、`host_sends.response_json`、长期任务的 `delivery_json`、原始片段、结构化日志字段名。

先写下的失败方式：

- 升级后某条消息的 `message_no` 与原 `telegram_message_id` 或原房间序号不相等，历史 Context 里的 `reply:<id>`、群聊记忆事件引用的区间、`/cut_topic` cutoff 全部指错。
- 重建时外键被 CASCADE 触发，会话或消息被删；或 `foreign_key_check` 不干净却提交了。
- 新唯一约束让 Telegram 入库的 `ON CONFLICT` upsert 找不到冲突目标，重复 Update 插出两行，或者编辑消息不再追加 Revision。
- Telegram 与另一 Host 存在同值 `host_chat_id` / `host_sender_id` 时相撞，或者同一 Host 内的重复没被拒绝。
- 某条写入路径漏写 `host_kind`：以前靠默认值悄悄变成 Telegram，现在应当直接失败。
- 列改名后，Admin 响应字段名或类型变了（例如 `room_seq` 消失、`telegram_message_id` 在房间行上不再是 `null`）。
- 索引没跟着重建，历史查询退化为全表扫描（`test/schema/index-plans.test.ts` 管这个）。

验收：
