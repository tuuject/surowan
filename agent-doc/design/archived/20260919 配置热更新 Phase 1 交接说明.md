## 目标

1. `ConfigReloader.reloadFromFile()`：把配置文件中白名单字段的变化应用到当前进程；其余字段报告为待重启，不阻塞白名单字段。
2. 已有自定义 Provider 的 `models[]` 热更新。
3. `invocations.config_hash` 记录 invocation 转为 running 时快照的 active hash。
4. `/model` 与 Admin `PUT /model` 改为写配置文件再 reload。删除内存态 override、`/model reset` 与 `DELETE /model`。
5. Admin 后端提供「应用配置文件」端点与配置状态端点，前端提供一个最小的按钮。

## 不在本阶段范围

以下内容都不要做：

- agent / Vision 模型可选、`no_agent_model` 跳过：方案 Phase 1b。
- 模型禁用表、models.dev、Provider 与模型列表的编辑表单、保存接口里的在用模型保护：方案 Phase 2。
- 「立即重启」、上次可用配置的保存与回退、配置变更审计事件：方案 Phase 2。
- 表单级「重启后生效」元数据端点：方案 Phase 2 随表单一起做。本阶段只保证白名单只在一个模块里定义。
- restart-only 字段的热更新，包括 MCP、Vision、Provider 连接字段、allowlist：方案 Phase 3。
- filesystem watcher。
- 数据库 Schema 与迁移。

## 设计

### 1. `src/platform/config.ts`

- 导出 `validateSemantics`。
- 新增同步函数 `assembleRawConfig(fileConfig, systemPrompt, instructionsByChatId: ReadonlyMap<number, string>): RawConfig`。`resolvePrompts` 读完 Prompt 文件后改为调用它；candidate 构造也用它。
- 注意：`resolvePrompts` 用浅展开构造 RawConfig，所以 `LoadedConfig.config` 与 `LoadedConfig.fileConfig` 共享嵌套对象，例如 `admin`、`providers`、`paths`。本阶段的任何代码都不能修改这两个对象，candidate 一律从 `structuredClone` 得到的副本构造。
  - e2e 夹具 `apps/admin-next/e2e/server.ts` 在创建服务之前把 `loaded.config.admin.port` 改成了 0。由于对象共享，这同时改了 `fileConfig.admin.port`，所以 e2e 里执行 reload 时，`admin.port` 会出现在待重启列表中。这是预期结果，不要为此改生产代码。

### 2. 字段分类与差异：`src/platform/config-diff.ts`

纯函数模块，不做 IO。方案 §6.1 的白名单只在这里定义，新增字段默认是 restart。

- 输入：active 与 file 各一份 `{ file: FileConfig; raw: RawConfig }`。
- 输出：`ConfigChange[]`，每项为 `{ path: string; kind: 'hot' | 'restart' | 'outside_serve' }`，按 path 去重、排序。

| 路径 | 分类 |
| --- | --- |
| `agent.provider`、`agent.model` | hot（例外 1） |
| `agent.system_prompt_file`（路径或 Prompt 内容变化） | hot |
| `agent.thinking_level`、`agent.context_stop_ratio`、`agent.send_max_text_length`、`agent.send_disallow_blank_lines`、`agent.send_nudge_enabled` | hot |
| `agent.context.max_wall_clock_seconds`、`agent.context.idle_grace_seconds` | hot |
| `agent.rate_limits.*` | hot |
| `agent.daily_budget.max_tokens`、`agent.max_concurrency`、`agent.history_messages` | hot |
| `telegram.chats[<id>].instructions_file`（两边都有的 chat，路径或内容变化） | hot |
| `providers.<alias>.models[<model id>]`（两边都是 custom 的同一个 alias；模型新增、删除或定义变化） | hot（例外 2） |
| `paths.backups`、`retention.online_days`、`retention.backup_copies` | outside_serve |
| 其它所有路径 | restart |

比较规则：

- 对象逐字段递归比较。只在一边存在的字段也算变化，覆盖可选字段的增删。
- 数组整体做深比较，路径就是数组本身，例如 `telegram.sticker_sets`、`mcp.servers`。两个例外：
  - `telegram.chats` 按 `id` 对齐。新增或删除的 chat 报 `telegram.chats[<id>]`（restart）；两边都有的 chat 逐字段比较。
  - `providers.<alias>.models` 按模型 `id` 对齐。
- `providers` 按 alias 对齐：
  - 新增或删除的 alias 报 `providers.<alias>`（restart）。
  - `kind` 变化报 `providers.<alias>`（restart）。
  - builtin Provider 的任何字段变化都是 restart。custom Provider 除 `models` 以外的字段变化是 restart。
- Prompt 内容从 raw 比较：
  - `agent.system_prompt` 不同时报 `agent.system_prompt_file`。
  - 两边都有的 chat，`instructions` 不同时报 `telegram.chats[<id>].instructions_file`。

两个例外（需要 active 与 candidate 的引用关系）：

1. **agent 指向新增的 Provider**：文件里的 `agent.provider` 不在 active 的 `providers` 中时，`agent.provider` 与 `agent.model` 都改为 restart（方案 §6.1）。
2. **在用模型的定义变化**（方案 §9.4 手改配置文件的规则）：
   - 在用模型指 active 的 agent 模型与 vision 模型。只处理它们属于 custom Provider 的情况。
   - 如果文件修改了在用模型的定义，并且 candidate 仍然引用它，这一项 `providers.<alias>.models[<id>]` 改为 restart，candidate 沿用 active 的定义。「candidate 仍然引用」指 candidate 的 agent 引用它，或者它是 vision 模型（vision 恒为 active 的值）。
   - candidate 不再引用它时，按 hot 处理。例如 agent 已切到别的模型，并且它不是 vision 模型。
   - 删除一个仍被引用的在用模型，会在 `loadConfig` 的第一遍校验就失败，不需要特殊处理。

同一模块导出 candidate 构造：

- `candidateFile = structuredClone(active.file)`，然后把所有 hot 与 outside_serve 路径的值从文件的 FileConfig 复制过来。文件里不存在的字段就从 candidate 中删除。
  - `telegram.chats[<id>].instructions_file` 写到 candidate 中同 id 的 chat 上。
  - `providers.<alias>.models` 按文件中的顺序重建：hot 的条目取文件的定义，例外 2 的条目取 active 的定义。
- `candidateRaw = assembleRawConfig(candidateFile, file.raw.agent.system_prompt, instructions)`。
  - 两边都有的 chat 取 `file.raw` 的 instructions。
  - 只在 active 中存在的 chat（删除待重启）取 `active.raw` 的 instructions。
  - 不重新读盘。否则当 chat 与它的 instructions 文件一起被删掉时，reload 会失败（方案 §9）。

### 5. `ConfigReloader`：`src/platform/config-reload.ts`

```ts
export interface ConfigReloaderOptions {
  readonly loaded: LoadedConfig; // 启动时的加载结果
  readonly store: RuntimeConfigurationStore;
  readonly models: MutableModels; // registry.models
  readonly modelSwitcher: AgentModelSwitcher;
  readonly secrets: SecretStore;
  /** 工具注册表放不进该模型的 context window 时抛错。 */
  readonly validateAgentModel: (model: Model<Api>) => void;
  /** 每次成功 publish 之后调用；application 用它唤醒 scheduler。 */
  readonly onPublished: () => void;
}

export class ConfigReloader {
  constructor(options: ConfigReloaderOptions);
  reloadFromFile(): Promise<ConfigApplyResult>;
  setAgentModel(provider: string, model: string): Promise<ConfigApplyResult>;
  status(): ConfigStatus;
}

export type ConfigErrorCode =
  | 'config_permissions'
  | 'config_invalid'
  | 'candidate_invalid'
  | 'model_unusable'
  | 'unknown_provider'
  | 'unknown_model'
  | 'not_text_capable'
  | 'config_symlink'
  | 'config_write_failed';

export interface ConfigStatus {
  readonly generation: number;
  readonly activeHash: string;
  readonly fileHash: string; // 最近一次成功加载的文件 hash
  readonly restartRequired: readonly string[];
  readonly lastError: { readonly code: ConfigErrorCode; readonly message: string; readonly at: string } | null;
}

export type ConfigApplyResult =
  | {
      readonly ok: true;
      readonly applied: readonly string[];
      readonly restartRequired: readonly string[];
      readonly outsideServe: readonly string[];
      readonly status: ConfigStatus;
    }
  | {
      readonly ok: false;
      readonly code: ConfigErrorCode;
      readonly message: string;
      readonly fileWritten: boolean; // 只有 setAgentModel 写入后 reload 失败时为 true
      readonly status: ConfigStatus;
    };
```

内部状态：

- `#activeFile: FileConfig`：初始为 `structuredClone(loaded.fileConfig)`。active 的 RawConfig 就是 `store.current().config`。
- `#fileHash`（初始为 `loaded.hash`）、`#restartRequired`、`#lastError`。
- 一个用 promise 链实现的互斥锁。

`reloadFromFile()` 持锁执行：

1. `assertConfigPermissions(configPath)`，失败返回 `config_permissions`。编辑器保存后可能改变文件权限。
2. `loadConfig(configPath)`，失败返回 `config_invalid`。
3. 计算差异，构造 candidate。
4. `validateSemantics(candidateFile)`，失败返回 `candidate_invalid`。message 先说明：文件本身合法，但与当前进程中尚未生效的重启字段组合后不合法，这些字段重启后会一起生效。然后附上原错误和 restart 路径列表。
5. prepare：
   - candidate 的 `models` 与 active 不同的 custom alias，调用 `rebuildCustomProvider` 得到新 Provider。此时先不 `setProvider`。
   - 解析 candidate 的 agent 模型：custom alias 从新 Provider（没有重建时从注册表）取，builtin alias 用 `models.getModel` 取。不存在或不支持 `text` 时返回 `model_unusable`。
   - 调用 `validateAgentModel(model)`，失败返回 `model_unusable`。
6. publish。这一步是同步代码，中间不能有 `await`：
   1. 对每个新 Provider 调用 `models.setProvider`。
   2. `store.publish({ config: candidateRaw, hash: activeHash })`。
   3. 更新 `#activeFile`、`#fileHash`、`#restartRequired`，清空 `#lastError`。
   4. 调用 `onPublished()`。
7. 输出日志事件 `config_reloaded`，带 generation、active_hash、file_hash、applied、restart_required、outside_serve（列表用逗号拼接）。

其它规则：

- 没有 hot 与 outside_serve 变化时不 publish，generation 不变。仍然更新 `#fileHash` 与 `#restartRequired`，返回 ok。
- active hash：
  - restart 列表为空时，candidate 与文件一致，直接用 `loadConfig` 返回的文件 hash。这样可以继续和 `check-config` 的输出比对。
  - 否则对 `JSON.stringify(candidateRaw)` 做 SHA-256。
- 任何失败：active、`#activeFile`、`#fileHash`、`#restartRequired` 都不变；记录 `#lastError`；输出日志事件 `config_reload_failed`（code、error）。message 一律经过 `secrets.redact`。
- 两遍校验都不能省：第一遍（`loadConfig`）保证下次启动可用，第二遍保证当前进程可用。
- 日志与 `src/store/sleep.ts` 等模块一样直接 `console.log(JSON.stringify({ event, …, at }))`，不要从 `application.ts` 导入 `logEvent`。

`setAgentModel(provider, model)` 持同一把锁，写入与 reload 之间不能插入别的 reload：

1. `modelSwitcher.option(provider, model)` 校验，失败时返回对应的 `ModelSwitchError` code。
2. 对这个模型调用 `validateAgentModel`，失败返回 `model_unusable`。
3. 调用 §6 的写入函数修改 `agent.provider` 与 `agent.model`。失败时按错误返回 `config_permissions` / `config_symlink` / `config_invalid` / `config_write_failed`，文件与 active 都不变。
4. 执行与 `reloadFromFile` 相同的加载与应用流程：在锁内调用私有实现，不要递归取锁。这一步失败时 `fileWritten: true`。

### 6. 配置文件写入：`src/platform/config-file.ts`

```ts
export async function writeConfigEdits(
  configPath: string,
  edits: readonly { readonly path: JSONPath; readonly value: unknown }[],
): Promise<void>;
```

Phase 2 的表单也会复用它。步骤：

1. `lstat`：配置文件是符号链接时抛出 `config_symlink`，因为 rename 会把链接替换成普通文件。
2. `assertConfigPermissions`。
3. 读原文。有 BOM 时先去掉，改完再加回。
4. jsonc-parser 的 `modify` + `applyEdits`，`formattingOptions: { insertSpaces: true, tabSize: 2 }`。只替换值，保留注释与其它格式。不要照搬 `src/tui/configure.ts` 的 `JSON.stringify` 整体回写，那会抹掉注释。
5. 写到同目录的临时文件 `.<basename>.<pid>.<随机串>.tmp`：`open(tmp, 'wx', 0o600)`，写入，`sync()`，关闭。
6. `loadConfig(tmp)` 做完整校验。Prompt 路径相对同一目录解析，和正式文件一致。失败时删除临时文件，抛出 `config_invalid`。
7. `rename(tmp, configPath)`。

其它 IO 失败时尽力删除临时文件，抛出 `config_write_failed`。错误用一个带 `code` 的 Error 子类表达，由 `ConfigReloader` 转成结果。

### 7. 运行时读取的调整

  - `validateAdditionalTools(context, additionalTools, model: Model<Api>)`：增加必填的 `model` 参数，按它的 `contextWindow` 判断。

  - 删除 `#override`、`switch()`、`reset()`。
  - `#option` 改为公开的 `option(provider, model)`。

- MCP registry validator 的两个调用方都改为传入模型：`application.ts` 传 `modelSwitcher.model()`，`doctor.ts` 传 `requireModel(...)` 的结果。

### 11. `src/application.ts` 接线

```ts
const configReloader = new ConfigReloader({
  loaded,
  store: configStore,
  models: registry.models,
  modelSwitcher,
  secrets,
  validateAgentModel: (model) =>
    runtime.validateAdditionalTools(preview, additionalTools(preview, Number.MAX_SAFE_INTEGER), model),
  onPublished: () => startedScheduler.wake(),
});
```

`preview` 与 `additionalTools` 已经在 `application.ts` 中定义，注意声明顺序。唤醒 scheduler 是为了让调大的 `max_concurrency` 立即生效。
