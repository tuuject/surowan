# Keychain 实施计划

对应 PRD：[`doc/design/20261116-keychain.md`](../../doc/design/20261116-keychain.md)。本文是 AI 直出的实施契约，未经用户逐条审核；与 PRD 冲突时以 PRD 为准。用户确认过的内容见[已确认](#已确认)，其余是实施默认，集中在[实施默认](#实施默认)，用户可以逐条推翻。文中的文件路径、行号与行为描述取自写作时的 `develop`（`91f22c21`），动手前请核对源码。

## 目标

把现有的 key jar 升级成 keychain：每把密钥有稳定、可读的名字，可以被多处使用，可以原地轮换；面板提供 keychain manager 查看、新建、轮换、删除和清理孤儿。不新增配置概念，`{ "jar": "<name>" }` 的写法与 `key.json` 的文件名都不变。

## 已确认

以下各条均于 2026-11-16 在对话中确认，并已写入 PRD。

1. keychain 就是升级后的 key jar。配置里的引用写法不变，文件仍叫 `key.json`、位置不变。
2. 文件格式升级为带版本号的结构，每个条目保存值和创建时间，名字就是标签。`serve` 与 `configure` 启动时一次性原地迁移，之后只认新格式。迁移不改配置文件，存量条目保留原名。
3. 条目名稳定，换密钥是在原条目上替换值。热应用除了看引用有没有变，还要看被引用条目的值有没有变；手工改 `key.json` 的值，下一次热应用同样能识别。
4. 所有需要密钥的输入处二选一：「填新密钥」或「选用已有条目」，面板与 `configure` 相同。填新密钥时自动建条目，名字按使用处推导，重名加后缀，录入时可以改。
5. 面板会话与服务器上的 `configure` 选用已有条目不设限。外部 Agent 与客户端 CLI（API key 或已配对客户端）只能提交新密钥，不能选用已有条目；修改连接地址时仍须在同一次请求里重新提交密钥。面板里修改连接地址不再要求重新提交密钥。
6. Keychain manager 放在面板的系统设置栏目：列出条目（名字、创建时间、使用处），新建暂时没人用的密钥，轮换，删除单个没有被使用的条目，一键清理孤儿，另有只读的「外部引用」列表。任何地方都不显示密钥的值。
7. 取消所有自动回收，包括 `configure` 退出时的清理。孤儿只由显式清理移除。孤儿的定义：磁盘上的配置文件没有引用它，并且运行中生效的配置也没有引用它；磁盘一侧看文件原始内容，被忽略的配置段里的引用也算数。配置文件无法解析时拒绝清理。清理前弹窗列出条目名，不可撤销。「没有被使用」与孤儿是同一个判断。
8. `env` 与 `command` 引用不迁移，原样保留。面板只读展示它们（用在哪、哪一种、环境变量名；`command` 的 argv 不展示），可以替换成 keychain 条目，但不能新建这两种引用。它们的轮换语义不变，值变化检测只对 keychain 条目做。
9. 这一期不做：条目事后改名、清理图片配置里的 `credentials` 这一层、条目备注等额外信息。

## 现状与落点

动手前需要知道的现状，按主题列出。

**存储**

- `src/platform/key-jar.ts`：`KeyJar` 是 `Record<string, string>`；`updateKeyJar` 只支持 `add`（名字必须是新的，`key-jar.ts:85-88`）与 `remove`，写入是同目录临时文件加 rename，`0600`，拒绝符号链接；`referencedJarNames` 结构化遍历配置找出所有 `{ jar }` 引用。
- `src/platform/secrets.ts`：`SecretStore.resolve` 每次都重读文件（`secrets.ts:79-97`）。
- `src/platform/config/write.ts`：`ConfigEdit.keys` 携带要新建的条目；`secretEdit` 用 `newKeyJarName()` 生成 16 位随机 hex 名。

**自动回收（要全部删除）**

- `src/adapters/local-monolith/config/file.ts:167-173`：每次 `writeConfigEdits` 之后删除新文件不再引用的条目。
- `src/tui/configure.ts:79` 与 `pruneKeyJar`（`configure.ts:86-111`）：`configure` 退出时清理。
- 依赖这两处回收的文字说明：`src/ingress/admin/routes/image.ts:52-57`、`src/ingress/admin/routes/search.ts:22-29` 的注释，以及 `agent-doc/configuration.md`、`agent-doc/admin-panel.md` 里「随之回收」的描述。

**疑似误删 bug（阅读代码得出，未复现）**

`file.ts:102` 的「之前引用」取自原始 JSONC；`file.ts:167` 的「之后引用」取自 `loadConfig` 返回的 `fileConfig`。而 `src/platform/config/validate.ts:35-45` 在 `image` 段结构不合法时会 `delete root.image`。两者相减，`image.credentials` 下的条目会被当作「不再引用」而删除，触发条件是 `image` 段不合法时发生任意一次配置写入，包括成员的 `/ignoreme`。删除自动回收后此问题消失，仍须补一条回归测试，见[测试](#测试)。

**热应用怎么判断连接变化**

- 联网搜索：`src/plugins/web-search/request.ts:46` 每次请求解析，天然即时生效。
- MCP：`src/capabilities/mcp/index.ts:247,261` 在连接时解析；`mcp.servers` 是重启字段。

**面板写入密钥的入口**

- Provider：`src/ingress/admin/providers/write.ts:37-41`（新建）、`:121-124`（改 key）。改地址须重交密钥的防护在 `:126-145`。

## 文件格式与迁移

新格式（D1）：

```json
{
  "version": 1,
  "entries": {
    "openrouter": { "value": "sk-...", "created_at": "2026-11-16T08:00:00.000Z" }
  }
}
```

- 旧格式是值全为非空字符串的扁平对象。判别规则：顶层 `version` 是数字且 `entries` 是对象即为新格式；否则按旧格式校验。旧格式里恰好有一个叫 `version` 的条目时，它的值是字符串，不会误判。
- 迁移把每个旧条目变成 `{ value, created_at: 迁移时刻 }`，名字不变。写入沿用现有的临时文件加 rename、`0600`、拒绝符号链接。
- 迁移入口：`serve`（组合根构造 `SecretStore` 之前，`src/adapters/local-monolith/runtime/index.ts:28` 附近）、`configure` 启动时，以及 `doctor`（D2）。`doctor` 要解析 SecretRef，不迁移的话升级后第一次诊断必然失败。
- 迁移之外的读路径只认新格式，遇到旧格式报出可操作的错误（提示启动 `serve` 或运行 `configure`），不做静默兼容读取。
- 不为 `key.json` 留备份副本：多一份明文密钥文件得不偿失，原子 rename 已经保证读者只看到旧文件或完整的新文件。
- 迁移后旧版本程序读不了新文件。PR 说明里要写明这是单向升级。
- 错误信息沿用现有约束：只含路径与条目名，不回显文件内容。

写操作从 `{ add, remove }` 扩展为 `{ add, remove, replace }`。`add` 仍要求名字是新的；`replace` 要求条目已存在，保留 `created_at`。

## 命名规则

自动命名（D14）按使用处推导，结果必须匹配 `^[A-Za-z0-9_-]{1,64}$`，不合法字符替换为 `-`，超长截断：

| 使用处 | 条目名 |
| --- | --- |
| `providers.<alias>.api_key` | `<alias>` |
| `providers.<alias>.headers.<h>` | `<alias>-<h>` |
| `telegram.token` | `telegram` |
| `web_search.engines[].api_key` | `search-<engine id>` |
| `mcp.servers[]` 的 `env` / `headers` | `mcp-<server 名>-<键名>` |
| `image.credentials.<name>` | `<name>`（与现状一致） |
| manager 里新建 | 管理员输入，必填 |

- 自动推导的名字重名时依次加 `-2`、`-3`。
- 管理员显式指定的名字重名时返回冲突错误，不替他改名。
- `newKeyJarName()` 的随机 hex 不再使用，删除。

## 热应用与轮换

**值变化检测（D4）**

- keychain 模块提供条目摘要：对 `{ jar }` 引用返回条目值的 SHA-256，对 `env` / `command` 返回空。摘要只在内存里，不落盘、不进日志。
- `reload-apply.ts` 的应用状态（现有的 `imageSnapshotId`、`telegramTokenId` 旁边）记下每个 Provider 上次构建时的摘要集合；`buildModelRegistry` 复用连接的条件从「连接字段相同」变为「连接字段相同且摘要相同」。
- 摘要只对 `jar` 引用计算，因此不会为了检测而执行 `command`。
- 图片与 Telegram token 已经在每次应用时重新解析，不需要改。
- 联网搜索每次请求解析，不需要改。
- 已经开始的 Invocation 继续用它冻结的连接快照，下一次 Invocation 才用新密钥，与现有的 Provider 热更新语义一致。

**MCP（D5）**

`mcp.servers` 是重启字段，密钥在连接时解析。原计划本期不改它的生命周期（轮换后由 manager 提示「重启后生效」）。**用户于 2026-11-18 决定改为：轮换被 MCP Server 使用的条目时，apply 把这些 alias 视作配置发生变化的 Server，经既有的热 MCP 切换路径重连并解析新密钥（Chats 走同一套 fence/rebuild/continuation 规则），不再有重启等待**；PRD 的「值变了，使用它的连接就重新建立」对 MCP 成立。

**轮换的触发**

manager 轮换一个条目后必须触发一次应用（配置文件哈希没有变化，但条目值变了）。`reload-apply.ts:112-114` 的注释表明文件不变时应用仍会走完整流程，复用 `reloadFromFile` 这条路径即可。

**并发**

`writeConfigEdits` 对 `key.json` 是读改写。manager 的写操作必须和配置写入走同一把 `ConfigReloader` 锁，否则两者会互相覆盖。做法是把 keychain 的读写挂到 `ConfigController` 契约上，由 local-monolith 实现；`ingress` 不直接碰文件。

## 录入与写端点

**取消自动回收**

- 删除 `file.ts:167-173` 的释放逻辑。`file.ts:160-164` 在 rename 失败时撤销本次新建的条目属于事务回滚，保留。
- 删除 `configure.ts` 的 `pruneKeyJar` 及其调用。
- 图片关闭、搜索引擎删除不再回收条目，更新相关注释与文档。

**`SecretInput`（D6）**

所有接受密钥的写端点统一成一个联合类型：

```ts
type SecretInput =
  | string                               // 新密钥，自动命名（现有写法，保持可用）
  | { value: string; name?: string }     // 新密钥，可指定条目名
  | { entry: string };                   // 选用已有条目
```

- `{ entry }` 写入前校验条目存在，否则会写出一个引用不存在条目的配置文件。
- `{ entry }` 来自外部凭据时返回 403，见[调用方区分](#调用方区分)。
- 提交的明文照旧经 `SecretStore.remember` 登记，保证后续输出被脱敏。

**「填新密钥」的语义（D7）**

输入处当前已指向某个条目时再填新密钥：

- 该条目只被这一处使用：原地替换值，名字不变。配置文件没有变化，所以不能走 `writeConfigEdits`（`file.ts:119-121` 会因为「没有改动」报错），要走 keychain 的 `replace` 加一次应用。
- 该条目还被别处使用：新建条目并把这一处改指过去，其它使用处不受影响。原条目不动。
- 想让所有使用处一起换，去 manager 轮换。

两种情况对应的都是「我只改了这一处」的直觉。PRD 没有写到这一层，请用户确认。

**删除专用复用路径（D8）**

搜索的 `key_source`（只限 DeepSeek）和图片的 `credential_sources`（只限 OpenRouter）是通用「选用已有条目」出现之前的局部方案。按清理式切换删除，面板改用通用的条目选择。代价有一处：这两条路径复用的是 Provider 的 SecretRef 本身，Provider 的密钥来自 `env` / `command` 时也能复用；删除后，面板不能再把这种密钥一键用到搜索或图片上（PRD 规定面板不能新建这两种引用），要手写配置文件。这是对现有行为的收紧，请用户确认。

另有一处需要核对：现状下外部凭据提交 `key_source` 或 `keep_api_key` 的同时覆盖引擎 `endpoint`，可能已经能把 DeepSeek 密钥发往任意地址（`resolveEngineKey` 只检查服务商有没有变，不检查地址）。本计划的 D8 与 D9 会关上这条路；动手时先确认它是否真实存在，存在的话在 PR 说明里单独写明。

## 调用方区分

- 向写处理器显式传入调用方类别 `'session' | 'programmatic'`（D10）。现有的 actor 字符串只用于审计，不要靠解析它的前缀做权限判断。
- `'programmatic'`：`{ entry }` 一律 403；Provider 的 `base_url` 变化仍须同请求重交密钥与全部 header 值（`providers/write.ts:126-145` 的现有逻辑保留）。
- `'session'`：`{ entry }` 放行；`base_url` 变化不再要求重交密钥。
- 推广（D9）：对 `'programmatic'`，凡是「保留原有密钥」与「目标地址变化」同时出现的写入都拒绝，要求重交。目前已知的地址字段是 Provider 的 `base_url` 与搜索引擎的 `endpoint`；其它带地址的写端点请在实施时逐个排查。
- `configure` 运行在服务器 shell，按 `'session'` 同等对待，不设限。

## Manager API

全部端点只对面板会话开放（D11）：不在 `packages/admin-surface` 登记，外部凭据因此得到 403，也不会出现在 CLI 命令与 MCP 工具里。理由是已确认的原则本来就不让外部凭据接触已有条目；想开放需要用户另行决定。写端点都校验 `Origin`，并登记到 `agent-doc/admin-panel.md` 的写端点白名单。

| 端点 | 行为 |
| --- | --- |
| `GET /api/keychain` | 条目列表与外部引用列表，见下 |
| `POST /api/keychain` | 新建条目 `{ name, value }`；重名 409 |
| `PUT /api/keychain/<name>` | 轮换 `{ value }`；条目不存在 404；成功后触发一次应用，响应带应用结果 |
| `DELETE /api/keychain/<name>` | 删除单个条目；仍被使用时 409 |
| `POST /api/keychain/purge` | 清理孤儿 `{ names }`（D12） |

`GET` 的响应：

- 条目：`name`、`created_at`、`used_by`（磁盘配置里的引用路径列表）、`active`（运行中的配置是否引用）、`orphan`。永不包含值，也不包含值的片段或摘要。
- 外部引用：`path`、`kind`（`env` / `command`）、`env` 时带变量名。`command` 的 argv 不返回。

**使用处的计算**

- 把 `referencedJarNames` 泛化为返回「条目名 → 引用路径列表」，同一次遍历顺带收集 `env` / `command` 引用。
- 磁盘一侧用原始 JSONC 的解析结果，不用 `loadConfig` 校验后的配置，这样被忽略的 `image` 段里的引用也算数。JSONC 解析有错误时整个判断失败，`purge` 与 `DELETE` 返回错误，`GET` 标明使用处不可用。
- 运行中一侧取应用状态里的 `activeFile`（`reload-apply.ts:18`）。典型场景：重启字段（如 `telegram.token`、`mcp.servers`）在文件里已经改掉，但进程仍在用旧引用，这时旧条目不是孤儿。

**清理（D12）**

面板先用 `GET` 的结果弹窗列出孤儿，管理员确认后把这批名字提交给 `purge`。服务端重新计算，只删除其中此刻仍是孤儿的条目，并在响应里分别列出已删除与被跳过的名字。这样确认与执行之间状态变化时，不会删掉管理员没见过的条目。

## 测试

按仓库规则先写下失败方式再写代码。Provider 与 Telegram 一律用现有 Faux 与 fixture。

**隔离测试（vitest）**

- 迁移：旧格式转新格式且幂等；旧格式含名为 `version` 的条目；权限不是 `0600` 时拒绝；符号链接拒绝；JSON 损坏时错误信息不含文件内容；新格式不被再次迁移。
- 不再回收：配置写入移除一处引用后条目仍在；`configure` 退出后本次新建的条目仍在。
- 误删回归：`image` 段结构不合法时做一次无关的配置写入，`image.credentials` 引用的条目必须仍在。先在旧代码上确认它会失败，以此复现原故障。
- 值变化检测：只改条目值后应用，Provider 连接重建，下一次请求带新密钥；运行中的 Invocation 仍用旧快照；`env` Provider 不受影响；`command` 引用在这次应用中执行次数为零。
- 原地替换与改指向（D7）：条目独占时名字不变、值更新；条目共享时新建条目，其它使用处的值不变。
- 孤儿判断：文件已移除引用但运行中的配置仍在用（重启字段），不算孤儿；配置文件无法解析时 `purge` 与 `DELETE` 拒绝；`purge` 只删提交名单里仍是孤儿的条目。
- 删除：被使用的条目返回 409。
- 调用方：API key 与已配对客户端提交 `{ entry }` 得到 403；它们改 `base_url` 或搜索 `endpoint` 而不重交密钥被拒绝；面板会话两者都放行；keychain 端点对外部凭据返回 403。
- 泄露：所有 keychain 端点的响应、应用结果与日志里都不出现密钥值，提交过的明文被脱敏。
