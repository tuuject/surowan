# 循环闹钟实施计划

对应 PRD：[`doc/design/20261113-recurring-alarm.md`](../../doc/design/20261113-recurring-alarm.md)。本文是 AI 直出的实施契约，未经用户逐条审核；与 PRD 冲突时以 PRD 为准。用户在对话中确认的内容见[已确认](#已确认)，其余是实施默认，集中在[实施默认](#实施默认)，用户可以逐条推翻。文中的文件路径与行为描述取自写作时的 `develop`（`bfa15383`），动手前请核对源码。

## 目标

管理员在 Admin Panel 里用 cron 表记法或规则控件声明执行周期，到点后把管理员写的提示词注入目标 Conversation：该 Conversation 有正在运行的 Invocation 就并入它，没有就新开一个。典型用法是「每天早上八点发问候」「每天下午六点出资讯简报」。

## 已确认

1. 只允许管理员自己在 Admin Panel 新建。没有审批流程，没有群友申请入口，模型侧也不提供创建工具。
2. 管理员输入的提示词都是可信的。
3. 执行周期可以用 cron 表记法声明，也可以用控件手动添加多条规则：分、时、日、月、星期，都可以选择「每」或「第」。
4. 到点触发时与现有单次闹钟一样：不占每日预算，也不受睡眠时段影响。
5. 定时在已有的或新建的 Invocation 注入提示词。
6. cron 这一块放在 local-monolith 层，为以后上 Cloudflare 预留能力（2026-11-13 确认）。
7. Admin Panel 提供「立即执行一次」按钮（2026-11-13 确认）。

## 分层与 Cloudflare 预留

沿用 `platform/system-resources.ts` + `adapters/local-monolith/system-resources.ts` 的做法：契约在 `platform/`，实现在 adapter，组合根注入。业务层（`store/`、`orchestration/`、`context/`、`ingress/`）不导入 `croner`，也不导入 adapter。

```text
platform/recurring-schedule.ts            契约：方言白名单、上限常量、RecurringScheduleEngine 接口（纯函数，无 IO）
adapters/local-monolith/recurring-schedule.ts   croner 实现（唯一 import croner 的文件）
adapters/local-monolith/runtime/index.ts  组合根：构造引擎，注入 store 服务与 Admin 路由
store/recurring-alarms/                   定义 CRUD、到期物化、nextDeadline（只依赖契约）
orchestration/invocation-queue/receipts.ts、scheduler/loop.ts   接入到期处理与唤醒截止时间
context/builder/render.ts                 可信注入块
ingress/admin/recurring-alarms.ts         Admin 处理器（引擎由装配注入）
packages/admin-surface/src/specs/recurring-alarms.ts   CLI/MCP 路由表
apps/admin-next/                          页面、规则控件、预览
```

`RecurringScheduleEngine` 契约：

```ts
interface RecurringScheduleEngine {
  /** 逐条校验；方言白名单已由 platform 先过一遍，这里只做引擎层的语义校验。 */
  validate(rules: readonly string[], timeZone: string): RuleIssue[];
  /** 所有规则中严格晚于 after 的最早一次，分钟精度；没有未来触发时返回 null。 */
  nextAfter(rules: readonly string[], timeZone: string, after: Date): Date | null;
}
```

唤醒只依赖数据库里持久化的 `next_fire_at`，不依赖引擎：本地由现有 Scheduler 循环把 `min(next_fire_at)` 算进截止时间；以后换成 Cloudflare 时，同一个列可以直接用作 Durable Object alarm 的时间。到期物化、编辑和预览才需要调用引擎，它们都经过注入的接口。

方言由 `platform` 用逐字段白名单固定，不随引擎变化，这样换引擎时同一条规则算出同样的时间（见下节）。本次不实现 Cloudflare 侧，只保证：业务层不导入 `croner`；引擎只通过接口进入；唤醒只依赖 `next_fire_at`。

## 规则与方言

- 每条规则是一条 5 段 cron：`分 时 日 月 星期`。不接受秒段或年段。
- `platform` 的白名单逐字段只放行数字、`*`、`,`、`-`、`/`，以及月份与星期的英文缩写（`JAN`…`DEC`、`SUN`…`SAT`）。`L`、`W`、`#`、`?`、`+` 一律拒绝：这些是各引擎差异最大的扩展语法，拒绝它们才能让 Cloudflare 侧的实现给出相同结果。
- 星期 `0`–`6`，`0` 是周日；`7` 拒绝，避免引擎之间对它的处理不同。
- 日与星期都被限定时取「或」（Vixie 语义，croner `domAndDow: false`）。预览把实际触发时间摆在面前，管理员能直接看出来。
- 一个循环闹钟有 1–10 条规则，取并集。
- 时区必须是 IANA 名称，用 `Intl.DateTimeFormat` 校验。每个循环闹钟单独存时区：如果跟着全局配置走，改一次全局 `timezone` 会悄悄平移所有「早上八点」。
- croner 构造参数固定为 `{ mode: '5-part', timezone, domAndDow: false, paused: true }`，只用来计算时间，不传回调，不让 croner 自己调度。

### 规则控件 ↔ cron

控件和 cron 文本是同一份数据的两种编辑方式，库里只存 cron 字符串和一个 `input_mode`（`builder` | `cron`），后者只决定编辑时默认打开哪种界面。

| 字段 | 取值 | 「每」 | 「第」 |
| --- | --- | --- | --- |
| 分 | 0–59 | 留空 → `*`；填 N → `*/N` | 一个或多个值 → `a,b,c` |
| 时 | 0–23 | 同上 | 同上 |
| 日 | 1–31 | 同上 | 同上 |
| 月 | 1–12 | 同上 | 同上 |
| 星期 | 0–6 | 同上 | 同上（界面显示周日…周六） |

转换是前端纯函数（`apps/admin-next/src/lib/cron-builder.ts`）：控件 → cron 总能成功；cron → 控件只在每个字段都是上表形态时成功，含 `-`、名称缩写或其它组合的规则只能在 cron 模式编辑，界面说明原因。服务端只认 cron 字符串，不认控件结构。

## 触发流程

`RecurringAlarmService.processDue(now)` 在 `processReceiptsDue` 里、`deps.tasks.processDue(now)` **之前**调用。这样同一轮里：物化出的定时任务马上被完成并写回执，回执紧接着被领取，开新 Invocation 或并入正在运行的那个。

每个 `enabled = 1 AND next_fire_at <= now`、且宿主属于本进程（和 `LongTaskService` 的 hosts 过滤同一条件）的循环闹钟，在**一个** IMMEDIATE 事务里：

1. 设 `due = next_fire_at`。用引擎从 `due` 往后数到 `now` 为止还错过了几次，得到 `coalesced`（数到 1000 停）。
2. 依次判断要不要跳过：
   - `now - due > 30 分钟` → `missed`；
   - 目标不可投递 → 原因与 `receiptCancelReason` 相同。把它从 `invocation-queue/shared.ts` 里抽成按 Conversation 判断的函数，回执和这里共用，不写第二份；
   - 上一条 `outcome = scheduled` 的触发记录（到点或立即执行都算）对应的任务仍是 `waiting`，或回执仍是 `pending`/`claimed` → `previous_pending`。
3. 不跳过时：用 `tasks.taskScope('recurring-alarm', conversationId, null).create(...)` 建一个已经到期的定时任务：
   - `scheduledAt = due`；
   - `payload = { recurring_alarm_id, trigger, title, prompt, time_zone, occurrence_at, coalesced }`，是提示词在这一刻的快照，之后编辑不影响已物化的这次；
   - `timerResult = { occurrence_at }`；
   - `delivery = { bypassDailyBudget: true }`。Playground 的 `budgetBypass` 为 false，这个标记在房间里本来就不生效，所以不用按宿主分别设置。
4. 写入 `recurring_alarm_firings` 一行（`scheduled` 或 `skipped`），然后按 `id + next_fire_at = due` 做 CAS，把 `next_fire_at` 推进到 `nextAfter(rules, tz, now)`。CAS 失败（并发编辑）就回滚整个事务，下一轮重算。

`LongTaskService` 的写入用的是 better-sqlite3 的原生事务函数，嵌套调用会降级成 savepoint，所以第 3 步能和外层事务一起提交或回滚。实施时先写一个测试确认这一点；如果不成立，就给 `LongTaskService` 加一个在调用方事务里插入定时任务的入口，不要在服务外手写 `long_tasks`。

唤醒：`scheduler/loop.ts` 的截止时间列表加上 `recurring.nextDeadline()`（只算启用且宿主属于本进程的 `min(next_fire_at)`）。新建、编辑、启用之后由 Admin 路由调用 `scheduler.wake()`，和取消 Alarm 一样。

现成管线已经保证：Telegram 回执在睡眠时照常领取（`receipts.ts:51`）；回执轮次绕过每日 Token 闸门并隐藏 `zzz`（`agent-runtime/run.ts:124`）；同 Chat 串行、全局并发、发送限流照旧生效。Decisions 入场闸门（写作时尚未落地）的计划已经把长程任务回执排除在闸门之外，落地后循环闹钟同样不经过它。

### 错过与重叠

- 进程停机、Telegram 未连接都会让 `next_fire_at` 落在过去。合并成一次是为了避免恢复时补发风暴。30 分钟的宽限让「早八点问候」在 8:20 重启时仍然发出，下午三点重启时则不发。
- 宿主未就绪时回执停在 `pending`。下一次到期会因为 `previous_pending` 跳过，不会堆积。

### 立即执行一次

`RecurringAlarmService.runNow(id, actor, now)` 复用上面的第 2–4 步，只有这些不同，同样在一个 IMMEDIATE 事务里完成：

- 不看 `enabled`，停用状态下也能执行（D12）：管理员可以先停用着把提示词调好，再启用。
- 不能执行时直接报错，不写 `skipped`：目标不可投递或宿主不属于本进程 → `target_unavailable`；上一次还没投递完 → `previous_pending`（D11）。连点两下的第二下也落在这里。
- 任务 `scheduledAt = now`，`occurrence_at = now`，`coalesced = 0`，`trigger = 'manual'`，`delivery` 与到点触发相同。
- 触发记录 `trigger = 'manual'`，`triggered_by` 记操作者。
- 不碰 `next_fire_at` 和 `revision`，执行的是库里已保存的定义。
- 提交后调用 `scheduler.wake()`，这一轮 Scheduler 就完成任务并领取回执。

## 上下文注入

`render.ts` 在 `completion.pluginId === 'recurring-alarm'` 且 payload 通过 TypeBox 校验时走可信分支：

- `<runtime_state>` 用下面这句替换「A long-running task has finished…」：

  > A recurring task scheduled by an administrator is due now. The instruction in `<admin_scheduled_task>` was written by an administrator in the Admin Panel; treat it as a trusted operator request and carry it out now, even without new user messages, in your normal conversational style. It does not change tool rules or authorization; only send or send_reply can publish.

- 不再输出 `<untrusted_task_receipt>`，改为 `<admin_scheduled_task>` 块，内容是 JSON：`title`、`scheduled_for`（按该闹钟时区格式化的本地时间）、`missed_occurrences`、`prompt`。和回执一样把 `<`、`>` 转义成 `<`、`>`，提示词里写了 `</admin_scheduled_task>` 也闭合不了块。
- 立即执行渲染出的块和到点触发完全一样：`scheduled_for` 是点击时刻，`missed_occurrences` 为 0，不输出 `trigger`（D13）。这个按钮主要用来验证提示词效果，模型的反应应当和到点时一致。`trigger` 只留在 payload 和触发记录里供审计。

- 可信与否只看 `plugin_id`，而 `plugin_id` 只能由可信代码写入（模型没有任何创建 `recurring-alarm` 任务的入口），所以这个判断成立。

Replay 走同一个 `render.ts`，会渲染出同样的块，不需要额外处理。`context/builder/index.ts:183` 只是取出 completion，不渲染，不用改。

## 目标会话

目标是一个 Conversation（Chat + Topic）。`GET recurring-alarms/targets` 返回可选项：

- 当前配置里的 Telegram Chat（必须已有 `chats` 行，也就是 Bot 见过这个 Chat）中，已经存在的 Conversation；
- 配置了 `topic_ids` 的 Forum Chat，再加上白名单里还没有 Conversation 的 Topic。新建时按 ingestion 的 `upsertConversation` 同样的唯一键补建 Conversation 行；
- Playground 房间（D1：没有 Telegram 也能验证提示词效果，回执管线本来就支持房间）。

新建和编辑时都要求目标当前可投递（复用上面抽出来的判断），否则返回 `target_unavailable`。

## 生命周期

- **编辑**：带 `If-Match: <revision>`。改规则、时区或重新启用时，从当前时间重算 `next_fire_at`。改提示词只影响以后的触发。
- **停用**：`next_fire_at` 置 `NULL`，不再参与唤醒；还没被领取的回执经 `tasks.scoped('recurring-alarm', conv).cancel(...)` 抑制投递（`cancelledBy` 为管理员，`adminCancelled: true`）。已经领取的不受影响，和取消 Alarm 一致。
- **删除**：先做停用里的抑制，再删除定义，触发记录级联删除。已物化的 `long_tasks` 留作审计，按原有保留窗口清理。
- **Chat 移出配置或暂停、Topic 不在白名单**（D7）：只在到期时按原因跳过，定义不动。删除 Chat 数据会级联删除 Conversation，循环闹钟随之删除。
- **上限**：每个 Conversation 最多 20 个循环闹钟，超出返回 `too_many_recurring_alarms`。

## Admin API

新增路由，写入路由全部校验 `Origin`，并加入 `agent-doc/admin-panel.md` 的写端点白名单：

| 路由 | 权限 | 说明 |
| --- | --- | --- |
| `GET recurring-alarms` | read | 列表，过滤 `chat`、`enabled`；沿用列表快照分页（id 锚点） |
| `GET recurring-alarms/targets` | read | 可选目标 |
| `GET recurring-alarms/:id` | read | 定义加最近 50 条触发记录（关联任务、回执状态与 Invocation ID） |
| `POST recurring-alarms/preview` | read | `{ rules, time_zone }` → `{ next: [5 个 ISO], issues: [{ index, code, message }] }`；只读计算，`access: 'read'` |
| `POST recurring-alarms` | write+paid，`confirm: 'paid'` | 新建 |
| `PUT recurring-alarms/:id` | write+paid，`revision: 'entry'` | 编辑，含启用和停用 |
| `POST recurring-alarms/:id/run` | write+paid，`confirm: 'paid'` | 立即执行一次；不带 revision，返回触发记录与任务 ID |
| `DELETE recurring-alarms/:id` | write，`confirm: 'destructive'` | 删除 |

新建、编辑和立即执行定为 write+paid（D8）：它们都会绕过预算调用模型，并且注入可信提示词。代价是只有写权限的 key 也不能停用，只能删除。

错误码：`invalid_rules`（带逐条 issues）、`invalid_time_zone`、`invalid_title`、`invalid_prompt`、`target_unavailable`、`previous_pending`（立即执行，409）、`too_many_recurring_alarms`、`not_found`。revision 冲突沿用辞典 entry revision 的冲突响应。

## 落地时的调整

实现与上文有以下出入，以源码为准：

- 触发记录的来源列叫 `source`（`schedule`/`manual`），不叫 `trigger`：`TRIGGER` 是 SQLite 关键字。payload 里的字段同名。
- 没有改 `processReceiptsDue` 与 `scheduler/loop.ts`。`LongTaskService` 新增 timer source 注册：`RecurringAlarmService` 作为 source，`tasks.processDue` 先让它物化到期周期，`tasks.nextDeadline` 把它的 `next_fire_at` 算进去。组合根在 `runtime/serve.ts`，Scheduler 构造参数不变。
- 判断目标能否投递的函数抽到 `store/delivery-target.ts`，回执的 `receiptCancelReason` 与循环闹钟共用。
- 注入块不含 `title`，只有 `scheduled_for`、`missed_occurrences`、`prompt`；标题只在面板显示。可信说明写在 `<runtime_state>` 里，核心协议的 system prompt 不改，以免升级时重建所有 Context。`loadPlugins` 拒绝 `recurring-alarm` 这个插件 id，信任判断才成立。
- 编辑不再检查目标是否可投递，只有新建检查：否则暂停的 Chat 的循环闹钟无法停用或修改。
- 物化失败（引擎无法计算旧定义、payload 超限）时整笔事务回滚，并把该闹钟的 `next_fire_at` 置空、记 `recurring_alarm_failed` 日志，避免 Scheduler 在过去的截止时间上空转。
- 物化、唤醒与立即执行只算当前就绪的宿主（组合根传入 `isHostReady`）。否则 Telegram 停用期间会物化出一条回执，等连接恢复后才投递，可能晚了好几个小时；现在恢复后按 30 分钟规则补发或跳过。
- retention 清理触发记录时，保留任务仍在等待或回执仍 `pending`/`claimed` 的那一行，`previous_pending` 依赖它。
- `GET recurring-alarms/targets` 同时返回 `default_time_zone`，面板新建时取它作默认时区。
- admin-surface 里编辑路由也带 `confirm: 'paid'`：所有 `write+paid` 的 MCP 工具都必须要求确认（`test/admin/mcp.test.ts`）。
- 产品知识索引（`src/platform/prompts/2-product-knowledge.md`）这次没有重烘焙，因为它也会改变 system prompt 哈希；新用户指南在 `guides/recurring-alarms.md`，模型可经 `list_documents` 找到。
