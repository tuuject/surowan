## Doctor 行为

实现位于 `src/doctor.ts`：

| 配置状态 | 行为 | 成功输出 |
| --- | --- | --- |
| 没有 `telegram` 段，或段内没有 `token` | 不创建 `Bot`、不调用 `getMe`；provider / vision / required MCP 等其余检查照常。required MCP 的 schema 校验使用 `unwiredImHost('telegram', 'Telegram is disabled')` 占位，避免因为缺少 Telegram 实例跳过 MCP 检查 | `telegram_status: "disabled"`、`telegram_bot_id: null` |
| `token` 的 SecretRef 可解析 | 保持现有 `getMe` 探针；MediaService、Telegram host 与 Bot 身份正常构造 | `telegram_status: "connected"`、`telegram_bot_id: "<id>"` |
| `token` 的 SecretRef 不可解析（环境变量未设、key jar 无此项、命令失败、解析为空串） | 在早期检查阶段直接失败，错误为 `Telegram token cannot be read: <redacted reason>`；不把配置异常误报成「停用」 | 无成功 JSON，退出码 1 |

实现细节：

- 新增并导出 `resolveDoctorTelegram(config, secrets)`，复用 `resolveTelegramTokenSource` 的三态；`runDoctorChecks` 在任何模型探针之前调用它，保持坏 token 尽早失败的顺序。
- `resolveAllSecrets` 不再接收 `telegramToken` 参数，只解析 Provider 与 MCP 的 SecretRef，因此不会再假设 `telegram.token` 一定存在。
- `telegram_status` 是本单元新增字段；`telegram_bot_id` 在停用时为 `null`，保持 JSON 字段存在，便于脚本统一读取。
- 新增 `test/doctor-telegram.test.ts`：无 `telegram` 段、段内无 token、可解析 token、环境变量缺失、解析为空串五种情况。网络 `getMe` 本身仍由真实 Telegram 人工验收覆盖，不在自动化测试里连接网络。

## 剩余不确定项

- Doctor 在 Telegram 停用时仍会启动 required MCP 并构造 `AgentRuntime`，用 `unwiredImHost` 完成工具 schema 校验。这保证「其余检查照常」，但本单元没有 required MCP 的真实外部服务可用，只由类型检查与现有 MCP 测试间接覆盖。
- `telegram_status` 是新增输出字段；仓库内没有其它消费者，但外部脚本若严格断言旧 JSON 字段集合，需要知道多出这个字段且 `telegram_bot_id` 在停用时为 `null`。
- 清理式 grep 的 4 行测试残留如前述，是有意的回归守卫与历史文件名；如果要求字面零命中，需要另起改动重命名 U3 测试或改写 U7 断言，本单元没有为了 grep 外观改动这些测试。
