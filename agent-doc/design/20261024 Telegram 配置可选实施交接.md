# 20261024 Telegram 配置可选实施交接

本文交给执行实现的 Agent。产品决策以 PRD [`doc/design/20261024-make-telegram-config-optional.md`](../../doc/design/20261024-make-telegram-config-optional.md) 为准；本文是未经用户审核的实施方案，和 PRD 冲突时按 PRD 做，并在交付报告里指出冲突。本文里标了「推断」的地方是 PRD 没写、由本文补上的决定，实现前先读 §6。

按 §7 的 review 单元推进：每完成一个单元就提交、写交付报告，然后停下，等 review 通过再开始下一个。

## 1. 目标

PRD 的结论，按实现顺序整理：

1. `telegram` 配置段可选。chats 可以为空，为空时不处理任何 Chat。
2. `admin` 配置段必填；`admin.enabled` 保留，改为可选，默认 `true`。没写 `admin` 的旧配置直接报错。
3. 删除 `serve --playground-only`，不做兼容。「只跑虚拟群聊」改由 Telegram 处于停用状态来体现。
4. 每个 IM 有一份连接状态，按 namespace 区分（现在只有 Telegram）。Telegram 的状态有四种：
   - **停用**：没有 `telegram` 段，或 Bot Token 为空。
   - **正常**：token 有效，实例在运行。
   - **网络异常**：连不上 Telegram 服务器。
   - **配置异常**：Telegram 返回 401 或 409，或者 token 来源取不到（环境变量没设、命令执行失败等）。
5. grammY 实例的启停跟着状态走，塑料碗服务全程不重启：
   - 面板应用配置时：正常 a → 正常 b 重启实例；正常 → 停用/配置异常 停止实例；停用/配置异常 → 正常 启动实例。
   - 运行中遇到 401/409 进入配置异常并停止实例，**服务不再退出**。
   - 网络错误在冷启动、应用配置、运行中三种场景下都无限重试：连不上时是网络异常，连上后自动回到正常。
6. 实例停止时全部作废：正在运行的 Telegram invocation 中断，排队的 invocation 作废，已批准、未送达的消息不再投递。
7. 实例停止期间到期的 Alarm 这类定时任务先挂起，实例恢复后补投。
8. 实例从停用/配置异常进入正常、以及 a → b 切换到 b 时，补拉积压消息，每个群最多收录 100 条。冷启动的补拉保持不变。
9. 警告：停用不发；网络异常、配置异常用常态警告，文案按原因区分（见 §4.8）。
10. 面板关闭且 Telegram 停用时拒绝启动，日志报错 `Surowan is useless if neither admin panel is enabled nor telegram is configured`。配置异常、网络异常不触发这条。
11. 面板是 Telegram 配置的主入口，但不提供删掉整个 `telegram` 段的功能。
12. 支线任务：服务端 CLI 新增一个「建号或重置」命令，取代 `admin-reset`（§4.11）。

## 3. 现状（实现前自己再核对一遍）

### 3.1 配置

- `src/platform/config-schema.ts`：`telegram` 段必填，`telegram.token` 是必填的 `SecretRef`，`chats` 是 `minItems: 1`；`admin` 段可选，`admin.enabled` 必填。
- `src/platform/config.ts` 的 `assembleRawConfig` 把 `FileConfig` 组装成运行时的 `RawConfig`；`agent`、`vision` 已经有「文件里可缺省、运行时补默认值」的先例（`resolveAgentSection`、`resolveVisionSection`）。
- 运行时有 30 多处直接读 `config.telegram.*`（`chats`、`bucket_window_seconds`、`sticker_trigger_enabled`、`participation`、`proactive_reply` 等），包括 Playground 也会走的共享路径，例如 `src/orchestration/agent-runtime-support.ts:210`、`src/orchestration/invocation-queue/due.ts:186`。
- `src/platform/secrets.ts` 的 `resolve` 对「环境变量没设、jar 里没有这一项、命令失败」和「解析出空字符串」都抛 `SecretResolutionError`，目前不区分。
- `src/platform/config-diff.ts`：`telegram.token` 不在热更新白名单里，改它属于 restart 字段。删除 Chat 也是 restart 字段，新增 Chat 是热更新。

### 3.2 serve 装配

- `src/adapters/local-monolith/runtime-host.ts`、`runtime-host-serve.ts`、`runtime-host-serve-run.ts` 按 `playgroundOnly` 分两条路：非 Playground-only 时在启动阶段一次性构造 `Bot`、调 `getMe()`、注册命令、`deleteWebhook`、`TelegramIngestion(me)`、`TelegramMediaClient(api, token)`、`StickerService(api)`、`McpManager`、`TelegramHost(grammyTelegramTransport(api))`，最后 `await bot.start()` 阻塞到退出。
- Host 范围是静态的：`servedHosts` 决定 `LongTaskService`、Scheduler（`src/orchestration/scheduler-loop.ts` 的 `servedConversations`）和图片生成资格（`src/image/host-eligibility.ts`）。`createCoreRuntime` 要求 tasks 和 runtime 的 host 集合完全一致。
- Bot 身份（`id`、`displayName`、`username`）在 `createCoreRuntime` 时作为常量传入，流向 `AgentRuntime`、`ProactiveReplyGate`、send 记录（`src/capabilities/send-tool-record.ts`）和参与判定（`src/platform/participation.ts`）。Playground-only 时 `id` 是 `0n`。

### 3.3 Telegram 错误处理

- 冷启动时 `getMe()` 失败（401 或网络问题）会让 serve 直接起不来。
- 运行中 grammY 1.46.0 的长轮询（`node_modules/grammy/out/bot.js` 的 `handlePollingError`）：401、409 直接抛出；429 按 `retry_after` 等待；其它错误每 3 秒重试，没有上限。抛出的错误冒到 `runServeLoop` 的 `await runningBot.start(...)`，serve 走关停流程，以退出码 1 退出。Docker 部署配了 `restart: unless-stopped`，会反复重启。
- 发送失败的分类在 `src/adapters/local-monolith/telegram-host.ts` 的 `classifyTelegramDeliveryError`。

### 3.4 补拉、作废与长期任务

- `src/startup-catch-up.ts` 在 Scheduler 启动**之前**分页（每页 100 条）把积压的 update 全部拉完，然后 `scheduler.finishStartupCatchUp` 把这段时间的 Bucket 排成 invocation。首次初始化（`app_state.telegram_initialized` 不存在）时用 `deleteWebhook({ drop_pending_updates: true })` 丢掉积压。
- 作废的先例：
  - `src/ingress/admin/operations.ts` 的 `cancelOngoingSessions`（面板「Cancel ongoing」）：把 `collecting`/`queued` Bucket 和「已 attach 未注入」的 Bucket 置为 `expired`；把被排队 invocation claim 了的 receipt 置为 `suppressed`；把排队的 invocation 置为 `aborted`。它不区分 Host。
  - `src/orchestration/invocation-queue/outcomes.ts` 的 `skipQueuedInvocations`（睡眠）只处理 Telegram。
  - Scheduler 有 `abortInvocations(ids, reason)`、`pauseChat`、`abortAll`。
- 长期任务的 receipt 状态有 `pending`、`claimed`、`handled`、`suppressed`。到期的任务由 Scheduler 的 `processTasksDue` 处理，receipt 被 claim 进一个排队的 invocation。

### 3.5 面板、警告与 CLI

- 面板目前没有编辑 Telegram token 的页面或端点。写 secret 的先例是 Provider 的 `api_key`（`src/ingress/admin/providers-admin-write.ts`，`secretEdit` 写 key jar），以及 `PUT /image/config`。
- 常态警告由 `src/platform/warning-catalog.ts` 的 `standingWarnings(config)` 在每次读取时从配置推导，唯一调用方是 `src/ingress/admin/warnings-admin.ts`。前端模板在 `apps/admin-next/src/components/warnings/warning-card.tsx` 和 `apps/admin-next/src/locales/{en,zh-CN}/pages/warnings.ts`。
- `admin-reset`（`src/ingress/admin/recover.ts`、`AdminAuth.recoverCredentials`）：只能给**已有**用户名重置密码，不能建号、不能改用户名，每次都删光 passkey、注销全部会话；服务运行时因为拿不到 `ServeLock` 拒绝执行。面板首次建号走 `POST /auth/setup`，只在 `admin_users` 为空时可用。

## 4. 目标设计

### 4.1 配置层

- `ConfigSchema.telegram` 改为 `Type.Optional`。段内字段的必填性保持不变，只有两处改动：`chats` 去掉 `minItems`；`token` 改为可选（缺省就是「token 为空」，面板清空 token 时删掉这个字段）。
- `admin` 改为必填；`AdminSchema.enabled` 改为可选，运行时默认 `true`。`src/adapters/local-monolith/runtime-host-serve-run.ts:234` 现在的判断是 `=== true`，要改成「缺省视为 true」。
- 运行时 `RawConfig.telegram` 保持**总是存在**：文件里没有这一段时，`assembleRawConfig` 补一个空段（`chats: []`，`token` 缺省，其余必填标量用固定默认值）。这样 30 多处读 `config.telegram.*` 的地方，大部分不用改成判空。默认值集中定义在一处，不要每个调用点各写一份。要补哪些默认值，以 `process_bot_messages`、`bucket_window_seconds` 为准，在交付报告里列出来。
- 只读 `FileConfig` 的地方（`config-diff.ts`、面板配置写入、`config-inspection.ts`）必须正确处理 `telegram` 缺失。
- `config-diff.ts`：`telegram.token` 改成热更新，由 §4.3 的连接管理器接管；从无到有加上 `telegram` 段时，段内字段各自按现有规则分类。删除 Chat 仍是 restart 字段，不在本任务里改。
- useless 规则在 `serve` 启动时检查：解析出 Telegram 处于**停用**、且面板关闭时，抛出 `Surowan is useless if neither admin panel is enabled nor telegram is configured`，进程以非零退出码结束。只认停用；token 取不到属于配置异常，不触发这条。`check-config` 只做 schema 和语义校验，不解析 secret，所以不判断这条（推断）。

### 4.2 连接状态模型

- 新增一个进程内的连接状态登记处，按 namespace 存每个 IM 的状态，例如键 `telegram`，以后加 `discord`、`whatsapp`、`slack`。值包含：
  - `status`：`disabled` | `connected` | `network_error` | `config_error`；
  - `reason`：只在 `config_error` 时有，取值 `unauthorized`（401）、`conflict`（409）、`token_unreadable`（token 取不到）；
  - `since`：进入当前状态的时间；
  - 可选的 `bot`：最近一次 `getMe` 的 id 和 username，供面板展示。
- 状态只在内存里，进程重启后重新推导，不建表（推断：PRD 没要求持久化，常态警告本身也只反映当前状态）。
- 键名和取值都是面向以后多 IM 的通用词汇，不要写成 Telegram 专用的类型。

### 4.3 Telegram 连接管理器

新增一个模块（建议放在 `src/adapters/local-monolith/`，例如 `telegram-connection.ts`），持有 grammY 实例的整个生命周期。serve 只构造它一次，之后所有启停都经过它。

**输入**：当前 token 的解析结果，三选一：空（停用）、取不到（配置异常 / `token_unreadable`）、明文 token。

**启动流程**：

1. 新建 `Bot`，循环调 `getMe()`：
   - 成功：记下身份，继续下一步；
   - 401：进入配置异常（`unauthorized`），流程结束；
   - 网络错误、5xx、429：进入网络异常，等一段时间后重试，不设上限。退避策略自定，上限不超过 60 秒（推断）。
2. 注册命令、`deleteWebhook`。运行时启动一律**不**丢弃积压（见 §4.7）。
3. 用新身份构造或重建 `TelegramIngestion`，更新 §4.4 的身份与 transport 间接层。
4. 执行限量补拉（§4.7）。
5. 进入正常，后台启动长轮询。

**运行中**：

- 不再 `await bot.start()` 阻塞 serve。serve 改为总是等待 `idle`（现在 Playground-only 用的那个 promise），长轮询放在管理器内部的后台任务里。
- `bot.start()` 因 401/409 reject 时，捕获后进入配置异常（`unauthorized`/`conflict`），走 §4.5 的停止流程，**不要**让错误冒到 serve。
- 网络异常的感知：grammY 内部吞掉了长轮询的网络错误，只打 debug 日志。用 `bot.api.config.use(transformer)` 观察 `getUpdates` 的结果：失败（非 401/409）就标记网络异常，下一次成功就回到正常。不要自己重写长轮询循环。
- 网络异常期间实例保持运行，Scheduler 照常放行（§4.5），发送失败按现有分类处理。

**应用配置时的迁移**（由 `ConfigReloader` 在发布配置时通知管理器，参考现有 `imageConfig` 的 prepare/publish 钩子）：

| 当前 | 新 token | 动作 |
| --- | --- | --- |
| 实例运行中（正常或网络异常） | 与当前相同 | 不动 |
| 实例运行中 | 另一个明文 token | 走 §4.5 停止流程，再按新 token 走启动流程 |
| 实例运行中 | 空 | 停止，进入停用 |
| 实例运行中 | 取不到 | 停止，进入配置异常（`token_unreadable`） |
| 停用或配置异常 | 明文 token | 走启动流程 |
| 停用或配置异常 | 空 / 取不到 | 只更新状态 |

- 启动流程里的 `getMe` 可能长期重试，所以应用配置的 HTTP 请求**不要**等它完成：配置发布成功即返回，面板再去读连接状态。
- 同一时刻只允许一个迁移在执行。迁移进行中又收到新 token 时，取消当前迁移（abort 正在进行的 `getMe` 重试和补拉），再按最新的 token 开始。
- token 是否相同按解析后的明文比较，不按 SecretRef 比较。日志和错误里一律不出现明文，经 `SecretStore.redact`。

**冷启动**：serve 先按配置解析 token，再交给管理器走同一套流程。冷启动时连不上 Telegram 不再阻止服务启动。冷启动的补拉保持现有行为（不限量，首次初始化时丢弃积压），在 Scheduler 启动之前完成；如果冷启动时 `getMe` 一直在重试，Scheduler 不等它，补拉推迟到连上之后，按「运行时启动」处理（推断，见 §6）。

### 4.4 运行时解耦：身份与 transport

现在这些对象都在启动时绑死一个 `Bot`。改成通过间接层读取「当前实例」：

- **Bot 身份**：`createCoreRuntime({ bot })` 改为传一个 getter 或持有者对象，`AgentRuntime`、`ProactiveReplyGate`、send 记录、参与判定每次用的时候读当前值。没有实例时（停用、配置异常、冷启动还没连上）身份为空，凡是需要身份的 Telegram 路径都不应该被调用到（Scheduler 不放行，见 §4.5）。Playground 的显示名逻辑保持不变：有 Telegram 身份时沿用它，没有时用 `PLAYGROUND_BOT_DISPLAY_NAME`。身份变化后，已经打开的房间显示名怎么变，按现有逻辑走，不额外处理。
- **TelegramHost**：`createTelegramHost` 只构造一次，它的 `transport` 改为转发到当前实例的 `api`。没有实例时调用直接返回 `permanent` 类失败（例如 code `telegram_unavailable`），不要抛未分类的异常。
- **媒体下载**：`TelegramMediaClient` 同样转发到当前实例；没有实例时拒绝下载，错误信息参考现在 Playground-only 的 `'this process has no Telegram media transport'`。
- **Sticker**：`StickerService` 依赖 Bot API 同步贴纸集。跟随实例启停：实例启动后 `sync()` 并 `start()`，停止时 `stop()`。搜索能力在没有实例时的行为保持和现在 Playground-only 一致（不提供）。
- **MCP**：以后总是构造 `McpManager`（和现在的非 Playground-only 模式一样），不再按 Telegram 状态开关。
- **Host 范围**：`servedHosts` 固定为 `['telegram', 'playground']`。「现在能不能执行 Telegram 工作」改由连接管理器提供的动态判定回答（§4.5、§4.6），不要再靠缩小 host 集合来表达。

### 4.5 调度、停止与作废

**Scheduler 放行条件**：Telegram 会话的 invocation 只在实例**已就绪**时启动。已就绪指已经拿到身份，状态是正常或网络异常。停用、配置异常、冷启动还没连上时，Telegram 的排队工作留在原处，不启动、不判失败。Playground 不受影响。实现上给 `servedConversations` 一类的过滤加一个动态谓词，不要改成每次重建 Scheduler。

**停止流程**（a → b 重启、进入停用、进入配置异常都走这一套，顺序固定）：

1. 标记实例「停止中」，Scheduler 从这一刻起不再启动新的 Telegram invocation。
2. 停止长轮询（`bot.stop()`，吞掉它附带的 offset 确认请求的 rejection，参考 `runtime-host.ts` 现有写法），停掉 Telegram host 的全部 activity（输入中状态）。
3. 在一个事务里作废 Telegram 会话的待处理工作。写法参考 `cancelOngoingSessions`，但只限 `host_kind = 'telegram'`：
   - `collecting`、`queued` 的 Bucket，以及「已 attach 到运行中 invocation、还没注入」的 Bucket，置为 `expired`；
   - 排队的 invocation 置为 `aborted`；
   - 新的原因码统一用 `telegram_stopped`（推断）。
4. 中断正在运行的 Telegram invocation：`scheduler.abortInvocations(ids, 'telegram_stopped')`。中断信号会传到发送路径，`deliver` 在每一段之前检查 `signal`，未送达的部分不再投递。
5. 等这些 invocation 落到终态。可以设一个宽限时间，超时只记日志，不阻塞后面的步骤。
6. 停用 Sticker，清空身份与 transport 间接层，更新连接状态。

**长期任务的 receipt**（推断，对应 PRD 第 7 条）：第 3 步作废排队 invocation 时，**不要**像 `cancelOngoingSessions` 那样把它 claim 的 receipt 置为 `suppressed`，而是退回 `pending`（清掉 `invocation_id`、`claimed_at`），等实例恢复后重新投递。第 4 步中断的运行中 invocation，如果带着 claim 了的 receipt，同样要保证 receipt 最终回到 `pending`，而不是被当成已处理。实现前先读 `src/orchestration/invocation-queue/receipts.ts`，确认中断后 receipt 现在落到什么状态；如果改动要碰 receipt 的状态机，在交付报告里写清楚。

### 4.6 定时任务挂起

- 实例未就绪时，Telegram 会话的长期任务**照常到点完成计时**，但 receipt 不 claim、不排 invocation，留在 `pending`。实例就绪后，Scheduler 的下一轮自然会投递。
- 图片生成里属于 Telegram 会话的工作同样挂起：`generationEligibilityForHosts` 改为动态判定，未就绪时不执行，留在队列里（推断：PRD 只点名了 Alarm「这类」定时任务，图片生成的回执属于同一类）。
- 恢复后可能一次补投很多过时的提醒。PRD 已经接受这个代价，不做合并或过期处理。

### 4.7 运行时补拉

- 触发：停用/配置异常 → 正常，以及 a → b 切换到 b。冷启动不走这里。
- Telegram 的 `getUpdates` 是整个 bot 共用的一条流，不能按群拉取。做法：按 `offset` 把积压全部取完（每页 100 条，和现在一样），先缓存在内存里，按 Chat 分组后每个 Chat 只保留**最新的** 100 条 message，再按原 update 顺序交给 `ingestCatchUp`（推断：PRD 的目的是「知道群里最近一小段时间讨论了什么」，所以留最新的）。
- 限量只针对 message。编辑、命令等其它 update 的处理方式自定，在报告里说明。`/pause`、`/resume` 命令要按原顺序执行，和冷启动补拉一致。
- 运行时补拉和 Scheduler 并发执行。`finishStartupCatchUp` 现在假设自己在 Scheduler 启动前跑；先读 `src/orchestration/invocation-queue/recovery.ts`，确认能否复用。不能复用就新写一个只处理本次补拉 Bucket 的收尾函数，不要改冷启动的语义。
- 补拉可以被中断：迁移被新 token 取消、或进程关停时，abort 掉正在进行的补拉。

### 4.8 警告

- 在 `WARNING_DEFINITIONS` 加常态警告，category 用 `runtime`（推断）：
  - `telegram_network_error`：网络异常。
  - `telegram_config_error`：配置异常，`variables` 里带 `reason`。
- `standingWarnings` 现在只吃配置。改成同时接收连接状态登记处的快照（例如 `standingWarnings(config, connections, now)`），`warnings-admin.ts` 传进去。停用不产生任何警告。
- 前端模板与文案（`warning-card.tsx` 与两个 locale）：

| 情况 | 中文 |
| --- | --- |
| 网络异常 | 未能成功连接 Telegram 服务器 |
| 配置异常 / `unauthorized` | 你的 Telegram Token 已被吊销或无效 |
| 配置异常 / `conflict` | 这个 Telegram Token 正在被其他程序使用 |
| 配置异常 / `token_unreadable` | 无法读取 Telegram Token |

  后三句在 PRD 里标了暂定，原样实现即可。英文文案自拟，保持同样的区分。

### 4.9 面板

后端：

- `GET /telegram`：返回连接状态（§4.2 的结构）、token 是否已配置（只给布尔值，不回显 secret）、是否存在 `telegram` 段，以及配置 revision。
- `PUT /telegram`：body 至少包含 `token`：
  - 字符串：写 key jar，配置里只留 `{ jar }` 引用；
  - `null`：删掉 `telegram.token` 字段，回收不再被引用的 jar 条目；
  - 段不存在时，用 §4.1 的默认值建段，`chats` 为空数组。
  - 写入沿用现有的 If-Match revision、原子写入和 reloader 机制，参考 `PUT /image/config` 和 Provider 的写端点；明文注册进 `SecretStore` 用于脱敏。
  - 只改 token，不碰 Chats，也不提供删掉整段的写法（PRD 第 11 条）。其它 `telegram.*` 字段要不要在这个端点里一起编辑，按现有页面覆盖情况决定，在报告里说明。
- 两个端点都要加进 `agent-doc/admin-panel.md` 的端点表，写端点进白名单，校验 `Origin`。
- 已有的 Chats 端点要能在 `telegram` 段不存在时工作。在一个 token 都没有的配置上新增 Chat，是否顺带建段，按 §4.1 的默认值处理（推断）。

前端（`apps/admin-next`）：

- 新增一个 Telegram 设置入口（独立页面，或放进现有设置区域，按现有信息架构选）：显示连接状态、bot 用户名、token 输入与清空。不要做删除整个 Telegram 配置的按钮。
- 看板或侧边栏能看到 Telegram 当前状态；警告已经覆盖异常状态，这里不必重复做提醒。
- 文案进两个 locale；e2e 至少覆盖新页面渲染、保存 token、清空 token 三个场景。

## 6. 推断清单（PRD 没写，本文补的）

review 时重点看这些，有异议就停下来问，不要自行改方向：

1. 连接状态只在内存里，不持久化（§4.2）。
2. 冷启动连不上 Telegram 时，Scheduler 不等它；补拉推迟到连上之后，按运行时启动处理（§4.3）。
3. 运行时启动一律不丢弃积压；首次初始化时丢弃积压只保留在冷启动路径（§4.3、§4.7）。
4. 原因码统一用 `telegram_stopped`；作废时连 `collecting` 的 Bucket 一起作废（§4.5）。PRD 只说了「排队的 invocation」，但不作废 `collecting` Bucket 的话，它们会在实例恢复后变成新的 invocation，和「全部作废」的意图相反。
5. 作废排队 invocation 时，它 claim 的 receipt 退回 `pending`，而不是 `suppressed`（§4.5）。
6. 图片生成按定时任务同样挂起（§4.6）。
7. 补拉每个 Chat 留**最新的** 100 条 message（§4.7）。
8. 警告 category 用 `runtime`；`check-config` 不判断 useless 规则（§4.1、§4.8）。
9. 新命令名 `admin-account`；多于一个管理员时报错（§4.11）。
10. `getMe` 退避上限 60 秒（§4.3）。

## 8. 测试要求

- 遵守 `AGENTS.md` 的 Testing Guidelines：断言落盘状态和审计事件，不只断言返回值；时间基准统一。
- Telegram 一律用现有 Faux / fixture，不连真实网络。401、409、网络错误分别用 `GrammyError`（`error_code` 401/409）和 `HttpError` 模拟。
- 状态迁移测试要能断言：迁移后 grammY 实例数（不能泄漏旧实例的长轮询）、连接状态值、常态警告的有无。
- 真实 Telegram 验收（换 token、吊销 token、同一个 token 开两个进程制造 409、断网后恢复）写进 PR 说明的「未执行的检查」，交给人工。

## 9. 必须停下来报告的情况

- 现状和 §3 描述不一致，而且影响方案。
- 需要新建表或迁移（本文的方案不需要）。
- §6 的任何一条推断在实现中站不住。
- 中断运行中 invocation 后 receipt 的去向无法保证回到 `pending`。
- 文件超过 5,000 token 的限制，又不能按职责拆开。
- 任何测试或 e2e 失败，而且原因不在本单元的改动范围内。
