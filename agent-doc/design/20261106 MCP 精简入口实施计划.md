# MCP 精简入口实施计划

没有对应 PRD。本文是 AI 直出的实施契约，来源是 2026-11-06 与用户的讨论；用户在讨论中确认的三点见[已确认](#已确认)，其余内容未经逐条审核。判断现状仍以源码为准。

## 背景

- `/mcp` 把 `ADMIN_SURFACE_SPECS` 中所有 `specIsMcpExposed` 的路由一一暴露为工具，目前 133 个（`read` 66 个，其余 67 个）。`tools/list` 序列化（`JSON.stringify({ tools })`）约 83 KB，按 3.6 字节/token 估算约 2.3 万 token。
- 不支持 tool search 或工具聚合的 harness 每轮都要携带完整目录。部分模型 API 对单次请求的工具数量有上限（已知 OpenAI 为 128，本仓库未验证），把 MCP 工具原样透传的 harness 会直接报错。
- 逐路由拆分的 schema 信息量很低：`body` 一律是 `additionalProperties: true`，字段由 Admin API 自己校验。拆成 133 个工具，多出来的只有路径参数、query 参数名和 `if_match`/`confirm`/`dry_run`。

## 决定

1. **两个入口**
   - `/mcp`：精简目录，只有 4 个 dispatcher 工具。
   - `/mcp/full`：4 个 dispatcher 加上全部逐路由专用工具，是精简目录的超集。
   - 其余 `/mcp/*` 子路径返回 404。
   - 默认入口给精简版，因为两边出错的代价不对称：完整版接进不支持 tool search 的 harness，轻则浪费上下文，重则超出工具数上限报错；精简版接进支持 tool search 的 harness，只是多一次往返。`/mcp` 由 `37e537f2`（2026-11-05）引入，尚未进入任何 tag，调换默认目录没有存量用户。
2. **完整版是超集**：Skill 只教 dispatcher 一种调用方式，不需要判断当前连的是哪个入口；在聚合或延迟加载的 harness 里，靠工具列表判断入口并不可靠。
3. **命名避开现有命令**：`search show` / `search update`（网络搜索配置）已生成 `surowan_search_show` / `surowan_search_update`，所以 dispatcher 不叫 `surowan_search`。
4. **两个入口共用同一条执行路径**：认证、权限、`confirm`、`if_match`、`nullClearedBy`、`dry_run` 和响应转换都留在现有的 `callTool`/`toResult`，dispatcher 只负责定位 spec 和校验参数。

## 工具契约

| 工具 | 输入 | annotations | 行为 |
| --- | --- | --- | --- |
| `surowan_find_command` | `{ query?: string }` | readOnly、idempotent、非 openWorld | 省略或空白 `query`：按 spec 顺序返回全部 MCP 可见命令的 `{ command, access }`。有 `query`：按评分返回前 10 条 `{ command, summary, access, confirm, revision, dispatcher }`。没有命中时返回空数组，并提示不带 `query` 再调用一次 |
| `surowan_describe_command` | `{ command: string }` | readOnly、idempotent、非 openWorld | 返回 `{ command, summary, method, path, access, confirm, revision, dispatcher, input_schema }`，`input_schema` 就是现有 `inputSchema(spec)` 的输出。未知命令返回 `isError`，附最多 3 个候选 |
| `surowan_run_read` | `{ command: string, args?: object }` | `readOnlyHint: true`、`destructiveHint: false`、`idempotentHint: false`（`replay-preflight` 等读型 POST）、`openWorldHint: false` | 只接受 `specAccess(spec) === 'read'` 的命令；其它命令返回 `isError`，提示改用 `surowan_run_write` |
| `surowan_run_write` | `{ command: string, args?: object }` | `readOnlyHint: false`、`destructiveHint: true`、`idempotentHint: false`、`openWorldHint: true` | 只接受非 `read` 命令；`read` 命令返回 `isError`，提示改用 `surowan_run_read`。拒收读命令，是为了让 harness 按 annotations 做的自动放行和审批保持准确 |

- `dispatcher` 字段取值为 `surowan_run_read` 或 `surowan_run_write`，让 agent 不必自己推断。
- `args` 的形状与完整版专用工具的参数完全相同：路径参数、query 参数、`body`、`if_match`、`confirm`、`dry_run`。
- **评分**沿用 `src/capabilities/execute-tool.ts` 中 `searchCapabilities` 的规则：整句命中 +10；词元命中命令名 +3，命中 summary +1，命中 path +1。只在 MCP 层实现，不跨层 import `capabilities/`。
- **description**：`surowan_run_read` / `surowan_run_write` 的 description 带上领域关键词表，取所有 MCP 可见命令的首个词并去重（invocation、prompt、chat、provider、model、memo、dictionary、image、room……），让 harness 自带的工具搜索也能命中。同时写明「Surowan admin commands are not separate MCP tools; find them with surowan_find_command」。关键词表由 spec 生成，不手写。

### 参数校验

新增 `validateArgs(spec, args)`，按 `inputSchema(spec)` 生成的形状校验：

- 必填字段是否存在；未知字段一律拒绝。
- 类型：路径参数和 query 参数接受 string，也接受有限 number（与现有 `stringArg` 一致）；`confirm`/`dry_run` 必须是 boolean；`body` 必须是 object；enum 取值必须合法。
- 失败时返回 `isError`，错误文本附上该命令的 `input_schema`，agent 一轮就能修正。

校验放在 `callTool` 之前的共用路径里，dispatcher 和完整版专用工具都会执行，两个入口的行为保持一致。这是完整版专用工具唯一的行为变化：未知字段从静默忽略变成报错（用户已确认，见[已确认](#已确认)第 3 条）。

### 安全不变量

- dispatcher 只在 `ADMIN_SURFACE_SPECS.filter(specIsMcpExposed)` 里查找命令，不用 `findSurfaceSpec` 或 `PANEL_SPECS`。账号、Passkey、`auth/*` 与 `api-keys*` 路由经 find/describe/run 都不可见、不可达。
- 权限检查、确认闸门、`nullClearedBy` 和 revision 解析保持在 `callTool` 内，原样执行；dispatcher 不新增也不绕过任何闸门。
- `nullClearedBy` 的报错文本改成与入口无关的写法：直接写出命令名，例如 `Run the command "telegram token clear" with confirm: true after the user approves the deletion.`，不再引用 `toolName(clearCommand)`。
- 构建目录时断言 4 个 dispatcher 名与 `toolName(spec.command)` 生成的名字没有冲突；一旦冲突，模块加载即抛错。

## 路由与目录

- `src/ingress/admin/index.ts`：`segments[0] === 'mcp'` 时把 `segments.slice(1)` 交给 `McpEndpoint.handle`。
- `McpEndpoint` 按子路径选目录：`[]` 选精简目录，`['full']` 选完整目录，其它返回 404。modern 和 legacy 两个分支都使用所选目录。
- `instructions()` 按入口分两版：
  - 精简版说明 Surowan 命令不是独立工具，要经 `surowan_find_command` → `surowan_describe_command` → `surowan_run_read`/`surowan_run_write` 调用；第一步执行 `surowan_run_read` `{"command":"key show"}`。
  - 完整版额外说明：专用工具与 dispatcher 等价，两者都能用。
- Skill manifest（`skills.ts`）两个入口共用，内容相同。
- `callAdmin` 回环仍走 `this.handle(request, 'mcp')`，不变。

## 代码布局

`scripts/file-token-limit.ts` 的 pre-commit 限制是每个文件 20,000 字节（5,000 token）。当前 `tools.ts` 约 12.8 KB，`index.ts` 约 14.7 KB。

- `src/ingress/admin/mcp/tools.ts`：保留逐路由目录、`callTool`、`toResult`/`binaryResult`；导出 `inputSchema`、`callTool`、`toolName` 和 MCP 可见 spec 列表。`TOOL_CATALOG` 改为按入口构建的两份目录（例如 `TOOL_CATALOGS.compact` / `TOOL_CATALOGS.full`）。
- 新增 `src/ingress/admin/mcp/commands.ts`：评分、`find`/`describe`、`validateArgs` 和 4 个 dispatcher 定义。
- 如果 `tools.ts` 超限，把 `toResult`/`binaryResult` 拆到 `mcp/results.ts`。`mcp/` 目录已存在，不新增同前缀的平铺文件。

## Skill

两个入口共用一份 `skills/surowan-mcp/`。核心改法：**Skill 只写命令名，不写工具名**。命令名同时是 CLI、完整版工具名（`surowan_` + 命令名，空格和连字符换成下划线）和 dispatcher `command` 参数的共同词汇。

- **SKILL.md**
  1. 新增「调用方式」，全文只有这一节涉及 MCP 形态：
     - dispatcher 流程，附 JSON 示例，例如 `{"command":"key show"}`、`{"command":"invocation list","args":{"chat":"…"}}`。
     - 明确写出：Surowan 命令不是独立的 MCP tool，harness 自带的工具搜索搜不到，要用 `surowan_find_command`。
     - harness 可能给工具名加前缀（例如 `mcp__<server>__surowan_run_read`）。
     - 如果看得到 `surowan_<command>` 专用工具，也可以直接调用，参数与 `args` 相同。
  2. 「每次任务先读权限」改为调用 `surowan_run_read` 执行 `{"command":"key show"}`。
  3. 删除「读操作」「写操作」下的工具名清单（与 tools.md 重复），换成 4–5 个常用流程：未回复排查（`invocation list` → `invocation show`）、改 Prompt（`prompt global view` → 取 `content_hash` → `prompt save`）、重放（`invocation replay-preflight` → 用户确认 → `invocation replay`）、改配置（读 → 说明 → 确认 → 写 → 读回）。示例中的命令一律写成 `"command":"…"` 形式，供一致性测试抽取。
  4. 写操作、计费、参数约定、错误、信任边界这几节保留，工具名一律换成命令名。
- **references/tools.md** 改为命令索引：第一列 `命令`（反引号包裹的 command 字符串），后面是权限、用途；保留现有注意事项（`tool_call_id`/`asset_id` 为字符串、二进制 16 MiB 上限等）。
- **frontmatter `description`** 与 **`agents/openai.yaml` 的 `default_prompt`** 去掉 `surowan_*` / `surowan_key_show`，改成与入口无关的说法。

## Admin Panel

API key 页（`/api-keys`）新增一张「MCP endpoints」卡片，列出两个 URL 并说明区别。

- **位置**：放在 key 列表卡片之前；`apps/admin-next/src/pages/api-keys.tsx` 已有约 18.1 KB，接近 20,000 字节上限，所以卡片写成新组件 `apps/admin-next/src/components/api-keys/mcp-endpoints.tsx`，页面里只引用它。
- **URL 来源**：`${window.location.origin}/mcp` 与 `${window.location.origin}/mcp/full`。面板与 `/mcp` 由同一个 AdminServer 在同一端口提供，`admin.public_url` 也只允许纯 origin（不带路径），所以不需要新的后端字段或端点。
- **每行内容**：URL（等宽字体，可复制，复用 `KeyReveal` 的复制状态模式，复制失败时提示手动选择）、名称徽标、一两句说明。
- **文案要点**（英文为源，`zh-CN` 逐键对应）：
  - 公共说明：两个入口使用同一把 API key（`Authorization: Bearer`），权限与可做的事完全相同；区别只是把多少工具定义交给 Agent。
  - `/mcp`（标 Recommended）：只有 4 个通用工具，Agent 先查找命令再执行；适用于任何 MCP 客户端，包括不支持工具搜索的。
  - `/mcp/full`：在这 4 个之外，为每个面板命令再提供一个专用工具。只建议用在支持工具搜索或按需加载工具定义的 harness；会把全部工具每轮都发给模型的客户端会白白占用大量上下文，部分模型 API 还会因工具数量超限直接拒绝请求。
  - 文案不写具体工具数，避免随 spec 增加而过时。
- **locale**：`apps/admin-next/src/locales/en/pages/api-keys.ts` 与 `zh-CN/pages/api-keys.ts` 新增 `mcpEndpoints` 键组；页面顶部 `description` 不改。
- React 代码遵循仓库的 no-use-effect 约定：URL 直接由 `window.location.origin` 派生，不用 effect 同步。

## 测试

写在 `test/admin/mcp.test.ts`（当前约 15.3 KB）。超过 20,000 字节时把新增用例放进 `test/admin/mcp-dispatch.test.ts`。Provider 与 Telegram 一律使用现有替身。

1. **目录**：`/mcp` 的 `tools/list` 恰好返回 4 个 dispatcher；`/mcp/full` 返回 dispatcher 加全部 MCP 可见 spec 对应的工具；`/mcp/other` 返回 404。modern 和 legacy 各跑一遍。
2. **预算**：`/mcp` 的 `tools/list` 序列化后不超过 8 KiB。
3. **一致性**：遍历每条 MCP 可见 spec，在 `/mcp/full` 上分别用 dispatcher 和专用工具以 `dry_run: true` 调用，返回文本完全相同。这样不产生副作用就能覆盖全部路由的分发。
4. **权限**：只读 key 经 `surowan_run_write` 调用写命令，错误文本与专用工具相同；`surowan_run_read` 拒收非 read 命令，`surowan_run_write` 拒收 read 命令。
5. **闸门**：经 dispatcher 调用计费命令时，没有 `confirm` 就不发出 Admin 请求（沿用现有 replay 用例的 `seen` 断言）；`nullClearedBy` 经 dispatcher 同样拒绝，报错里带命令名 `telegram token clear`。
6. **排除**：`setup` 等 `auth/*`、`api-keys*` 命令在 find 结果里不出现，describe 和 run 都返回未知命令。
7. **纠错**：未知命令返回候选；缺少必填字段、出现未知字段或类型错误时返回 `isError`，并附 `input_schema`。
8. **查找**：`query: "replay"` 时排名靠前的是 `invocation replay` 与 `invocation replay-preflight`；不带 `query` 时返回全部 MCP 可见命令。
9. **annotations**：4 个 dispatcher 的 annotations 与上表一致。
10. **二进制**：经 `surowan_run_read` 调用 `invocation media-content`，返回的字节与 16 MiB 上限行为和专用工具一致。
11. **Skill 一致性**：tools.md 第一列的每个命令都存在且对 MCP 可见；每个 MCP 可见命令都出现在 tools.md；Skill 各文件中所有 `"command":"…"` 都是合法命令；所有 `surowan_[a-z_]+` 标识符要么是 dispatcher 名，要么是完整版里的工具名。
12. 更新现有断言：第 69–74 行改为针对 `/mcp/full`；第 93 行 Skill 正文断言从 `surowan_key_show` 改成 `key show`；第 313 行 `nullClearedBy` 文本改成命令名。
13. **面板 e2e**：在 `apps/admin-next/e2e/14-api-keys-ui.e2e.ts`（英文 locale）断言 API key 页显示两个 URL，值分别等于 `<baseURL>/mcp` 和 `<baseURL>/mcp/full`，各带复制按钮，`/mcp` 标为 Recommended。复制成功与失败的状态只需覆盖一个入口，沿用现有 key 复制用例的做法。

## 交付顺序

一个 PR，按以下顺序推进：

1. 服务端：目录拆分、dispatcher、参数校验、路由、`instructions()`，以及测试 1–10、12。
2. Skill 重写与测试 11。
3. Admin Panel 卡片、locale 与测试 13。
4. 文档。

## 已确认

用户于 2026-11-06 确认：

1. 路径为 `/mcp`（精简，默认）+ `/mcp/full`（完整，超集）；不使用 `/mcp/simple`。
