# IM 表情 GIF 的时长、帧数与 LLM 抽帧建议

核查日期：2026-09-27。性质：研究结果与待验证的工程建议，不是已实施的 GIF 功能。

## 结论

**优先为“几秒、十几到几十帧”的内容设计，但为十几秒、数百帧的长尾设置独立预算。不要把一个中间帧当成动态表情的完整含义。**

本次从三个公开表情仓库各抽取 150 份 `.gif` 资产，共 450 份；排除 5 份实际为 JPEG、44 份单帧 GIF，以及 20 份合成后所有画面完全一致的多帧 GIF，得到 381 个有画面变化的样本记录。以下统计分别描述各仓库，不把它们拼成“全网平均”。

- 两套中文表情包仓库的单轮时长中位数约 **1.5 秒**，原始编码帧数中位数 **13 / 16 帧**。
- 英文 reaction GIF 收藏的单轮时长中位数 **2.82 秒**，原始编码帧数中位数 **38 帧**。
- 三套样本的时长 P95 分别为 **10.10 / 8.36 / 11.67 秒**；帧数 P95 分别为 **61.45 / 130.4 / 148.55 帧**。
- 最大观测值达到 **36.6 秒**与 **506 帧**，但两者不一定来自同一个文件。样本最大值不是格式上限。
- 可把“按完整单轮时间轴抽取，首轮最多 12 张，必要时补到总计 24 张”作为实验起点；**本研究没有做 LLM 理解准确率实验，不能证明 12 张足够。**

时长按下述明确的 delay 归一化策略计算。这里的“中文/英文”指仓库定位与分类语言，不是用户地域或发送流量的推断。

### 编码帧不等于内容复杂度

原始帧数指 GIF image descriptor 数量。每帧可能只更新一个局部矩形，必须按透明度和 disposal 规则合成为完整画面，再判断视觉变化。

对合成后的全分辨率 RGBA 做逐帧 MD5 校验得到：

| 动态内容子集 | 编码帧数中位数 | 全局不同 RGBA 画面中位数 |
| --- | ---: | ---: |
| ChineseBQB | 13 | 11 |
| EmojiPackage | 16 | 15 |
| animated-gifs | 38 | 37.5 |

“全局不同画面”只是像素指标，不是语义状态数，也不能据此任意打乱或全局去重。例如 A→B→A 的最后一次 A 仍有时序意义。若仅合并**连续相同**画面并累加其停留时间，三个子集的状态段数中位数仍为 13、16、38；状态段数 ≤12 的比例分别为 48/98、60/133、5/150。

这说明不少简单中文表情可直接保留全部状态；真人影视 reaction 往往仍需抽样。数字不能证明抽样后的语义完备性。

## 时长到底在量什么

依据 [GIF89a 规范](https://giflib.sourceforge.net/gif89.txt)，每个 Graphic Control Extension 的 delay 单位是 **1/100 秒**。GIF 可以变帧间隔，不宜用“帧数 ÷ 固定 10 FPS”反推时长。

本研究保留两种口径：

1. **原始字段和：**保留每帧 `delaysCs`，缺失为 `null`；`rawDurationSeconds` 只累加已指定值，缺失项按 0 参与求和。这个数不保证是播放器的实际播放时长。
2. **主表分析口径：**缺失、0、1 cs 都替换为 10 cs（100 ms），其余 delay 保持不变；累加得到单轮 `durationSeconds`。这是明确声明的播放策略假设，不是 GIF 格式规定，更不保证与所有浏览器或 Telegram 一致。

归一化影响不能忽略：三个动态子集的原始字段和中位数为 **1.485 / 1.100 / 2.685 秒**，主表为 **1.485 / 1.500 / 2.820 秒**。含缺失或 <2 cs delay 的文件分别为 5/98、14/133、14/150。三个子集有变帧间隔的文件分别为 37/98、44/133、17/150。

三个子集的 `编码帧数 / 归一化单轮时长` 中位数恰好均为 10；这是逐文件有效帧率的中位数，**不代表 GIF 天然是 10 FPS**。

[2022 年的跨播放器调查](https://www.biphelps.com/blog/The-Fastest-GIF-Does-Not-Exist)记录过 Chromium/Firefox 对 ≤10 ms delay 使用 100 ms 的行为，是上述策略的历史参考，不作为当前所有播放器行为的保证。

此外：

- 单轮时长不乘无限循环次数。循环元数据单独保留。
- GIF user-input 标志可能让播放等待交互。本样本没有命中；未来实现应显式处理或拒绝，不能当普通定时动画。
- 不将没有 GCE、0 delay 或 `.gif` 扩展名误认为充分的格式/动画证据。

## 已有公开研究能支持什么

### TGIF：较大规模但并非 IM 专项

[TGIF 发布页](http://raingo.github.io/TGIF-Release/)给出 102,068 个 GIF、4,143,450 总帧，平均 **40.62 帧、3.65 秒**。收集对象是 2015 年 5–6 月随机选取的 Tumblr 帖子，不是当前中文 IM 的发送样本。

[CVPR 2016 论文](https://arxiv.org/abs/1604.02748)正文另报 3.10 秒，与发布页 3.65 秒有差异，本研究没有足够依据解释它。引用 3.65 秒时限定为“发布页统计”，不悄悄统一两者。论文模型实验中的 10 FPS 是输入采样设置，不应冒充源 GIF 原始帧率。

它支持“短片段、几十帧是一个重要规模”的方向判断；均值无法给出 P95 或解码上限。

### ReactionGIF / GIFGIF：语用接近，但没有核实到技术分布

- [ReactionGIF](https://github.com/bshmueli/ReactionGIF)：30K Twitter 文本与 GIF reaction 配对。更接近“用动图表达回应”，但此次可获取的材料没有提供可核实的时长/原始帧数分位数；30K 配对也不是 30K 独立动画资产。
- [GIFGIF](https://lucas.maystre.ch/gifgif-data)：6,170 个 GIF 的情绪比较数据。页面提供 5.3 GiB 原始图档，但未公开所需的技术分位数。本次未下载整个图档测量。

这些可以成为后续语义评测数据源，不能用它们的名字给本次统计增加虚假的代表性。

### 平台规则：是约束，不是自然分布

- [GIPHY 官方最佳实践](https://support.giphy.com/hc/en-us/articles/360019914771-GIF-Creation-Best-Practices)的搜索索引摘要写明上传限 15 秒、建议不超过 6 秒。正文抓取为 403，因此这里只引用官方页面的**搜索摘要**，不声称全文核实。
- [LINE 动画贴纸规范](https://creator.line.me/en/guideline/animationsticker/)要求 APNG、5–20 帧、1–4 次循环且合计播放不超过 4 秒。这是特定产品的作者约束，既不是 GIF 格式上限，也不是网络表情的实测分布。
- [Telegram 官方 GIF 说明](https://core.telegram.org/api/gifs)指出聊天 GIF 使用无声 H.264/MPEG-4，上传原始 GIF 会被服务端转换。因此面向本项目的实现必须覆盖 **GIF 文件与 Telegram MP4 animation**，不能仅在图片 MIME allowlist 增加 `image/gif`。

## 对 LLM 输入的建议：有界起点，不是已验证最优方案

### 1. 按播放时间抽样，不按原始下标机械等距抽样

先按 GIF 的矩形、透明度、disposal 合成完整画面，再用有效 delay 建立单轮时间轴。相同的停留画面可以占 1 秒，也可以只有 20 ms；按下标等距会丢失这种关系。MP4 使用实际解码时间戳，不套 GIF 的 delay 修正规则。

单取中间帧会丢掉动作方向、先后关系、字幕变化和最后反转。均匀抽样也可能漏过极短的关键帧，所以不能声称它保证理解完整。

### 2. 最小可试的策略

令 `S` 为合并连续相同合成画面后的状态段数，`T` 为单轮时长（秒）。保持段的先后顺序和起止时间；不要把不相邻的同画面合并。

- `S = 1`：按静态图处理。
- `2 ≤ S ≤ 12`：保留全部状态段。
- `S > 12`：目标预算 `K = min(S, 12, max(4, ceil(2*T)))`。
- 预算 **包含首尾**：第一张选首段，最后一张选末段；其余目标时间为 `i*T/(K-1)`，其中 `i=1..K-2`，选覆盖该时间的段。
- 同一段被多个目标命中时只发一次，保持时间顺序；实际输入可少于 `K`。非相邻复现的画面不按全局 hash 去掉。
- 每张附实际时间区间/序号，并说明整段时长与循环信息；若用户问题依赖快闪字幕、动作过程或末尾反转，针对有关时间区间补帧，默认总预算暂定 **24 张**。

这只是成本受控的基线：短动画通常 4–8 个目标，约 6 秒起触及 12 张上限。长动画仍覆盖全时轴，但会更稀疏；不能截前几秒后当成完整理解。若格式/预算导致无法完整查看，应明确向模型标记限制。

12 与 24 是待测的工程参数，不是从帧数分布推导出的准确率保证。也不要为此一开始就增加另一套模型或复杂关键帧检测系统。

### 3. 独立约束解码成本与模型成本

只限制输出 12 张并不能防止解码炸弹；还应分别约束：下载字节数、宽高/单帧像素、累计解码像素或帧数、单轮时长、转换墙钟时间、输出总像素与字节、模型图片数量/Token。

例如 500×500×500 帧的 RGBA 若整段常驻内存，约占 477 MiB。应顺序解码、保留有界缓冲，不默认将整段展开成一张超高图或全部帧数组。

本项目现有图片边界见 [media-image.ts:10](../../../src/capabilities/media/media-image.ts#L10)：20 MiB 下载、40,000,000 解码像素、10 MiB 标准化输出。当前 [格式列表:14](../../../src/capabilities/media/media-image.ts#L14)不包含 GIF；[现有媒体流程](../../../agent-doc/telegram-agent-flow.md#用户图片模型分流)主要仍是静态图片与 Sticker 代表帧。

本次原始资产最大约 38.7 MiB，不能为了样本全覆盖就取消现有安全边界。实际预算应结合服务器资源与 Telegram 转码后载荷另定；本研究未修改 runtime、权限或配置。

### 4. 上线前真正需要验证的指标

收集经授权的实际会话动画，分别覆盖中文文字梗、重复动作、真人 reaction、多镜头、快闪字幕和末尾反转。对比中间 1 帧、下标均匀、时间均匀 8/12/24 帧，以及预算允许时的完整状态序列。

人工按完整动画标注内容、动作方向、关键文字和反转，不把“全帧模型回答”直接当真值。比较正确率/漏掉关键事件、延迟、图片 Token、失败率；重点检查长尾类别，不能只看平均准确率。成本不足时可先用小型分层集合筛选方案，再扩大样本。

当前没有做这项模型实验，也没有做 Telegram 实际上传前后时序对照。它们可能改变最合适的采样上限和 delay 策略，但不妨碍报告本次资产分布。

## 抽样、校验与复现

### 抽样设计与局限

1. 固定上述三个仓库的 commit，并记录对应 tree。
2. 在完整 Git tree 中选择 `.gif` 扩展名的 blob，排除 README 路径；每个仓库按 blob SHA 去重。
3. 用固定种子 `im-gif-20260927:` 与 blob SHA 拼接，按 SHA-256 排序取前 150 个，不按文件大小或时长挑选。
4. 从固定 commit 下载，核对长度与 Git blob SHA-1。下载上限为 64 MiB；本次没有因该上限剔除样本，也没有补抽替换失败文件。
5. 解析 GIF image descriptor、原始 delay、循环字段；用 Sharp metadata 交叉校验帧数、尺寸与每帧 delay。
6. 对所有 401 份多帧 GIF 使用 FFprobe 解码帧时序和 FFmpeg 合成 RGBA hash 验证；全部成功。去除 20 份全画面相同文件后分别计算主表。

这些是**便利选取的公开仓库、仓库内确定性散列抽样**：不是按平台、发送次数或活跃用户加权的概率样本。它们可能偏向作者喜好、旧素材与特定画风；不覆盖现成 MP4/APNG/WebP 资产。没有按逐张人工语义筛查“是否适合 IM”，也没有测量当前微信/QQ/Telegram 的真实发送流量。

跨库有 2 个重复 blob，三个仓库不是相互独立的人群样本。主表按库分开，不给“381 个独立 GIF 的总体分布”或全网置信区间。帧数分位数采用线性插值，因此 P95 可以是小数，实际文件帧数仍是整数。

### 交叉验证发现的坑

测试环境：Node.js 24.18.0、Sharp 0.35.3、FFmpeg/FFprobe 9.0.1 Windows Gyan essentials build。

- 5 个 `.gif` 实际为 JPEG；依据实际头部检查，保留失败记录，不静默替换样本。
- Sharp 对缺失 delay 返回 100 ms，解析器保留 `null`；比较时必须体现这种语义差异。
- 本机 FFprobe 解码帧对缺失/0 delay 使用 100 ms，但保留 1 cs 为 10 ms。所有原始帧的时序均按这个观察口径交叉核对；4 个文件与主表的 `<2 cs → 10 cs` 策略不同，未把差异误报成解析器故障。不能仅根据命令帮助中的默认参数推断实际输出。
- 25 个文件的 `format.duration` 不等于解码帧 duration 之和。例如 `b99303fccef6877ea63403b2efe3e3f6f92ea6bf` 的原始 delay 是 `[null,7,6,7,7]`，解码帧合计 0.37 秒，但容器报告 0.27 秒。**不能只信容器 duration。**
- 3 个文件尾部带 `XMP DataXMP` 扩展，FFprobe 报告比图像数多 1 个 packet，但实际解码帧数与 GIF parser/Sharp 一致。最终验证比较解码帧，不用 packet 数冒充帧数。
- RGBA hash 的用途是排除像素完全相同与统计重复，不是证明人类看得出动作，也未做多种解码器之间的逐像素一致性认证。

### 文件与命令

- [measure.mjs](measure.mjs)：固定输入来源、下载校验、GIF 结构解析、自检与统计。
- [measurements.json](measurements.json)：450 条记录、原始 per-frame delay、固定来源 URL 和多帧子集初始统计。
- [verify.mjs](verify.mjs)：独立解码、时序核对、相同画面过滤与动态子集统计。
- [verification.json](verification.json)：401 条解码结果与主表对应的 `changingImageSummary`、画面数统计。

从仓库根目录运行；需要已安装项目依赖、FFmpeg 和 FFprobe：

```sh
node docs/research/im-gif/measure.mjs --self-check
node docs/research/im-gif/measure.mjs
node docs/research/im-gif/verify.mjs
pnpm run check
pnpm run lint
```

下载缓存位于被 Git 忽略的 `test-tmp/gif-research/`，脚本从空缓存可按固定来源重取；资产未来可能不可下载，应保留实验环境的缓存以便离线复核。研究输出仅保存元数据，不将第三方 GIF 图像发布进仓库。未安装新依赖。

### 复核状态

初次独立复核要求补充“假动画”过滤、修正 packet/帧与 delay 口径，并明确抽样和 12 帧方案的适用边界。上述问题已按完整解码结果修订；最终独立复核重新计算各动态子集、主表分位数及阈值计数，结论为可交付，未发现阻断性问题。

实际验证：解析器自检通过；最终 401 份多帧 GIF 解码与时序核对全部通过；`pnpm run check`、`pnpm run lint`、`git diff --check` 通过。Lint/format 对被 Git 忽略的 1.6 MiB 仓库树缓存报告超过单文件大小限制的警告，不影响研究脚本检查。没有修改 runtime，没有运行完整 runtime 行为测试，也没有提交 Git。

FFprobe 时序断言对应上述特定版本的实测行为；升级解码器后应重跑，不应靠删除断言掩盖语义变化。
