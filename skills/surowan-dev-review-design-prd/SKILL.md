# 审阅与完善 PRD

## 这个 skill 的分工

`doc/design/` 是**用户逐条审核过的 PRD**，代表已确认的产品意图。所以：

- 用户是作者和裁决者，agent 是审阅者。agent 的工作是暴露问题、给出选项，不是补全内容。
- 审阅重点是 PRD 文本本身：内部是否自洽、决定是否明确、有没有漏掉影响面。源码可以拿来参考，用来确认现状、发现影响面，但写进 PRD 的必须翻译成宏观的产品设计。
- PRD 不写实施细节：表名、列名、字段取值、函数/类/模块名、日志事件名、错误码、源码路径都不出现。要指代某样东西时，用产品概念（Invocation、Bucket、Chat、Topic 这类领域术语）和它对用户可见的表现来说。用户自己写进去的不受此限，不要删改。
- 例外：允许用通俗的语言讲解、确认内部实现，例如「每个 Chat 只保存当前连续没抽中的次数，抽中即清零」。讲的是机制和后果，不是代码怎么写。
- 实施细节归 `agent-doc/design/`（AI 直出的实施文档）。需要记录时，向用户提出在那边另起一篇，不要塞进 PRD。本 skill 不碰 `agent-doc/devlogs/`。

## 新建：从模板开始

用户要新起一篇 PRD 时，文件名用 `YYYYMMDD-<kebab-case 名字>.md`，正文严格从这份模板开始，标题一字不改：

```markdown
# 功能名称

## 为什么要做？
目前有什么问题？

## 希望实现什么？
用户最终能做什么？

## 打算怎么做？
我已经确定了哪些设计？

## 还有什么没想清楚？
哪些地方需要继续思考？
```

填写规则：

- 只写用户表达过的内容。用户没说的，把那节的引导问句留着，或写一句「待定」，不要替用户构想方案。
- 用户口头描述里的**定义性澄清**要原样搬进正文，包括他用的比喻和反例（例如「这个路径本身是一个 key，不会被当成普通文件路径处理」）。这类句子往往就是审阅时要反复引用的约束。
- 用户明确否决的方向**不要**写进 PRD。否决掉的东西留在对话里，PRD 只记录确定的和待定的。

## 审阅：先读全文，再找问题

每轮审阅都重新读一遍当前文件。用户会边想边改，凭上一轮的记忆审阅会重复提问，也会对着已经删掉的段落说话。

按这个顺序过一遍，只挑**真正影响落地**的问题：

1. **边界**：明确说了不做什么吗？把范围外的场景写出来，比只写做什么更能挡住后续膨胀。
2. **概念歧义**：同一个词在两处含义不同，或同一件事用了两个名字。用户的定义句优先，遇到冲突按定义句重新推导。
3. **自相矛盾**：某节承诺 A，另一节的机制会导致非 A。
4. **谁来负责**：每个安全或权限相关的机制，说清是哪一层执行（Harness、宿主、外部组件）。读的人要能判断「这条靠什么生效」。
5. **失败模式**：默认值、省略参数、超时、外部组件不按预期返回时会发生什么。
6. **生命周期**：数据在什么时候失效、过期、被清理；谁可以主动删除。
7. **部署形态**：裸机、容器、远端服务下，同一个设计是否成立；不成立的地方是否写明了限制。
8. **前置工作与阻塞**：文档依赖的现有能力是否已经具备。缺前置的工作单独列，不要和「还没想清楚」混在一起。
9. **已经想清楚却还留在待定区的内容**：正文里已经写定的判断，应该从「还有什么没想清楚」挪到正文。

一次审阅给 3～6 条，按影响排序。宁可少给几条扎实的，也不要给一长串边缘问题淹没重点。

## 意见怎么写

统一写进「还有什么没想清楚」这一节的末尾——也就是它后面下一个二级标题之前；如果文档有「边界」之类的结尾章节，意见在它上面，不要写到文末。使用三级小节：

```markdown
### 审阅意见

1. **<一句话结论>**：问题在哪、会导致什么。
   - 选项：A（代价）；B（代价）。
   - 需要决定：<具体要用户回答的那一个问题>。
```

每条都要落到一个**用户能直接回答的问题**上。「这里需要更明确」不是意见；「这个 key 的授权跟不跟随 GC 失效？跟随的话跨 Invocation 的旧引用会失效，不跟随则存储会一直增长」才是。

给出的选项要带上代价，不要只列优点。如果只有一个方案站得住，就说清为什么其它方案不行，再请用户确认，而不是假装中立。

## 协商时怎么说话

这些是从实际审阅中总结出来、真正起作用的做法：

- **结论先行**。第一句回答「能不能做、卡在哪」，然后再列依据。用户在意的是决策，不是过程。
- **区分事实与偏好**。事实性的判断要给得出处；如果是推断，标明是推断。用户会拿这个来反驳或采纳，含糊的断言只会拖慢讨论。
- **用户澄清概念后，先接受定义再重新推导**，不要解释自己原来的理解。整段基于旧理解的推论直接作废，不用逐条辩护。
- **用户说「这个不用管」时就停**。比如「管理员接了高危 MCP 是管理员的责任」，就不要在 PRD 里加防护机制，也不要再把它写进待定区换个说法重提。
- **一次只推进一步**。用户否定一个方案后，基于他的否定给出下一个方案，而不是重新论证被否掉的那个。
- **不要把自己的建议写成用户的决定**。待定区里的每一条都属于用户，措辞用「需要决定」「目前倾向」，不用「我们决定」。
- **用用户的原话锚定**。他给出的比喻、命名、反例是最稳的约束，引用它们比转述成术语更不容易走样。

## 用户审阅之后

用户会逐条给出结论。收到后：

- 只处理他明确表态的那几条：把结论写成正文对应章节里的句子，然后删掉待定区里的这一条。
- 没有表态的条目原样留着，不要顺手改写或合并。
- 「### 审阅意见」小节清空后整节删除。
- 正文措辞跟随 PRD 现有风格：中文、短句、结论在前，不引入新的术语层级。
- 改完直接说明改了哪几节、哪几条仍待定，不要提交 git，除非用户要求。
